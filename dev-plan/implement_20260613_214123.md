## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발생한 이슈는 해당 Phase에서 수정하고 기록한다.
- 체크박스 상태를 실제 진행 상태와 맞게 업데이트한다.
- 문서에 없는 범위 확장은 하지 않는다.
- 버전은 `manifest.json`의 현재 값 `5.10.3`을 유지한다. 승인 없는 `5.10.4` 승격 금지.
- Registry 도입 후에도 기존 17개 모드의 visible output 계약은 후퇴시키지 않는다.
- **Registry 역할은 단계별로 다르다(혼동 금지):** B-lite에서는 기존 정본과 byte/semantic equal이어야 하는 **authoritative mirror(검증 미러)** 이고, validator는 여전히 자기 dict를 읽는다. B-full에서만 validator가 실제로 Registry를 읽는 **executable source of truth**가 된다. **B-lite 단계에서 validator가 Registry를 읽게 만들면 안 된다.**
- 기존 문서의 역사적 설명은 보존하되, “현행 기준”으로 읽히는 표는 Registry와 일치해야 한다.
- 검증 OK만으로 완료하지 않는다. governance, examples validate, quality, completion, package byte-match까지 최종 확인한다.


## 진행 단계 분할 (리뷰 반영 — B-lite 먼저)

**"validator 2,000줄 재배선"은 오해 프레임이다(전문가 분석 실측).** `validate_output.py`는 2,400줄+이지만 **모드별 데이터는 `MODE_TEMPLATE_CONTRACTS` 블록 단 104줄(17개 항목)** 뿐이고, 나머지는 모드와 무관한 교차 게이트(no-JS·body-icon·section-surface·header·테마·버전/패키지 정합 등 ~50종)다. registry는 그 교차 게이트를 건드리지도 줄이지도 않는다. 따라서 B-full의 실제 작업량은 **데이터 104줄 추출 + 로더 ~30줄 + deep-equal 테스트 1개 ≈ 순변경 150줄 이하**이며, 소비 함수 로직은 불변·데이터 소스만 교체한다.

| 단계 | 포함 Phase | Registry 역할 | 성격 | 가치 / 위험 |
|---|---|---|---|---|
| **B-lite** | Phase 0·1·2·4 | **authoritative mirror** (기존 정본과 byte/semantic equal, validator는 안 읽음) | Registry를 **검증 미러(sync gate)** 로만 도입. validator 동작은 불변 | 매 편집 드리프트 방지 대부분 확보 / **validator 회귀 위험 0** |
| **B-full** | Phase 3·5·6·7 | **executable source of truth** (validator가 실제로 Registry를 읽음) | `MODE_TEMPLATE_CONTRACTS`(104줄 데이터)를 registry 생성으로 교체 + runbook. 소비 로직·교차 게이트 불변 | 신규 모드 추가 비용 축소 / 위험 낮음(deep-equal로 동일성 증명) |

**기본 진행 = B-lite 완료까지.** B-full(Phase 3 이후)은 (a) 실제 18번째 모드 필요 또는 (b) 사용자 명시 지시가 있을 때만 착수한다. B-lite 동안 validator는 **읽지 않고 비교만** 한다(byte/semantic mirror).

> **압축 ≠ 축소(중요).** registry는 모드 정의를 **단일 출처화**할 뿐 검증기를 작게 만들지 않는다(데이터 104줄 빼도 로더 ~30줄이 들어와 순감 -70줄 수준). 검증기가 큰 이유는 모드 데이터가 아니라 ~50개 교차 게이트이며, 그 통합은 이 작업 범위 밖이다.

### Registry 고정 schema

> **고정 결정:** Registry 정본은 `skills/adaptive-html-final/modes/NN-<mode>.json` 17개 파일이다. `manifest.json`, `SKILL.md`, `AGENTS.md`, references, validator, examples는 Registry와 불일치하면 실패해야 한다. 단일 `mode-registry.json`은 채택하지 않는다.

```json
{
  "id": "landing_brief_html",
  "priority": 16,
  "label": "Landing Brief",
  "layout_class": "layout-landing",
  "layout_file": "landing-brief.html",
  "recipe": "recipes/landing-brief.prompt.md",
  "triggers": ["랜딩", "소개 페이지", "요약 페이지"],
  "required_blocks": ["hero", "value_props", "how_it_works", "faq", "cta"],
  "layout_placeholders": ["{{HERO}}", "{{VALUE_PROPS}}", "{{HOW_IT_WORKS}}", "{{FAQ}}", "{{CTA}}"],
  "primary_vt": "hero-map",
  "vt_candidates": ["hero-map", "card-grid", "feature-flag", "soft-workflow-map"],
  "vt_markers": ["\\bhm-grid\\b"],
  "wg_candidates": ["wg-02", "wg-05", "wg-08", "wg-09", "wg-16"],
  "wg_markers": ["wg-02-", "wg-05-", "wg-08-", "wg-09-", "wg-16-"],
  "toc_contract": {
    "rule": "structural_h2_gte_4",
    "required_class": null,
    "forbid_plain_text_toc": true
  },
  "examples": [
    {
      "file": "examples/12_landing_pagercalm_brief.html",
      "purpose": "reference"
    }
  ],
  "quality_contract": {
    "requires_body_icon": true,
    "requires_header_lens": true,
    "requires_render_audit": true,
    "mode_depth_min_avg": 400
  },
  "custom_contracts": []

```

> **스키마 주의 (리뷰 반영 — 실측 확정):**
> - **`recipe` 파일명은 불규칙**하다(`<mode_id>.prompt.md` 아님). 실측: `seo`→`recipes/seo.prompt.md`·`platform_blog`→`recipes/platform.prompt.md`처럼 짧은 것도 있고, `landing_brief_html`→`recipes/landing-brief.prompt.md`·`github_analysis`→`recipes/github-analysis.prompt.md`처럼 다른 것도 있다. **17개 전부 실제 `recipes/*.prompt.md` 파일명을 verbatim 기입**한다(P0-1).
> - **`vt_markers`는 vt 이름이 아니라 `mode_template_contract_gate`가 실제 매칭하는 내부 마커 정규식 토큰**이다(P0-2). `MODE_TEMPLATE_CONTRACTS` 실측: beginner=`\bconcept-ring\b`, expert=`\brm-grid\b`, article=`\bdt-q\b`·`\bdt-options\b`, landing/github/manual/github_feature=`\bhm-grid\b` 등. `["vt-hero-map"]` 같은 vt-name을 넣으면 deep-equal이 즉시 실패한다.
> - **`layout_placeholders`는 실제 placeholder명(대문자 `{{...}}`)** 이다(P0-3). `assets/layouts/landing-brief.html` 실측: `{{HERO}}`·`{{VALUE_PROPS}}`·`{{HOW_IT_WORKS}}`·`{{FAQ}}`·`{{CTA}}`. lower-case 의미 키는 `required_blocks`(semantic)로 분리해 두 필드를 혼동하지 않는다.
> - `toc_contract.rule`은 현행 `analysis_toc_map_required_gate`(`is_required = is_analysis or h2_count>=4`)를 그대로 표현한다. 분석 모드(github/github_feature/youtube/manual)=`"always"`, 그 외=`"structural_h2_gte_4"`. **정적 `requires_toc_map` 불리언·`min_links`는 쓰지 않는다**(P1-1).
> - **`toc_contract.required_class`(P1-5):** 분석 모드는 모드별 필수 toc class가 있다 — github=`github-question-toc`, github_feature=`feature-toc`, youtube=`youtube-question-toc`, manual=`manual-reader-toc`. 이 값을 Registry에 담거나(권장) Python mapping을 유지함을 명시한다. 비분석 모드는 `null`.
> - `quality_contract`에는 **현행 게이트에서 역산한 임계만** 넣는다. `mode_depth_min_avg`(현행 400)는 실재, `min_sections`/`min_pattern_kinds` 등은 대응 게이트가 있을 때만 추가한다(없으면 발명 금지, P2-1).
> - **`examples.file`은 priority와 무관**하다(P2-1). landing은 priority 16이지만 예제 파일은 `examples/12_landing_pagercalm_brief.html`다. 와일드카드가 아니라 **실제 참조 파일명**으로 고정한다.

### 문서 동기화 방식 고정

문서 전체를 파싱하지 않고, Registry에서 생성되거나 검증되는 표 구간만 marker block으로 한정한다. 예:

```md
<!-- AHF:MODE_TABLE_START -->
... Registry 기반 모드 표 ...
<!-- AHF:MODE_TABLE_END -->
```

- `SKILL.md`, `AGENTS.md`, `references/mode-selection.md`, `references/visual-html-system.md`, `references/widget-system.md`의 현행 결정표는 marker block 내부만 sync 대상이다.
- 역사 설명, CHANGELOG성 문장, 배경 설명은 sync 대상에서 제외한다.
- marker block 밖의 자유 문구를 이유로 실패시키지 않는다. 단, “현행/현재” 표면이 Registry와 충돌하면 별도 textual drift gate로 실패시킨다.
- **비교 방식 = 의미 비교(P2-2).** marker block을 **표로 파싱해 셀 값(모드 id·layout·priority·primary vt·wg 후보)을 Registry와 대조**한다. byte/문자열 일치를 요구하지 않는다(열 정렬·공백·줄바꿈 등 포맷 차이로 전부 실패하는 취약성 회피). 표 렌더 포맷은 사람이 유지하고, 검증기는 값만 본다.
- **마커 삽입은 1회성 별도 태스크.** 기존 표를 `<!-- AHF:MODE_TABLE_START -->`/`<!-- AHF:MODE_TABLE_END -->`로 감싸는 작업은 Phase 4에서 문서별로 명시 수행하며, 삽입 시 표 내용은 변경하지 않는다(정합 검증과 분리).
