## 개발 목적

동일 문제 0을 목표로 한다. 반복된 문제의 실제 원인을 다음과 같이 재정의한다.

| 잘못된 원인 가설 | 폐기 사유 | 이번 계획의 정정 |
|---|---|---|
| LLM이 HTML을 쓰면 안 된다 | HTML은 결국 LLM이 작성해야 하므로 넌센스 | LLM이 HTML을 쓰되 공식 템플릿 구조를 실제로 읽고 유지한다 |
| 검증기 몇 개를 더 추가하면 된다 | 클래스/마커 흉내로 계속 우회 가능 | 검증 전 **생성 절차 자체**를 공식 템플릿 기반으로 고정한다 |
| 17개를 한 번에 만들고 마지막에 검증하면 된다 | 후반부가 앞선 산출물 패턴을 복사함 | 1개 모드 작성→캡쳐→수정→승인 후 다음 모드 진행 |
| validate/completion OK면 품질 OK다 | 현재 게이트는 최소 구조 확인이며 전문 품질 보증이 아님 | 검증 OK + 공식 템플릿 실제 사용 증거 + 브라우저/수동 시각 QA가 필요 |
| Registry가 있으니 생성 품질도 보장된다 | Registry는 결정표 데이터 정합이지 HTML 작성 품질 보장이 아님 | Registry는 라우팅 정본으로만 쓰고, 작성 품질은 별도 build protocol로 잠근다 |

## 리뷰 반영 요약 (2026-06-14 재정리)

이전 초안(0/148) 검토에서 확인된 4가지 + 사용자 추가 1가지를 반영했다.

1. **중복 제거** — Phase 2 "반복 이슈 체크리스트" 11개 중 7개는 직전 C1~C6 작업으로 **이미 게이트 강제**됨(§중복 게이트). 새 게이트로 재구현하지 않고 참조만 한다.
2. **코어 해시 모순 해소** — M1~M9를 자산 분류(코어-해시 / 조건부 / 비-CSS / output-only)로 나눠, 코어 해시를 건드리는 항목은 **선행 결정 게이트 통과 후에만** 착수한다(§선행 결정 게이트, §Phase 3.5).
3. **output 독립 원칙 정합** — output 산출물은 독립 테스트 결과물이며 무종속이다. Phase 4 재생성물은 그냥 결과물이고, Phase 3.5의 M계열 스킬 반영은 "명시적 승격일 때만 허용" 규칙에 따른 의도적 승격임을 명시한다.
4. **자동 검출 한계 인정** — "LLM이 공식 템플릿을 실제로 읽었는지"는 정적 게이트로 검출 불가. Z1 자동검출 야망을 내려놓고 **`build-evidence.json`(읽은 파일 경로+sha256) 존재 게이트 + 마이크로 레이아웃 감사**를 실효 수단으로 삼는다.
5. **(사용자 추가) 단색 rail 반복(M9)** — 반복 카드의 좌측 rail이 모두 `var(--accent)` 한 색이라 단조롭다. 공식 토큰 `--vt-red/--vt-blue/--vt-green/--vt-gold` 중 3종 이상을 의미 있게 순환해야 한다.
6. **(사용자 추가) body-level footer 좌측 붙음(M10)** — `{{FOOTER}}` 슬롯이 `<main>` 뒤에 렌더되어 `.source-note`가 본문 폭이 아니라 viewport 왼쪽 기준으로 붙는다. `body>footer.source-note`를 본문 폭 중앙 정렬로 고정한다.
