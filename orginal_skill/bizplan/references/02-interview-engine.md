# 02 — Gate 1 실행 프로토콜: AI 심층 인터뷰 엔진

> SKILL.md가 **Gate 1 진입 시 Read**하는 상세 실행 프로토콜.
> 대상: PRD §8 전체 (심층 인터뷰 엔진).
> 목표: 사용자가 당연시하거나 말하지 않은 현장 경험·경쟁력을 끌어내고, 모호어를 수치·사례로 굳혀 사업 코어의 입력을 만든다.
> 산출물 위치: `bizplan-<slug>/02-interview/`

## 7대 절대 규칙 (이 단계에서의 의미)

- **인터뷰 우선**: 첫 설명만으로 사업을 단정하지 않는다. 이 게이트를 끝내기 전에 리서치·작성으로 넘어가지 않는다.
- **임의 창작 금지**: 사용자가 말하지 않은 고객·매출·계약·성능을 채우지 않는다. 없으면 `[확인 필요]`.
- **사실/추정/가정/목표 분리**: 답변을 기록할 때 `[사실][추정][가정][목표][확인 필요]` 태그를 붙인다. 특히 "줄어든다/된다"는 미래 진술은 실측이면 `[사실]`, 예상이면 `[목표]`.
- **출처는 발화자**: 인터뷰 내용의 "출처"는 사용자다. `[출처: 인터뷰 transcript L<줄>]`로 추적.

## 1. 적응형 인터뷰 원칙 (PRD §8.2)

**고정 설문지를 한꺼번에 보여주지 않는다.** 답변에 따라 다음 질문을 결정한다.

```text
질문 → 답변 해석 → 모호한 부분 탐지 → 반례/구체적 사례 질문 → 근거 확인 → 다음 질문 선택
```

운영 규칙:
- **한 번에 최대 3문항.** AskUserQuestion 한 묶음 또는 대화 한 턴에 3개를 넘기지 않는다.
- 답변이 추상적이면 다음 단계로 넘어가지 말고 **그 자리에서 구체화 후속질문**(§3 모호어 표)을 던진다.
- 사용자가 "모른다/아직 없다"고 하면 캐묻지 말고 `[확인 필요]`로 분류하고 다음으로 간다(인터뷰 피로 방지).
- 답변 간 **모순**이 보이면 즉시 확인 질문을 넣고 `contradictions.md`에 적는다.
- 단계는 순서대로가 기본이나, 답변이 다른 단계로 자연스럽게 흐르면 따라간다(적응형).

## 2. 10단계 질문 은행 (PRD §8.3 — 50개 질문 전량) + 단계별 목표

각 단계 머리에 **"무엇을 캐내야 하는가"**(목표)를 적었다. 질문은 그대로 던지지 말고 사용자 맥락에 맞게 변형한다.

### 1단계: 창업 동기와 문제 발견
**목표** — 창업자가 이 문제를 *직접* 발견한 계기, 현장에서 반복 관찰한 장면. 책상에서 만든 아이디어인지, 현장 통증인지 가른다.
- 이 사업을 처음 생각하게 된 계기는 무엇인가?
- 문제를 직접 경험한 적이 있는가?
- 가장 기억나는 구체적인 장면은 무엇인가?
- 이 문제가 해결되지 않으면 누가 어떤 손실을 보는가?
- 문제는 얼마나 자주 발생하는가?

### 2단계: 고객과 사용자
**목표** — 사용자/구매자/지불자 분리. "막연한 모두"를 첫 고객 1명으로 좁힌다.
- 실제 제품을 사용하는 사람은 누구인가?
- 구매 결정을 내리는 사람은 누구인가?
- 비용을 지불하는 사람과 사용하는 사람이 같은가?
- 가장 먼저 구매할 가능성이 높은 고객은 누구인가?
- 고객이 현재 사용하는 대안은 무엇인가?

### 3단계: 현재 해결 방식
**목표** — 기존 대안의 구체적 불편 순간과 전환 장벽. "왜 지금까지 안 바꿨나"를 캔다.
- 고객은 지금 어떻게 문제를 해결하고 있는가?
- 엑셀, 외주, 수작업, 기존 제품 중 무엇을 사용하는가?
- 기존 방식에서 가장 불편한 순간은 언제인가?
- 고객이 기존 방식을 쉽게 버리지 못하는 이유는 무엇인가?

### 4단계: 제품과 기술
**목표** — 핵심 기능 vs 부가 기능 분리, 가장 어려운 기술 난제, 모방 난이도(해자).
- 제품이 작동하는 과정을 처음부터 끝까지 설명할 수 있는가?
- 반드시 필요한 핵심 기능은 무엇인가?
- 없어도 되는 기능은 무엇인가?
- 가장 어려운 기술적 문제는 무엇인가?
- 경쟁사가 쉽게 따라 할 수 없는 요소는 무엇인가?

### 5단계: 구현 가능성
**목표** — 현재 개발 단계(아이디어/설계/프로토타입/PoC/출시), 필요한 자원, 검증 지표. 실현가능성 배점의 근거.
- 현재 구현된 것은 어디까지인가?
- 프로토타입, 코드, 설계, 데이터가 있는가?
- 개발에 필요한 인력과 장비는 무엇인가?
- 외부 기관이나 파트너가 필요한가?
- 성공 여부를 어떤 수치로 검증할 것인가?

### 6단계: 시장과 사업모델
**목표** — 지불 의사 대상, 가격, 과금 구조, 고객 획득 경로. 첫 10명의 출처.
- 고객은 무엇에 돈을 내는가?
- 예상 가격은 얼마인가?
- 일회성 판매인가, 구독인가, 구축형인가?
- 고객 한 명을 확보하는 데 어떤 과정이 필요한가?
- 첫 10명의 고객은 어디에서 만날 수 있는가?

### 7단계: 경쟁과 대체재
**목표** — 인지하는 경쟁사, 선택 이유, 가격 경쟁 대응, "아무것도 안 함"이라는 숨은 경쟁자.
- 유사한 제품이나 회사를 알고 있는가?
- 고객은 왜 기존 제품 대신 이 제품을 선택해야 하는가?
- 경쟁사가 가격을 낮추면 어떻게 대응할 것인가?
- 고객이 아무것도 하지 않는 선택도 경쟁 아닌가?

### 8단계: 팀과 실행 역량
**목표** — founder-market-fit, 내부 수행 vs 외주, 부족 역량, 협력 네트워크.
- 대표자가 이 사업을 수행하기 적합한 이유는 무엇인가?
- 팀 내부에서 직접 수행할 업무는 무엇인가?
- 외주로 맡길 업무는 무엇인가?
- 현재 부족한 역량은 무엇인가?
- 협력 가능한 고객, 기관, 전문가가 있는가?

### 9단계: 성과와 증거
**목표** — 실재하는 트랙션과 증빙. 여기서 나온 것만 `confirmed-facts.md`로 간다. 없으면 절대 만들지 않는다.
- 매출, 사용자, 상담, 계약, 테스트 결과가 있는가?
- 고객 인터뷰 기록이 있는가?
- MOU, LOI, NDA, PoC가 있는가?
- 특허, 저작권, 상표, 인증이 있는가?
- 제품 성능을 입증할 데이터가 있는가?

### 10단계: 비전과 파급효과
**목표** — 성공 시 고객/산업/사회 변화. 정책 부합·파급효과 배점의 재료.
- 이 사업이 성공하면 고객의 하루가 어떻게 달라지는가?
- 산업의 구조는 어떻게 달라지는가?
- 고용, 생산성, 비용, 안전에 어떤 변화가 생기는가?
- 3년 후 이 사업은 어떤 모습이어야 하는가?

## 3. 모호어 9종 — 탐지 즉시 구체화 후속질문 (PRD §8.4)

아래 표현이 답변에 나오면 **다음 단계로 넘어가지 말고** 그 자리에서 구체화를 요청한다. 핵심은 "수치인가 사례인가, 실측인가 목표인가"를 가르는 것.

| 모호어 | 구체화 후속질문(예시) |
|---|---|
| 많은 고객 | "몇 명/몇 개 기업입니까? 그 숫자의 근거는 무엇입니까? 지금 접촉 중인 곳이 있습니까?" |
| 시장성이 크다 | "어느 시장입니까? 규모(금액·수)는요? 그 수치의 출처는 어디입니까?" |
| 효율적이다 | "무엇 대비 효율적입니까? 시간/비용/인원 중 어느 지표가 얼마나 좋아집니까?" |
| 혁신적이다 | "기존 방식과 구체적으로 무엇이 다릅니까? 그 차이를 한 문장으로 말하면?" |
| 사용하기 쉽다 | "누가, 몇 번의 단계로, 얼마 만에 첫 결과를 얻습니까? 사용성 테스트 결과가 있습니까?" |
| 비용이 절감된다 | "현재 비용은 얼마이고 도입 후 얼마가 됩니까? 그 수치는 실측입니까 목표입니까?" |
| 기존 제품보다 좋다 | "어떤 제품과 비교한 것입니까? 어떤 항목에서 얼마나 좋습니까? 비교 데이터가 있습니까?" |
| AI를 활용한다 | "구체적으로 어떤 모델/기법을 어느 단계에 씁니까? 직접 학습합니까, 외부 API를 호출합니까?" |
| 글로벌 진출이 가능하다 | "어느 국가/시장입니까? 진입 근거(수요·규제·파트너)는요? 시점은 언제입니까?" |

PRD §8.4 예시(그대로 적용):

```text
사용자: 업무 시간이 크게 줄어듭니다.
AI: 현재 한 건을 처리하는 데 몇 분 또는 몇 시간이 걸립니까?
    제품 도입 후에는 어느 정도로 줄어들 것으로 예상합니까?
    그 수치는 실제 테스트 결과입니까, 목표입니까?
```

> 마지막 질문("실측이냐 목표냐")은 **모든 수치형 답변에 반드시** 던진다. 답이 실측이면 `[사실]`+증빙 확인, 목표면 `[목표]`로 태깅된다. 이 한 질문이 7대 규칙 #2를 작동시킨다.

## 4. 인터뷰 진행 방법과 transcript 기록

- 진행 채널: **항상 `AskUserQuestion` 도구**(SKILL.md "🗣️ 사용자 상호작용 규칙" — ABSOLUTE). 평문으로 질문을 나열하지 않는다. 동기·경험담 같은 서술형 질문도 대표 보기 2~4개(+자동 "Other")를 제시하고 사용자가 "Other"에 자유 서술하거나 보기를 골라 답하게 한다 — 보기는 답을 떠올리게 하는 단서다. (예외: 사용자가 "직접 길게 서술하겠다"고 자청한 경우만 그 답변을 대화로 받음.)
- **모든 문답을 `02-interview/interview-transcript.md`에 즉시 기록**한다. 줄 번호가 출처 참조의 단위가 된다.

transcript 기록 형식:

```markdown
# 인터뷰 기록 — <프로젝트명>

## 세션 1 (YYYY-MM-DD)

### [단계 1] 창업 동기
**Q1.** 이 사업을 처음 생각하게 된 계기는?
**A1.** (사용자 답변 원문) → 태그: [사실]
  - 모호어 탐지: "많은" → 후속 Q1a
**Q1a.** 몇 곳입니까?
**A1a.** (답변) → 태그: [추정]

### [단계 2] 고객
...
```

- 인터뷰 도중 과제명 단서가 나오면 별도로 `03-idea-and-title/title-candidates.md`(→ `references/03-title-design.md` 참조)에 가설로 적는다.
- 키워드 확장(PRD §7.3 12영역: 고객/사용자/문제/제품/기술/산업/시장/정책/경쟁/사업모델/성과/위험)은 `02-interview/keyword-map.yaml`에 채운다.

## 5. 인터뷰 완료 조건 13항목 (PRD §8.5)

다음 13항목이 **구체화되었거나 `[확인 필요]`로 명시 분류**되면 인터뷰를 종료한다.

1. 핵심 고객
2. 구매자와 사용자(분리)
3. 문제의 빈도와 심각도
4. 현재 대안
5. 해결책의 작동 방식
6. 제품의 핵심 기능
7. 기술적 난제
8. 사업모델
9. 경쟁 차별성
10. 현재 성과(트랙션)
11. 팀 역량
12. 필요한 자금
13. 목표 성과

진행 점검표(인터뷰 중 수시 확인):

```markdown
| # | 항목 | 상태(구체화/[확인 필요]) | transcript 줄 |
|---|---|---|---|
| 1 | 핵심 고객 | 구체화 | L12 |
| 2 | 구매자/사용자 | [확인 필요] | L20 |
...
```

## 6. 종료 시 작성하는 7개 산출물 (PRD §8.5)

`02-interview/`에 아래 7개를 작성한다. 모두 transcript를 출처로 추적 가능해야 한다.

### 6.1 `interview-transcript.md`
원문 문답 전체 (§4 형식). 다른 모든 산출물의 출처.

### 6.2 `interview-summary.md`
```markdown
# 인터뷰 요약
## 13항목 요약 (한 항목 1~2문장 + 태그 + 출처)
- 핵심 고객: … [사실][출처: L12]
- 문제 빈도/심각도: … [추정][출처: L30]
...
## 한 줄 사업 정의(잠정)
```

### 6.3 `founder-insight.md`
```markdown
# 창업자 인사이트 (말하지 않았던 강점)
- 현장에서만 아는 업무 흐름:
- 보유 네트워크/고객 접근력:
- 직접 구현해본 경험:
- 실패했던 시도와 학습:
- 대표/팀의 고유 역량:
```
PRD §8.1의 "당연하다고 여겨 말하지 않은 것"을 모아둔 곳. 차별성·founder-market-fit 근거의 원천.

### 6.4 `confirmed-facts.md`
```markdown
# 확인된 사실 ([사실]만)
| 사실 | 증빙 형태 | 검증 가능성 | 출처 |
|---|---|---|---|
| 파일럿 3개사 진행 | 계약서 | 사용자 보유 | L80 |
```
증빙이 있는 것만. 증빙이 없으면 여기 넣지 않는다(→ assumptions 또는 follow-up).

### 6.5 `assumptions.md`
```markdown
# 가정 ([가정]·[추정])
| 가정 | 근거(약함/없음) | 검증 방법 | Gate 2에서 조사할 항목 |
|---|---|---|---|
```
리서치(Gate 2)에서 검증해야 할 가설의 출발점.

### 6.6 `contradictions.md`
```markdown
# 모순·불일치
| 항목 | 진술 A (줄) | 진술 B (줄) | 확인 결과 |
|---|---|---|---|
```
