# 03 — 과제명 설계 엔진 실행 프로토콜

> SKILL.md가 **Gate 1(인터뷰) 단계에서 함께 Read**하는 상세 실행 프로토콜.
> 대상: PRD §9 (과제명 설계 엔진).
> 목표: 사업과 기술이 모두 드러나는 과제명을 설계한다. 인터뷰 초기에 가설을 잡고, 리서치·인터뷰가 끝난 뒤 최종 재제안한다.
> 산출물 위치: `bizplan-<slug>/03-idea-and-title/title-candidates.md`

## 7대 절대 규칙 (이 단계에서의 의미)

- **임의 창작 금지**: 과제명에 검증되지 않은 수치·성능·"세계 최초/유일" 같은 표현을 넣지 않는다. 인터뷰·리서치로 확인된 것만.
- **인터뷰 우선**: 사용자가 가진 제목을 최초 가설로 존중하고 보존한다. AI가 멋대로 갈아엎지 않는다.
- **사실/목표 분리**: 제목에 담긴 주장이 [사실]인지 [목표]인지 본문에서 일관되게 받쳐줘야 한다.

---

## 1. 인터뷰 초기 — 과제명 가설 질문 (PRD §9.1)

인터뷰 **1단계(동기) 직후** 또는 아이디어 접수 시점에 한 번 묻는다.

```text
현재 생각하고 있는 과제명이나 제품명이 있습니까?
완성된 제목이 아니어도 핵심 단어만 알려주십시오.
```

처리:
- 사용자가 제시한 제목/단어를 **최초 가설(H0)**로 `title-candidates.md` 상단에 그대로 저장한다(원문 보존).
- 제목이 없다고 하면 강요하지 않는다. 인터뷰에서 나온 핵심 키워드로 임시 가설을 적고 `[확인 필요]` 표시.
- **여기서 제목을 확정하지 않는다.** 리서치·인터뷰가 끝난 뒤 최종 재제안한다(§4).

---

## 2. 과제명 구성요소 5종 — 최소 3개 포함 규칙 (PRD §9.2)

모든 후보 제목은 아래 5요소 중 **최소 3개**를 포함해야 한다. 사업과 기술이 한 제목 안에서 동시에 읽혀야 한다.

| # | 구성요소 | 예시 표현 |
|---|---|---|
| 1 | 대상 고객 또는 산업 | "중소 제조업체", "1인 자영업자", "물류 현장" |
| 2 | 해결하려는 문제 | "재고 과잉", "민원 응대 지연", "수기 검수 오류" |
| 3 | 핵심 기술 또는 작동 방식 | "온디바이스 비전 AI", "RAG 기반 검색", "센서 융합" |
| 4 | 개발하려는 제품 또는 서비스 | "관제 플랫폼", "검수 솔루션", "SaaS" |
| 5 | 사업화 또는 실증 범위 | "사업화", "실증", "상용화", "구축" |

점검: 후보를 만든 뒤 5요소 중 어떤 것을 포함했는지 표기하고 3개 미만이면 보강한다.

---

## 3. 3개 제목 공식 (PRD §9.2) — 실제 예시 포함

문서 유형(SKILL 발동 3번)에 따라 주력 공식이 달라진다. R&D는 기술개발형, 창업/투자는 사업화형, 공공·기관은 공공형이 기본축.

### 3.1 기술개발형 (R&D·산학협력 과제에 적합)
```text
[핵심 기술]을 활용한 [대상 산업·고객]용 [제품·시스템] 개발
```
예시:
- "온디바이스 비전 AI를 활용한 중소 제조업체용 실시간 외관검사 시스템 개발"
  - 포함 요소: 기술(3)+고객/산업(1)+제품(4) → 3개 충족
- "센서 융합 기반 물류 현장용 자율 재고 관제 시스템 개발"

### 3.2 사업화형 (창업지원·투자덱·중소기업 지원에 적합)
```text
[고객 문제]를 해결하는 [차별화 방식] 기반 [서비스] 사업화
```
예시:
- "소상공인 세무 신고 부담을 해결하는 영수증 자동 인식 기반 세무 SaaS 사업화"
  - 포함 요소: 문제(2)+기술/방식(3)+제품(4)+사업화(5) → 4개 충족
- "1인 의원의 보험청구 오류를 줄이는 청구 검증 자동화 서비스 사업화"

### 3.3 공공형 (공공기관 제안·정책 연계 사업에 적합)
```text
[사회·산업 문제] 개선을 위한 [수행 방식] 기반 [사업·플랫폼] 구축
```
예시:
- "지역 소상공인 폐업 위험 개선을 위한 데이터 분석 기반 상권 진단 플랫폼 구축"
  - 포함 요소: 문제(2)+방식(3)+플랫폼(4)+구축(5) → 4개 충족
- "고령 농가 안전사고 저감을 위한 IoT 모니터링 기반 현장 관제 체계 구축"

> 제목은 공고의 **사업 목적·평가 항목 표현과 어휘를 맞춘다**(`01-notice-analysis/notice-summary.md` 참조). 공고가 "사업화"를 강조하면 사업화형, "기술개발·정량목표"를 강조하면 기술개발형으로.

## 4. 리서치·인터뷰 후 최종 재제안 절차 (PRD §9.1)

Gate 2(리서치) 완료 후, 또는 인터뷰 종료 시점에 제목을 다시 설계한다.

1. **입력 정리** — `confirmed-facts.md`(검증된 차별성), `founder-insight.md`(고유 강점), `04-research/`(시장·경쟁·기술 결과), `notice-summary.md`(공고 어휘)를 모은다.
2. **3축 후보 생성** — 기술 중심 / 고객 문제 중심 / 사업화 중심 각 1개 이상.
3. **각 후보 검증** — 5요소 ≥3개? 검증된 사실로 받쳐지나? 공고 어휘와 정합? 너무 넓거나 모호하지 않나(PRD §2.1 "지나치게 넓거나 모호" 방지)?
4. **권장 최종 1개 선정** — 문서 유형의 평가 논리에 가장 부합하는 것. 사용자에게 제시하고 확정(`AskUserQuestion` 1회).
5. 확정된 최종 제목을 `business-core.yaml`의 `business.title`로 반영(Gate 3).

## 5. 산출물 구조 — `title-candidates.md` (PRD §9.2 출력)

```markdown
# 과제명 후보 — <프로젝트명>

## 최초 가설 (H0)
- 사용자 제시 제목/키워드: "<원문 그대로>"  [출처: 인터뷰 L<줄>]
- 비고: (없으면 키워드 기반 임시 가설 + [확인 필요])

---

## 후보 1 — 기술 중심
- 제목: "<공식 3.1 적용>"
- 포함 구성요소: 기술(3) / 산업(1) / 제품(4)  → 3개
- 근거 사실: [출처: confirmed-facts L..]
| 장점 | 위험 |
|---|---|
| 기술성 배점에 강함, R&D 적합 | 사업화·시장 메시지 약함 |

## 후보 2 — 고객 문제 중심
- 제목: "<문제 강조>"
- 포함 구성요소: 문제(2) / 고객(1) / 제품(4)  → 3개
| 장점 | 위험 |
|---|---|
| 문제 인식 배점에 강함, 공감 유발 | 기술 차별성 안 드러남 |

## 후보 3 — 사업화 중심
- 제목: "<공식 3.2 적용>"
- 포함 구성요소: 문제(2) / 방식(3) / 서비스(4) / 사업화(5)  → 4개
| 장점 | 위험 |
|---|---|
| 성장전략·시장성 배점에 강함 | 기술 깊이 약해 보일 수 있음 |

---

## 권장 최종 제목
- "<선정안>"
- 선정 사유: 문서 유형(<type>)의 평가 논리 + 공고 어휘 정합 + 검증된 사실 뒷받침
- 포함 구성요소: (5요소 중 N개)
- business-core 반영: business.title ← 이 값

## 제목별 장점·위험 종합
| 후보 | 핵심 장점 | 핵심 위험 | 적합 유형 |
|---|---|---|---|
| 1 기술중심 | 기술성 | 사업성 약함 | R&D |
| 2 고객문제중심 | 공감·문제인식 | 기술성 약함 | 창업지원 |
| 3 사업화중심 | 성장전략 | 기술깊이 | 투자/사업화 |
| 권장 | … | … | <type> |
```

## 6. 통과 체크리스트

- [ ] 인터뷰 초기에 과제명 가설 질문을 던졌고 사용자 제목을 H0로 원문 보존
- [ ] 후보 3종(기술중심·고객문제중심·사업화중심)이 각각 5요소 ≥3개 충족
- [ ] 각 후보에 장점·위험 표 작성
- [ ] 리서치/인터뷰 결과 반영하여 최종 재제안 완료
- [ ] 제목 주장이 검증된 사실로 뒷받침됨(임의 수치·"세계 최초" 없음)
- [ ] 권장 최종 제목을 사용자와 확정하고 `business-core.yaml`의 `business.title`에 반영
