# BizPlan Architect PRD

## AI 기반 사업계획서·제안서 설계 및 작성 시스템

* 문서 버전: v1.0
* 제품 유형: AI 에이전트 기반 사업계획서 작성 스킬
* 기본 명령어: `/bizplan`
* 주요 산출물: DOCX, HWPX, PDF, PPTX, XLSX, MD
* 적용 대상: 정부지원사업, R&D 과제, 투자 피치덱, 기업·공공기관 제안서

---

# 1. 제품 개요

## 1.1 제품 정의

BizPlan Architect는 사용자가 제공한 공고문과 사업 아이디어를 분석하고, AI가 사용자를 심층 인터뷰한 뒤 관련 시장·기술·경쟁사·특허·논문을 조사하여 목적에 맞는 사업계획서와 제안서를 작성하는 시스템이다.

이 제품은 빈칸을 문장으로 채우는 일반적인 문서 생성기가 아니다.

다음 네 가지를 통합하는 **사업 논리 설계 시스템**이다.

1. 공고와 평가 기준 분석
2. 창업자·사업 책임자 심층 인터뷰
3. 시장·기술·특허·논문 기반의 증거 수집
4. 공식 서식에 맞춘 문서 작성과 검증

---

## 1.2 핵심 가치 제안

> 하나의 사업 아이디어를 깊이 인터뷰하고 조사하여
> 정부지원서, R&D 계획서, 투자덱, 기관 제안서로 변환한다.

사용자는 완성된 사업계획을 가지고 있을 필요가 없다.

몇 개의 키워드와 막연한 아이디어만 제공해도 AI가 질문을 통해 다음 내용을 구체화한다.

* 누구의 어떤 문제를 해결하는가
* 왜 지금 필요한가
* 어떤 기술과 방식으로 해결하는가
* 고객이 돈을 낼 이유가 있는가
* 경쟁 제품과 무엇이 다른가
* 실제로 구현할 수 있는가
* 어떤 성과를 만들 수 있는가
* 지원금이나 투자금이 왜 필요한가

---

# 2. 문제 정의

## 2.1 사용자가 겪는 문제

사업계획서를 처음 작성하는 사용자는 다음 문제를 겪는다.

* 공고문과 첨부파일이 여러 곳에 흩어져 있다.
* 공고의 평가 기준이 문서 안에 분산되어 있다.
* 무엇을 써야 하는지는 알지만 어떤 근거가 필요한지 모른다.
* 자신의 사업을 한 문장으로 정의하기 어렵다.
* 사업계획서 제목을 지나치게 넓거나 모호하게 정한다.
* 시장 자료와 통계 출처를 찾는 데 많은 시간이 든다.
* 경쟁회사와 경쟁 제품을 제대로 구분하지 못한다.
* 기술의 차별성과 사업의 차별성을 혼동한다.
* 특허가 있다는 사실과 실제 권리 범위를 구분하지 못한다.
* 논문 내용을 사업과 연결하지 못한다.
* 공식 서식에 맞춰 내용을 재배치하는 과정이 어렵다.
* 사업계획서마다 고객, 시장 규모, 매출 목표가 달라진다.
* AI가 그럴듯하지만 사실이 아닌 내용을 만들어낼 위험이 있다.

---

## 2.2 기존 AI 문서 작성 방식의 한계

기존 생성형 AI 기반 사업계획서 작성은 대체로 다음 순서로 진행된다.

```text
사용자 아이디어 입력
→ 목차 생성
→ 문장 생성
```

이 방식은 빠르지만 다음 문제가 발생한다.

* 충분한 인터뷰 없이 사용자의 의도를 추정한다.
* 사실과 가정이 섞인다.
* 조사 전에 결론이 만들어진다.
* 출처가 없는 시장 수치가 생성된다.
* 경쟁사를 피상적으로 나열한다.
* 특허의 제목과 초록만 보고 기술 차별성을 판단한다.
* 논문을 요약하지만 구현 가능성과 연결하지 못한다.
* 공고의 평가 기준과 문서 내용이 일치하지 않는다.

BizPlan Architect는 이를 다음 순서로 바꾼다.

```text
공고 분석
→ 심층 인터뷰
→ 가설 설정
→ 리서치
→ 사업 논리 설계
→ 공식 서식 매핑
→ 초안 작성
→ 검증과 반복
```

# 3. 제품 목표

## 3.1 핵심 목표

1. 공고문 링크만으로 관련 문서와 첨부파일을 최대한 자동 수집한다.
2. AI가 사용자와 심층 인터뷰하여 사업의 숨은 경험과 경쟁력을 끌어낸다.
3. 사업과 기술이 모두 드러나는 과제명을 설계한다.
4. 시장·산업·경쟁·기술·특허·논문을 체계적으로 조사한다.
5. 모든 주장에 출처 또는 근거를 연결한다.
6. 공식 사업계획서 서식을 분석하여 목차와 입력 위치를 보존한다.
7. 텍스트, 표, 그래프, 다이어그램, 이미지를 조합하여 초안을 작성한다.
8. 평가위원 관점에서 논리, 사업성, 기술성, 실행 가능성을 검증한다.
9. 같은 사업의 여러 문서에서 수치와 메시지가 일관되도록 관리한다.
10. 제출 가능한 DOCX, HWPX, PDF, PPTX 결과물을 생성한다.

---

## 3.2 비목표

초기 버전에서 다음 기능은 보장하지 않는다.

* 변리사 또는 변호사의 법률 의견을 대체하는 특허 침해 판단
* 회계사의 공식 기업가치 평가
* 모든 정부기관 HWP 서식의 완전한 원형 보존
* 로그인이 필요한 사이트의 무단 접근
* 유료 시장조사 보고서의 우회 취득
* 존재하지 않는 통계나 고객 반응 생성
* 선정 가능성 또는 투자 유치 가능성 보장

# 4. 핵심 사용자

## 4.1 창업자와 예비 창업자

아이디어는 있으나 사업계획서 작성 경험이 부족한 사용자.

## 4.2 중소기업 대표와 사업개발 담당자

정부지원사업, 기술개발사업, 기관 제안에 참여하려는 사용자.

## 4.3 연구개발 책임자

기술 내용은 잘 알지만 시장성과 사업화 계획 작성이 어려운 사용자.

## 4.4 컨설턴트와 사업계획서 작성 전문가

여러 고객의 사업 자료를 빠르게 조사하고 구조화해야 하는 사용자.

## 4.5 대학·연구기관 산학협력 담당자

논문과 연구 기술을 사업화 과제로 전환하려는 사용자.

## 4.6 사내 신사업 담당자

내부 아이디어를 사업 제안서와 투자 검토 자료로 만들려는 사용자.

# 5. 제품 설계 원칙

## 5.1 인터뷰 우선

AI는 사용자의 첫 설명만으로 사업을 단정하지 않는다.

문서 작성 전에 심층 인터뷰를 수행한다.

## 5.2 증거 우선

좋은 문장보다 확인 가능한 근거를 우선한다.

## 5.3 조사와 작성의 분리

먼저 조사 보고서를 작성하고, 이후 사업계획서에 필요한 근거를 선별한다.

## 5.4 하나의 사업 코어

모든 문서는 `business-core.yaml`에서 파생한다.

## 5.5 목적별 변환

정부지원서, R&D 계획서, 투자덱, 기관 제안서는 서로 다른 평가 논리를 적용한다.

## 5.6 사실·추정·가정·목표의 분리

모든 수치와 주장을 다음과 같이 구분한다.

```text
[사실] 확인된 정보
[추정] 근거와 계산식에 의한 수치
[가정] 아직 검증하지 않은 전제
[목표] 앞으로 달성하려는 성과
[확인 필요] 추가 자료가 필요한 항목
```

## 5.7 AI의 임의 창작 금지

고객, 매출, 계약, 특허, 인증, 기술 성능을 임의로 만들지 않는다.

# 8. AI 심층 인터뷰 엔진

## 8.1 목적

심층 인터뷰의 목적은 정보를 수집하는 데 그치지 않는다.

사용자가 당연하다고 여기거나 말하지 않은 다음 내용을 발견해야 한다.

* 창업자가 이 문제를 발견한 계기
* 현장에서 반복적으로 관찰한 문제
* 기존 사업자가 해결하지 못한 이유
* 창업자만 알고 있는 업무 흐름
* 보유한 네트워크와 고객 접근력
* 실제로 구현해본 경험
* 잠재고객의 반응
* 실패했던 시도
* 기술적·사업적 제약
* 대표자와 팀의 고유한 역량

---

## 8.2 인터뷰 진행 원칙

AI는 고정된 설문지를 한꺼번에 보여주지 않는다.

사용자의 답변에 따라 다음 질문을 결정하는 적응형 인터뷰를 수행한다.

```text
질문
→ 답변 해석
→ 모호한 부분 탐지
→ 반례 또는 구체적 사례 질문
→ 근거 확인
→ 다음 질문 선택
```

한 번에 질문하는 문항은 최대 3개로 제한한다.

---

## 8.3 인터뷰 단계

### 1단계: 창업 동기와 문제 발견

* 이 사업을 처음 생각하게 된 계기는 무엇인가?
* 문제를 직접 경험한 적이 있는가?
* 가장 기억나는 구체적인 장면은 무엇인가?
* 이 문제가 해결되지 않으면 누가 어떤 손실을 보는가?
* 문제는 얼마나 자주 발생하는가?

### 2단계: 고객과 사용자

* 실제 제품을 사용하는 사람은 누구인가?
* 구매 결정을 내리는 사람은 누구인가?
* 비용을 지불하는 사람과 사용하는 사람이 같은가?
* 가장 먼저 구매할 가능성이 높은 고객은 누구인가?
* 고객이 현재 사용하는 대안은 무엇인가?

### 3단계: 현재 해결 방식

* 고객은 지금 어떻게 문제를 해결하고 있는가?
* 엑셀, 외주, 수작업, 기존 제품 중 무엇을 사용하는가?
* 기존 방식에서 가장 불편한 순간은 언제인가?
* 고객이 기존 방식을 쉽게 버리지 못하는 이유는 무엇인가?

### 4단계: 제품과 기술

* 제품이 작동하는 과정을 처음부터 끝까지 설명할 수 있는가?
* 반드시 필요한 핵심 기능은 무엇인가?
* 없어도 되는 기능은 무엇인가?
* 가장 어려운 기술적 문제는 무엇인가?
* 경쟁사가 쉽게 따라 할 수 없는 요소는 무엇인가?

### 5단계: 구현 가능성

* 현재 구현된 것은 어디까지인가?
* 프로토타입, 코드, 설계, 데이터가 있는가?
* 개발에 필요한 인력과 장비는 무엇인가?
* 외부 기관이나 파트너가 필요한가?
* 성공 여부를 어떤 수치로 검증할 것인가?

### 6단계: 시장과 사업모델

* 고객은 무엇에 돈을 내는가?
* 예상 가격은 얼마인가?
* 일회성 판매인가, 구독인가, 구축형인가?
* 고객 한 명을 확보하는 데 어떤 과정이 필요한가?
* 첫 10명의 고객은 어디에서 만날 수 있는가?

### 7단계: 경쟁과 대체재

* 유사한 제품이나 회사를 알고 있는가?
* 고객은 왜 기존 제품 대신 이 제품을 선택해야 하는가?
* 경쟁사가 가격을 낮추면 어떻게 대응할 것인가?
* 고객이 아무것도 하지 않는 선택도 경쟁 아닌가?

### 8단계: 팀과 실행 역량

* 대표자가 이 사업을 수행하기 적합한 이유는 무엇인가?
* 팀 내부에서 직접 수행할 업무는 무엇인가?
* 외주로 맡길 업무는 무엇인가?
* 현재 부족한 역량은 무엇인가?
* 협력 가능한 고객, 기관, 전문가가 있는가?

### 9단계: 성과와 증거

* 매출, 사용자, 상담, 계약, 테스트 결과가 있는가?
* 고객 인터뷰 기록이 있는가?
* MOU, LOI, NDA, PoC가 있는가?
* 특허, 저작권, 상표, 인증이 있는가?
* 제품 성능을 입증할 데이터가 있는가?

### 10단계: 비전과 파급효과

* 이 사업이 성공하면 고객의 하루가 어떻게 달라지는가?
* 산업의 구조는 어떻게 달라지는가?
* 고용, 생산성, 비용, 안전에 어떤 변화가 생기는가?
* 3년 후 이 사업은 어떤 모습이어야 하는가?

## 11.5 청구항 분석

AI는 특허의 제목이나 초록만으로 권리 범위를 판단하지 않는다.

독립 청구항을 중심으로 구성요소를 분해한다.

예:

```text
청구항 요소 A
+ 청구항 요소 B
+ 청구항 요소 C
+ 요소 간 결합 관계
```

이를 사용자의 제품 구성과 비교한다.

| 청구항 요소   | 사용자 제품   | 일치 여부 | 비고          |
| -------- | -------- | ----- | ----------- |
| 문서 입력 모듈 | 있음       | 일치 가능 | 입력 형태 확인 필요 |
| 의미 분석 엔진 | 있음       | 부분 일치 | 구현 방식 다름    |
| 장면 자동 생성 | 있음       | 일치 가능 | 청구항 해석 필요   |
| 영상 렌더링   | 외부 도구 사용 | 부분 일치 | 직접 수행 여부 확인 |

## 11.6 FTO 예비 분석

Freedom to Operate 분석은 다음 단계로 수행한다.

1. 제품을 핵심 기능 단위로 분해한다.
2. 기능별 관련 특허를 찾는다.
3. 유효한 권리인지 확인한다.
4. 독립 청구항을 요소별로 분해한다.
5. 사용자 제품과 비교한다.
6. 위험 특허를 분류한다.
7. 회피 설계 가능성을 제시한다.
8. 변리사 검토가 필요한 특허를 표시한다.

주의:

> AI의 특허 분석은 기술·사업 기획을 위한 예비 검토다.
> 침해 여부, 무효 가능성, 권리 범위에 관한 최종 판단은
> 변리사 또는 특허 전문 변호사의 검토가 필요하다.

```text
→ 실제 환경 실증
→ 상용 제품 적용
```

필요한 경우 TRL 형태로 표시한다.

## 12.7 벤치마크 분석

논문 간 성능을 비교할 때 다음을 확인한다.

* 동일한 데이터셋인지
* 동일한 평가 지표인지
* 동일한 하드웨어 조건인지
* 추론 비용이 포함되었는지
* 품질과 속도의 균형
* 실제 제품 환경에서 재현 가능한지

서로 다른 조건의 숫자를 단순 비교하지 않는다.

## Gate 0. 공고와 자료 수집

* 해결책
* 기술
* 사업모델
* 팀
* 목표

모호한 항목이 없거나 `[확인 필요]`로 분류되어야 한다.

## Gate 2. 리서치

* 공식 자료 포함
* 국내외 시장 조사
* 경쟁 제품 조사
* 특허 조사
* 논문 조사
* 부정적 근거 포함
* 출처와 기준일 기록

## Gate 3. 사업 논리

```text
문제
→ 해결책
→ 제품
→ 기술
→ 시장
→ 수익모델
→ 실행 계획
→ 예산
```

단절된 연결이 없어야 한다.

## Gate 4. 숫자

* TAM·SAM·SOM
* 가격
* 고객 수
* 매출
* 비용
* 인력
* 일정
* 사업비

문서 전체에서 같은 수치를 사용해야 한다.

## Gate 5. 특허와 논문

* 특허 법적 상태 확인
* 독립 청구항 분석
* 초록만으로 권리 범위를 판단하지 않음
* 논문 조건이 다른 성능을 단순 비교하지 않음
* 최신 연구와 상충 여부 확인

## Gate 6. 서식

* 목차 누락 없음
* 지정 분량 준수
* 폰트와 글자 크기
* 공란 없음
* 표와 그림의 제목
* 서명과 첨부서류

## Gate 7. 평가위원 시뮬레이션

네 개의 평가자 역할을 사용한다.

1. 행정·서식 평가자
2. 기술·산업 전문가
3. 사업성 평가자
4. 회의적인 반대 평가자

# 26. 비기능 요구사항

## 신뢰성

* 출처 없는 수치를 핵심 근거로 사용하지 않는다.
* 생성 내용과 원문 인용을 구분한다.
* 파일 다운로드 실패를 명시한다.
* 분석하지 못한 특허와 논문을 숨기지 않는다.

## 보안

* 기업 내부 자료는 프로젝트별로 격리한다.
* 원본 문서를 임의로 외부 공개하지 않는다.
* API 키와 로그인 정보는 암호화한다.
* 민감 자료는 사용자 승인 없이 외부 검색에 사용하지 않는다.

## 재현성

* 사용한 검색어를 저장한다.
* 출처와 접근일을 저장한다.
* 생성한 다이어그램 원본을 보존한다.
* 각 문서 버전과 수정 이력을 기록한다.

## 성능

* 긴 작업은 단계별 산출물을 먼저 제공한다.
* 실패한 단계부터 다시 실행할 수 있어야 한다.
* 전체 프로젝트를 처음부터 다시 생성하지 않아야 한다.

# 29. 위험요소와 대응

## 과도한 자동화

위험: 사용자가 내용을 검토하지 않고 그대로 제출할 수 있다.

대응:

* 확인이 필요한 내용을 별도 표시
* 최종 승인 체크리스트 제공
* 사용자 확인 전 확정 문장으로 전환하지 않음

## 부정확한 특허 판단

위험: AI의 결과를 법률 의견으로 오해할 수 있다.

대응:

* 예비 분석으로 명시
* 위험 특허는 전문가 검토 대상으로 분류
* 법적 상태와 청구항 원문 연결

## 논문 성능의 과장

위험: 실험 환경의 결과를 상용 제품 성능처럼 사용할 수 있다.

대응:

* 연구 환경과 실제 환경 구분
* 데이터셋과 하드웨어 조건 표시
* 논문 결과와 제품 목표 분리

## 출처 편향

위험: 사업에 유리한 자료만 수집할 수 있다.

대응:

* 반대 자료와 실패 사례 검색
* 경쟁 제품의 강점도 기록
* 시장 축소와 규제 위험 포함

## 공식 서식 손상

위험: HWPX 또는 DOCX 변환 과정에서 표가 깨질 수 있다.

대응:

* 원본 보존
* 출력 전 렌더링 검사
* 삽입 가이드 대체 제공
* 서식 손상 보고서 생성

11. 숫자와 일정이 문서 전체에서 일치한다.

13. 평가위원 시뮬레이션을 통과했다.
14. 제출용 파일과 체크리스트가 생성되었다.

# 31. 제품의 핵심 문장

> 좋은 사업계획서는 글을 잘 써서 만들어지는 것이 아니다.
> 사업을 깊이 질문하고, 근거를 찾고, 반론을 견딜 수 있도록
> 논리를 설계했을 때 만들어진다.

BizPlan Architect는 사용자의 아이디어를 대신 꾸며주는 도구가 아니다.

사용자가 가진 현장 경험과 기술, 시장의 증거, 특허와 논문, 실행 계획을 연결하여 **지원하거나 투자할 이유가 보이는 사업**으로 만드는 시스템이다.
