# Content Verification Checklist

Run this after the manual draft/media exists. This is separate from technical QA.

## Reader Fit

- [ ] The target reader and job are explicit.
- [ ] The manual uses terms the reader sees or already knows.
- [ ] Internal implementation names are removed unless visible to the reader.
- [ ] Prerequisites and permissions are stated before steps.

## Coverage

- [ ] Every documented route/menu/control exists in the current system.
- [ ] Every important reader goal in scope has a lesson or section.
- [ ] Missing routes, broken screens, and dead controls are listed as product issues or out-of-scope.
- [ ] Public/output verification is included where relevant.

## Sequencing

- [ ] Overview, setup, operation, verification, and troubleshooting are not mixed randomly.
- [ ] Lesson boundaries match natural task pauses.
- [ ] Risky/destructive/publishing actions have their own warning or checkpoint.
- [ ] The same menu is not duplicated across lessons unless it teaches a different goal.

## Truthfulness

- [ ] Impossible states/statuses/filters are not documented as normal cases.
- [ ] Screenshots/video match the text and current UI labels.
- [ ] The manual does not invent edge cases or future features.
- [ ] Unresolved decisions are marked as unresolved, not papered over.

## Usefulness

- [ ] Each major step says what success looks like.
- [ ] The reader can recover from common mistakes or know when to ask for help.
- [ ] The manual is not just a UI tour; it teaches real operating outcomes.
