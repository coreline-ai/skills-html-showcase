wg 01 · three code approaches

코드 비교

한 문제, 세 가지 구현 접근

문제: 중복 없는 정수 배열에서 두 수의 합이 target이 되는 인덱스 쌍 찾기. 세 접근의 코드·장단점·트레이드오프를 나란히 비교합니다.

A

완전 탐색 (Brute Force)

O(n²) · 추가 메모리 없음

def two_sum(nums, target):
  for i in range(len(nums)):
    for j in range(i+1, len(nums)):
      if nums[i]+nums[j] == target:
        return [i, j]
  return []

▲ 장점

  • 구현이 단순, 버그 위험 낮음
  • 메모리 O(1)

▼ 단점

  • 큰 입력에서 느림
  • 중첩 루프 확장성 낮음
시간 O(n²) 공간 O(1) 읽기 쉬움
B

해시맵 1-pass 권장

O(n) · 메모리 트레이드

def two_sum(nums, target):
  seen = {}
  for i, n in enumerate(nums):
    need = target - n
    if need in seen:
      return [seen[need], i]
    seen[n] = i
  return []

▲ 장점

  • 선형 시간, 단일 순회
  • 대규모 입력에 안정적

▼ 단점

  • O(n) 추가 메모리
  • 해시 충돌 의존
시간 O(n) 공간 O(n) 실무 기본
C

정렬 + 투 포인터

O(n log n) · 인덱스 보존 필요

def two_sum(nums, target):
  arr = sorted(enumerate(nums), key=lambda x: x[1])
  l, r = 0, len(arr)-1
  while l < r:
    s = arr[l][1] + arr[r][1]
    if s == target: return [arr[l][0], arr[r][0]]
    l, r = (l+1, r) if s<target else (l, r-1)
  return []

▲ 장점

  • 정렬 데이터에 재사용 용이
  • 공간 O(1)~O(n)

▼ 단점

  • 정렬 비용 발생
  • 원본 인덱스 추적 복잡
시간 O(n log n) 공간 O(n) 정렬 의존

wg 14 · feature explainer

기능 안내 · v2.8 릴리스

스마트 머지 큐 (Smart Merge Queue)

PR을 자동으로 줄 세워 순차 머지하고, 충돌·CI 실패를 머지 전에 잡아내는 기능입니다.

TL;DR

버튼 하나로 PR을 큐에 넣으면 메인 브랜치 기준 재검증 후 자동 머지됩니다. 평균 머지 대기 18분 → 4분, 실패 머지 -82%.

01 무엇을 해결하나요

여러 PR이 동시에 메인에 머지될 때 발생하는 '머지 후 깨짐(semantic conflict)'을 방지합니다. 각 PR은 머지 직전 최신 메인 위에서 CI를 다시 돌립니다.

  • 충돌·테스트 실패 PR은 큐에서 자동 제외 후 작성자에게 알림
  • FIFO 우선순위, priority:hotfix 라벨은 새치기 허용
  • 배치 머지: 독립 PR 최대 5개를 한 번에 검증
02 동작 방식
  1. 1 PR에 /merge-queue 코멘트 또는 큐 버튼 클릭
  2. 2 임시 브랜치에 (메인 + 큐 + 내 PR) 병합
  3. 3 CI 통과 시 머지, 실패 시 해당 PR만 이탈

설정 예시

merge_queue:
  enabled: true
  method: squash
  max_batch: 5
  required_checks:
    - build
    - test:unit

wg 15 · concept explainer

개념 교보재 · 분산 시스템

컨시스턴트 해싱 (Consistent Hashing)

노드를 원형 해시 링 위에 배치해, 노드가 추가·제거돼도 재배치되는 키를 최소화하는 분산 기법입니다.

왜 단순 모듈로(hash % N)로는 부족할까

방식 비교
기준모듈로 해싱컨시스턴트 해싱
노드 추가 시 이동 키거의 전부 (~N-1/N)1/N 만
부하 분산균등가상노드로 균등화
구현 난도낮음중간
대표 사용처고정 샤드Cassandra · DynamoDB · CDN

단계별로 이해하기

A B C D k1 k2 0° / 360°

1. 노드를 링 위에 해시한다

각 노드 ID를 해시해 0~360° 원형 공간의 한 점에 놓습니다. A·B·C 세 노드가 링 위 서로 다른 위치를 차지합니다.

핵심: 키와 노드가 같은 공간을 공유합니다.

2. 키는 시계방향 첫 노드에 귀속

키 k1, k2도 동일하게 해시해 링에 놓고, 시계방향으로 만나는 첫 노드가 그 키를 소유합니다. k1→B, k2→C.

조회·저장 모두 이 규칙 하나로 결정됩니다.

3. 노드 D 추가 — 이동은 국소적

새 노드 D가 들어오면 D와 직전 노드 사이 구간의 키만 D로 이동합니다. 나머지 키는 그대로 → 전체 재배치 없음.

이것이 모듈로 대비 핵심 이점입니다.

130분 접근성 점검

배포 전 30분 안에 끝내는 핵심 점검. 각 카드는 점검 영역 · 예상 소요 · 통과/실패 기준을 담는다.

키보드8분

키보드만으로 전체 탐색

Tab/Shift+Tab으로 모든 인터랙션에 도달·조작되는지 본다.

  • PASS포커스 링이 항상 보인다
  • FAIL마우스로만 열리는 메뉴가 있다
대비7분

본문·칩 대비 AA

본문 텍스트와 흐린 칩/메타가 4.5:1을 넘는지 본다.

  • PASS흐린 메타도 4.5:1 이상
  • FAIL상태를 색으로만 구분
구조10분

제목 계층·대체 텍스트

h1→h2→h3 순서와 이미지 alt, 스킵 링크를 확인한다.

  • PASS도형 SVG에 의미 있는 alt
  • FAILh2를 건너뛰고 h4 사용
단일 규칙

상태·심각도는 절대 색만으로 전달하지 않는다 — 텍스트 라벨(PASS/FAIL/WARN)이나 형태 단서를 항상 함께 둔다.

2실패 모드와 함정

자주 반복되는 실패와 해결책. 표는 모바일에서 가로 스크롤된다.

접근성 실패 모드 · 증상 · 해결
실패 모드증상해결
색-단독 상태색맹 사용자가 상태 구분 불가텍스트/형태 단서 병기
role="img" 남용컨테이너 텍스트가 prune됨role 제거, 장식만 aria-hidden
포커스 소실키보드 위치를 알 수 없음:focus-visible 링 유지
함정

"나중에 손볼게요"

대비·포커스는 사후 보정이 가장 비싸다. 토큰 단계에서 잡는다.

해결

토큰에 단서 내장

상태 토큰에 텍스트 라벨 컴포넌트를 묶어 색-단독을 구조적으로 차단한다.

사례

토글 3-상태화

ON/WARN/OFF 텍스트 라벨로 스위치의 색-단독 신호를 제거.

3릴리스 준비 체크

아래 항목이 모두 충족되면 접근성 관점에서 배포 가능하다.

  1. 키보드 전 경로 — 모든 기능이 Tab으로 도달·조작
  2. 가시 포커스 — 전 인터랙션에 :focus-visible 링
  3. AA 대비 — 본문·칩·메타 4.5:1 이상
  4. 비색 단서 — 상태/심각도에 텍스트·형태 병기
  5. 의미 있는 alt — 정보성 이미지에 대체 텍스트
  6. 축소 모션 — prefers-reduced-motion 폴백
