1산출물 형식 게이트

운영 매뉴얼은 "그럴듯한 데모"가 아니라, 무엇이 화면 근거로 확정됐고 무엇이 캡처 대기인지 분리하는 단일 HTML 패키지여야 합니다. 형식이 먼저 닫혀야 내용 검수가 가능합니다.

이 문서는 정적 단일 HTML 패키지로 배포됩니다. 모든 링크는 문서 내부 앵커이며 외부 네트워크 호출, 외부 CSS, 동작 스크립트를 사용하지 않습니다. 운영자가 오프라인 사내망에서 열어도 동일하게 동작하는 것이 형식 기준입니다.

Format Verdict
운영자가 단독으로 따라갈 수 있는 단일 HTML

구조는 html lang="ko" · viewport · h1 1개 · main id="main" · 목차 앵커를 포함합니다. 머지 승인부터 프로덕션 검증까지의 흐름을 한 화면에서 따라가도록 구성했습니다.

HTML 파일

2대상 독자와 전제

이 매뉴얼은 "코드를 잘 짜는 사람"이 아니라, 배포 절차를 깨뜨리지 않고 운영하며 위험 작업 앞에서 멈출 줄 아는 사람을 위해 씁니다. 초보 운영자가 첫날 한 번의 안전한 배포를 끝내는 것이 목표입니다.

Primary

신규 릴리스 운영자

입사 1주 차, 릴리스 콘솔을 처음 다룹니다. 머지 승인·카나리 배포·검증 화면을 순서대로 따라가며 첫 배포를 완료합니다.

Secondary

당직 엔지니어

배포 후 알림을 받는 사람. 롤백 트리거와 인수인계 메모를 읽고 다음 행동을 결정합니다.

Reviewer

릴리스 책임자

위험 작업 승인과 최종 검증 기록을 판정합니다. CAPTURE_REQUIRED가 남으면 "프로덕션 배포 가능" 상태로 보지 않습니다.

전제: 독자는 사내 SSO 계정과 deploy-operator 역할을 이미 부여받았다고 가정합니다. 권한 신청·계정 발급 절차는 이 매뉴얼이 다루지 않으며(§7), 권한이 없으면 §6 워크플로의 1번 레인에서 막힙니다.

범위: 배포 운영 절차 비범위: 권한 발급·법무 검토 화면 버전: Release Console v3.2

3출처 위계 — 화면 근거가 먼저다

운영 매뉴얼은 1차 화면 근거가 최상위입니다. 실제 콘솔 화면·로그가 정본이고, 사내 문서는 보조이며, 작성자 추정은 가장 아래입니다. 위계를 뒤집으면 매뉴얼은 설득문이 되고 검증 문서가 되지 못합니다.

Level 1 · 최우선

실제 화면·로그

Release Console 화면 캡처, 배포 이벤트 로그, 헬스체크 대시보드. 운영자가 실제로 보는 것이 정본입니다. 화면 근거가 없는 절차는 CAPTURE_REQUIRED로 남깁니다.

Level 2 · 보조

사내 문서

릴리스 정책 문서, 런북 위키, 변경 관리 규정. 화면 절차를 보강·해석하지만 화면과 어긋나면 화면이 이깁니다.

Level 3 · 최하위

작성자 추정

"아마 이 버튼일 것"이라는 추정. 단독 근거로 본문에 쓰지 않고 반드시 1·2차로 승격하거나 캡처 요청으로 남깁니다.

Anti-pattern
화면을 안 보고 쓴 절차

가장 흔한 매뉴얼 사고는 작성자가 콘솔을 열지 않고 기억·추정으로 버튼 이름을 적는 것입니다. v3.2에서 메뉴 명칭이 바뀌었는데 구버전 명칭이 그대로 남으면 운영자는 첫 화면에서 막힙니다. 그래서 모든 조작 단계에는 어느 화면의 어느 요소인지 근거 위치를 붙입니다.

4워크플로 인벤토리 — 작성 전 목록 고정

매뉴얼은 화면 설명서가 아니라 업무 단위 목록입니다. 작성을 시작하기 전에 모든 업무를 인벤토리로 먼저 적고, 각 업무에 입력·담당·완료 기준·화면 근거 상태를 붙입니다. 빈 인벤토리 상태에서 본문 작성을 시작하지 않습니다.

7이 매뉴얼이 다루는 범위와 안 다루는 범위

매뉴얼이 모든 것을 가르치려 하면, 위험한 판단까지 초보 운영자에게 떠넘기게 됩니다. 가르칠 범위와 넘길 범위를 분명히 분리합니다.

9위험 작업과 안전 fixture

롤백·트래픽 100% 승격·강제 배포 같은 되돌리기 어려운 작업은 실제 프로덕션이 아니라 안전 fixture(샌드박스 환경)에서 먼저 연습합니다. 초보 운영자의 첫 실습은 프로덕션이 아니어야 합니다.

위험
프로덕션에서 바로 연습하지 않는다

롤백 모달, 트래픽 100% 즉시 승격, 헬스체크 무시 강제 배포는 실패 시 사용자 영향이 즉각적입니다. 신규 운영자는 이 동작들을 sandbox-release 환경에서 먼저 재현하고, 프로덕션에서는 §6 워크플로의 책임자 승인 단계를 거친 뒤에만 수행합니다.

아래 흐름은 안전 fixture에서 "실패 → 롤백" 경로를 연습하는 시나리오입니다. 각 단계 박스를 누르면 아래 상세로 이동합니다.

시작카나리 배포

샌드박스에서 의도적으로 오류를 심은 빌드를 10% 트래픽으로 배포합니다. 실제 사용자 영향은 없습니다.

관찰헬스체크

오류율이 임계(예: 2%)를 넘으면 실패 경로로 분기합니다. 임계값과 대시보드 위치는 실제 화면 확인 후 확정합니다.

실패롤백 & 사유 기록

직전 안정 릴리스 태그로 롤백하고, 롤백 사유와 시각을 검증 기록(§10)에 남깁니다. 이 연습을 프로덕션 전에 최소 1회 완료합니다.

완료100% 승격

지표가 정상이면 비율을 100%로 올립니다. 프로덕션에서는 이 단계 전에 §6 책임자 승인을 거칩니다.

안전 fixture는 실패해도 되는 환경에서 실패를 먼저 경험하게 하는 장치다.

롤백을 처음 눌러보는 곳이 프로덕션이어서는 안 됩니다. 운영자가 샌드박스에서 실패-롤백을 한 번 통과해야, 실제 장애 상황에서 손이 멈추지 않습니다.

검증은 단계 절차와 분리된 별도 기록입니다. 누가·언제·무엇을·어떤 화면으로 확인했고, 무엇을 보류했는지 남겨야 "배포 완료"가 근거를 갖습니다. 기록 없는 배포는 완료로 보지 않습니다.

11인수인계 경계와 다음 담당

운영자가 끝낼 수 있는 것과 다음 담당자에게 넘겨야 하는 것을 명시합니다. 경계가 없으면 보류 항목과 비범위 작업이 조용히 배포에 섞입니다. 다음 행동은 아래 순서로 진행합니다.

운영자 → 릴리스 책임자

최종 판정 요청

HOLD·CAPTURE_REQUIRED가 남은 검증 항목을 묶어 책임자에게 넘깁니다. 운영자는 "배포 완료"를 단독 선언하지 않습니다.

운영자 → 당직

관찰 인계

배포 후 1시간 관찰 구간을 당직에게 인계합니다. 롤백 트리거 조건과 직전 안정 태그를 함께 전달합니다.

운영자 → 제품팀

화면 근거 요청

후보 생성 모달, 오류율 임계선, 롤백 모달의 실제 화면 캡처를 제품팀에 요청해 CAPTURE_REQUIRED를 해소합니다.

  1. §10의 CAPTURE_REQUIRED 2건(후보 생성 모달·오류율 임계선)과 HOLD 1건의 실제 화면 캡처를 확보한다.
  2. 확보한 캡처로 §4 인벤토리의 "화면 근거" 열을 모두 확정 상태로 갱신한다.
  3. §9 안전 fixture 롤백 연습을 신규 운영자가 1회 완료했는지 책임자가 확인한다.
  4. 릴리스 책임자가 §10 검증 게이트를 최종 판정하고, PASS면 프로덕션 100% 승격을 승인한다.
