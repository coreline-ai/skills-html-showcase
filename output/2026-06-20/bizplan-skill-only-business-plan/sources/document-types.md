# 11 — 문서 유형별 변환 프로토콜

> 진입 조건: `business-core.yaml` 확정 + 초안 섹션 작성(`references/10-drafting.md`) 시작.
> 핵심 원칙(7대 규칙 외): **하나의 코어, 네 개의 변환.** 같은 `business-core.yaml`을 정부지원·R&D·투자덱·제안서로 변환할 때 새 사실을 만드는 게 아니라, **앞세울 것과 줄일 것을 바꾼다.** PRD §18 기반.

문서 유형 게이트(SKILL.md 발동 3번)에서 확정한 유형에 따라 이 문서의 해당 절을 적용한다. 수치·고객·시장은 모든 유형에서 동일하다(7대 규칙 #7). 달라지는 것은 **순서, 분량 비중, 강조점**뿐이다.

---

## 0. 변환의 3원칙

1. **코어 불변.** TAM/SAM/SOM·가격·고객수·매출·인력·일정은 유형이 달라도 같은 값을 쓴다. 유형별로 숫자가 달라지면 그것은 변환이 아니라 조작이다.
2. **강조 재배치.** 각 유형의 평가 논리에 맞춰 `business-core.yaml`의 어떤 블록을 앞·크게 두고 어떤 블록을 뒤·작게 둘지 결정한다.
3. **누락이 아니라 압축.** 어떤 유형에서 비중을 줄이는 항목도 삭제하지 않는다. 1~2문장으로 압축해 남긴다(예: 투자덱의 사업비 세부는 부록 1장으로).

---

## 1. 정부지원사업 (창업/중소기업 지원)

**평가 논리:** 문제를 정확히 인식했고, 실제로 해낼 수 있으며, 정책 목적에 맞고, 고용·매출 성과로 이어지는가. 균형 + 사업성(PRD §20 시장성 15점).

**강조(앞·크게) ↔ 코어 매핑**

| 평가 중점 | business-core 블록 | 부각 포인트 |
|---|---|---|
| 문제 인식 | `problem` | 빈도·심각도·현재 대안의 한계, 현장 근거 |
| 실현 가능성 | `solution`, `technology` | 현재 구현 단계, 프로토타입/PoC 증거 |
| 성장 전략 | `market`, `business_model` | SAM→SOM 경로, 고객 확보 첫 10명 |
| 팀 구성 | `team` | founder-market fit, 부족 역량 보완 계획 |
| 고용·매출 | `finance`, `impact` | 연차별 고용·매출 목표(전부 `[목표]` 태그) |
| 정책 부합성 | `impact.policy_alignment` | 공고 사업 목적과 1:1 연결 |
| 사업비 적절성 | `finance.use_of_funds` | 항목별 산식, 공고 사업비 기준 준수 |

**줄이는 것:** 특허 청구항 상세(요약 + 부록), 논문 벤치마크 표(핵심 1개만).

**권장 목차 골격**
1. 사업 개요 / 과제명
2. 문제 인식 (배경·필요성, 현황·문제점)
3. 실현 가능성 (제품·기술, 개발 현황, 검증)
4. 성장 전략 (시장·고객, 사업모델, 진입·확대)
5. 경쟁력·차별성
6. 팀 구성·보유 역량
7. 사업 추진 일정·예산(사업비)
8. 기대 성과 (고용·매출·정책 기여)

## 2. R&D 기술개발·산학협력 과제

**평가 논리:** 기술적 난제가 진짜 어렵고, 기존 기술로 안 되는 이유가 분명하며, 정량 목표와 검증 계획이 구체적이고, 끝나면 사업화·파급이 되는가. 기술성·특허/논문 근거 중점.

**강조 ↔ 코어 매핑**

| 평가 중점 | business-core 블록 | 부각 포인트 |
|---|---|---|
| 기술적 난제 | `technology.technical_challenge` | 왜 어려운지, 누가 못 풀었는지 |
| 기존 기술의 한계 | `research.research_gap`, `competition` | 논문·특허로 입증한 공백 |
| 정량 목표 | `technology.target_performance` | 수치 목표 + 측정 조건(`[목표]`) |
| 연구 방법 | `solution.core_mechanism`, `execution` | 단계별 연구개발 방법론 |
| 검증 계획 | `technology.verification_method` | 평가 지표·검증 환경·성공 기준 |
| 특허·논문 | `intellectual_property`, `research` | claim-chart, paper-evidence-table |
| 사업화·파급 | `business_model`, `impact` | 종료 후 상용화 경로, TRL 상승 |

**줄이는 것:** 투자 트랙션 서사(피치 톤), 마케팅 채널 상세.

**핵심 게이트:** 특허는 법적 상태·독립 청구항 분석 필수, 초록만으로 권리범위 판단 금지. 논문은 조건 다른 벤치마크 단순 비교 금지, 연구 성능 ≠ 제품 성능(7대 규칙 #6, Gate 5 — `references/12-verification.md`).

**권장 목차 골격**
1. 과제명·연구개발 목표
2. 기술 개발의 필요성 (난제·기존 기술 한계)
3. 국내외 기술·특허·논문 동향
4. 연구개발 내용·방법 (단계별)
5. 정량 목표·평가 지표·검증 계획
6. 추진 체계·일정 (산학 역할 분담)
7. 연구개발비 (비목별)
8. 사업화 방안·기대 파급효과

## 3. 투자 피치덱 (IR)

**평가 논리:** 큰 문제인가, 왜 당신들이, 왜 지금인가, 얼마나 큰 시장이고 얼마나 빠르게 크는가. 시장성·트랙션 중점. 텍스트가 아니라 **슬라이드** 단위로 사고한다.

**강조 ↔ 코어 매핑**

| 슬라이드 | business-core 블록 |
|---|---|
| 큰 문제 | `problem` |
| 독특한 해결책 | `solution`, `competition.differentiation` |
| 왜 지금 | `research`, 정책/시장 변화(리서치) |
| 시장 규모 | `market` (TAM/SAM/SOM 산식) |
| 성장 지표·트랙션 | `traction` (전부 `[사실]`만) |
| 사업모델 | `business_model` |
| 경쟁우위 | `competition`, `intellectual_property` |
| 팀 | `team.founder_market_fit` |
| 투자금 사용처 | `finance.use_of_funds` |

**줄이는 것:** 사업비 세부 비목(요약 1장), 특허 청구항 분해(IP 1장으로 요약), 서식·행정 요건(투자덱엔 없음).

**피치덱 10~12장 권장 구성**
1. 표지 (한 줄 정의 + 임팩트)
2. 문제 (큰 문제, 고객 고통)
3. 해결책 (제품, 한 화면 데모)
4. 왜 지금 (시장·기술·규제 변곡점)
5. 시장 규모 (TAM/SAM/SOM, 산식 명시)
6. 사업모델 (가격·수익 구조)
7. 트랙션 (매출·사용자·계약 — 사실만)
8. 경쟁·차별성 (포지셔닝 맵)
9. 기술/IP 해자
10. 팀 (founder-market fit)
11. 재무 전망 (3~5년, 가정 명시)
12. 투자 요청 (금액·사용처·마일스톤)

> 데이터 슬라이드는 숫자만 던지지 말고 "그래서 무슨 뜻인지" 한 줄을 붙인다. 트랙션은 부풀리지 않는다 — 없으면 `[확인 필요]`나 파일럿 단계로 정직하게.

## 4. 기업·공공기관 제안서

**평가 논리:** 우리 문제를 정확히 이해했고, 무엇을 어떻게 해줄지 명확하며, 책임 주체·일정·품질·비용이 분명하고, 비슷한 일을 해봤는가. 수행능력·신뢰 중점.

**강조 ↔ 코어 매핑**

| 평가 중점 | business-core / 산출물 |
|---|---|
| 고객의 현재 문제 | `problem`, `customer` (발주처 관점으로 재서술) |
| 제안 범위 | `solution.key_features`, `use_cases` |
| 수행 방법 | `solution.core_mechanism`, `execution` |
| 역할·책임 | `team` (RACI 표) |
| 일정 | `execution.roadmap` (WBS·마일스톤) |
| 품질관리 | `technology.verification_method` (QA 계획) |
| 비용 | `finance` (산출 내역) |
| 유사 실적 | `traction.contracts`, `pilots`, `partnerships` |

**줄이는 것:** 시장 규모 서사(제안서는 시장이 아니라 발주처 한 곳이 고객), 투자·트랙션 톤.

**권장 목차 골격**
1. 제안 개요 (발주처 요구 이해)
2. 현황 분석·문제 정의 (발주처 관점)
3. 제안 범위·목표
4. 수행 방안·방법론
5. 추진 체계·역할 분담 (조직·RACI)
6. 추진 일정 (WBS)
7. 품질·위험 관리 방안
8. 투입 인력·비용 (산출 내역)
9. 유사 수행 실적
10. 기대 효과

## 5. 변환 적용 체크 (17단계)

- [ ] 확정 문서 유형에 맞는 절(§1~§4)을 적용했는가?
- [ ] 강조 블록을 **앞·크게**, 비중 낮은 블록을 **압축(삭제 아님)**했는가?
- [ ] 모든 유형에서 수치가 `business-core.yaml`과 동일한가? (7대 규칙 #7, Gate 4)
- [ ] 권장 목차 골격이 공식 서식(`template-structure.yaml`)과 충돌하지 않는가? 충돌 시 공식 서식 우선.
- [ ] 트랙션·성능을 유형 톤에 맞춰 부풀리지 않았는가? (사실/목표 태그 유지)
- [ ] 같은 사업의 다른 유형 문서가 이미 있으면, 코어 변경분이 모두 반영됐는가?

> 변환은 "다시 쓰기"가 아니라 "재배치"다. 하나의 사업 논리가 네 개의 평가 렌즈를 통과하도록 순서와 비중만 바꾼다.
