# 12 — 검증·반복 시스템 + 평가위원 시뮬레이션

> 진입 조건: `business-plan-draft.docx` 초안 통합 완료(18단계 진입).
> 산출물: `09-audit/evaluator-{admin,tech,biz,skeptic}.md`, `09-audit/scorecard.md`, `09-audit/revision-log.md`.
> 이 문서는 Gate 5·7의 실행 프로토콜이다. PRD §19(게이트), §20(배점), §30(완료기준) 기반.

검증은 "맞춤법 보기"가 아니다. **평가위원이 실제로 던질 질문을 미리 던지고, 반론을 견디게 고치는 것**이다. 마인드셋: "이 주장은 회의적 반대 평가자의 질문을 견디는가?"

## 1. 7개 게이트 통합 체크리스트 (Gate 0 ~ Gate 7)

각 게이트는 다음 단계로 넘어가기 전 통과해야 한다. 실패 게이트부터 재실행하고 처음부터 다시 만들지 않는다(PRD §26).

### Gate 0 — 공고와 자료 수집 (`references/01-notice-analysis.md`)
- [ ] 공고 본문 확보 (`00-source/notice/`)
- [ ] 필수 첨부파일 확보 또는 **누락 목록 명시**
- [ ] 최신/구버전 구분
- [ ] 평가 배점표·서식 제약 추출 완료

### Gate 1 — 심층 인터뷰 (`references/02-interview-engine.md`)
- [ ] 핵심 13항목(고객·구매자·문제 빈도/심각도·대안·해결 방식·핵심 기능·기술 난제·사업모델·차별성·트랙션·팀·자금·목표) 구체화
- [ ] 모호어("많은/효율적/혁신적/AI 활용/글로벌") 잔존 0
- [ ] 미확정 항목은 모두 `[확인 필요]`로 분류

### Gate 2 — 리서치 (`references/04~06`)
- [ ] 공식 자료(정부·공시·특허청·학술) 포함
- [ ] 국내외 시장·경쟁 제품 조사
- [ ] 특허 조사(법적 상태·청구항) + 논문 조사(재현성·TRL)
- [ ] **부정적 근거·실패 사례·경쟁 강점 포함**(출처 편향 방지)
- [ ] 모든 핵심 수치에 출처·기준일·접근일 기록(`source-index.xlsx`)

### Gate 3 — 사업 논리
- [ ] 사슬에 단절 없음: 문제 → 해결책 → 제품 → 기술 → 시장 → 수익모델 → 실행 → 예산
- [ ] 각 연결의 "왜"가 근거로 떠받쳐짐

### Gate 4 — 숫자
- [ ] TAM/SAM/SOM·가격·고객수·매출·비용·인력·일정·사업비가 코어·엑셀·문서 전체에서 **동일**
- [ ] 불일치 0건

### Gate 5 — 특허·논문
- [ ] 특허 법적 상태 확인, 독립 청구항 분석(초록만으로 권리범위 판단 금지)
- [ ] 위험 특허 = 변리사 검토 대상 표시
- [ ] 논문: 조건 다른 성능 단순 비교 금지, 연구 환경 ≠ 제품 성능, 최신 연구 상충 확인

### Gate 6 — 서식
- [ ] 목차 누락 없음, 지정 분량 준수
- [ ] 폰트·글자 크기·여백 준수
- [ ] 공란 없음, 표·그림 제목, 서명·첨부서류

### Gate 7 — 평가위원 시뮬레이션
- [ ] 4역할 채점 완료 → `scorecard.md` 통합 (아래 §2~§3)

## 2. 평가위원 4역할 시뮬레이션

PRD §19 Gate 7의 4역할. 각 역할은 **독립된 인격**으로 초안을 읽고 질문을 던진 뒤 채점한다. `Task` 도구로 4역할 **병렬 dispatch** 가능(아래 §5). 각 역할 산출은 `09-audit/evaluator-<role>.md`.

### 역할 산출 파일 공통 구조

```markdown
# 평가위원 시뮬레이션 — <역할명>
## 1. 총평 (2~3문장)
## 2. 질문 리스트 (각 질문 → 초안에서 답이 되는 위치 또는 "답 없음")
## 3. 영역별 점수 (PRD §20 배점표 기준, 근거 1줄씩)
## 4. 치명적 결함 (있으면) — 사실 오류 / 무출처 통계 / 숫자 불일치
## 5. 수정 요구 (우선순위 순, revision-log로 넘길 항목)
```

### 2.1 행정·서식 평가자 → `evaluator-admin.md`
공고 요건·서식 준수를 본다. "선정 이전에 접수 자격이 되는가."
1. 신청 자격(업력·매출·업종·지역)을 충족함을 문서가 입증하는가?
2. 공식 목차 항목이 하나도 빠지지 않았는가? 순서가 서식과 같은가?
3. 지정 분량(페이지·글자 수)·폰트·여백을 지켰는가?
4. 필수 제출 서류·서명·첨부 목록이 체크리스트와 일치하는가?
5. 모든 표·그림에 제목·단위·기준일·출처가 있는가? 공란은 없는가?
6. 사업비 항목이 공고 사업비 기준(인건비 비율·장비 한도 등)에 맞는가?
7. 제외·중복 지원 제한에 걸리지 않는가?

### 2.2 기술·산업 전문가 → `evaluator-tech.md`
기술이 진짜인지, 구현 가능한지를 본다. "이 분야를 아는 사람이 보면 들통나는 곳."
1. 기술적 난제가 진짜 어려운가, 아니면 일반 개발 업무인가?
2. 정량 목표 성능의 측정 조건(데이터셋·하드웨어·지표)이 명시됐는가?
3. 연구 환경 성능을 제품 성능처럼 쓴 곳은 없는가?(7대 규칙 #6)
4. 청구항 분석이 초록이 아닌 독립 청구항 기준인가? 위험 특허에 변리사 검토 표시가 있는가?
5. 조건이 다른 벤치마크를 단순 비교한 곳은 없는가?
6. 현재 구현 단계(TRL)와 목표 단계의 간극을 기간·인력으로 메울 수 있는가?
7. "AI 활용"이 차별점으로 둔갑한 곳은 없는가?

### 2.3 사업성 평가자 → `evaluator-biz.md`
돈이 되는지, 시장이 있는지, 실행되는지를 본다.
1. TAM/SAM/SOM 산식이 검증 가능한가, 위에서 아래로 추정만 했나?
2. 가격·단위 경제성(CAC/LTV/마진)에 근거가 있는가?
3. 첫 10명 고객을 만날 구체적 경로가 있는가?
4. 매출 추정의 전제 가정이 명시됐고 보수적인가?
5. 경쟁사가 가격을 낮추거나 따라오면 어떻게 되는가?
6. 사업비 대비 기대 성과(고용·매출)가 합리적인가?
7. 트랙션이 사실인가, 목표를 사실처럼 쓴 곳은 없는가?

### 2.4 회의적 반대 평가자 → `evaluator-skeptic.md` (가장 날카롭게)
"왜 이 사업이 안 될 것인가"를 입증하려는 역할. 가장 가혹하게 공격한다.
1. 이 문제가 정말 고객이 돈 내고 풀 만큼 아픈가, 아니면 "있으면 좋은" 수준인가?
2. 고객이 **아무것도 안 하는** 선택지가 가장 강한 경쟁자 아닌가?
3. 핵심 통계 중 출처가 약하거나 자사에 유리한 자료만 고른 곳은?
4. 기술 차별성이 6개월 안에 경쟁사가 복제 가능한 것 아닌가?
5. "정확도 91%" 같은 수치가 현장에서 재현 안 되면 사업 전체가 무너지지 않는가?
6. 팀이 이 사업을 실제로 끝까지 할 역량·이력이 있는가, 부족 역량을 숨겼는가?
7. 가장 낙관적인 가정 3개가 동시에 틀리면 사업은 어떻게 되는가?
8. 이 문서에서 가장 약한 한 곳은 어디이고, 평가위원이 그곳만 파고들면 떨어지는가?

> 회의적 평가자가 답하지 못하게 만든 질문은 곧 `revision-log.md`의 최우선 수정 항목이다.

## 3. 배점표 → `scorecard.md` (PRD §20)

4역할의 영역별 점수를 통합한다. 10개 영역, 총 100점.

| 영역 | 배점 | 주 평가 역할 |
|---|--:|---|
| 공고 및 평가 기준 부합성 | 10 | admin |
| 문제 정의와 증거 | 10 | skeptic·biz |
| 해결책과 제품 적합성 | 10 | tech·biz |
| 기술성과 구현 가능성 | 10 | tech |
| 특허·논문 기반 기술 근거 | 10 | tech |
| 시장성과 사업모델 | 15 | biz |
| 경쟁력과 차별성 | 10 | biz·skeptic |
| 실행 계획과 예산 | 10 | biz·admin |
| 팀 역량 | 5 | skeptic |
| 수치·출처·서식 완성도 | 10 | admin |
| **합계** | **100** | |

```markdown
|---|--:|--:|--:|--:|--:|--:|--:|

| ... |
| 합계 | 100 | | | | | 86 | — |

## 미통과 영역 → revision-log 항목 번호
```

## 4. 반복 수정 루프 + `revision-log.md`

### 루프
```text
초안 → 4역할 채점(scorecard) → 미통과?
  → revision-log에 결함 기록 → 해당 섹션·코어 수정 → 재채점
  → 통과 시 종료 (최대 N=3 라운드 권장)
```
- 코어(`business-core.yaml`)가 수정되면 파생 문서·엑셀·덱을 모두 갱신한다(7대 규칙 #7).
- 3라운드 안에 못 넘기면 남은 결함을 `[확인 필요]`로 명시하고 사용자에게 보고(자동 확정 금지, PRD §29 과도한 자동화 대응).
- 자동 검증 보조: `scripts/validate_project.py bizplan-<slug>/` (서식·공란·숫자 일관성 기계 점검).

### `revision-log.md` 기록 방식

```markdown
## 라운드 1
| # | 결함(역할) | 위치 | 유형 | 조치 | 상태 |
|---|---|---|---|---|---|
| 1 | 시장규모 산식 출처 없음 (biz) | 04-성장전략 | 무출처 통계 | source-index #19 연결 | 완료 |
| 2 | "정확도 91%" 현장 재현 미검증 (skeptic) | 03-기술 | 사실/목표 혼동 | [목표] 태그+PoC 분리 | 완료 |
| 3 | 매출 2030년 수치 덱과 불일치 (admin) | finance | 숫자 불일치 | 코어 기준 통일 | 완료 |
```
유형은 `중대 사실 오류 / 무출처 통계 / 숫자 불일치 / 논리 단절 / 서식` 중 하나로 분류한다.

## 5. 4역할 병렬 dispatch (Task 도구)

검증은 4역할이 서로 독립이므로 단일 메시지에 `Task` 4개를 동시 호출한다(SKILL.md §병렬 리서치 패턴 동일).

각 역할 Task에 **반드시 전달**:
1. `business-plan-draft.docx`(또는 `08-draft/` md 묶음) 경로
2. `business-core.yaml`·`source-index.xlsx`·`evidence-ledger.xlsx` 경로
3. PRD §20 배점표 + 해당 역할의 질문 리스트(§2)
4. 7대 절대 규칙
5. 산출 파일 경로(`09-audit/evaluator-<role>.md`)

메인은 4개 결과를 받아 `scorecard.md`로 통합·판정한다. 서브에이전트가 없는 환경이면 메인이 4역할을 순차로 1인 다역 수행한다(결과 동일, 속도만 차이).

## 6. 완료 기준 14항목 (PRD §30) — 21단계 최종 체크

프로젝트 완료 선언 전 `10-final/submission-checklist.md`에서 전수 확인한다.

- [ ] 1. 공고와 첨부파일 분석 완료
- [ ] 2. 사용자 심층 인터뷰 완료
- [ ] 3. 과제명이 사업 범위를 반영
- [ ] 4. 시장·경쟁·기술 리서치 완료
- [ ] 5. 주요 특허의 권리 상태·청구항 분석 완료
- [ ] 6. 핵심 논문·연구 동향 분석 완료
- [ ] 7. `business-core.yaml` 확정
- [ ] 8. 공식 목차의 모든 항목 작성
- [ ] 9. 모든 핵심 통계에 출처 있음
- [ ] 10. 사실·추정·가정·목표 구분됨
- [ ] 11. 숫자·일정이 문서 전체에서 일치
- [ ] 12. 필요한 표·다이어그램 삽입됨
- [ ] 13. 평가위원 시뮬레이션 통과 (scorecard ≥ 85, 5기준 만족)
- [ ] 14. 제출용 파일과 체크리스트 생성됨

> 14항목 전부 체크되어야 "완료"다. 하나라도 미달이면 미달 항목을 사용자에게 명시 보고하고, 사용자 확인 없이 확정 문장으로 전환하지 않는다(PRD §29).
