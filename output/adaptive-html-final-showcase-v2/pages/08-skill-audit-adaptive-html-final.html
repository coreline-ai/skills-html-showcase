1. 목적과 정체성

이 스킬은 무엇을 하는 도구이고, 어떤 계보에서 왔는가

adaptive-html-final은 URL·PDF·텍스트·이미지 추출문·메모·기술 자료·블로그 초안·SKILL.md/.skill 패키지를 입력받아, 한국어 editorial HTML 산출물을 만드는 다중 모드 생성 스킬이다. 단순 HTML 변환기가 아니라 "입력 분석 → 사실/해석/추론 분리 → 독자 수준 판단 → 모드 선택 → 레이아웃 선택 → 렌더링 → 품질검수"라는 파이프라인을 실행하는 라우터형 스킬이다.

정체성은 명확하다. 스킬 본문(SKILL.md §0 Identity)은 자신을 html-for-beginners → adaptive-html-blog-writer → adaptive-html-blog-writer-v2 → adaptive-html-learning-ultimate 계열을 하나로 합친 최종 통합본으로 규정한다. 뼈대는 ultimate의 13개 모드 라우터·레이아웃·평가 체계이고, 거기에 blog-writer의 블로그/SEO/플랫폼/박스 선택 상세 규칙을 references로 흡수했다.

핵심 정의 모드 라우터(Mode Router) 입력과 트리거 문구를 보고 13개 모드 중 하나를 우선순위로 고른 뒤, 그 모드 전용 레이아웃 골격과 필수 블록을 채우는 분기 장치. 여러 트리거가 겹치면 Priority 숫자가 낮은(=우선순위가 높은) 모드를 택하고, 사용자가 모드를 명시하면 그 지시가 최우선이다.
한 줄 비유

이 스킬은 만능 프린터가 아니라 편집국 데스크에 가깝다. 같은 원고(입력)라도 "초보 독자용 입문서"로 갈지 "전문가 리포트"로 갈지 "검색 유입용 블로그"로 갈지를 먼저 판정한 뒤, 그 지면에 맞는 판형(레이아웃)과 구성 요소(필수 블록)를 배치한다. 감사 모드(skill_audit)는 그 데스크가 자기 자신을 교열하는 자리다.

감사 관점에서 중요한 점은, 이 스킬이 자기 감사 기준을 내장한다는 것이다. references/skill-audit-system.md는 12개 진단 기준(목적 명확성, 트리거 정확성, 입력/출력 명확성, 워크플로우 실행 가능성, 금지 규칙·안전 경계, 실패 대응, 품질 게이트, 완료 기준, 예시 프롬프트, 패키지 구조, progressive disclosure 설계, assets/references/scripts 분리)과 산출물 형태(Executive diagnosis → Score table → Line/section findings → 개선 우선순위 → 개선본/패치 계획 → 검증 체크리스트)를 규정한다. 이번 리포트는 그 기준표를 스킬 자신에게 그대로 적용한 결과다.

감사 결론을 먼저 말하면: 이 스킬은 "동작 결함"이 아니라 "정합성·테스트 커버리지"를 다듬는 단계에 있다. v4.1.0 패치 노트가 스스로 밝히듯, 패치 대상 19건은 모두 medium·low였고 동작 결함은 0건이었다.

2. 진단 요약 점수

스킬 내장 0~5점 루브릭으로 본 항목별 점수와, 트리거·워크플로우 정밀 점수

점수는 스킬 자신의 references/eval-rubric.md(7개 항목, 각 0~5점, 합 35점 만점)를 적용한 정성 평가다. 루브릭 규정상 총점 28점 이상이면 통과, 24~27점은 보완 후 통과, 23점 이하는 재작성이다.

Mode Fit · 5/5

요청-모드 일치. 13개 모드가 우선순위 표와 tie-breaker(교육↔공개글, GitHub Pages 단독→article)까지 정의되어 모호성이 거의 없다.

Layout Fit · 5/5

13개 모드 ↔ 13개 레이아웃 골격이 manifest에서 {id, layout} 객체로 1:1 매핑. recipes 13/13 완비.

Design DNA · 5/5

theme/components/visual-components/layouts/print의 계층형 CSS가 명확. v4.1.0에서 미정의 클래스 39개를 정의해 차집합 0 달성.

Content Depth · 4/5

모드별 필수 블록·전문가 모드 최소 행수 규정 등 깊이 강제 장치가 있으나, 깊이 보장은 여전히 실행 시 판단에 의존.

SEO / A11y · 5/5

skip link + id="main" 13/13, 단일 h1, AA 대비·focus-visible·reduced-motion, accessibility-checklist 회귀 가드 신설.

Factuality · 4/5

"확인되지 않은 사실 단정 금지", TODO_CHECK 분리 원칙이 명문화. 다만 강제는 게이트 체크리스트와 작성자 규율에 의존.

Source Handling · 4/5

출처 6개 초과 나열 금지, source-note/source hub 정리 규칙 존재. 출처 허브 경로는 일반화 표기로 교정됨(L6).

총점 · 32 / 35

판정: 통과(Pass). 28점 기준선을 충분히 상회. 감점은 모두 "런타임 판단 의존" 성격으로, 스킬 구조 결함이 아니다.

2-1. 트리거 점수 — 4.6 / 5

트리거 설계는 이 스킬의 강한 부분이다. description에 "반드시 사용해야 하는 트리거" 목록이 모드군별로 명시되어 있고(예: "HTML로 정리", "블로그 작성", "SEO 글", "티스토리/벨로그/네이버/워드프레스용", "스킬 분석", "SKILL.md 개선", "한 줄 한 줄 분석"), §3 Mode Router 표가 각 모드의 트리거 키워드와 레이아웃을 한 줄씩 짝지어 둔다.

잘 된 점 충돌 해소 규칙이 실재한다

"여러 트리거 동시 감지 → Priority 우선", "사용자 명시 지정 → 그 지시 우선", 그리고 교육↔공개글이 겹칠 때 education_html 우선, GitHub Pages 단독 언급 시 article_html 선택이라는 tie-breaker가 §3 끝에 한 줄로 추가되어 있다.

감점 사유 키워드 기반 분기의 본질적 한계

트리거가 자연어 키워드 매칭에 의존하므로, "이 문서를 잘 정리해줘"처럼 모드 단서가 약한 요청에서는 라우팅이 작성자 해석에 좌우될 수 있다. 의도 확인 질문(clarify) 단계가 워크플로우에 명시적으로 들어가 있지 않다. -0.4점.

2-2. 워크플로우 점수 — 4.7 / 5

워크플로우(SKILL.md §6)는 Step 1 요청 이해 → Step 2 소스 처리 → Step 3 사실/해석/추론 분리 → Step 4 콘텐츠 기획 → Step 4.5 비주얼 브리프 → Step 5 HTML 렌더링 → Step 6 비주얼 구성 게이트로 이어진다. 각 단계가 입력/판단/산출을 분명히 가지며, Step 1은 JSON 스키마(goal·mode·audience·platform·format·source_type·verification_need·layout·visual_need·visual_strategy)로 내부 상태를 구조화한다.

실행 가능성 근거

Step 4의 모드별 필수 블록 목록이 13개 모드 전부에 대해 구체적으로 적혀 있어("skill_audit: purpose, trigger score, workflow score, line/section diagnosis, improved skill" 등) 빈 골격을 채우는 작업이 결정적(deterministic)으로 정의된다. Step 4.5는 모드별 기본 비주얼 템플릿 매핑까지 표로 제공한다.

감점 사유 개선본 산출의 자동 검증 부재

skill_audit 모드는 "improved skill(개선본)"을 산출하도록 요구하지만, 그 개선본이 원본보다 실제로 나아졌는지 자동 회귀 검증하는 절차는 워크플로우에 들어 있지 않다. accessibility/quality 체크리스트는 출력 HTML용이지 개선본 SKILL.md용이 아니다. -0.3점.

4. 강점과 리스크

감사 점수를 의사결정용으로 압축한다

강점 (유지할 것)

  • 모드↔레이아웃 1:1 정합. 라우터 13개 모드, manifest 13개 {id, layout} 객체, recipes 13/13이 서로 어긋나지 않는다. v4.1.0의 M3이 이 정합을 단일화했다.
  • 접근성이 회귀 가드로 고정. id="main" 13/13, 단일 h1, 외부 JS 0, focus-visible를 grep 기대값으로 자동검증하는 체크리스트가 존재해, 향후 변경에도 접근성이 깨지면 즉시 잡힌다.
  • 디자인 토큰 차집합 0. 레이아웃이 참조하는 모든 CSS 클래스가 정의되어 "스타일 누락으로 깨지는 골격"이 구조적으로 제거됐다.
  • 자가 감사 기준 내장. 스킬이 자기 평가 루브릭과 출시 게이트를 분리 보유(eval-rubric=정성 0~5, quality-gates=출시 가부, Blog Score=블로그 전용)해 평가 목적이 혼동되지 않는다.

영향 중 · 발생 중

R1 — 라우팅 모호성. 모드 단서가 약한 요청에서 키워드 매칭이 빗나갈 수 있다. clarify 단계가 워크플로우에 없어, 잘못된 모드로 끝까지 진행될 여지가 있다.

영향 중 · 발생 낮음

R2 — 개선본 검증 공백. skill_audit이 산출하는 개선본 SKILL.md가 원본 대비 실제로 개선됐는지 자동 회귀하는 절차가 없다.

영향 중 · 발생 낮음

R3 — 사실성 강제 한계. "확인 필요 단정 금지"는 원칙·체크리스트로만 강제된다. 작성자 규율에 의존하므로, 긴 본문에서 추론이 사실처럼 새어 나갈 위험이 잔존한다.

영향 낮음 · 발생 낮음

R4 — 실패 대응 폴백 약함. 입력 불완전 시 진행 원칙은 있으나, 모드 판정 실패·근거 전무 시 "어떤 최소 산출물로 안전 종료하는가"의 분기가 명시적이지 않다.

영향 낮음 · 정보성

R5 — 문서-파일 재검증 갭. CHANGELOG의 "13/13", "39개 정의", "차집합 0"은 패치 당시 검증값이다. 이후 변경 시 파일 단위 재측정 없이는 수치를 단정하지 않는 편이 안전하다.

5. 개선 권고

우선순위 로드맵 — 동작 결함이 아닌 정합·강제력 강화 중심

P0 · 라우팅 안전성

의도 확인(clarify) 분기를 Step 1에 명문화. 모드 단서 신뢰도가 임계 이하일 때 1~2개 확인 질문을 던지거나, 가장 안전한 기본 모드로 폴백하고 그 가정을 산출물 상단에 표시하도록 규칙화한다. R1·R4를 동시에 완화.

P1 · 자가 개선 검증

개선본 회귀 게이트 추가. skill_audit이 개선본 SKILL.md를 낼 때, accessibility/quality 체크리스트 외에 "개선본도 13모드 라우터·필수 블록·금지 규칙을 보존하는가"를 자동 점검하는 미니 게이트를 워크플로우 Step 6 이후에 둔다. R2 대응.

P1 · 사실성 강제

TODO_CHECK 가시화 의무화. 긴 본문에서 추론/미확인 주장이 있으면 본문 내 표식(예: "확인 필요" 인라인 마크)을 남기고, source-note에 "검증되지 않은 주장 N건" 요약을 두도록 게이트화한다. R3 대응.

P2 · 수치 신뢰성

패키지 전수 점검 스크립트 운영. CHANGELOG의 "13/13·39개·차집합 0" 같은 수치를 릴리스마다 파일 단위로 재측정해 문서값과 동기화한다. 이미 존재하는 accessibility grep 가드를 recipes/CSS 차집합까지 확장하면 된다. R5 대응.

권고 요약: 이 스킬에 필요한 것은 재작성이 아니라 "강제력 보강"이다. 원칙으로만 존재하는 안전장치(clarify, 사실성, 개선본 검증, 수치 동기화)를 워크플로우 단계나 자동 게이트로 끌어올리면, 현재의 32/35 점수는 실제 산출물 품질의 하한선으로 굳어진다.

6. 종합 판정과 재감사 트리거

출시 가부와 다음 감사 시점

종합 판정: 통과 (32 / 35). 스킬 내장 루브릭의 28점 통과선을 충분히 상회한다. 12개 감사 기준 중 11개 양호, 1개(실패 대응) 보완 권장. 동작 결함은 근거 문서 기준 0건이며, 잔여 이슈는 모두 medium·low 등급의 정합성·강제력 항목이다.

다음 재감사를 부르는 조건

  • 모드 라우터에 14번째 모드가 추가되거나, manifest의 modes/layouts/recipes 수가 13에서 변동될 때 — 1:1 정합 재확인 필수.
  • Visual Template System(v4.2.0) 사용이 일반화되어, SVG 8000×6000·alt·figcaption·캔버스 잘림 게이트가 실제 산출물에서 빈번히 적용될 때.
  • P0~P1 권고(clarify·개선본 검증·사실성 강제)를 반영한 패치가 나오면, 그 즉시 본 리포트를 갱신해 점수를 재산정.

이 리포트는 스킬 자신의 skill_audit 모드 산출물 형태(Executive diagnosis → Score table → Section findings → 개선 우선순위 → 패치 계획 → 검증)를 그대로 따른다. 개선본 SKILL.md가 필요하면 P0·P1 권고를 패치 계획으로 확장해 다음 릴리스 노트에 반영하면 된다.
