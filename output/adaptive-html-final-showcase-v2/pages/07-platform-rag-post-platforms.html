RAG 글을 티스토리·벨로그·네이버·워드프레스로 변환하기

하나의 RAG vs Fine-tuning 원문을 네 플랫폼으로 옮길 때, 제목·문단 길이·코드 표현·태그·발행 체크리스트가 어떻게 달라져야 하는지 발행 관점에서 정리합니다.

1원문 요약

옮길 메시지를 먼저 고정합니다. 플랫폼이 바뀌어도 이 핵심은 변하지 않습니다.

원문은 "사내 문서 챗봇을 만들 때 RAG와 Fine-tuning 중 무엇을 먼저 선택할까"를 다룹니다. 결론은 단순합니다 — 대부분의 지식 질의응답은 RAG에서 출발하고, 형식·톤·반복 작업의 일관성이 필요할 때 Fine-tuning을 더한다는 것입니다. 이 글은 그 결론을 바꾸지 않고, 네 플랫폼의 문법과 독자 기대에 맞게 다시 포장하는 방법만 다룹니다.

  • RAG(검색 증강 생성): 최신·사내·도메인 지식을 검색해 프롬프트에 붙입니다. 문서가 자주 바뀌거나 출처를 밝혀야 할 때 강합니다.
  • Fine-tuning(미세조정): 응답의 형식·톤·말투를 모델에 학습시킵니다. "항상 이런 구조로 답하라" 같은 일관성 요구에 적합합니다.
  • 출발점: 사내 문서 챗봇은 거의 항상 RAG가 먼저입니다. 지식이 계속 바뀌기 때문입니다.
  • 함께 쓸 때: retrieval(검색이 맞는 문서를 가져왔는가) 평가와 generation(모델 응답이 정확한가) 평가를 분리해야 원인을 추적할 수 있습니다.
용어
Canonical URL (정규 URL)
같은 글이 여러 주소에 존재할 때 "이게 원본이다"라고 검색엔진에 알려주는 링크입니다. 한 원문을 여러 플랫폼에 올릴 때 중복 콘텐츠 패널티를 피하는 핵심 장치입니다.

2변환 원칙

복사-붙여넣기는 가장 빠르지만 가장 손해 보는 방법입니다. 같은 메시지를 네 가지 문법으로 다시 씁니다.

네 플랫폼은 에디터, 독자, 검색 유입 경로가 모두 다릅니다. 티스토리는 HTML을 받아주는 검색형 블로그, 벨로그는 Markdown 기반 개발자 커뮤니티, 네이버는 자체 에디터(스마트에디터 ONE)와 네이버 검색 생태계, 워드프레스/GitHub Pages는 직접 HTML과 메타데이터를 통제할 수 있는 자체 호스팅에 가깝습니다.

비유로 이해하기

하나의 강연 원고를 네 곳에서 발표한다고 생각해 보세요. 대학 세미나(티스토리)에서는 목차와 슬라이드 번호가 필요하고, 개발자 밋업(벨로그)에서는 코드 데모가 중심이며, 동네 주민 설명회(네이버)에서는 짧은 문장과 사진이 잘 통하고, 공식 백서 사이트(워드프레스)에서는 인용·각주·메타데이터가 필요합니다.

약점도 같습니다 — 한 원고를 그대로 네 곳에서 읽으면, 어느 자리에서도 딱 맞지 않습니다.

변환에서 바꾸는 축은 네 가지입니다. 제목(검색 의도), 본문 구조(문단 길이와 heading), 코드/시각 표현, 태그와 CTA. 본문의 사실과 결론은 그대로 두고 이 축만 조정합니다.

3플랫폼 카드 4종

각 카드에 플랫폼별 추천 제목, 본문 구조, 태그를 정리했습니다. 그대로 발행 초안의 출발점으로 쓸 수 있습니다.

본문 구조: 목차(앵커 리스트) → 정의 → 비교표 → 의사결정 기준 → FAQ. <h2>·<h3>·<ul>·<blockquote> 중심으로, HTML 모드에서 안정적으로 렌더링되는 태그만 씁니다. 문단은 3~5문장으로 짧게 끊습니다.

4변환 비교표

제목·구조·태그·발행 시 주의점을 한 표로 비교합니다. 문단 길이와 CTA만 바꿔도 독자 경험이 크게 달라집니다.

5흔한 실수와 권장 패턴

멀티 플랫폼 발행에서 가장 자주 깨지는 지점을 함정-해결 짝으로 정리했습니다.

함정
한 글을 그대로 네 곳에 복붙

같은 HTML을 벨로그와 네이버에 붙이면 코드블럭이나 표가 깨지고, 같은 제목을 네 곳에 쓰면 검색에서 서로 자기 글과 경쟁합니다. 중복 콘텐츠로 노출이 분산될 수 있습니다.

해결
제목은 다르게, 원본은 하나로

플랫폼마다 제목과 도입부를 다시 쓰고, 한 곳을 "원본"으로 정해 나머지에는 canonical 또는 본문 하단 출처 링크로 원본을 가리킵니다. 검색 신호를 한 곳에 모읍니다.

함정
네이버에 긴 H2/H3 트리와 코드블럭

네이버 독자는 짧은 문단과 이미지에 익숙합니다. 개발 블로그식 긴 heading 구조와 검은 코드블럭은 가독성과 체류 시간을 떨어뜨립니다.

해결
소제목 문장 + 이미지로 호흡 만들기

"RAG가 뭐냐면요" 같은 소제목 문장으로 끊고, 개념마다 도식 이미지를 한 장씩 넣습니다. 코드가 꼭 필요하면 캡처 이미지 또는 핵심 한 줄만 인용합니다.

반대로 워드프레스/GitHub Pages에서는 메타데이터를 직접 통제할 수 있다는 점을 적극 활용합니다. 아래는 Article 구조화 데이터의 형태 예시입니다. 동작 스크립트가 아니라 검색엔진에 글의 메타 정보를 알려주는 메타데이터입니다.

application/ld+json: { "@type": "Article", "headline": "RAG vs Fine-tuning: A Decision Guide", "author": {...}, "datePublished": "확인 필요", "mainEntityOfPage": "정규 URL" } — 실제 값은 발행 시점에 채웁니다.

datePublished, author, mainEntityOfPage(정규 URL) 등 확정되지 않은 값은 발행 시점에 채우고, 게시 후 구조화 데이터 검사 도구로 유효성을 확인하세요.

Publish Checklist

발행 전 체크리스트

  1. 원본·canonical 전략 확정 — 어느 플랫폼을 "원본"으로 둘지 정하고, 나머지에는 canonical 또는 출처 링크로 원본을 가리킵니다.
  2. 제목 4종 재작성 — 티스토리(검색형), 벨로그(문제 제기형), 네이버(경험형), 워드프레스(전문가형)로 제목을 각각 다시 씁니다.
  3. 표·코드 모바일 확인 — 표는 가로 스크롤되는지, 코드블럭이 잘리지 않는지 390px 폭에서 점검합니다.
  4. 벨로그 버전 Markdown 단순화 — 인라인 HTML/CSS를 걷어내고 펜스 코드블럭과 체크리스트로 바꿉니다.
  5. 네이버 버전 이미지 위치 표시 — 개념 도식·답변 캡처·요약 이미지의 삽입 지점을 본문에 명시합니다.
  6. 워드프레스 메타 점검 — slug, meta description(120~160자), 내부 링크, Article JSON-LD, canonical을 채우고 검증합니다.
  7. 플랫폼별 CTA 정렬 — 결론의 다음 행동을 독자에 맞춥니다(티스토리: 관련 글, 벨로그: 깃허브 링크, 네이버: 이웃추가, 워드프레스: 뉴스레터).
  8. 최신성 재확인 — 모델명·가격·정책 등 변하기 쉬운 정보는 발행 직전 한 번 더 확인합니다.
