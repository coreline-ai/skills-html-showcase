매뉴얼 결론

결론: 좋은 매뉴얼은 긴 설명서가 아니라 역할별 첫 성공 경로와 복구 경로입니다. 이 모드는 원문을 그대로 요약하지 않고, 사용자 역할·권한·위험·증상 기준으로 재배열합니다.

1Source & Version Snapshot

매뉴얼은 오래된 내용이 섞이기 쉬우므로 출처와 버전을 맨 앞에서 고정합니다.

FACT

입력 원문

제품 FAQ, 운영 노트, 릴리스 메모, 고객지원 답변을 출처 단위로 분리합니다. 이 예제의 입력은 6개 파일이며(§6 원문 보존 참조), 각 절차 옆에는 어느 원문 몇 번째 항목에서 왔는지 근거 위치를 남깁니다.

UNKNOWN

확인 불가

소유자·최신 버전·권한 정책이 불명확하면 본문에 섞지 않고 Source Limits에 둡니다. 예컨대 릴리스 메모는 2.4 기준인데 FAQ 스크린샷은 2.2 기준이라, 메뉴명이 다른 두 절차는 모두 버전 주석을 달았습니다.

OWNER

승인 필요

삭제/환불/권한 상승처럼 위험한 절차는 운영 책임자 검토 전 “초안”으로 표시합니다. 이 문서에서는 §4의 삭제/초기화, §9의 릴리스 전 점검 두 곳이 소유자 승인 대기 상태입니다.

2Reader Role Router · 역할별 독자 경로

같은 매뉴얼이라도 역할마다 필요한 첫 페이지가 다릅니다 — 역할별 진입점과 읽기 순서를 먼저 고정합니다.

처음 쓰는 사용자

첫 로그인, 기본 설정, 첫 성공 예제만 읽습니다. 권장 경로는 §3 첫 성공 경로 → §8 증상별 해결이며, 운영·권한 섹션은 건너뛰어도 첫 성공에 지장이 없습니다.

운영 담당자

권한, 모니터링, 장애 대응, 롤백 절차를 우선 확인합니다. 권장 경로는 §4 안전 조건 → §9 운영 런북 → §5 작업 레시피 순이며, 위험 작업 전 §1의 승인 대기 항목을 반드시 확인합니다.

고객지원

증상별 진단 질문과 안전한 안내 문구를 사용합니다. §8 트러블슈팅의 진단 순서를 그대로 따라가되, 권한 변경이 필요한 순간 §7 선택 기준에 따라 운영자에게 이관합니다.

3First Success Path · 첫 성공 경로

신규 사용자가 30분 안에 “되는 상태”를 한 번 경험하게 만드는 최단 경로 — 각 단계에 성공 기준과 실패 분기를 붙입니다.

STEP 1

접속 확인

계정, 조직, 권한을 확인하고 실패 시 지원 채널로 이동합니다. 성공 기준은 대시보드에 조직명이 표시되는 것이며, 조직이 보이지 않으면 §8의 첫 번째 증상 시나리오로 분기합니다.

STEP 2

기본 설정

필수 설정만 먼저 완료하고 선택 설정은 뒤로 보냅니다. 필수는 알림 채널·기본 권한 그룹·백업 대상 3개뿐이며, 원문 FAQ의 12개 설정 항목 중 나머지 9개는 첫 성공 이후로 미뤄도 된다는 것이 재배열의 핵심입니다.

STEP 3

검증

성공 화면, 로그, 알림 수신 여부로 완료를 확인합니다. 세 가지 중 알림 수신이 가장 자주 누락되므로, 테스트 알림 발송 버튼으로 즉시 확인하고 미수신 시 STEP 2의 알림 채널 설정으로 되돌아갑니다.

4Prerequisites / Safety · 사전조건과 안전

되돌리기 어려운 작업일수록 절차보다 “하기 전 조건”이 중요합니다 — 경고는 실행 버튼보다 앞에 둡니다.

권한·요금·데이터 삭제·외부 공유처럼 되돌리기 어려운 작업은 실행 전 경고와 복구 조건을 함께 둡니다. 원문에서는 경고가 절차 끝의 “주의” 박스에 몰려 있었지만, 재구성본은 각 위험 작업의 첫 단계 앞으로 옮겼습니다.

위험

삭제/초기화

백업과 승인자 확인 없이는 진행하지 않습니다. 복구 조건은 “백업 스냅샷 ID 확보 + 승인자 기록”이며, 둘 중 하나라도 없으면 이 절차는 시작 자체가 금지입니다.

권한

관리자 작업

역할이 맞지 않으면 화면이 다를 수 있으므로 권한을 먼저 확인합니다. 권한 부족 상태로 절반쯤 진행되는 절차가 가장 위험하므로, 시작 전에 관리자 메뉴 진입 가능 여부로 판별합니다.

UNKNOWN

버전 차이

화면명·메뉴명이 오래된 경우 원문 위치와 확인 불가 표시를 남깁니다. 환불 정책 문구는 원문 두 곳(billing-policy.md, support-macro.md)이 서로 달라 소유자 확인 전까지 양쪽 모두 인용 보류 상태입니다.

작성 가능한 작업을 최소 4개 식별하고, 각 레시피를 목적·사전조건·절차·완료 기준·롤백·원문 근거 6필드로 닫습니다.

6Reference Extract · 원문 보존

재구성은 원문을 대체하지 않습니다 — 모든 절차가 어느 원문에서 왔는지 추적 가능해야 갱신이 가능합니다.

매뉴얼 본문은 실행 흐름으로 재배열하되, 원문 위치·버전·주석은 별도 보존합니다. 아래 6개 파일이 이 문서의 전체 입력이며, 이 목록에 없는 정보(예: SLA 수치, 법무 문구)는 본문 어디에도 등장하지 않아야 합니다. 원문이 갱신되면 §1의 스냅샷 날짜와 함께 이 목록의 버전 주석부터 갱신합니다.

7Decision Guide · 선택 기준

“누가 처리하는가”를 증상이 아니라 필요 권한 기준으로 판정합니다 — 이관 기준이 명확해야 핑퐁이 사라집니다.

사용자 해결

권한 변경 없이 화면에서 직접 해결 가능하면 사용자 경로로 안내합니다. 판정 질문은 “설정 화면에서 본인이 바꿀 수 있는 값인가”이며, 그렇다면 §3 경로의 해당 단계 링크만 전달합니다.

운영자 처리

로그·설정·권한 확인이 필요한 경우 운영자 경로로 넘깁니다. 이관 시 필수 첨부는 조직 ID·발생 시각·재현 단계 3종이며, 이 정보 없이 넘기면 운영자가 다시 사용자에게 되묻는 왕복이 발생합니다.

개발 이관

데이터 무결성, 반복 장애, 재현 가능한 버그는 이슈 템플릿으로 이관합니다. 운영자가 같은 증상을 2회 이상 수동 복구했다면 그 시점부터는 무조건 개발 이관 대상으로 승격합니다.

8Troubleshooting · 증상별 문제 해결

증상 → 가능 원인 → 진단 순서 → 복구의 4단 구조를 고정합니다 — 진단 없이 복구부터 시도하지 않게 하는 것이 목적입니다.

조직이 보이지 않음

증상: 로그인은 되지만 대시보드에 조직명이 표시되지 않습니다.

가능 원인: 초대 미수락, 잘못된 워크스페이스, 권한 미부여가 빈도순 원인입니다.

진단 순서: 초대 메일 → 조직 ID → 관리자 권한 로그를 확인합니다.

복구: 초대 재발송 → 권한 재부여 → 감사 로그 첨부 후 이관 순으로 처리하고, 2회 실패 시 개발 이관합니다.

알림이 오지 않음

증상: 테스트 알림 버튼은 성공으로 보이지만 실제 채널에는 메시지가 도착하지 않습니다.

가능 원인: 채널 URL 오기재, 조직 알림 권한 누락, 외부 메신저 rate limit입니다.

진단 순서: 채널 URL 재확인 → 최근 발송 로그 → 외부 응답 코드 → rate limit 시간을 확인합니다.

복구: 채널 재연결 후 테스트 알림을 재발송하고, rate limit이면 15분 대기 후 재시도합니다.

결제 실패 반복

증상: 카드 갱신 후에도 결제 실패 배지가 사라지지 않고 청구 알림이 반복됩니다.

가능 원인: 결제 수단 미검증, 플랜 권한 부족, billing-policy.md와 support-macro.md의 정책 문구 불일치입니다.

진단 순서: 결제 수단 상태 → 플랜 권한 → 최근 청구 이벤트 → 정책 문구 소유자 확인 순으로 봅니다.

복구: 검증 완료 후 재청구를 1회만 실행하고, 정책 문구가 불일치하면 환불 안내를 보류한 채 소유자에게 이관합니다.

백업 복원 후 데이터 불일치

증상: 복원은 완료됐지만 일부 조직 설정이나 결제 상태가 이전 값과 다릅니다.

가능 원인: 오래된 스냅샷, 부분 복원, 복원 후 캐시 미무효화, 마이그레이션 누락입니다.

진단 순서: 스냅샷 ID → 복원 범위 → 감사 로그 → 핵심 테이블 diff를 확인합니다.

복구: 사용자 안내보다 먼저 읽기 경로를 동결하고, 데이터 무결성 사안으로 개발 이관합니다.

모든 시나리오는 첫 응답에서 복구를 시작하지 않고 진단 순서를 먼저 완료합니다. 권한 변경·환불·데이터 무결성처럼 되돌리기 어려운 항목은 §7 이관 기준과 §10 감사 결함을 함께 확인한 뒤 처리합니다.

9Operations Runbook · 운영 절차

정기 점검을 주기별로 분리하고, 각 점검에 “이상일 때 어디로 가는가”를 붙여야 런북이 됩니다.

일일

오류 알림, 큐 적체, 결제 실패율 확인. 결제 실패율이 평소 범위를 벗어나면 §8의 결제 실패 시나리오로 진입하고, 큐 적체는 30분 후 재확인에서도 지속될 때만 대응을 시작합니다.

주간

반복 문의, 미해결 티켓, 문서 업데이트 후보 정리. 같은 증상 문의가 주 3회 이상이면 §8에 새 시나리오로 추가하고, 그 증상이 §3 첫 성공 경로와 관련되면 매뉴얼 자체의 결함으로 분류해 §10 감사 대상에 올립니다.

릴리스 전

스크린샷 변경, API 옵션 변경, 안전 경고 문구 확인. 릴리스 메모와 매뉴얼의 버전 주석이 어긋난 채 배포되는 것이 가장 흔한 문서 사고이므로, 이 점검은 릴리스 승인 조건에 포함합니다(소유자 승인 대기 — §1).

10Manual Audit · 품질 감사

매뉴얼 자체의 결함(누락·낡음·모순)을 찾아 원문 근거와 함께 기록합니다 — 지적에는 반드시 위치가 붙어야 합니다.

오래된 화면명이나 서로 모순되는 절차가 있으면 삭제하지 말고 원문 위치와 확인 불가를 남긴 뒤 소유자 검토로 보냅니다. 이번 감사에서 확인된 결함은 세 가지입니다. 환불 정책 문구 모순(billing-policy.md §3 vs support-macro.md §1), FAQ 스크린샷의 구버전 메뉴명(FAQ-로그인.md §2, 릴리스 2.4와 불일치), 롤백 절차의 소요 시간 미기재(ops/rollback.md §2 — 장애 대응 중 판단 지연 요인). 셋 모두 본문에서는 보류/주석 처리했고 소유자 검토 후 확정합니다.
