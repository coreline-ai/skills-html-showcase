릴리즈 전 접근성 플레이북 · WCAG 2.2 A/AA

웹 접근성 배포 전 30분 체크리스트

문서 구조부터 키보드, 포커스, 폼, ARIA, 모바일 확대까지. 배포 버튼을 누르기 전 통과/실패를 분명히 가르는 6개 게이트 점검.

대상: 프론트엔드·QA·디자인 시스템 담당 · 소요 약 30분 · 기준: WCAG 2.2 Level A/AA

접근성은 출시 직전에 통째로 끝낼 수 있는 일이 아니다. 하지만 "눈에 띄게 깨진 것"을 막는 마지막 방어선은 30분이면 세울 수 있다. 이 플레이북은 그 30분짜리 방어선이다.

이 문서의 목적은 완벽한 감사(audit)가 아니라 배포 게이트다. 즉 "지금 나가도 되는가, 멈춰야 하는가"를 사람이 망설이지 않고 판단하도록 만드는 것이 전부다. 그래서 모든 항목은 감상이 아니라 통과(PASS)·실패(FAIL)로 끊어 적었다.

언제 쓰나 (Use Case)
  • 스프린트 끝, 릴리즈 브랜치를 머지하기 직전의 최종 손검수.
  • 자동 검사 도구(axe, Lighthouse 등)가 잡지 못하는 문맥·키보드·초점 흐름을 사람이 확인할 때.
  • 접근성 전담 인력이 없어 개발자가 직접 30분 안에 핵심 회귀를 막아야 할 때.
  • QA 체크리스트나 PR 템플릿에 그대로 붙여 반복 가능한 게이트로 운영할 때.
비유로 이해하기

이 체크리스트는 정밀 건강검진이 아니라 출국장 보안검색에 가깝다. 모든 질병을 찾아내지는 못하지만, "이 상태로는 절대 비행기에 태울 수 없는" 항목은 확실히 걸러낸다. 그래서 항목 수는 적고, 판정은 빠르고 단호하다.

먼저 짚을 오해
"자동 도구가 100점이면 접근성은 통과다"

자동 검사는 전체 WCAG 성공 기준의 일부(대체로 30~40% 수준으로 알려져 있으며 도구·버전에 따라 차이가 있으니 확인 필요)만 자동으로 판정한다. 의미 있는 alt인지, 포커스 순서가 논리적인지, 라벨이 진짜 그 입력을 가리키는지는 결국 사람이 본다. 이 30분이 필요한 이유다.

130분 점검 그리드

6개 게이트, 각 5분. 각 카드의 항목은 "이렇게 보이면 PASS / 이러면 FAIL"로 바로 판정하도록 적었다.

게이트 1 · 5분

문서 구조 & 단일 h1

스크린리더 사용자에게 페이지는 "제목 목록"으로 먼저 들린다. 골격이 어긋나면 내용은 멀쩡해도 길을 잃는다.

  • PASS 페이지에 <h1>이 정확히 1개이고 페이지 주제를 담는다.
  • PASS 제목 단계가 건너뛰지 않는다(h2 다음 바로 h4 금지).
  • PASS header / nav / main / footer 랜드마크가 있고 main은 1개다.
  • FAIL 시각적 크기 때문에 <div class="title">로 제목을 흉내냈다.
  • FAIL 목록처럼 보이는데 <ul>/<li>가 아니라 <br> 나열이다.

기준: WCAG 1.3.1 정보와 관계, 2.4.6 제목과 레이블.

게이트 2 · 5분

키보드 내비게이션

마우스를 치우고 Tab, Shift+Tab, Enter, Space, 방향키만으로 핵심 흐름을 끝까지 해본다.

  • PASS 모든 버튼·링크·입력에 Tab으로 도달하고 동작한다.
  • PASS 탭 순서가 화면의 시각적 순서와 일치한다.
  • PASS 모달·드롭다운에서 Esc로 빠져나올 수 있다.
  • FAIL 메뉴를 열었더니 Tab이 뒤 배경으로 새어 나간다(포커스 트랩 부재).
  • FAIL 클릭으로만 되는 커스텀 위젯이 있다(키보드 도달 불가).

기준: WCAG 2.1.1 키보드, 2.1.2 키보드 트랩 없음, 2.4.3 초점 순서.

게이트 3 · 5분

포커스 가시성 & 대비

"지금 어디에 포커스가 있는지" 한눈에 보여야 하고, 글자는 배경과 충분히 구분돼야 한다.

  • PASS Tab으로 이동할 때 항상 또렷한 포커스 표시가 보인다.
  • PASS 본문 텍스트 대비가 최소 4.5:1, 큰 글자(약 24px 이상 또는 19px 굵게)는 3:1 이상이다.
  • PASS 포커스 표시 자체도 인접 색과 3:1 이상 구분된다.
  • FAIL 디자인 정리한다고 outline: none만 주고 대체 표시가 없다.
  • FAIL 연회색 placeholder를 본문 텍스트처럼 쓰고 있다(대비 미달).

기준: WCAG 1.4.3 대비(최소), 2.4.7 보이는 초점, 2.4.11 초점 가림 방지(2.2 신규).

게이트 4 · 5분

폼 라벨 & 오류

입력칸은 "무엇을 적는 칸인지"가 코드 수준에서 이름과 연결돼 있어야 한다. placeholder는 라벨이 아니다.

  • PASS 모든 입력에 <label for> 또는 aria-label이 연결돼 있다.
  • PASS 필수·오류가 색뿐 아니라 텍스트로도 안내된다.
  • PASS 오류 메시지가 해당 입력과 프로그램적으로 연결돼(예: aria-describedby) 읽힌다.
  • FAIL placeholder만 있고 라벨이 없어, 입력하면 안내가 사라진다.
  • FAIL "빨간 테두리"로만 오류를 표시한다(색 의존).

기준: WCAG 1.3.1, 3.3.2 레이블·지시, 1.4.1 색 사용, 4.1.2 이름·역할·값.

게이트 5 · 5분

ARIA 남용 방지 & 대체텍스트

ARIA는 강력하지만, "없는 것보다 잘못 쓴 ARIA가 더 나쁘다". 네이티브 요소로 되는 일에 굳이 얹지 않는다.

  • PASS 의미 있는 이미지에 내용을 설명하는 alt, 장식 이미지는 alt=""다.
  • PASS 버튼은 <button>, 링크는 <a href>로 쓴다(div+role 남발 금지).
  • PASS role을 붙였으면 키보드 동작과 상태(aria-expanded 등)까지 함께 구현했다.
  • FAIL alt에 "이미지", "사진", 파일명이 그대로 들어가 있다.
  • FAIL <div role="button">인데 Enter/Space로 눌리지 않는다.

기준: WCAG 1.1.1 비텍스트 콘텐츠, 4.1.2 이름·역할·값.

게이트 6 · 5분

모바일 & 확대

실제 사용자는 흔들리는 버스에서, 200%로 키운 화면에서 본다. 데스크톱에서 멀쩡한 것이 여기서 무너지기 쉽다.

  • PASS 브라우저 확대 200%에서 가로 스크롤 없이 본문이 읽힌다.
  • PASS 주요 터치 타깃이 충분히 크다(WCAG 2.2의 2.5.8은 24×24px 최소, 권장은 더 큼).
  • PASS <meta viewport>에 user-scalable=no나 maximum-scale=1로 확대를 막지 않는다.
  • FAIL 세로 모드에서 버튼 두 개가 손가락 하나 폭으로 붙어 있다.
  • FAIL 확대하면 텍스트가 컨테이너 밖으로 잘려 사라진다.

기준: WCAG 1.4.4 텍스트 크기 조정, 1.4.10 리플로우, 2.5.8 타깃 크기(최소, 2.2 신규).

판정 규칙
한 카드라도 FAIL이면 게이트는 닫힌다

6개 카드 중 어느 하나라도 FAIL 항목이 남으면 그 릴리즈는 "조건부 보류"다. 핫픽스로 그 항목만 해결하거나, 명시적으로 위험을 기록하고 책임자가 예외 승인을 남긴다. "바빠서 그냥 넘겼다"는 기록은 남기지 않는 것이 진짜 위험이다.

2자주 새는 실패 모드

체크리스트를 돌렸는데도 빠져나가는 단골 패턴. 30분 안에 가장 자주 놓치는 다섯 가지를 먼저 의심하라.

실패 모드 빠른 진단표
증상숨은 원인30초 확인법최소 조치
포커스가 사라진다 전역 outline: none Tab을 눌러도 표시가 안 보임 :focus-visible로 또렷한 표시 복원
읽히지 않는 입력칸 placeholder로 라벨 대체 입력 시작하면 안내가 사라짐 가시 <label> 연결, placeholder는 보조로
메뉴에 갇힘 모달 포커스 트랩 미구현 Esc·외부 영역으로 못 빠져나감 트랩 + Esc 닫기 + 닫은 뒤 초점 복귀
스크린리더 침묵 div로 만든 가짜 버튼 요소가 "버튼"으로 안 읽힘 네이티브 <button>으로 교체
200%에서 깨짐 고정 px 폭·뷰포트 확대 잠금 확대 시 가로 스크롤·잘림 상대 단위·리플로우 허용, 확대 잠금 해제
함정
ARIA를 "고치는 약"으로 오해하기

접근성이 안 된다고 role과 aria-*를 덧바르는 순간 문제가 더 깊어질 때가 많다. ARIA는 역할만 선언할 뿐 동작을 만들어주지 않는다. role="button"을 붙였다면 키보드 활성화, 포커스, 눌림 상태까지 직접 구현해야 한다.

해결
"네이티브 먼저, ARIA는 보강"

버튼·링크·체크박스·셀렉트는 네이티브 HTML 요소가 키보드·포커스·상태·스크린리더 노출을 공짜로 처리한다. ARIA는 네이티브로 표현할 수 없는 패턴(탭, 트리, 라이브 영역 등)을 보강할 때만 꺼낸다.

사례

한 팀이 Lighthouse 접근성 점수 100점을 받고 배포했는데, 스크린리더 사용자 제보로 핵심 결제 버튼이 전혀 눌리지 않는 사실이 드러났다. 원인은 <div onclick>으로 만든 버튼이었다. 자동 점수는 "보이는 텍스트 대비, alt 존재" 같은 것만 채점했고, 키보드로 눌리는지는 사람이 Tab을 눌러봤어야 잡혔다. 게이트 2가 있었다면 5분 만에 막혔을 회귀다.

3완료 기준 — 배포해도 좋다는 신호

아래를 모두 "예"로 답할 수 있을 때만 게이트를 연다. 하나라도 "아니오"면 멈추거나 명시적으로 예외를 기록한다.

  1. 구조 — h1이 1개이고 제목 단계가 건너뛰지 않는다. 랜드마크가 갖춰져 있다.
  2. 키보드 — 마우스 없이 핵심 흐름(검색·로그인·구매 등)을 처음부터 끝까지 마쳤고, 어디에도 갇히지 않았다.
  3. 포커스·대비 — Tab 이동 시 항상 포커스가 보이고, 본문 대비 4.5:1을 만족한다.
  4. 폼 — 모든 입력에 연결된 라벨이 있고, 오류는 색이 아닌 텍스트로도 전달된다.
  5. 의미 — 의미 있는 이미지에 적절한 alt가 있고, 버튼·링크는 네이티브 요소이며 잘못된 ARIA가 없다.
  6. 모바일·확대 — 200% 확대에서 가로 스크롤 없이 읽히고, 확대 잠금이 없으며, 터치 타깃이 너무 붙어 있지 않다.
  7. 기록 — FAIL이 있었다면 수정했거나, 책임자 승인과 함께 위험으로 남겼다.
출처와 검토 기준

WCAG 2.2 권고안의 Level A/AA 성공 기준을 바탕으로 작성했습니다. 구체적인 수치(자동 검사 커버리지 비율, 도구 버전 등)는 도구·시점에 따라 달라질 수 있으니 적용 전 원문과 최신 도구 문서를 확인하세요. 이 체크리스트는 전체 적합성 감사를 대체하지 않습니다.
