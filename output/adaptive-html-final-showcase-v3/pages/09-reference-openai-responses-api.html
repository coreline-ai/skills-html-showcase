OpenAI Responses API 실무 레퍼런스

엔드포인트, 입력/출력 모델, 내장 도구와 함수 호출, 스트리밍, 상태 관리, 그리고 Chat Completions에서 넘어올 때의 마이그레이션 포인트를 한 장에 정리한 개념적 레퍼런스입니다.

Responses API는 OpenAI가 Chat Completions와 Assistants의 사용 경험을 합쳐 정리한 하나의 생성 엔드포인트입니다. 메시지 배열을 직접 조립하던 방식 대신, "입력(input)을 주고 출력(output) 아이템 배열을 받는다"는 더 단순한 멘탈 모델을 제공하며, 웹 검색·파일 검색·코드 실행 같은 내장 도구와 서버 측 상태 관리를 한 인터페이스 안에 둡니다. 이 레퍼런스는 그 구조를 빠르게 떠올릴 수 있도록 정리한 것입니다.

비유로 이해하기

Chat Completions가 "대화 기록 전체를 매번 손으로 봉투에 담아 보내는 우편"이라면, Responses API는 "이전 대화에 꼬리표(이전 응답 ID)를 붙여 보내면 서버가 맥락을 알아서 이어주는 등기"에 가깝습니다. 다만 자동으로 이어준다는 편리함의 이면에는 "상태를 누가 보관하느냐"라는 새로운 선택지가 생긴다는 점이 함정입니다.

1Quick Reference — 한눈에 보는 핵심

바쁘면 이 표와 체크리스트만 봐도 전체 그림이 잡힙니다.

ENDPOINT

POST /v1/responses

모델 호출의 기본 엔드포인트. 생성된 응답 조회·삭제·취소를 위한 보조 경로(GET/DELETE 등)도 함께 제공됩니다. 정확한 경로는 공식 문서 확인 필요.

필수 입력

model + input

input은 문자열 한 줄이거나, 역할(role)·콘텐츠 파트로 이뤄진 구조화 배열입니다. 둘 다 허용됩니다.

대표 출력

output[] + output_text

출력은 메시지·도구 호출·추론 등 아이템(item) 배열입니다. SDK는 텍스트만 모은 편의 속성(output_text)도 제공합니다.

상태 이어가기

previous_response_id

이전 응답 ID를 넘기면 서버가 대화 맥락을 이어줍니다(서버 측 상태). store 설정과 함께 동작 방식이 정해집니다.

스트리밍

stream: true

SSE 기반의 의미 단위 이벤트(semantic events)로 토큰·도구 진행 상황이 흘러옵니다.

도구

tools[] + tool_choice

사용자 정의 함수와 내장 도구(웹 검색·파일 검색 등)를 같은 배열에 함께 선언합니다.

아래는 통합을 시작할 때 거의 항상 결정해야 하는 항목들입니다. 익숙해지면 자연스럽게 떠오르지만, 처음에는 명시적으로 짚고 넘어가는 편이 안전합니다.

시작 전 결정해야 할 것
  1. 대화 상태를 서버에 맡길지(previous_response_id) 클라이언트가 보관할지 정한다.
  2. 응답을 저장(store)할지 결정한다 — 저장 정책은 데이터 보존·프라이버시 요구와 직결된다.
  3. 구조화된 출력이 필요하면 JSON 스키마(structured outputs)를 쓸지 정한다.
  4. 응답을 실시간으로 보여줄 거라면 스트리밍 이벤트 처리를 먼저 설계한다.
  5. 함수 호출 결과를 다시 모델에 돌려주는 루프를 어디서 끊을지 정한다.

2핵심 개념 · 요청/응답 모델

"메시지 배열"이 아니라 "입력과 출력 아이템"으로 생각을 바꾸는 것이 핵심입니다.

Responses API의 가장 큰 변화는 데이터 모델입니다. Chat Completions는 messages라는 단일 배열을 주고 choices[0].message를 받는 구조였습니다. Responses는 입력과 출력을 더 풍부한 아이템 단위로 다룹니다.

용어
input (입력)
모델에 전달하는 콘텐츠. 가장 단순하게는 문자열 한 줄이고, 복잡하게는 역할(user/assistant/system 또는 developer)과 콘텐츠 파트(텍스트·이미지·파일 등)를 가진 아이템 배열입니다. 이전 턴의 도구 호출 결과도 이 입력에 포함시켜 다음 턴으로 넘깁니다.
용어
output item (출력 아이템)
응답의 output 배열을 채우는 단위. 대표 타입은 message(모델의 답변), 함수/도구 호출 아이템, 그리고 추론 과정을 나타내는 reasoning 아이템 등입니다. 모델은 한 번의 응답에서 여러 아이템을 순서대로 만들 수 있습니다.
용어
output_text
출력 아이템 중 텍스트만 이어 붙인 편의 속성입니다. 공식 SDK가 제공하는 헬퍼 성격이며, 복잡한 출력에서는 raw output 배열을 직접 순회하는 편이 안전합니다.

요청에서 자주 쓰는 필드

아래 표는 일반적으로 알려진 수준의 주요 필드입니다. 신규 파라미터·정확한 기본값·허용 범위는 버전에 따라 달라질 수 있으므로 공식 API 레퍼런스 확인이 필요합니다.

Responses 요청에서 자주 쓰는 필드 (개념 수준)
필드역할메모
model사용할 모델 식별자모델명·세대별 차이는 모델 문서 확인 필요
input입력 콘텐츠(문자열 또는 아이템 배열)멀티모달 콘텐츠 파트 허용
instructions시스템/개발자 지시역할 메시지 대신 분리해 전달하는 경로

상태(state)를 누가 가지나

서버에 맡기면 코드가 단순해지지만, 저장된 응답에 의존하므로 보존·삭제 정책과 데이터 거버넌스를 함께 설계해야 합니다.

응답 메타데이터

응답에는 id, 상태(완료/진행/실패), 사용량(usage) 등이 포함됩니다. 이어가기와 디버깅의 기준점이 되므로 로깅해 두는 편이 좋습니다.

함정
"messages를 그대로 input에 넣으면 되겠지"

Chat Completions의 messages 구조와 Responses의 input 아이템 구조는 비슷해 보여도 동일하지 않습니다. 특히 도구 호출 결과를 다음 턴으로 되돌리는 방식, 역할 명칭(developer vs system) 처리에서 차이가 납니다.

해결
SDK 헬퍼와 아이템 타입을 따른다

공식 SDK가 제공하는 입력 빌더와 아이템 타입을 사용하면 구조 차이를 흡수할 수 있습니다. 직접 JSON을 조립할 때는 응답의 output 아이템을 그대로 다음 input에 이어 붙이는 패턴을 기본으로 삼습니다.

3도구와 스트리밍 패턴

함수 호출 루프와 이벤트 스트림 처리는 통합에서 가장 많이 막히는 두 지점입니다.

3.1 도구(tools)와 함수 호출

Responses API는 두 종류의 도구를 같은 tools 배열에 함께 선언합니다. 하나는 사용자 정의 함수(function calling), 다른 하나는 OpenAI가 실행을 맡는 내장 도구(built-in tools)입니다.

사용자 함수

function

이름·설명·JSON 스키마 파라미터를 선언합니다. 모델이 호출을 결정하면 호출 아이템이 출력에 나타나고, 실제 실행은 내 코드가 합니다.

내장 도구

web search

모델이 웹에서 정보를 찾도록 합니다. 실행·결과 통합을 OpenAI 쪽이 처리합니다. 제공 여부·요금은 확인 필요.

내장 도구

file search

업로드/색인된 문서에서 관련 구절을 검색합니다. RAG 유사 시나리오를 도구 형태로 제공합니다.

내장 도구

code interpreter 등

코드 실행, 컴퓨터 사용, 이미지 생성 같은 도구가 모델 세대·플랜에 따라 제공됩니다. 가용성은 공식 문서 확인 필요.

핵심 차이
실행 책임의 위치
사용자 함수는 "모델이 무엇을·어떻게 부를지 결정 → 내 서버가 실행 → 결과를 다시 input으로 반환"하는 왕복 루프입니다. 내장 도구는 그 실행 단계를 OpenAI가 대신하므로, 내 코드는 결과를 받아 이어 쓰기만 하면 됩니다.
패턴 1 — 함수 호출 왕복 루프

가장 표준적인 도구 흐름입니다. 끝나는 조건(모델이 더 이상 함수를 호출하지 않거나, 최대 반복 횟수 도달)을 반드시 코드로 제어해야 무한 루프를 막을 수 있습니다.

  1. 요청에 tools로 함수 스키마를 선언한다.
  2. 응답 output에 함수 호출 아이템이 있으면, 인자를 파싱해 실제 함수를 실행한다.
  3. 실행 결과를 함수 호출 출력 아이템으로 만들어 다음 요청 input에 이어 붙인다(이어가려면 previous_response_id 또는 전체 input 재전송).
  4. 모델이 최종 텍스트 답변을 낼 때까지 2~3을 반복하되, 반복 상한을 둔다.
패턴 2 — 구조화 출력으로 결과 고정

응답을 다운스트림 시스템에 바로 넣어야 한다면, 자유 텍스트 대신 JSON 스키마를 강제하는 structured outputs를 사용합니다. 파싱 실패와 환각 필드를 크게 줄일 수 있습니다. 스키마 표현·엄격 모드의 정확한 옵션명은 확인 필요.

3.2 스트리밍 패턴

스트리밍을 켜면 응답이 한 덩어리가 아니라 의미 단위 이벤트의 연속으로 도착합니다. 이전 Chat Completions의 "델타 조각"보다 구조화되어 있어, 어떤 아이템이 시작/추가/완료되는지 이벤트 타입으로 구분할 수 있습니다.

스트리밍 이벤트의 개념적 분류 (정확한 이벤트명은 공식 문서 확인 필요)
이벤트 성격의미처리 팁
응답 생성 시작/완료전체 응답의 라이프사이클 경계완료 이벤트에서 최종 응답 객체와 usage를 확보
아이템 추가새 출력 아이템(메시지·도구 호출 등) 등장아이템 타입별로 렌더링 분기
텍스트 델타답변 텍스트가 조각으로 누적UI에 즉시 append
도구/함수 인자 델타함수 호출 인자가 점진적으로 완성완료 신호 전까지 인자 파싱을 미룬다
오류 이벤트스트림 중 발생한 오류부분 출력 폐기·재시도 정책 적용
함정
델타가 도착하는 대로 JSON을 파싱한다

함수 호출 인자나 구조화 출력은 조각으로 나뉘어 도착합니다. 중간 조각은 그 자체로 유효한 JSON이 아니므로, 매 델타마다 파싱하면 깨집니다.

해결
조각은 누적, 파싱은 완료 시점에

델타는 버퍼에 이어 붙이기만 하고, 해당 아이템의 "완료" 이벤트가 온 뒤에 한 번 파싱합니다. UI 텍스트만 실시간으로 흘리고, 구조화 데이터는 완성 후 처리하는 것이 안전합니다.

4예제 — 요청·응답·스트리밍

아래 예제는 형태(shape)를 보여주기 위한 개념 스케치이며, 실제 필드명·기본값은 사용 중인 SDK·버전에 맞춰 확인이 필요합니다.

4.1 기본 요청 (curl)

요청 예시 — 단일 입력
curl https://api.openai.com/v1/responses \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "MODEL_NAME",
    "input": "Responses API를 한 문단으로 설명해줘."
  }'

4.2 응답의 개념적 형태

응답 예시 — output 아이템 배열 (요약)
{
  "id": "resp_...",
  "status": "completed",
  "output": [
    {
      "type": "message",
      "role": "assistant",
      "content": [
        { "type": "output_text", "text": "Responses API는 ..." }
      ]
    }
  ],
  "usage": { "input_tokens": 0, "output_tokens": 0 }
}

실제 필드 구성은 모델·도구 사용 여부에 따라 달라집니다. output은 항상 배열이라는 점을 기억하세요.

4.3 함수 도구 선언 (Python SDK 스케치)

코드 스케치 — 함수 호출 루프의 골격
from openai import OpenAI
client = OpenAI()

tools = [{
  "type": "function",
  "name": "get_weather",
  "description": "도시의 현재 날씨를 반환",
  "parameters": {
    "type": "object",
    "properties": {"city": {"type": "string"}},
    "required": ["city"]
  }
}]

resp = client.responses.create(
    model="MODEL_NAME",
    input="서울 날씨 알려줘",
    tools=tools,
)

# resp.output 를 순회하며 function 호출 아이템을 찾고,
# 실제 get_weather() 실행 결과를 다음 요청의 input 으로 되돌린다.
# (정확한 메서드/아이템 접근 방식은 SDK 버전 확인 필요)

4.4 스트리밍 수신 (스케치)

코드 스케치 — 이벤트 루프
stream = client.responses.create(
    model="MODEL_NAME",
    input="긴 답변을 스트리밍으로 보여줘",
    stream=True,
)

for event in stream:
    # event.type 으로 분기:
    #  - 텍스트 델타 → UI에 append
    #  - 인자 델타   → 버퍼에 누적 (파싱 금지)
    #  - 완료 이벤트 → 최종 객체/usage 확정
    handle(event)
비유로 이해하기

스트리밍 이벤트 루프는 택배 송장 스캔과 같습니다. "출고됨 → 허브 도착 → 배송 중 → 배송 완료"처럼 단계마다 상태가 찍히죠. 텍스트 델타는 "배송 중" 알림이라 즉시 보여줘도 되지만, 함수 인자 같은 내용물은 "배송 완료" 이벤트가 찍힌 뒤 열어봐야 온전합니다.

5Chat Completions → Responses 마이그레이션 체크리스트

엔드포인트만 바꾸는 게 아니라 데이터 모델과 상태 관리 관점을 함께 옮겨야 합니다.

두 API는 당분간 함께 제공되는 것으로 알려져 있으므로, 한 번에 전환하기보다 새 기능부터 Responses로 작성하고 기존 경로를 점진적으로 옮기는 방식이 안전합니다. 정확한 지원·폐기(deprecation) 일정은 공식 공지 확인이 필요합니다.

전환 체크리스트
  1. 엔드포인트/SDK 호출부를 responses.create 계열로 교체했다.
  2. messages 조립 로직을 input 아이템 구성으로 다시 매핑했다.
  3. 응답 파싱을 choices[0].message에서 output 아이템 순회로 바꿨다.
  4. 대화 이어가기를 "전체 재전송"으로 둘지 previous_response_id로 옮길지 결정하고, store 정책을 검토했다.
  5. 함수 호출 결과 반환 형식과 종료 조건(반복 상한)을 새 모델에 맞게 점검했다.
  6. 스트리밍 처리를 델타 누적이 아닌 이벤트 타입 분기로 재작성했다.
  7. JSON 출력이 필요한 경로를 structured outputs로 옮기고 스키마를 검증했다.
  8. 로깅·관측에서 새 응답 id·usage·도구 호출을 추적하도록 했다.

6자주 묻는 질문

통합 초반에 가장 자주 나오는 질문들을 모았습니다.

Chat Completions는 곧 없어지나요?

현재로서는 두 API가 함께 제공되는 것으로 알려져 있으며, Responses가 새 기능의 우선 적용 지점으로 안내되는 경향이 있습니다. 다만 구체적인 지원·폐기 일정과 권고 사항은 시점에 따라 달라질 수 있으므로 공식 공지 확인이 필요합니다.

상태를 서버에 맡기는 게 항상 좋은가요?

코드는 단순해지지만, 응답 저장(store)과 데이터 보존·삭제 정책에 의존하게 됩니다. 규제·프라이버시 요구가 강한 환경에서는 클라이언트가 맥락을 보관하고 매 요청에 명시적으로 전달하는 방식이 더 통제하기 쉬울 수 있습니다.

내장 도구를 쓰면 함수 호출은 필요 없나요?

역할이 다릅니다. 내장 도구는 OpenAI가 실행을 맡는 범용 기능(웹/파일 검색 등)이고, 사용자 정의 함수는 내 시스템 고유의 동작(주문 생성, 사내 DB 조회 등)을 모델이 호출하도록 하는 것입니다. 둘은 같은 tools 배열에서 함께 쓸 수 있습니다.

응답 형식을 JSON으로 강제하려면?

structured outputs로 JSON 스키마를 지정하면 출력이 그 스키마를 따르도록 유도/강제할 수 있습니다. 자유 텍스트에 JSON을 요청하는 것보다 파싱 안정성이 높습니다. 정확한 옵션 명칭과 엄격(strict) 모드 동작은 공식 문서 확인이 필요합니다.

한 문장 요약

Responses API는 "input을 주고 output 아이템을 받는다"는 단일 모델 위에 도구·스트리밍·서버 측 상태를 통합한 엔드포인트이며, 마이그레이션의 본질은 엔드포인트 교체가 아니라 데이터 모델과 상태 관리 관점의 전환입니다.
