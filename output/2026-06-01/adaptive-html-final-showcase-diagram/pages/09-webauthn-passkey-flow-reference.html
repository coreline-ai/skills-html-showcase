FIDO2 · WebAuthn 구현 레퍼런스

WebAuthn 패스키 등록·인증 흐름 레퍼런스

패스키는 비밀번호를 없애고 기기 인증기(authenticator)가 공개키 쌍을 만든다. 등록(attestation)과 인증(assertion)은 둘 다 challenge로 시작하지만 검증 포인트가 다르다 — 이 문서는 그 차이를 바로 찾게 한다.

대상: 패스키 로그인을 구현하는 백엔드·프런트엔드 개발자 · 기준: W3C WebAuthn Level 2 / FIDO2 (2026-05 기준, 세부 API는 브라우저별 차이 있음) · 핵심 용어: challenge · attestation · assertion · rpId · userHandle · origin 검증

빠른 참조

패스키 구현에서 막히는 지점은 거의 항상 "지금 등록(attestation) 흐름인지, 인증(assertion) 흐름인지", 그리고 "서버가 challenge·origin·rpId를 제대로 다시 검증했는지"다. 아래 칩과 한 줄 정의로 먼저 위치를 잡고, 이어지는 흐름도·필드 표로 내려간다.

  • challenge — 서버가 매 요청마다 새로 생성하는 16바이트 이상 랜덤값. 재전송(replay) 방어의 핵심이며, 세션에 묶어 저장했다가 응답의 clientDataJSON 안 값과 1:1로 비교한다. 한 번 쓰면 폐기(일회용)한다.
  • attestation — 등록 단계의 응답. 새로 만든 공개키와 인증기 출처 증명을 담는다(navigator.credentials.create()). 대부분의 소비자 패스키 서비스는 attestation: "none"으로 출처 증명을 요구하지 않는다.
  • assertion — 인증 단계의 응답. 저장된 공개키로 검증할 서명을 담는다(navigator.credentials.get()). 새 키를 만들지 않는다.
  • rpId — Relying Party ID. 보통 등록 가능 도메인(예: example.com). 패스키는 이 rpId에 묶이며 서브도메인 범위 규칙을 따른다. 인증 시 응답의 rpIdHash가 기대값과 같아야 한다.
  • userHandle — 사용자 식별용 불투명(opaque) 바이트열(user.id). 이메일·전화번호 같은 PII를 넣지 않는다. 인증 응답에서 어떤 계정인지 되찾을 때 쓴다(특히 사용자명 없는 discoverable 흐름).
  • origin 검증 — 응답의 clientDataJSON.origin이 기대한 출처(스킴+호스트+포트, 예: https://example.com)와 정확히 일치하는지 서버가 확인. 피싱 방어의 핵심이라 절대 생략하지 않는다.

아래로 갈수록 구체화된다: ① 핵심 개념·필드 → ② 등록/인증 두 흐름도와 검증 패턴 → ③ 실제 옵션·요청 예시 → ④ 구현 체크리스트와 오류 처리.

핵심 개념과 필드

패스키 구현은 결국 두 개의 브라우저 API와 그 응답을 서버가 검증하는 일이다. 먼저 등록과 인증이 만들고 다루는 데이터가 어떻게 다른지 정확히 구분한다 — 같은 단어(challenge)를 쓰더라도 검증 대상이 달라진다.

흐름과 검증 패턴

두 흐름 모두 "서버가 challenge 발급 → 브라우저가 인증기 호출 → 서버가 응답 재검증"이라는 같은 골격을 따른다. 아래 흐름도는 인증(assertion) 로그인 경로를 좌→우로 보여준다. 등록도 같은 5단계지만 3단계가 "새 키 생성"으로, 마지막이 "공개키 저장"으로 바뀐다는 점만 다르다.

등록(attestation) 흐름 — 키를 만든다

등록의 목표는 "이 사용자·이 기기에 한 쌍의 키를 만들고, 공개키를 서버가 보관"하는 것이다. 서버는 user.id(userHandle), rp.id(rpId), 새 challenge, 그리고 이미 등록된 자격증명을 막을 excludeCredentials를 담아 옵션을 내려보낸다. 브라우저는 create()로 인증기에 키 생성을 요청하고, 응답의 attestationObject에서 공개키와 credentialId를 꺼내 서버에 보낸다.

서버 검증의 핵심은 ① clientDataJSON의 type==="webauthn.create"·challenge 일치·origin 일치, ② rpIdHash 일치와 UP 플래그, ③ 정책에 따라 attestation 서명. 소비자 서비스 대부분은 출처 추적·프라이버시 이유로 attestation: "none"을 써서 ③을 생략한다. 검증을 통과하면 credentialId·공개키·signCount·transports를 그 계정에 저장한다.

인증(assertion) 흐름 — 서명을 검증한다

인증은 새 키를 만들지 않는다. 서버가 새 challenge를 발급하고(사용자명 흐름이면 allowCredentials에 등록된 credentialId 목록을 넣는다), 브라우저가 get()으로 서명을 받아온다. 서버는 응답의 userHandle(또는 credentialId)로 계정과 저장된 공개키를 찾은 뒤, 그 공개키로 authenticatorData ‖ SHA-256(clientDataJSON)에 대한 signature를 검증한다.

검증 순서를 어기면 보안 구멍이 생긴다. 반드시 (1) challenge 일치, (2) origin 일치, (3) rpIdHash 일치, (4) UP(필요 시 UV) 플래그, (5) 서명 검증, (6) signCount 역행 여부 순으로 본다. signCount는 일부 패스키(특히 동기화형)에서 항상 0일 수 있으므로, 0이 아닌 값이 줄어들 때만 복제 의심으로 처리하는 것이 안전하다(약식 권고, 인증기별 정책 확인 필요).

discoverable credential(사용자명 없는 로그인)

패스키 UX의 핵심은 사용자명을 먼저 묻지 않는 로그인이다. 등록 시 residentKey: "required"(또는 "preferred")로 만들면 자격증명이 인증기에 저장(discoverable)되어, 인증 시 allowCredentials를 비워 보낼 수 있다. 이때 누구인지는 응답의 userHandle로 식별하므로, 등록 단계에서 user.id를 PII 없는 안정적 불투명 값으로 설계해 두는 것이 다음 행동의 전제다.

옵션·요청 예시와 파일 배치

아래는 서버가 등록 단계에서 내려보내는 PublicKeyCredentialCreationOptions의 대표 형태다(바이너리 필드는 실제로 base64url 인코딩된 ArrayBuffer). 값은 예시이며 운영에서는 challenge·user.id를 안전하게 생성·저장한다.

// 등록 옵션 (서버 → 클라이언트, JSON 직렬화 형태)
{
  "rp":   { "id": "example.com", "name": "Example" },
  "user": { "id": "<userHandle: base64url, PII 없음>",
            "name": "user@example.com", "displayName": "사용자" },
  "challenge": "<랜덤 16바이트+, base64url>",
  "pubKeyCredParams": [ { "type": "public-key", "alg": -7  },   // ES256
                        { "type": "public-key", "alg": -257 } ], // RS256
  "authenticatorSelection": { "residentKey": "required",
                              "userVerification": "preferred" },
  "excludeCredentials": [ /* 이미 등록된 credentialId 목록 */ ],
  "attestation": "none",
  "timeout": 60000
}

인증 단계 옵션은 더 짧다. 사용자명 흐름이면 allowCredentials에 그 계정의 credentialId를 넣고, discoverable 흐름이면 비워 둔다.

// 인증 옵션 (서버 → 클라이언트)
{
  "challenge": "<매번 새 랜덤값>",
  "rpId": "example.com",
  "allowCredentials": [],          // discoverable: 비움 / 사용자명 흐름: credentialId 목록
  "userVerification": "preferred",
  "timeout": 60000
}

서버 측 검증 코드를 어디에 두고 무엇을 책임지게 할지도 흐름만큼 중요하다. 아래 파일 투어는 challenge 발급, 등록·인증 검증, 자격증명 저장을 분리한 전형적인 백엔드 배치를 보여준다. 검증 로직을 라우터에서 떼어 한곳에 모으면 origin·rpId·signCount 규칙을 빠뜨리지 않고 일관되게 적용할 수 있다.

구현 체크리스트와 오류 처리

아래 항목을 통과하면 등록·인증의 보안 핵심은 갖춘 것이다. 색이 아니라 [필수] · [권장] 라벨로 우선순위를 표시했다.

  • [필수] challenge는 16바이트 이상 CSPRNG로 매번 새로 생성, 세션 바인딩, 사용 후 즉시 폐기(replay 방어).
  • [필수] clientDataJSON.origin이 기대 origin과 정확히 일치하는지 서버에서 확인(피싱 방어).
  • [필수] authenticatorData.rpIdHash === SHA-256(rpId), UP 플래그 set 확인.
  • [필수] 인증 응답의 signature를 저장된 공개키로 검증(authenticatorData ‖ hash(clientDataJSON)).
  • [권장] 민감 작업은 userVerification: "required"로 UV(생체·PIN) 강제.
  • [권장] signCount 역행 감지 시 경보·재인증(0 고정 인증기는 예외 처리).
  • [권장] 등록 시 excludeCredentials로 중복 등록 차단, residentKey로 패스키 UX 확보.
  • [권장] 패스키 분실 대비 복구 경로(추가 인증기 등록·백업 코드)를 미리 설계.

출처와 범위

근거 기준: W3C Web Authentication (WebAuthn) Level 2 권고안과 FIDO2/CTAP, FIDO Alliance의 패스키 가이드. API 세부와 브라우저·플랫폼 인증기 동작(특히 signCount, discoverable credential, 동기화형 패스키)은 구현체마다 차이가 있으므로 운영 적용 전 대상 플랫폼 문서를 다시 확인하기 바란다. 본문의 옵션 값·바이트 길이 등 수치는 일반적 권고 기준의 예시이며(약식), 규정 요구사항이 있으면 그쪽을 우선한다. 작성 기준 시점은 2026-05이다.
