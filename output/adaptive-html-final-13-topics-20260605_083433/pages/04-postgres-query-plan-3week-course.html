1학습 목표와 플랜을 읽는 관점

목표는 실행 계획을 빠르다/느리다로 단정하는 것이 아니라 접근 경로를 설명하는 것이다.

이 과정의 최종 산출물은 “인덱스를 추가했다”가 아니라 “왜 이 노드가 병목이라고 판단했고, 어떤 변경이 어떤 수치를 바꿨는가”를 설명하는 짧은 진단 보고서다.

학습자는 EXPLAIN, EXPLAIN ANALYZE 결과에서 scan, join, sort, aggregate 노드를 구분하고, 예상 row와 실제 row의 차이를 근거로 병목 가설을 세운다.

이 관점을 한 문장으로 줄이면 “플랜의 모든 줄은 답이 아니라 질문이다”가 된다. Seq Scan 한 줄을 보고 “인덱스가 없다”로 끝내는 대신, “이 노드가 읽은 row가 정말 다 필요했는가? 예상과 실제가 얼마나 벌어졌는가? 이 노드가 위쪽 join·sort에 어떤 입력을 넘기는가?”를 묻게 만드는 것이 목표다.

비유

플랜 트리는 영수증과 같다. 합계(맨 위 노드)만 보면 “비싸다”는 사실만 안다. 하지만 항목별 줄(하위 노드)을 보면 어디서 돈이 새는지 알 수 있다. EXPLAIN ANALYZE는 “영수증에 실제 결제 금액과 수량까지 찍힌 것”이고, EXPLAIN은 “주문서의 예상 금액”이다.

3실행 계획 기본 문법

실행 계획은 노드의 트리이며, 각 노드는 무엇을 얼마나 읽고 반복했는지 보여준다.

`cost`는 절대 시간이 아니라 planner가 선택을 비교하기 위한 내부 추정값이다. 따라서 cost만 보고 병목을 단정하지 말고, 실제 실행 정보가 있는 경우 `actual time`, `rows`, `loops`와 함께 읽어야 한다.

들여쓰기된 하위 노드는 상위 노드의 입력이 된다. 느린 쿼리는 보통 하나의 나쁜 노드만으로 발생하지 않고, 잘못된 row estimate가 조인 방식, 정렬, 집계 선택을 연쇄적으로 흔들면서 커진다.

플랜은 아래에서 위로, 안에서 밖으로 실행된다고 읽으면 가장 직관적이다. 가장 깊이 들여쓰기된 노드가 먼저 row를 만들고, 그 결과가 부모 노드의 입력이 되어 위로 올라간다. 한 줄을 읽을 때마다 세 가지 괄호 안 숫자를 분리해서 본다.

핵심 용어
cost=0.00..18.34 / rows=412 / width=64

cost는 시작 비용..총 비용(추정 단위), rows는 이 노드가 내보낼 것으로 예상한 row 수, width는 row당 평균 바이트다. ANALYZE를 붙이면 뒤에 actual time=0.01..0.92 rows=1530 loops=1처럼 실제 값이 추가된다.

아래는 EXPLAIN ANALYZE 출력의 한 줄을 어떻게 분해해 읽는지 보여주는 예시다(수치는 설명용 가상 값).

-- 읽는 순서: 들여쓰기가 깊은 줄부터 위로
EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 10;

Limit  (cost=0.43..2.81 rows=10 width=64)
       (actual time=0.05..0.07 rows=10 loops=1)
  ->  Index Scan Backward using orders_customer_created_idx on orders
        (cost=0.43..96.20 rows=412 width=64)        -- 예상 412행
        (actual time=0.04..0.06 rows=10 loops=1)    -- 실제 10행에서 조기 종료
        Index Cond: (customer_id = 42)
Planning Time: 0.18 ms
Execution Time: 0.10 ms
읽기 요령
이 줄에서 무엇을 확인했나

인덱스가 정렬 순서(Backward)까지 만족시켜 Limit이 10행만 읽고 멈췄다. 예상 412행 중 실제로는 10행만 읽었고 loops=1이므로 반복 비용도 없다. 이런 줄은 “건드릴 필요 없는 건강한 노드”로 분류한다.

4EXPLAIN vs EXPLAIN ANALYZE

EXPLAIN은 예상 계획을 보여주고, EXPLAIN ANALYZE는 실제 실행 결과를 포함한다.

`EXPLAIN`은 쿼리를 끝까지 실행하지 않고 planner가 예상한 계획을 보여준다. 빠르게 구조를 확인할 수 있지만 실제 시간과 실제 row는 알 수 없다. `EXPLAIN ANALYZE`는 실제 실행 결과를 포함하므로 예측과 현실의 차이를 볼 수 있다.

다만 EXPLAIN ANALYZE는 실제로 쿼리를 수행한다는 점을 반드시 고려해야 한다. 읽기 쿼리라도 캐시 상태, 동시 부하, 파라미터 값에 따라 결과가 달라질 수 있고, 쓰기 쿼리나 부작용이 있는 쿼리는 안전한 환경에서만 다룬다.

EXPLAIN과 EXPLAIN ANALYZE의 차이 한눈에 보기
항목EXPLAINEXPLAIN ANALYZE
쿼리 실제 실행안 함(계획만)함(끝까지 수행)
제공 수치cost, rows(예상), width위 + actual time, actual rows, loops
예상 vs 실제 비교불가가능(가장 큰 가치)
부작용없음INSERT/UPDATE/DELETE는 실제 반영됨
주 용도구조·인덱스 사용 여부 빠른 확인병목 진단, row estimate 오차 확인
안전 주의
EXPLAIN ANALYZE는 쓰기 쿼리를 실제로 실행한다

UPDATE나 DELETE에 ANALYZE를 붙이면 데이터가 실제로 바뀐다. 운영 DB에서 안전하게 실행 결과만 보고 롤백하려면 트랜잭션으로 감싼다.

BEGIN;
EXPLAIN (ANALYZE, BUFFERS)
UPDATE orders SET status = 'shipped' WHERE id = 1001;
-- 플랜과 실제 수치만 확인한 뒤
ROLLBACK;   -- 변경을 되돌린다

실무에서는 EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) 형태로 옵션을 함께 쓴다. BUFFERS는 공유 버퍼 히트/디스크 읽기 수를 보여줘 “느린 게 계획 탓인지 디스크 I/O 탓인지”를 가르는 데 도움이 된다.

5Scan 노드 읽기: Seq / Index / Bitmap

인덱스를 쓰는가보다 읽은 row 대비 실제 필요한 row가 얼마나 되는가를 본다.

Seq Scan

테이블을 순차적으로 읽는다. 작은 테이블이거나 조건 선택도가 낮으면 합리적인 선택일 수 있다.

Index Scan

인덱스를 통해 필요한 row를 찾는다. 조건이 좁고 정렬이나 조인에도 도움이 될 때 유리하다.

Bitmap Scan

여러 후보 row 위치를 모아 한 번에 테이블을 읽는 방식으로 이해하면 좋다.

판단 질문

테이블 접근이 반복되는가, 정렬과 조인까지 같이 줄였는가, 필요한 row가 충분히 좁혀졌는가를 본다.

세 scan을 선택도(selectivity, 조건이 걸러내는 비율)와 묶어 보면 판단이 쉬워진다. 핵심은 “인덱스가 있느냐”가 아니라 읽은 row 대비 정말 필요한 row의 비율이다.

Scan 종류별 유리한 상황과 위험 신호
Scan유리한 상황플랜에서 보는 위험 신호
Seq Scan작은 테이블, 또는 전체의 큰 비율을 읽어야 할 때큰 테이블에서 좁은 조건인데 Seq Scan → 인덱스/통계 점검
Index Scan조건이 좁고(선택도 높음) 정렬·조인에도 인덱스가 쓰일 때actual rows가 매우 큰데 Index Scan → 랜덤 I/O로 오히려 느릴 수 있음
Bitmap Heap Scan중간 선택도, 여러 조건/인덱스를 결합할 때Recheck Cond 후 버려지는 row가 많고 lossy 블록 다수

아래는 같은 조건이 선택도에 따라 다른 scan으로 갈리는 예시다(가상 수치).

-- 좁은 조건: 인덱스로 적은 row만 집는다
EXPLAIN ANALYZE SELECT * FROM events WHERE user_id = 7;
  Index Scan using events_user_idx on events
    (cost=0.42..33.1 rows=18 width=72) (actual rows=18 loops=1)
    Index Cond: (user_id = 7)

-- 넓은 조건: 전체의 절반을 읽으니 순차 읽기가 더 싸다
EXPLAIN ANALYZE SELECT * FROM events WHERE status <> 'archived';
  Seq Scan on events
    (cost=0.00..2210.0 rows=98000 width=72) (actual rows=97912 loops=1)
    Filter: (status <> 'archived')
    Rows Removed by Filter: 2088
미니 퀴즈
Q. 큰 테이블에서 Seq Scan이 보이면 무조건 인덱스를 추가해야 하나?
A. 아니다. 조건이 전체의 큰 비율을 거른다면(낮은 선택도) 인덱스로 랜덤 접근하는 것보다 순차 읽기가 더 싸다. Rows Removed by Filter가 작고 결과 row가 전체의 상당 비율이면 Seq Scan이 정상이다.
Q. Recheck Cond가 붙은 Bitmap Heap Scan에서 무엇을 의심하나?
A. 비트맵이 메모리에 다 들어가지 못해 블록 단위(lossy)로 표시되면 페이지 내 row를 다시 검사한다. 버려지는 row가 많으면 조건 축소나 work_mem 검토 대상이다.

6Join 노드 읽기: Nested Loop / Hash / Merge

조인 분석의 핵심은 어떤 테이블이 먼저 줄어드는가와 반복되는 쪽이 너무 큰가다.

`Nested Loop`는 한쪽 결과를 기준으로 다른 쪽을 반복 탐색한다. 바깥쪽 row가 적고 안쪽 접근이 빠르면 좋지만, row estimate가 틀려 반복 횟수가 커지면 급격히 비싸질 수 있다.

Hash Join은 한쪽 입력으로 해시 테이블을 만들고 다른 입력을 대조한다. 대량 조인에서 자주 유리하지만 입력 크기 추정과 메모리 사용을 함께 봐야 한다. Merge Join은 정렬된 입력을 순서대로 맞춰가며 조인한다.

조인 방식별 비용 모델과 진단 포인트
조인잘 맞는 상황플랜에서 보는 핵심 수치
Nested Loop바깥(outer) row가 적고 안쪽에 빠른 인덱스가 있을 때안쪽 노드의 loops 값 — 폭증하면 위험
Hash Join한쪽이 메모리에 들어가는 대량 동등 조인Batches 수, Hash 노드의 메모리/디스크 사용
Merge Join양쪽이 이미 정렬돼 있거나 정렬이 싸게 가능할 때앞단 Sort 비용, 정렬 입력 row 수

가장 흔한 사고는 row estimate 오차로 Nested Loop가 선택됐는데 실제 outer row가 폭증하는 경우다(가상 수치).

-- 위험: 예상 outer 5행 → 실제 4200행, 안쪽이 그만큼 반복된다
Nested Loop  (cost=0.42..512.0 rows=5 width=96)
             (actual time=0.1..1890.4 rows=4200 loops=1)
  ->  Seq Scan on customers
        (cost=0.00..40.0 rows=5 width=40)     -- 예상 5행
        (actual rows=4200 loops=1)            -- 실제 4200행 ← estimate 붕괴
  ->  Index Scan using orders_cust_idx on orders
        (cost=0.42..94.0 rows=3 width=56)
        (actual time=0.02..0.04 rows=2 loops=4200)  -- 4200번 반복!
대표 안티패턴
loops 폭증 = Nested Loop 비용 폭발

안쪽 노드의 loops가 outer 예상치(rows=5)가 아니라 실제 4200을 따라간다. 이때 해법은 보통 “인덱스 추가”가 아니라 outer 추정을 바로잡는 것(통계 갱신, 조건 상관관계 처리)이거나, 대량 조인이라면 Hash Join이 선택되도록 유도하는 것이다.

7Sort, Limit, Aggregate 판단법

LIMIT이 있어도 원하는 순서를 만들기 위해 많은 row를 먼저 읽고 정렬할 수 있다.

`Sort`는 결과 순서를 맞추기 위한 비용이다. 정렬 대상 row가 많거나 정렬 뒤 대부분을 버리는 구조라면 인덱스 정렬 가능성이나 조건 축소를 검토한다. `Limit`은 항상 빠르게 만든다고 볼 수 없다.

Aggregate는 그룹화나 집계 방식에 따라 비용이 달라진다. 그룹 수 추정이 틀리면 메모리 사용과 후속 정렬 비용도 달라질 수 있다. 실전 질문은 “정렬 전에 row가 충분히 줄었는가?”, “LIMIT이 조기 종료에 도움이 되는가?”, “집계 기준 컬럼의 분포를 알고 있는가?”다.

특히 정렬은 work_mem을 넘으면 메모리 정렬(quicksort)에서 디스크 정렬(external merge)로 떨어지며 비용이 크게 뛴다. 플랜의 Sort Method 줄이 결정적 단서다(가상 수치).

-- 디스크로 떨어진 정렬: Sort Method가 external merge
Sort  (cost=18540.0..18790.0 rows=100000 width=64)
      (actual time=420.1..512.7 rows=100000 loops=1)
  Sort Key: created_at DESC
  Sort Method: external merge  Disk: 8120kB   -- work_mem 초과 → 디스크 사용
  ->  Seq Scan on events (actual rows=100000 loops=1)

-- 건강한 경우: 인덱스가 순서를 제공해 Sort 노드 자체가 사라진다
Limit (actual rows=10 loops=1)
  ->  Index Scan Backward using events_created_idx on events
        (actual rows=10 loops=1)

비유

LIMIT 10은 “책에서 10페이지만 읽겠다”는 뜻이지만, “가장 최근 순서”를 요구하면 정렬이 인덱스로 보장되지 않는 한 DB는 전체를 먼저 줄 세운 뒤 위 10개만 건넨다. 즉 LIMIT은 “읽는 양”이 아니라 “건네는 양”을 줄일 뿐이다.

8통계와 Row Estimate

잘못된 통계는 잘못된 row estimate로 이어지고, 다시 잘못된 join/scan 선택으로 이어질 수 있다.

row estimate를 볼 때는 예상 rows와 실제 rows의 차이를 먼저 찾는다. 차이가 크면 인덱스 부재보다 통계, 데이터 편향, 조건 상관관계, 파라미터 분포 문제일 수 있다.

통계 문제를 다룰 때는 최근 데이터 변화가 있었는가, 조건 컬럼의 값 분포가 치우쳤는가, 여러 조건이 독립적이라고 보기 어려운가를 점검한다.

예상/실제 row 차이의 흔한 원인과 1차 점검
증상가능한 원인1차 점검·조치
예상이 실제보다 한참 작음통계가 오래됨, 대량 적재 직후ANALYZE 테이블 실행 후 플랜 재확인
특정 값에서만 추정이 빗나감값 분포 편향(소수 값에 집중)SET STATISTICS 상향 후 재수집
여러 조건 결합 시 추정 붕괴컬럼 간 상관관계(독립 가정 위배)확장 통계 CREATE STATISTICS 검토

아래는 통계 갱신과 분포 확인에 쓰는 대표 명령이다.

-- 1) 통계만 다시 수집(플랜이 즉시 달라질 수 있음)
ANALYZE orders;

-- 2) 편향이 심한 컬럼은 히스토그램 해상도를 올린다
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;

-- 3) 상관 있는 컬럼 묶음에 확장 통계 부여
CREATE STATISTICS orders_region_city (dependencies)
  ON region, city FROM orders;
ANALYZE orders;

-- 분포 확인: 현재 planner가 보고 있는 통계 들여다보기
SELECT null_frac, n_distinct, most_common_vals
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';
진단 순서
인덱스보다 통계를 먼저 의심하는 이유

예상/실제 row 차이가 10배 이상이면 인덱스를 추가해도 planner가 여전히 잘못된 조인·정렬을 고른다. 먼저 추정을 바로잡아야 인덱스가 의도대로 선택된다. 그래서 1차 조치는 거의 언제나 ANALYZE다.

9실습: 느린 쿼리 개선 루프

한 번에 하나만 바꿔야 어떤 조치가 효과를 냈는지 설명할 수 있다.

  1. 쿼리 텍스트, 바인딩 값의 성격, 실행 환경, 측정 시점을 기록한다.
  2. 변경 전 플랜을 캡처하고 핵심 노드를 표시한다.
  3. 병목 가설을 최소 2개 세운다.
  4. 인덱스 추가, 조건 변경, 쿼리 재작성, 통계 갱신 중 하나만 적용한다.
  5. 변경 후 플랜과 실제 실행 정보를 비교한다.
  6. 남은 리스크와 운영 적용 전 확인 사항을 적는다.

Q. 한 사이클에서 변경을 몇 개 적용했나?
A. 정확히 하나여야 한다. 인덱스 추가와 쿼리 재작성을 동시에 했다면 어느 쪽이 효과를 냈는지 설명할 수 없으므로 사이클을 분리한다.
Q. 보고서만 보고 동료가 같은 결과를 재현할 수 있나?
A. SQL 전문, 파라미터 성격, 환경(PG 버전·work_mem·캐시 상태), 변경 전후 플랜 캡처가 모두 있어야 한다. 하나라도 빠지면 재현 불가로 미완성 처리한다.

10퀴즈와 평가 루브릭

퀴즈는 용어 암기가 아니라 판단 근거를 확인한다.

  1. EXPLAIN과 EXPLAIN ANALYZE의 가장 중요한 차이는 무엇인가?
  2. Seq Scan이 보이면 항상 인덱스를 추가해야 하는가?
  3. Nested Loop가 위험해지는 대표 조건은 무엇인가?
  4. LIMIT 10이 있는데도 쿼리가 느릴 수 있는 이유는 무엇인가?
  5. 예상 rows와 실제 rows가 크게 다르면 어떤 의심을 해야 하는가?
  6. 좋은 실습 보고서에 반드시 들어가야 하는 증거는 무엇인가?

정답 요약: ANALYZE는 실제 실행 결과를 포함하며 안전성을 고려해야 한다. Seq Scan은 항상 문제는 아니다. Nested Loop는 반복 횟수가 커질 때 위험하다. LIMIT도 정렬과 읽기 비용을 없애지는 않는다. row estimate 차이는 통계와 분포 문제를 의심하게 한다. 좋은 보고서는 변경 전후 플랜, 핵심 노드 변화, 예상/실제 row 차이, 단일 변경 실험 근거를 포함한다.
