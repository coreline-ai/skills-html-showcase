Overview

AI 기능 출시는 빠른 감지와 안전한 되돌림이 핵심이다. 요약, 추천, 분류, 자동 작성처럼 사용자 판단에 영향을 주는 기능은 출시 전 별도 안전성 게이트가 필요하다.

이 플레이북은 "좋아 보이는 데모"가 아니라 데이터 권한, 실패 fixture, 보안 차단, 운영 rollback이 모두 준비되었는지 판단하는 출시 회의용 문서다.

“AI 기능은 되돌릴 수 있게 출시한다 — 모든 신규 기능은 feature flag 뒤에서 점진 롤아웃하고, 한 번의 토글로 즉시 롤백할 수 있는 경로를 먼저 확보한다.”

완벽한 사전 검증은 불가능하다. 실패는 막는 것이 아니라 빠르게 감지하고 안전하게 되돌리는 것이 목표다. flag·카나리·즉시 롤백 경로가 준비되지 않았다면, 평가를 아무리 통과해도 아직 출시 준비가 된 것이 아니다.

1출시 전 원칙

P0 실패 모드가 남아 있으면 출시하지 않고, P1 위험은 owner와 완화 일정이 있을 때만 허용한다.

데이터

개인정보, 삭제 요청, 출처 권한, 워크스페이스 경계를 확인한다. 모델 입력과 로그 보관 정책을 같은 표에서 검토한다.

품질

대표 질문 세트뿐 아니라 실패 fixture, 악성 입력, 회귀 fixture를 고정한다. 정확도 평균보다 P0 실패 0건이 먼저다.

보안

권한 없는 문서 노출, 프롬프트 공격, 로그 원문 저장, 민감 필드 재노출을 출시 차단 항목으로 둔다.

운영

feature flag, fallback UX, 온콜, 고객 공지, 신고율 대시보드, rollback drill을 출시 전 evidence로 남긴다.

2vt-05 체크리스트 플로우

1순위 vt=checklist-flow로 출시 전 확인 항목과 상태를 고정한다.

체크리스트 플로우는 "무엇을 확인했는가"가 아니라 "각 항목이 지금 어떤 상태인가"를 한눈에 보여주는 도구다. 항목마다 미시작 → 진행 중 → 차단 → 통과 네 가지 상태를 두고, 통과하지 못한 항목이 하나라도 차단(blocked)이면 출시 회의에서 자동으로 No-Go가 된다.

각 항목은 반드시 증거(evidence)를 가진다. "확인했다"는 주관적 보고가 아니라 fixture 실행 로그, 권한 테스트 결과 캡처, 대시보드 링크처럼 다른 사람이 다시 열어볼 수 있는 산출물을 남긴다. 증거가 없는 통과는 통과로 인정하지 않는다.

상태 어휘

차단(blocked) vs 보류(pending)

차단은 증거를 확인한 결과 출시 기준을 위반한 상태로, 수정 없이는 통과가 불가능하다. 보류는 아직 확인하지 못해 판단을 내릴 수 없는 상태다. 보류 항목이 남아 있으면 "모름"이므로 역시 출시하지 않는다.

3vt-06 품질 게이트

후순위 vt=quality-gate로 차단, 경고, 통과 기준을 분리한다.

품질 게이트는 평가 결과를 차단(block) · 경고(warn) · 통과(pass) 세 등급으로 나눠 자동 판정한다. 핵심은 "정확도 평균"이 아니라 P0 실패가 0건인가에 있다. 평균 점수가 높아도 권한 누락이나 차별적 응답이 한 건이라도 나오면 게이트는 차단이다.

게이트는 사람이 매번 눈으로 판단하지 않도록 수치 기준으로 고정한다. 예를 들어 회귀 fixture 통과율, 근거 표시율, 악성 입력 차단율에 임계값을 두고, 임계값 미달이면 자동으로 경고 또는 차단 등급이 매겨진다.

품질 게이트 등급별 판정 기준과 조치 (예시 임계값)
등급판정 기준조치예시 임계값
차단P0 실패 발생, 무단 노출, 차별 응답출시 중단, 원인 수정 후 재평가P0 실패 ≥ 1건
경고회귀 통과율·근거 표시율 하락베타 범위 축소, owner·완화 일정 필수회귀 통과율 < 95% (가상)
통과전 fixture 임계값 충족, P0 0건다음 게이트로 진행근거 표시율 ≥ 98% (가상)

대표 fixture

실제 사용 분포를 반영한 질문 세트. 평균 품질의 기준선을 본다.

실패 fixture

과거 사고·오답을 고정한 회귀 세트. 같은 실수가 다시 나오지 않는지 본다.

악성 fixture

인젝션·권한 우회·민감 정보 유도 입력. 방어 동작을 강제 점검한다.

흔한 함정

평균 점수로 P0 실패를 덮지 마라

전체 정확도 99%여도 1%에 권한 누락이나 차별 응답이 있으면 그 1%가 사고를 만든다. 게이트는 평균이 아니라 최악 케이스(P0)를 기준으로 판정해야 한다.

4wg-13 주석 플로우차트

권장 wg-13으로 출시 게이트의 정상 경로와 실패 경로를 클릭 가능한 구조로 보여준다.

주석 플로우차트는 출시 결정이 어떤 분기로 흘러가는지를 한 흐름으로 보여준다. 정상 경로는 데이터 → 품질 → 보안 → 운영 → 공지 다섯 게이트를 모두 통과해 5% 베타로 진입한다. 어느 게이트든 실패하면 흐름은 멈추고, 실패 종류에 따라 차단(원인 수정 후 재진입) 또는 완화(owner·일정 첨부 후 축소 출시) 경로로 갈라진다.

각 분기점에는 "무엇을 보고 어디로 가는가"가 주석으로 붙는다. 아래 의사코드는 게이트 흐름을 사람과 자동화가 동일하게 읽을 수 있도록 정리한 것이다.

gate_flow(feature):
    for gate in [데이터, 품질, 보안, 운영, 공지]:
        result = evaluate(gate)        # 증거 기반 판정
        if result == "block":
            return STOP("원인 수정 후 재진입")   # 실패 경로 A
        if result == "warn":
            require(owner, mitigation_plan)      # 실패 경로 B
            scope = "축소 베타"
    return START("5% 베타")            # 정상 경로

정상 경로

다섯 게이트 전부 pass. 5% 베타 시작 → 7일 모니터링 → 전체 확대 승인.

실패 경로 A · 차단

P0·무단 노출·차별 발생. 흐름 중단, 원인 수정 후 같은 게이트부터 재진입.

실패 경로 B · 완화

경고 등급. owner와 완화 일정을 첨부하면 축소 범위로만 진행 허용.

5wg-11 준비 상태판

권장 wg-11로 데이터, 품질, 보안, 운영 게이트 진행률을 보여준다.

준비 상태판은 출시 회의를 열기 전에 "지금 우리가 어디까지 와 있는가"를 한 장으로 정렬하는 보드다. 게이트별로 완료/전체 항목 수와 차단 건수를 함께 표시해, 진행률이 높아도 차단이 1건이라도 있으면 출시 불가임을 명확히 한다.

위 예시에서 품질 게이트는 5/6으로 거의 끝났지만 차단 1건이 있어 전체 출시 판정은 No-Go다. 상태판은 "얼마나 했는지"가 아니라 "막힌 게 있는지"를 먼저 보게 만드는 도구다.

6vt-14 책임 swimlane

후순위 vt=process-swimlane으로 PM, ML, 보안, 운영의 책임을 나눈다.

swimlane은 출시의 각 단계마다 누가 결정하고(owner) 누가 검토하는지(reviewer)를 명확히 나눠 "다들 봤겠지" 식의 책임 공백을 없앤다. 모든 게이트에는 단일 owner가 있어야 하며, owner는 증거를 제출하고 reviewer는 그 증거를 검증한다.

7vt-16 · wg-16 점진 출시 계획

후순위 vt=implementation-plan과 권장 wg-16으로 베타, 확대, 전체 출시의 조건을 고정한다.

점진 출시의 목적은 "문제가 생기면 작게 생기게" 만드는 것이다. 각 단계는 진입 조건 · 관찰 기간 · 다음 단계로 가는 졸업(graduation) 기준을 미리 정해 둔다. 조건을 만족하지 못하면 다음 단계로 넘어가지 않고, 악화되면 이전 단계나 fallback으로 되돌린다.

개념

관찰 기간(soak time)

새 단계에 들어간 뒤 지표가 안정적인지 지켜보는 최소 시간이다. 트래픽이 적은 시간대만 보고 넘어가면 문제를 놓치므로, 최소 한 번의 피크 트래픽을 포함하도록 잡는다. soak time이 끝나기 전에는 다음 단계로 확대하지 않는다.

8vt-18 · wg-18 위험 분류 보드

후순위 vt=triage-board와 권장 wg-18로 차단, 완화, 모니터링 위험을 정적 보드로 보여준다.

위험 분류 보드는 발견된 모든 위험을 차단(block) · 완화(mitigate) · 모니터링(monitor) 세 칸으로 나눈다. 분류 기준은 영향도와 발생 가능성이 아니라 더 단순하게 "이게 사고가 되면 되돌릴 수 있는가, 회복 가능한가"이다. 회복 불가능한 위험은 무조건 차단 칸으로 간다.

차단

회복 불가능·법적 위반. 출시 자체를 막는다. 예: 무단 데이터 노출, 차별적 추천.

완화

영향이 크지만 통제 가능. owner와 완화책을 붙여 축소 출시. 예: 비용 급증, 환각 빈도.

모니터링

영향이 작고 회복 쉬움. 지표만 추적. 예: 응답 길이 변동, 톤 일관성.

9wg-19 출시 플래그

권장 wg-19로 베타, 전체 확대, fallback, 위험 로그 플래그를 점검한다.

feature flag는 출시의 비상 정지 스위치다. 배포(deploy)와 노출(release)을 분리해, 코드는 이미 운영에 올라가 있어도 사용자에게는 flag로만 켜고 끈다. 플래그가 준비되어 있어야 트리거가 충족될 때 토론 없이 즉시 되돌릴 수 있다.

아래는 플래그 구성의 핵심 원칙이다. 기본값은 항상 안전한 쪽(fallback ON, 신규 기능 OFF)으로 두고, 켜는 행위만 명시적 결정으로 남긴다.

flags:
  ai_feature.enabled:      false   # 기본 OFF — 명시적으로만 켠다
  ai_feature.rollout_pct:  0       # 0 → 5 → 25 → 100, 단계별로만 증가
  ai_feature.fallback:     true    # 기본 ON — 실패 시 기존 동작 유지
  ai_feature.kill_switch:  ready   # 트리거 충족 시 즉시 enabled=false
출시 플래그 점검표 — 플래그·기본값·확인 항목
플래그안전 기본값확인 항목
enabledfalse대상 사용자만 켜지는지, 즉시 끌 수 있는지
rollout_pct0단계 값으로만 증가, 역방향(축소) 가능 여부
fallbacktrue실패·저신뢰 응답이 기존 동작으로 대체되는지
kill_switchreadydrill로 실제 차단까지 걸리는 시간 측정
검증 필수

끄는 동작을 실제로 한 번 해봐라

플래그가 "있다"는 것과 "작동한다"는 것은 다르다. 출시 전에 staging에서 kill_switch를 실제로 당겨 사용자 노출이 몇 초 안에 멈추는지 측정하고, 그 기록을 rollback drill 증거로 남긴다.

11영역별 추가 체크 그리드

데이터, 품질·평가, 보안·프라이버시, 운영·모니터링, 사용자 커뮤니케이션 다섯 영역의 점검 항목과 각 항목이 왜 출시 차단 조건이 되는지를 함께 본다.

데이터

출처 권한, 삭제 요청 반영, 워크스페이스 경계, 학습·로그 보관 동의를 점검한다.

품질·평가

대표·실패·악성·회귀 fixture를 고정하고 P0 실패 0건을 통과 기준으로 둔다.

보안·프라이버시

권한 없는 문서 노출, 프롬프트 인젝션, 로그 원문 저장, 민감 필드 재노출을 차단한다.

운영·모니터링

feature flag, fallback UX, 온콜, 신고율·비용 대시보드, rollback drill 증거를 남긴다.

사용자 커뮤니케이션

AI 한계와 수정 가능성, 신고 경로를 UI·릴리즈 노트·고객지원 macro에 반영한다.

영역별 추가 점검 항목과 출시 차단 사유
영역점검 항목증거왜 차단 조건인가
데이터출처 권한·삭제 요청·워크스페이스 경계 확인데이터 맵, 권한 테스트, 삭제 fixture권한 밖 데이터가 응답에 섞이면 프라이버시·계약 위반으로 즉시 롤백 사유가 된다.
품질·평가실패·악성·회귀 fixture에서 P0 실패 0건평가 리포트, 오답 샘플, 회귀 비교P0 실패가 남으면 사용자 판단을 잘못 유도해 회복 불가능한 피해로 이어진다.

비용·한도토큰·호출 비용 상한과 알림 임계값 설정예산 대시보드, 한도 알림 설정비용 폭주는 서비스 중단·계약 한도 초과로 직결되어 차단 대상이다.

Rollback Rule

롤백 트리거 1건이라도 충족되면 토론 없이 즉시 feature flag를 끈다.
