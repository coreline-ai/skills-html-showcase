★가장 먼저 챙길 것

"어떤 자료구조를 고르고, 어디에 TTL을 걸고, 무엇으로 원자성을 보장하느냐"가 실무의 80%입니다. 아래는 그 출발점입니다.

  • 자료구조 선택 · 단일 값/카운터는 String, 객체 필드는 Hash, 순서·큐는 List, 멤버십·교집합은 Set, 점수 정렬·랭킹은 Sorted Set, 이벤트 로그·소비자 그룹은 Stream.
  • 만료 · 키마다 EXPIRE key seconds 또는 쓰기와 동시에 SET key val EX 3600. 남은 시간은 TTL key(초) / PTTL key(ms).
  • 원자성 · 다중 명령은 MULTI/EXEC 또는 Lua EVAL. 단순 증감은 INCR/INCRBY 한 줄로 이미 원자적입니다.
  • 왕복 줄이기 · 같은 라운드에 여러 명령을 보내려면 트랜잭션이 아닌 파이프라인을 먼저 검토하세요(네트워크 RTT 절감).
  • 영속성 · 스냅샷이 필요하면 RDB, 손실 최소화가 중요하면 AOF. 운영에서는 둘을 함께 켜는 구성이 흔합니다(정확한 권장은 확인 필요).
  • 메모리 · maxmemory와 maxmemory-policy(예: allkeys-lru)를 설정해 가득 찼을 때 동작을 예측 가능하게 만드세요.

1핵심 자료구조와 대표 명령

여섯 가지 자료구조를 "무엇을 담나 · 대표 명령 · 주의점" 한 묶음으로 정리합니다. 같은 데이터라도 자료구조 선택이 성능과 코드 단순함을 가릅니다.

String — 값·카운터

용도 · 단일 문자열/숫자/직렬화 객체, 캐시 엔트리, 원자적 카운터.

대표 명령 · SET / GET / SETEX / INCR / INCRBY / SETNX / GETSET / MSET.

주의 · 값 하나가 수 MB로 커지면 단일 키가 핫스팟이 됩니다. JSON 통째 저장보다 필드 접근이 잦으면 Hash를 검토하세요.

List — 순서·큐

용도 · 양끝에서 넣고 빼는 큐/스택, 최근 항목 버퍼.

대표 명령 · LPUSH / RPUSH / LPOP / RPOP / LRANGE / LLEN / BLPOP(블로킹).

주의 · 가운데 임의 접근은 O(N)입니다. 본격 큐는 Stream + 소비자 그룹이 더 안전합니다.

Hash — 객체 필드

용도 · 필드/값 쌍으로 이뤄진 객체(사용자 프로필, 설정).

대표 명령 · HSET / HGET / HGETALL / HDEL / HINCRBY / HMGET.

주의 · HGETALL은 큰 해시에서 비용이 큽니다. 필요한 필드만 HMGET으로 가져오세요. 필드 단위 TTL은 버전 의존이라 확인이 필요합니다.

Set — 멤버십·집합

용도 · 중복 없는 집합, 태그, 고유 방문자, 집합 연산.

대표 명령 · SADD / SREM / SISMEMBER / SMEMBERS / SCARD / SINTER / SUNION.

주의 · SMEMBERS로 대형 셋을 통째로 읽으면 블로킹 위험이 있습니다. 대량 순회는 SSCAN으로 끊어 읽으세요.

Sorted Set — 점수·랭킹

용도 · 점수로 정렬되는 집합. 리더보드, 우선순위 큐, 시간순 인덱스.

대표 명령 · ZADD / ZRANGE / ZREVRANGE / ZRANK / ZSCORE / ZINCRBY / ZRANGEBYSCORE.

주의 · 옵션(WITHSCORES, REV, LIMIT 등)과 인자 순서가 버전에 따라 달라 확인이 필요합니다.

Stream — 이벤트 로그

용도 · 추가-전용 이벤트 로그, 소비자 그룹 기반 메시지 처리.

대표 명령 · XADD / XREAD / XRANGE / XLEN / XGROUP / XREADGROUP / XACK.

주의 · 무한히 자라지 않도록 XADD ... MAXLEN ~ N로 길이를 제한하고, 미확인 메시지는 XPENDING/XCLAIM으로 회수하세요.

자료구조가 정해지면 다음 질문은 거의 항상 두 가지입니다. 이 키는 언제 사라져야 하는가(TTL), 그리고 여러 명령을 묶을 때 무엇이 원자적으로 실행되는가입니다. 아래 표는 "이 데이터에는 무엇을 쓰나"를 빠르게 고르기 위한 요약입니다.

자료구조 선택 가이드 — 데이터 성격별 1차 후보
담는 데이터1차 후보핵심 명령대표 시간복잡도(개념)

2자료구조 선택을 단계로 풀어 보기

"사용자 프로필을 어디에 담을까"처럼 자주 부딪히는 결정을, 같은 데이터를 String·Hash·Sorted Set에 넣었을 때 무엇이 달라지는지 단계 토글로 비교하며 따라갑니다. 표는 후보 간 트레이드오프를, 단계는 결정의 흐름을 보여 줍니다.

개념 교보재 · Redis 자료구조 선택

같은 데이터, 다른 자료구조 — 무엇이 갈리나

예시는 사용자 프로필(닉네임·포인트·레벨) 하나입니다. 이 데이터를 String·Hash·Sorted Set 중 무엇에 담느냐에 따라 필드 접근 비용과 랭킹 조회 가능 여부가 결정됩니다.

후보별 트레이드오프

프로필 데이터를 담을 때 — 후보 자료구조 비교
기준String(JSON 통째)Hash(필드 분리)
한 필드만 읽기전체 역직렬화 필요HGET 한 번 · O(1)
한 필드만 갱신읽고-수정-쓰기(경합 위험)HSET / HINCRBY 원자적
객체 통째 캐싱SET 한 줄로 단순HSET 다중 필드
포인트로 랭킹불가 — 정렬 안 됨불가 — 별도 ZSet 필요

결정 흐름을 단계로 보기

str hash set zset nick pts key: user:42

1. 가장 단순한 선택 — String에 JSON 통째

프로필을 SET user:42 '{"nick":"coreline","pts":120,"lv":5}'로 한 줄에 저장합니다. 객체를 한꺼번에 읽고 쓸 때는 가장 간단합니다.

한계: 포인트 하나만 올리려 해도 전체를 읽어 파싱하고 다시 써야 합니다.

2. 필드 접근이 잦다 — Hash로 전환

같은 키를 HSET user:42 nick coreline pts 120 lv 5로 필드 분리하면 HGET user:42 pts로 한 필드만 읽고, HINCRBY user:42 pts 10으로 원자적 증가까지 됩니다.

nick·pts 같은 필드가 같은 키 안에서 독립적으로 다뤄집니다.

3. 랭킹이 필요하다 — Sorted Set을 보탠다

"포인트 상위 10명"은 Hash로는 못 풉니다. ZADD leaderboard 120 user:42로 점수-멤버를 따로 관리하면 ZREVRANGE leaderboard 0 9로 즉시 랭킹을 얻습니다.

핵심: 하나로 다 담지 말고, 접근 패턴마다 적합한 구조를 조합하세요.

3TTL·만료와 메모리 정책

캐시의 신뢰성은 "언제 사라지는가"를 명확히 정의하는 데서 나옵니다. TTL을 안 거는 키가 메모리 사고의 단골 원인입니다.

만료는 두 단계로 이해하면 깔끔합니다. 첫째, 키에 수명을 부여하는 방법 — 쓰기와 동시에 거는 SET key val EX 3600, 사후에 거는 EXPIRE key 3600, 절대 시각으로 거는 EXPIREAT key <unix>가 있습니다. 둘째, 남은 시간 조회와 해제 — TTL key는 남은 초를, PTTL key는 밀리초를 돌려주고, PERSIST key는 만료를 제거해 영구 키로 되돌립니다.

여기서 TTL(Time To Live)은 키가 자동 삭제되기까지 남은 수명을 뜻합니다. TTL key는 만료가 없으면 -1, 키 자체가 없으면 -2를 반환합니다(반환 규약은 버전 문서로 확인 필요). 또 하나 흔히 빠지는 함정은 기존 키를 다시 쓸 때 TTL이 의도와 다르게 동작하는 경우입니다. 예를 들어 일부 쓰기는 기존 TTL을 유지하고 일부는 초기화합니다. 캐시 갱신 로직에서 이를 혼동하면 키가 영영 사라지지 않거나, 반대로 너무 빨리 사라집니다.

함정
TTL 없는 키가 무한정 쌓인다

세션·임시 토큰·캐시를 TTL 없이 넣으면 메모리는 우상향하다 한계에서 eviction이 시작되고, 이때 무엇이 지워질지 통제되지 않으면 캐시 미스가 폭증합니다. "임시"라고 부르는 모든 키에는 만료를 부여하는 것을 기본 규칙으로 삼으세요.

메모리 상한과 가득 찼을 때의 동작은 별도로 정의해야 합니다. maxmemory로 상한을 두고, maxmemory-policy로 축출 정책을 지정합니다(예: noeviction, allkeys-lru, volatile-ttl 등). 정책 이름과 동작 세부, 기본값은 버전에 따라 다르므로 공식 문서를 확인하세요.

권장 패턴
쓰기와 동시에 TTL, 정책은 명시

캐시 값은 SET key val EX <ttl>처럼 만료를 한 번에 부여해 "TTL 누락"을 구조적으로 막습니다. 그리고 maxmemory + 캐시 전용 인스턴스에는 allkeys-lru 같은 정책을 명시해, 가득 찼을 때의 동작을 운영자가 예측할 수 있게 합니다.

4영속성: RDB와 AOF

Redis는 메모리 저장소지만 디스크 백업 옵션이 있습니다. 둘의 트레이드오프를 알면 "재시작하면 다 날아가나요?"에 정확히 답할 수 있습니다.

영속성에는 크게 두 방식이 있습니다. RDB(스냅샷)는 특정 시점의 데이터셋을 통째로 파일로 떠 둡니다. 복구가 빠르고 파일이 작지만, 마지막 스냅샷 이후 변경분은 유실될 수 있습니다. AOF(Append Only File)는 쓰기 명령을 로그로 누적해, 손실 창을 줄이는 대신 파일이 커지고 재생 시간이 늘 수 있습니다.

비유로 이해하기

RDB는 매시간 찍는 "전체 사진"이고, AOF는 그 사이의 모든 행동을 적는 "거래 장부"입니다. 사진만 있으면 복원이 빠르지만 마지막 사진 이후가 비고, 장부만 있으면 빠짐없이 재현하지만 장부를 처음부터 다시 읽어야 합니다.

그래서 실무에서는 둘을 함께 두어, 평소 복구는 RDB로 빠르게, 손실 최소화는 AOF로 보완하는 구성을 흔히 씁니다(정확한 권장 조합·동기화 주기는 환경별로 다름, 확인 필요).

RDB와 AOF 비교 — 개념 수준 요약
관점RDB (스냅샷)AOF (명령 로그)
저장 방식특정 시점 데이터셋을 파일로 덤프쓰기 명령을 순차 로그로 누적
데이터 손실 창마지막 스냅샷 이후 변경분동기화 주기에 따라 더 작음
복구 속도일반적으로 빠름로그 재생이 필요해 더 느릴 수 있음
파일 크기작은 편(압축)커질 수 있어 재작성(rewrite) 필요
제어 명령(예)SAVE / BGSAVEBGREWRITEAOF 등

fsync 정책, 스냅샷 트리거 조건, 혼합 영속성(AOF 안에 RDB 프리앰블) 같은 세부는 버전·설정에 크게 의존합니다. 정확한 옵션 이름과 기본값은 출처의 영속성 문서를 확인하세요. 또한 영속성은 백업이 아닙니다 — 별도 백업/복제 전략이 필요합니다.

5파이프라인·트랜잭션·Lua

"여러 명령을 빠르게" 보내는 것과 "여러 명령을 원자적으로" 묶는 것은 서로 다른 문제입니다. 둘을 혼동하면 성능 최적화로 정합성을 깨뜨립니다.

파이프라인은 여러 명령을 한 번에 전송해 네트워크 왕복(RTT)을 줄이는 기법입니다. 명령은 순서대로 실행되지만, 사이에 다른 클라이언트의 명령이 끼어들 수 있어 원자성을 보장하지는 않습니다. 순수하게 처리량을 위한 도구입니다.

트랜잭션은 MULTI로 시작해 명령을 큐에 쌓고 EXEC로 한꺼번에 실행합니다. 이 블록은 끼어들기 없이 실행되지만, 일반적인 RDBMS와 달리 명령 중간 실패 시 자동 롤백 개념이 다릅니다. WATCH로 낙관적 잠금(특정 키가 바뀌면 EXEC를 취소)을 구현할 수 있습니다.

용어
WATCH (Optimistic Locking)
WATCH key 이후 EXEC 직전까지 그 키가 변경되면 트랜잭션을 통째로 취소(nil 반환)합니다. "읽고-검사하고-쓰기"를 충돌 없이 수행하는 CAS 패턴의 기반입니다.

읽기-수정-쓰기를 진짜 한 덩어리로 묶고 싶다면 Lua 스크립트(EVAL / EVALSHA)가 가장 직접적입니다. 스크립트는 서버에서 원자적으로 실행되므로, 레이트리밋·재고 차감처럼 "검사와 변경이 분리되면 안 되는" 로직에 적합합니다. 다만 스크립트는 가능한 한 짧게 — 길고 무거운 스크립트는 단일 스레드 실행을 점유해 전체 지연을 키웁니다.

묶음 실행 기법 비교 — 언제 무엇을
기법목적원자성적합한 경우
파이프라인RTT 절감(처리량)보장 안 함독립적인 다수 명령을 빠르게
MULTI/EXEC끼어들기 없는 묶음 실행블록 단위여러 키를 함께 갱신
WATCH + MULTI낙관적 잠금(CAS)충돌 시 취소읽고-검사-쓰기, 재시도 허용
Lua EVAL서버측 원자 실행스크립트 단위검사와 변경이 분리되면 안 될 때

6흔한 패턴: 캐시·레이트리밋·큐·랭킹

자료구조와 원자성 도구를 조합하면 반복되는 네 가지 실무 패턴이 나옵니다. 각각의 "올바른 조합"과 자주 빠지는 함정을 짝으로 봅니다.

캐시 (Cache-Aside)

읽을 때 캐시 미스면 원본을 조회해 SET key val EX <ttl>로 채웁니다. 쓰기 시 캐시를 무효화(DEL)하거나 갱신합니다.

레이트리밋 (Fixed Window)

키를 INCR하고, 첫 증가 시 EXPIRE window를 겁니다. 카운트가 한도를 넘으면 거절. 정밀하려면 Lua나 Sorted Set 기반 슬라이딩 윈도우.

큐 / 작업 처리

간단하면 LPUSH+BRPOP, 재처리·소비자 그룹이 필요하면 Stream(XADD/XREADGROUP/XACK).

랭킹 / 리더보드

점수를 ZADD/ZINCRBY로 갱신, 상위 N은 ZREVRANGE key 0 N-1 WITHSCORES, 개인 순위는 ZREVRANK.

함정
레이트리밋을 GET→비교→SET로 구현

"값을 읽고, 한도와 비교하고, 다시 쓰는" 세 단계를 분리하면 동시 요청 사이에 경쟁 조건이 생겨 한도를 초과 허용합니다. 트래픽이 몰릴수록 정확히 그 순간 한도가 무너집니다.

해결
증가와 만료를 원자적으로

증가 자체가 원자적인 INCR을 쓰고, "이 키가 새로 생겼을 때만 만료를 건다"를 Lua 한 스크립트로 묶으면 경쟁 조건이 사라집니다. 슬라이딩 윈도우가 필요하면 타임스탬프를 점수로 쓰는 Sorted Set + 구간 밖 멤버 제거를 같은 스크립트 안에서 처리합니다.

캐시 패턴에서도 비슷한 정합성 문제가 나타납니다. 대표적으로 캐시 스탬피드 — TTL이 동시에 만료된 인기 키가 한꺼번에 미스되면 원본 DB에 요청이 폭주합니다. TTL에 약간의 지터를 주거나, 미스 시 한 클라이언트만 재생성하도록 짧은 잠금(예: SET lock val NX EX)을 거는 방식으로 완화합니다.

재고 차감도 같은 결의 문제입니다. "재고가 0보다 크면 1 줄인다"는 검사와 변경이 분리되면 안 되는 전형으로, WATCH+MULTI로 낙관적 잠금을 걸어 충돌 시 재시도하거나 Lua 스크립트로 "검사 후 차감"을 서버에서 한 번에 처리합니다. 후자는 재시도 로직이 없어 코드가 단순합니다.

7명령 시퀀스 예제

복붙 전에 키 이름·TTL·한도를 환경에 맞게 바꾸세요. 아래는 형식을 보여주는 예시이며, 정확한 옵션은 공식 문서를 확인합니다.

캐시 채우기 (TTL 동시 부여)

# 미스 시 원본 조회 후 1시간 캐시
SET user:42:profile "{...json...}" EX 3600
GET user:42:profile
# 원본이 바뀌면 무효화
DEL user:42:profile

고정 윈도우 레이트리밋 (개념)

# 1분에 100회 제한 — 첫 증가에서만 만료를 건다
INCR rate:ip:203.0.113.5
EXPIRE rate:ip:203.0.113.5 60 NX   # NX 동작은 버전 확인 필요
# 경쟁 조건을 없애려면 위 두 줄을 Lua EVAL 하나로 묶는다

리더보드 (Sorted Set)

ZADD game:leaderboard 1500 "player:alice"
ZINCRBY game:leaderboard 50 "player:alice"   # 점수 가산
ZREVRANGE game:leaderboard 0 9 WITHSCORES     # 상위 10명
ZREVRANK game:leaderboard "player:alice"      # 본인 순위(0부터)

스트림 큐 + 소비자 그룹

XADD jobs:email * to "u@example.com" tpl "welcome"
XGROUP CREATE jobs:email workers $ MKSTREAM
XREADGROUP GROUP workers w1 COUNT 1 STREAMS jobs:email >
XACK jobs:email workers 1700000000000-0       # 처리 완료 확인

낙관적 잠금 트랜잭션

WATCH stock:sku:777
# 애플리케이션에서 GET stock:sku:777 읽어 0보다 큰지 확인
MULTI
DECR stock:sku:777
EXEC            # WATCH한 키가 바뀌었으면 nil(취소) → 재시도
CHECKLIST · 운영 체크리스트

8배포 전 점검 7가지

  1. 자료구조 적합성 — 데이터 성격에 맞는 자료구조를 골랐는가? JSON 통째 String 대신 Hash가, List 큐 대신 Stream이 맞지 않은지 검토했는가?
  2. TTL 누락 점검 — "임시"라고 부르는 모든 키(세션·토큰·캐시)에 만료가 붙어 있는가? 갱신 로직에서 TTL이 의도대로 유지/초기화되는가?
  3. 메모리 정책 — maxmemory와 maxmemory-policy를 명시해, 가득 찼을 때 축출 동작을 예측 가능하게 했는가?
  4. 영속성·백업 — RDB/AOF 구성이 손실 허용 범위에 맞는가? 영속성과 별개로 외부 백업·복제 전략이 있는가?
  5. 원자성 — 검사와 변경이 분리되면 안 되는 로직(레이트리밋·재고)을 INCR/WATCH+MULTI/Lua로 원자화했는가?
  6. 핫키·블로킹 — KEYS·대형 HGETALL·SMEMBERS 같은 블로킹/전체스캔을 피하고 SCAN 계열로 끊어 읽는가?
  7. 버전 확인 — 사용 중인 명령 옵션·기본값·시간복잡도를 해당 Redis 버전 공식 문서로 최종 확인했는가?
