REST vs GraphQL vs gRPC 선택 기준

스키마·계약, 오버/언더페칭, 캐싱, 스트리밍, 타입 안전, 코드 생성, 그리고 브라우저·모바일·내부 서비스 적합성까지 — 세 패러다임을 기준별로 펼쳐 놓고 상황에 맞는 답을 고르는 매트릭스.

읽는 데 약 11분 · 백엔드/플랫폼 엔지니어 · 작성 2026-05

1먼저 정리하자: 무엇을 고르는 결정인가

"어느 게 제일 좋냐"가 아니라 "이 경계에서 무엇을 최적화하느냐"의 문제다.

REST, GraphQL, gRPC는 서로 대체재가 아니라 서로 다른 제약을 최적화한 도구다. 같은 시스템 안에서 외부 공개 API는 REST, 프런트엔드 집계 계층은 GraphQL, 내부 서비스 간 통신은 gRPC로 공존하는 구성이 오히려 흔하다. 그러니 선택의 출발점은 "트렌드"가 아니라 "이 API가 누구와, 어떤 경계를 넘어, 어떤 데이터를 주고받는가"다.

세 가지를 한 줄로 좁히면 이렇다. REST는 HTTP 자원 모델을 그대로 따르는 아키텍처 스타일이고, GraphQL은 클라이언트가 필요한 필드만 질의하는 쿼리 언어 + 런타임이며, gRPC는 Protocol Buffers 계약 위에서 HTTP/2로 동작하는 RPC 프레임워크다. 추상화의 결이 다르기 때문에 "표 한 줄로 우열을 매긴다"는 발상 자체가 함정이 된다.

이 문서는 다음 세 질문에 답할 수 있게 구성했다. (1) 기준별로 셋이 어떻게 다른가(매트릭스), (2) 특정 기준에서 누가 유리한가(승자), (3) 무엇을 얻고 무엇을 내주는가(트레이드오프). 마지막에 상황별 최종 추천으로 닫는다.

용어
스키마 / 계약(Contract)
클라이언트와 서버가 합의한 "요청·응답의 형태" 명세. gRPC는 .proto 파일, GraphQL은 SDL(Schema Definition Language)이 계약 그 자체이고 강제력이 강하다. REST는 OpenAPI 같은 별도 문서로 계약을 표현하지만 런타임이 강제하지는 않아 "문서와 실제가 어긋날" 여지가 크다.

이 차이가 뒤에 나올 거의 모든 항목 — 타입 안전, 코드 생성, 오버페칭, 버전 관리 — 의 뿌리다. 계약을 코드가 강제하느냐, 사람이 문서로 지키느냐가 갈림길이다.

2기준별 비교 매트릭스

10개 기준으로 세 패러다임을 같은 잣대 위에 올린다. 셀의 "유리" 표시는 절대 우열이 아니라 해당 기준 한정 강점이다.

표 1. REST · GraphQL · gRPC 기준별 비교 (셀은 일반적 경향이며 구현·버전에 따라 달라질 수 있음)
기준 REST GraphQL gRPC
전송/프로토콜 HTTP/1.1·2, JSON 중심 주로 HTTP POST 단일 엔드포인트, JSON HTTP/2 + 바이너리(Protobuf)
스키마·계약 OpenAPI 등 별도 문서(런타임 비강제) SDL이 곧 계약(강제) .proto가 곧 계약(강제)
오버/언더페칭 엔드포인트 고정 → 발생하기 쉬움 필요한 필드만 질의 → 최소화 메서드 단위 응답 고정(중간)
HTTP 캐싱 URL+메서드 기반 캐싱 강력 표준 HTTP 캐시 어려움(별도 전략 필요) HTTP 캐시 비적용(앱 레벨 캐시)
스트리밍 제한적(SSE·청크 등 보강 필요) Subscription(주로 WebSocket) 양방향 스트리밍 1급 지원
타입 안전 약함(문서 의존) 강함(스키마 기반) 매우 강함(Protobuf 타입)
코드 생성 OpenAPI 도구로 가능(품질 편차) 성숙(클라 타입·훅 생성) 1급 기능(다언어 stub)
브라우저 직접 호출 기본 지원(fetch) 기본 지원(fetch/클라) 프록시 필요(gRPC-Web)
버전 관리 URL/헤더 버저닝(명시적) 필드 deprecate·진화형 필드 번호 기반 호환 진화
관측·디버깅 curl·브라우저로 즉시 확인 쿼리 가시성 좋으나 도구 의존 바이너리라 사람이 읽기 어려움

표를 한 문장으로 압축하면 이렇다. REST는 캐싱·디버깅·범용성, GraphQL은 페칭 효율과 프런트엔드 생산성, gRPC는 성능·스트리밍·타입 안전이 강점이다. 어느 칸도 전 항목을 독식하지 못한다는 점이 핵심이다.

비유로 이해하기

REST는 정해진 메뉴판이다 — 주문(엔드포인트)은 명확하지만 "샐러드에서 토마토만 빼주세요"가 잘 안 된다. GraphQL은 뷔페 접시다 — 원하는 것만 정확히 담을 수 있지만 주방(서버) 입장에선 어떤 조합이 올지 예측이 어렵다. gRPC는 주방끼리 쓰는 전용 인터폰이다 — 빠르고 군더더기 없지만 손님(브라우저)이 직접 들을 수는 없다. 셋 다 강점만큼 약점도 분명하니, 비유는 직관을 줄 뿐 실제 선택은 아래 기준으로 따져야 한다.

3같은 요구, 세 가지 구현

"사용자 한 명과 그 사용자의 주문 목록을 한 번에 가져오기" — 동일한 요구를 REST·GraphQL·gRPC로 각각 구현하고 코드·장단점·트레이드오프를 나란히 비교한다.

코드 비교

사용자 + 주문 목록 가져오기

요구: id로 사용자 1명과 그 사용자의 주문 목록(주문 id·금액)을 클라이언트가 한 화면에서 쓸 형태로 받기. 같은 요구를 세 패러다임으로 구현해 호출 방식·계약·페칭 효율의 차이를 드러낸다.

R

REST

자원 엔드포인트 · 다중 라운드트립

GET /users/42
GET /users/42/orders

// 클라이언트가 두 응답을 합친다
const user = await fetch(`/users/${id}`)
const orders = await fetch(`/users/${id}/orders`)

▲ 장점

  • URL 단위 HTTP 캐싱 강력
  • curl로 즉시 검증·디버깅

▼ 단점

  • 두 번 호출(N+1 라운드트립)
  • 응답 필드 고정 → 오버페칭
호출 2회 캐싱 ◎ 계약 비강제
G

GraphQL 화면 적합

필요 필드만 · 단일 쿼리

query {
  user(id: 42) {
    name
    orders { id amount }
  }
}
// 한 번의 POST로 정확히 필요한 필드만

▲ 장점

  • 한 번 호출, 오버페칭 없음
  • 화면별 필드 조합 자유

▼ 단점

  • 리졸버 N+1·복잡도 폭발
  • HTTP 캐싱 어려움
호출 1회 페칭 ◎ BFF 기본
P

gRPC

.proto 계약 · 바이너리 RPC

rpc GetUserWithOrders(UserReq)
    returns (UserOrders);

// 생성된 stub 호출 (타입 안전)
res = stub.GetUserWithOrders(
  UserReq(id=42))

▲ 장점

  • 바이너리 + HTTP/2로 저지연
  • .proto로 다언어 타입 안전

▼ 단점

  • 브라우저는 gRPC-Web 프록시 필요
  • HTTP 캐시·디버깅 불리
호출 1회 타입 ◎ 내부 서비스

같은 요구라도 경계가 다르면 답이 갈린다. 공개·캐싱이면 REST, 화면 다양성이면 GraphQL, 내부 저지연이면 gRPC — 위 세 코드의 호출 횟수와 "내주는 것"을 그대로 다음 절의 기준별 승자·트레이드오프로 이어 읽으면 된다.

4기준별 승자: 어떤 항목에서 누가 앞서나

전체 우승자는 없다. 기준을 쪼개면 각자의 명확한 1등 구간이 보인다.

캐싱·범용성

REST

URL+메서드가 캐시 키가 되므로 CDN·브라우저·역방향 프록시 캐시를 그대로 활용한다. 별도 클라이언트 없이 curl로 즉시 검증 가능해 공개 API·디버깅에서 압도적이다.

페칭 효율·프런트엔드

GraphQL

화면이 요구하는 필드만 한 번에 가져와 오버/언더페칭을 줄인다. 화면마다 응답 모양이 다른 복잡한 UI, 다수의 백엔드를 하나로 합치는 BFF 계층에서 생산성이 가장 높다.

성능·스트리밍·타입

gRPC

바이너리 직렬화 + HTTP/2 멀티플렉싱으로 지연·대역폭에 유리하고, 양방향 스트리밍이 1급이다. .proto 계약과 다언어 stub 생성으로 내부 서비스 간 타입 안전이 가장 단단하다.

주의할 점은 "승자"가 곧 "도입 이유"는 아니라는 것이다. 예를 들어 캐싱이 트래픽의 병목이 아닌 시스템에서는 REST의 캐싱 우위가 의미를 덜 가지고, 응답 모양이 단순한 API에서는 GraphQL의 페칭 우위가 과한 복잡성으로 돌아온다. 승자 표는 "내 시스템의 진짜 병목이 어느 기준인가"를 먼저 정한 뒤에 읽어야 한다.

권장 판단 순서
병목 → 기준 → 패러다임

먼저 이 API의 가장 큰 제약(공개 캐싱? 화면 다양성? 서비스 간 지연?)을 한 가지로 정한다. 그 다음 위 매트릭스에서 해당 기준의 강자를 본다. 마지막에 나머지 기준에서 치명적 약점이 없는지 교차 확인한다. 순서를 뒤집어 "기술부터 고르고 이유를 붙이면" 거의 항상 후회한다.

5트레이드오프: 무엇을 얻고 무엇을 내주나

각 패러다임의 강점은 동전의 양면이다. 도입 전에 "내주는 쪽"을 먼저 본다.

REST가 내주는 것

단순함과 범용성을 얻는 대신, 화면별로 응답이 고정되어 오버/언더페칭이 쉽게 생긴다. N개의 화면이 미세하게 다른 데이터를 원하면 엔드포인트가 늘어나거나 클라이언트가 여러 번 호출(N+1 라운드트립)하게 된다. 또한 계약이 런타임에 강제되지 않아 OpenAPI 문서와 실제 응답이 어긋나는 드리프트를 운영으로 관리해야 한다.

GraphQL이 내주는 것

페칭 효율을 얻는 대신, 서버 복잡도가 클라이언트로부터 들어온다. 임의 쿼리를 허용하므로 N+1 쿼리, 쿼리 깊이·복잡도 폭발, 권한 검사 분산 같은 문제를 별도로 막아야 한다. 표준 HTTP 캐싱이 어렵고(단일 POST 엔드포인트), 관측·요금제·레이트리밋 설계가 REST보다 까다롭다.

함정
"GraphQL은 호출이 줄어드니 무조건 빠르다"

네트워크 라운드트립은 줄어도, 한 쿼리가 수십 개 리졸버를 깨우며 백엔드에서 N+1 DB 조회를 유발하면 오히려 더 느려진다. DataLoader 배칭, 쿼리 복잡도 제한, 영속 쿼리(persisted query) 없이 공개 GraphQL을 그대로 노출하면 성능·보안 모두 위험하다.

gRPC가 내주는 것

성능과 타입 안전을 얻는 대신, 사람이 읽고 디버깅하기 어려운 바이너리가 된다. 브라우저에서 직접 호출하려면 gRPC-Web 프록시 계층이 필요하고, 기존 HTTP 캐시·WAF·API 게이트웨이 생태계와의 궁합이 REST만큼 매끄럽지 않다. .proto 변경 시 다언어 stub을 함께 배포·동기화하는 빌드 파이프라인 비용도 따라온다.

요약하면 트레이드오프 축은 셋 다 같다 — 유연성을 키우면 운영·관측·보안 부담이 커지고, 성능·계약 강제를 키우면 범용성·접근성이 줄어든다. 공짜 점심은 없다.

6상황별 최종 추천

병목과 경계가 정해졌다면, 아래 휴리스틱으로 1차 결정을 내릴 수 있다.

  1. 공개 API·서드파티 연동·캐싱이 중요 → REST. 안정적 계약, 광범위한 도구·CDN 호환, 낮은 학습 곡선. OpenAPI로 문서·코드 생성을 보완한다.
  2. 화면마다 데이터 요구가 다른 복잡한 프런트엔드 / 여러 백엔드 집계(BFF) → GraphQL. 단, 공개 노출 시 영속 쿼리·복잡도 제한·DataLoader를 기본값으로 둔다.
  3. 내부 마이크로서비스 간 저지연 통신 / 스트리밍 / 다언어 환경 → gRPC. .proto 단일 계약으로 타입 안전과 성능을 동시에 확보한다.
  4. 실시간 양방향 데이터(체결·텔레메트리·채팅) → 서버 간은 gRPC 스트리밍, 브라우저 종단은 WebSocket/SSE 또는 GraphQL Subscription으로 분리 설계한다.
  5. 외부는 REST, 내부는 gRPC, 프런트는 GraphQL의 혼합이 대규모 시스템의 현실적 정답인 경우가 많다. "하나로 통일"을 목표로 삼지 말고 경계별 최적을 조합한다.

마지막 점검: 새 패러다임을 고르기 전에 "현재 팀이 운영·디버깅·보안까지 감당할 수 있는가"를 자문한다. 기술 적합성만큼 운영 성숙도가 실패와 성공을 가른다. 의심스러우면 가장 단순한 REST에서 시작해, 구체적 병목이 측정될 때 GraphQL/gRPC로 부분 이행하는 편이 안전하다.
