pr-summarizer SKILL.md 감사 리포트

1목적과 스킬 정체성

이 스킬이 무엇을 하는지, 어디서부터 어디까지 책임지는지 한 문장으로 말할 수 있어야 좋은 SKILL.md입니다.

먼저 분명히 해두면, pr-summarizer는 이 리포트를 위해 만든 가상의 예시 스킬입니다. 실제 배포된 도구가 아니라, SKILL.md 작성 품질을 진단하는 방법을 보여주기 위한 표본입니다. 아래에서 인용하는 원문 발췌도 흔히 보이는 초안 패턴을 재구성한 것입니다.

감사 대상 스킬의 자기소개는 이렇게 시작합니다. 그대로 옮기면 다음과 같습니다.

원문 발췌 · SKILL.md 상단

name: pr-summarizer
description: PR을 요약해 주는 스킬. 코드 리뷰를 도와준다. PR 관련 작업이 필요할 때 사용.

문제는 "PR 관련 작업"이라는 표현입니다. 라벨 달기, 머지, 충돌 해결, 리뷰어 지정도 전부 "PR 관련 작업"입니다. 스킬의 정체성은 "무엇을 입력받아 무엇을 산출하는가"로 좁혀질 때 비로소 호출 가능한 도구가 됩니다. 지금 description은 사람에게는 그럴듯하지만, 모델이 다른 스킬과 구별해 고를 근거가 약합니다.

권장 패턴
한 문장 정체성 + 경계

"diff를 입력받아 요약·리스크·리뷰 포인트 세 블록을 마크다운으로 출력한다. 코드를 수정하거나 PR 상태를 바꾸지 않는다." 처럼 산출물과 비책임 범위를 함께 적으면 호출 판단과 안전 경계가 동시에 서명됩니다.

정리하면 목적 자체는 가치 있고 범위도 현실적이지만, 정체성 문장이 추상적이라 트리거와 출력 정의가 연쇄적으로 흔들립니다. 이 리포트는 그 연쇄를 따라가며 여섯 개 축으로 점수를 매깁니다.

2트리거 점수: 언제 켜지는가

트리거는 "이 단어가 보이면 켜라"가 아니라 "이런 상황에서 켜고, 이런 상황에서는 끄라"여야 합니다.

현재 SKILL.md의 트리거 문구는 "PR 관련 작업이 필요할 때 사용"이 전부입니다. 발동 조건만 있고 억제 조건(SKIP)이 없습니다. 그 결과 모델은 PR 머지, 리뷰 코멘트 회신, 브랜치 정리 요청에서도 이 스킬을 부를 수 있습니다. 트리거 정확성은 발동·억제가 짝을 이룰 때 올라갑니다.

발동(TRIGGER)
2/5

"요약" 의도는 잡히지만 PR 링크·diff·코드 리뷰 요청 등 구체 신호가 명시되지 않아 과발동 위험이 큽니다.

억제(SKIP)
0/5

SKIP 조건이 전무합니다. 머지·라벨·CI 재실행 같은 비요약 작업과 구분할 근거가 없습니다.

모호어 제거
1/5

"PR 관련 작업"이라는 포괄어가 핵심 모호성의 원인입니다. 동사를 "요약·평가·정리"로 좁혀야 합니다.

트리거는 짧은 예시 문장 몇 개로 빠르게 강해집니다. "이 PR 요약해줘", "diff 보고 리스크 짚어줘", "리뷰 포인트 정리해줘"는 발동, "이 PR 머지해줘", "리뷰어 지정해줘"는 억제로 명시하면 분류 정확도가 크게 오릅니다.

함정
트리거를 description 안에 욱여넣기

한 줄 description에 발동·억제·예시를 모두 압축하면 어느 것도 또렷하지 않습니다. description은 "무엇을 하는가" 한 문장으로 두고, TRIGGER/SKIP/예시는 본문에 별도 절로 분리하는 편이 호출 판단과 가독성 모두에 유리합니다.

3워크플로우 점수: 단계가 실행 가능한가

좋은 워크플로우는 "diff를 읽고 잘 요약한다"가 아니라, 누가 봐도 같은 순서로 재현할 수 있는 단계 목록입니다.

SKILL.md의 워크플로우 절은 다음과 같이 한 줄로 끝납니다.

원문 발췌 · Workflow

1. PR을 읽는다. 2. 요약한다. 3. 결과를 보여준다.

세 줄 모두 동사는 있지만 입력 형태·처리 방법·중간 산출물·실패 처리가 비어 있습니다. "PR을 읽는다"가 URL fetch인지, 붙여넣은 diff 파싱인지, gh CLI 호출인지 알 수 없습니다. 단계는 다음 네 가지를 갖출 때 실행 가능해집니다 — 입력 정규화, 처리 규칙, 산출 형식, 실패 분기.

4섹션 진단: 6개 항목 0~5 채점

목적·트리거·입출력·워크플로우·품질 게이트·완료 기준을 한 표로 모아, 어디를 먼저 고쳐야 하는지 한눈에 봅니다.

용어
품질 게이트 (Quality Gate)
출력을 사용자에게 보이기 전에 통과해야 하는 자기 검수 조건의 묶음입니다. 예: "리스크 항목은 diff에 근거가 있어야 하고, 코드 정상 동작 여부를 단정하지 않는다." 게이트가 있으면 출력 품질의 하한선이 생깁니다.

입력·출력 정의(각 2점)는 중간 수준입니다. 출력 블록 이름(요약/리스크/리뷰)은 description에서 유추되지만, 본문에 명시적 템플릿이 없어 호출마다 구조가 흔들립니다. 입력은 "diff"라는 단어만 있고 통합·바이너리·대용량 처리 규칙이 없습니다.

5강점과 리스크

고치기 전에, 살릴 것과 막을 것을 먼저 구분합니다. 좋은 초안은 골격이 멀쩡한 경우가 많습니다.

점수가 낮다고 해서 처음부터 다시 쓸 필요는 없습니다. 이 스킬은 범위 설정과 출력 의도가 건강합니다. 코드를 직접 수정하지 않고 요약·평가에 머무르려는 태도는 안전 경계 설계에 유리한 출발점입니다.

강점 1

산출물이 세 블록(요약·리스크·리뷰)으로 자연스럽게 나뉘어, 출력 템플릿을 만들기 쉽습니다.

강점 2

"읽기 전용" 성향이 암묵적으로 깔려 있어, 비책임 범위를 명문화하면 그대로 안전 경계가 됩니다.

강점 3

워크플로우가 3단계로 단순해, 각 단계를 확장하는 방식의 점진적 개선이 가능합니다.

반대로, 명문화되지 않은 부분이 그대로 운영 리스크가 됩니다. 특히 사실과 추론을 섞는 문제가 위험합니다. 요약 스킬이 "이 변경은 버그를 고쳤다"처럼 diff만으로는 확인할 수 없는 결과를 단정하면, 리뷰어가 잘못된 신뢰를 갖게 됩니다.

리스크
근거 없는 단정과 대용량 diff

품질 게이트 부재로 "정상 동작한다", "성능이 개선된다" 같은 검증 불가 진술이 새어 나올 수 있습니다. 또한 입력 상한이 없어 수천 줄 diff에서 환각·누락이 발생할 위험이 있습니다. 둘 다 게이트와 입력 상한으로 막아야 합니다.

요약하면 리스크는 대부분 "안 적어서 생기는" 종류입니다. 정체성·게이트·완료 기준을 명문화하는 것만으로 강점은 유지하면서 위험을 상당 부분 닫을 수 있습니다.

6좋은 출력은 어떻게 생겼나: 주석 달린 PR

품질 게이트를 통과한 pr-summarizer 출력은 이런 모습이어야 합니다. 같은 diff에 리스크/리뷰 포인트를 라인 단위로 붙이되, 모든 주석은 변경된 라인에 근거를 두고 검증 불가한 단정을 피합니다.

추상적인 점수표 대신, 개선된 스킬이 실제로 만들어낼 출력을 한 장면으로 보겠습니다. 아래는 pr-summarizer가 작은 PR 하나를 받아 라인별로 주석을 붙인 결과의 예시입니다. 왼쪽 diff의 표식(!/i)을 누르면 오른쪽 해당 노트로, 노트의 라인 링크를 누르면 다시 diff로 이동합니다 — 모두 CSS 앵커 동작이며 추가 스크립트는 없습니다.

핵심은 모든 노트가 "리스크인지 리뷰 포인트인지"를 라벨로 구분하고, 색(critical/warn/info)에 더해 텍스트 라벨과 라인 근거를 함께 제시한다는 점입니다. critical 노트조차 "버그다"라고 단정하지 않고 "이런 입력에서 이런 위험이 있다"로 멈춥니다 — 이것이 5번에서 지적한 근거 없는 단정을 막는 품질 게이트의 실제 모습입니다.

7개선 권고와 개선된 SKILL.md 발췌

무엇을 먼저 고칠지 우선순위를 정하고, 그대로 붙여 쓸 수 있는 개선본 발췌를 제시합니다.

점수 분포를 보면 손대야 할 순서가 분명합니다. 0점인 품질 게이트·완료 기준을 먼저 신설하고, 그다음 트리거와 워크플로우를 구체화합니다. 정체성 문장은 모든 절의 기준점이 되므로 가장 먼저 한 줄 고쳐 둡니다.

개선 우선순위 로드맵
순위개선 항목기대 효과
P0정체성 한 문장 + 비책임 범위 고정이후 모든 절의 판단 기준 확보
P0품질 게이트 신설(사실/추론 분리, 코드 단정 금지)출력 하한선과 안전 경계 동시 확보
P1완료 기준 정의(3블록 + 게이트 통과)"언제 끝났는가"를 모델·사용자가 공유
P1TRIGGER/SKIP/예시 분리과발동 차단, 분류 정확도 향상
P2워크플로우 단계별 입력→처리→산출 + 실패 분기재현 가능한 실행 절차 확보
P2입력 상한·정규화 규칙 명시대용량 diff 환각·누락 방지

아래는 위 우선순위를 반영한 개선된 SKILL.md 발췌입니다. 전체가 아니라 가장 약했던 절들을 다시 쓴 부분이며, 그대로 옮겨도 동작 가능한 형태로 정리했습니다.

개선본 발췌 · SKILL.md

name: pr-summarizer
description: GitHub PR의 diff를 입력받아 "요약·리스크·리뷰 포인트" 세 블록을 마크다운으로 생성하는 읽기 전용 스킬. 코드나 PR 상태는 변경하지 않는다.

## TRIGGER
- 사용자가 PR/diff를 주며 요약·리스크·리뷰 포인트 정리를 요청할 때
- "이 PR 요약", "diff 리스크 짚어줘", "리뷰 포인트 정리" 류의 의도

## SKIP
- 머지·라벨·리뷰어 지정·CI 재실행 등 PR 상태 변경 요청
- diff 없이 일반 코드 작성/수정 요청

## INPUT
- 허용: 붙여넣은 unified diff, PR URL(권한 있을 때), gh CLI 출력
- 상한: 변경 1,500줄 초과 시 파일 단위로 분할 요약, 바이너리는 파일명만 기재

## WORKFLOW
1. 입력 정규화 — diff 소스를 식별하고 파일별 변경으로 파싱한다(부족하면 INPUT 요청).
2. 변경 분석 — 파일을 기능/테스트/설정/마이그레이션으로 분류하고 변경 의도를 추론한다.
3. 요약 생성 — "무엇이 왜 바뀌었나"를 5줄 이내로 정리한다(동작 정상 여부는 단정 금지).
4. 리스크/리뷰 — diff에 근거가 있는 항목만 우선순위와 함께 적는다.
5. 출력 조립 — 아래 3블록 템플릿으로 마크다운을 조립한다(빈 블록은 "해당 없음").
6. 실패 처리 — diff 누락/과대/접근 실패 시 작업을 멈추고 필요한 입력을 명확히 요청한다.

## QUALITY GATE (출력 전 검수)
- 사실(diff에 보임)과 추론(의도 해석)을 구분해 표기한다.
- "정상 동작/성능 개선" 등 diff만으로 확인 불가한 결과를 단정하지 않는다.
- 모든 리스크 항목은 변경된 파일/라인에 근거를 댄다.

## DONE (완료 기준)
- 요약·리스크·리뷰 3블록이 모두 채워지거나 "해당 없음"으로 표기됨
- 품질 게이트 3개 항목을 모두 통과함
- PR 상태를 변경하지 않았음

이 발췌만 반영해도 섹션 진단 합계는 9/35에서 30점대로 오를 것으로 추정됩니다(동일 척도 재채점 시 확인 필요). 핵심은 분량이 아니라 각 절이 "다음에 무엇을 할지"를 모델에게 분명히 지시하는가입니다.

바로 적용해볼 것
  1. description을 "무엇을 입력받아 무엇을 출력하는가" 한 문장으로 고쳐 쓴다.
  2. TRIGGER 아래에 SKIP 절을 신설하고 머지·라벨 등 비요약 작업을 명시한다.
  3. 워크플로우 각 줄을 "입력→처리→산출" 형태로 다시 적고, 마지막에 실패 분기를 한 줄 추가한다.
  4. QUALITY GATE에 "사실/추론 분리"와 "코드 동작 단정 금지"를 최소 2개 적는다.
  5. DONE을 "3블록 충족 + 게이트 통과 + 상태 미변경"으로 정의한다.
출처와 검토 기준

pr-summarizer는 SKILL.md 작성 품질을 설명하기 위한 가상의 예시 스킬이며, 인용한 원문/개선본 발췌는 일반적인 초안 패턴을 재구성한 것입니다. 진단 척도는 Anthropic의 Agent Skills 문서와 GitHub PR/diff 표준 개념을 참고했고, 특정 제품 동작이나 수치는 단정하지 않았습니다.
