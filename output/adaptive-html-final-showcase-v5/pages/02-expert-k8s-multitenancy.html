Platform Engineering · Governance Report

Kubernetes 멀티테넌시 프로덕션 거버넌스 리포트

네임스페이스·RBAC·NetworkPolicy·ResourceQuota·PodSecurity를 한 장의 거버넌스 모델로 묶는다. 소프트/하드 격리의 경계, 리스크 매트릭스, 90일 로드맵, 그리고 운영팀이 실제로 돌려볼 수 있는 검증 체크리스트까지 정리한다.

대상: 플랫폼팀 · SRE · 보안 난이도: 고급 범위: 단일 클러스터 멀티테넌시 업데이트: 2026-05
Executive Summary

핵심 결론 먼저

단일 Kubernetes 클러스터에서 여러 팀·서비스·고객을 함께 돌릴 때, "격리되어 있다"는 느낌과 "실제로 격리된다"는 보증은 다르다. 네임스페이스는 이름의 경계일 뿐, 그 자체로 보안·네트워크·자원 경계를 만들지 않는다. 경계는 RBAC, NetworkPolicy, ResourceQuota/LimitRange, Pod Security Standards를 명시적으로 쌓아 올릴 때 비로소 생긴다.

이 리포트는 한 가지 입장을 분명히 한다. 멀티테넌시는 "기능"이 아니라 "거버넌스 모델"이다. 어떤 단일 기능도 테넌트를 격리해 주지 않으며, 격리 수준은 항상 위협 모델과 신뢰 경계에서 거꾸로 정의된다. 사내 팀끼리 나눠 쓰는 소프트 멀티테넌시와, 서로 적대적일 수 있는 외부 고객을 한 클러스터에 태우는 하드 멀티테넌시는 같은 단어를 쓰지만 전혀 다른 요구사항을 갖는다.

지금 점검할 것

네임스페이스는 있는데 NetworkPolicy 기본 거부가 없다면, 테넌트 간 트래픽은 사실상 전부 열려 있다. 가장 흔한 격리 착각이다.

가장 큰 리스크

공유 컨트롤 플레인과 공유 커널. 소프트 격리에서 컨테이너 이스케이프나 RBAC 과다 권한은 곧 다른 테넌트 침해로 이어진다.

현실적 권고

적대적 신뢰 경계가 있다면 단일 클러스터 하드 격리에 의존하지 말고, 노드 격리 또는 클러스터 분리를 진지하게 검토한다.

1멀티테넌시란 무엇을 격리하는가

테넌트, 신뢰 경계, 그리고 "소프트"와 "하드"가 실제로 가르는 지점.

멀티테넌시를 설계하기 전에 답해야 할 질문은 "어떻게 나눌까"가 아니라 "누구로부터 누구를 보호하는가"다. 테넌트(tenant)는 자원과 권한을 공유하지 않아야 하는 격리 단위를 뜻한다. 같은 회사의 두 개발팀일 수도, 같은 제품의 dev/staging/prod 환경일 수도, 서로 모르는 외부 고객일 수도 있다. 이 세 경우의 위협 모델은 완전히 다르다.

용어
신뢰 경계 (Trust Boundary)
한쪽의 코드·사용자·워크로드가 다른 쪽에 대해 적대적일 수 있다고 가정해야 하는 선. 멀티테넌시의 격리 강도는 항상 이 경계를 기준으로 거꾸로 설계된다. 경계가 "협력적"이면 소프트 격리로 충분하고, "적대적"이면 하드 격리가 필요하다.

업계에서는 흔히 격리를 두 갈래로 나눈다. 소프트 멀티테넌시(soft multi-tenancy)는 서로를 어느 정도 신뢰하는 내부 테넌트를 가정한다. 실수와 자원 경쟁은 막되, 악의적 공격까지 완전히 차단하지는 않는다. 하드 멀티테넌시(hard multi-tenancy)는 테넌트가 서로 적대적일 수 있다고 가정하고, 한 테넌트의 침해가 다른 테넌트로 번지지 않도록 설계한다.

비유로 이해하기

소프트 격리는 오픈형 공유 오피스다. 각 팀에 지정 책상과 사물함은 있지만 벽은 없다. 같은 회사 동료라 큰 문제는 없되, 누군가 마음먹으면 옆 책상 서류를 들춰볼 수 있다.

하드 격리는 각자 잠금장치가 있는 독립 사무실이다. 다만 약점이 있다. 건물 골조(커널)와 정문(컨트롤 플레인)은 여전히 공유한다. 골조에 결함이 생기면 모든 사무실이 흔들린다. 그래서 진짜 적대적 환경에서는 "건물 자체를 분리"하는 클러스터 분리를 고려하게 된다.

중요한 것은 Kubernetes가 제공하는 기본 단위인 네임스페이스가 이 경계를 자동으로 만들어 주지 않는다는 점이다. 네임스페이스는 API 객체의 이름 충돌을 막고 정책을 거는 앵커일 뿐이다. 같은 노드에서 같은 커널을 공유하는 한, 네임스페이스만으로는 커널 수준 격리가 성립하지 않는다.

2격리 레이어 — 다섯 개의 통제를 쌓는다

네임스페이스 위에 RBAC·NetworkPolicy·Quota·PodSecurity·노드 격리를 어떻게 겹쳐 올리는가.

멀티테넌시 격리는 단일 스위치가 아니라 겹겹의 통제(defense in depth)다. 각 레이어는 서로 다른 차원의 격리를 담당하며, 하나라도 비면 그 차원은 열려 있는 셈이다. 아래 표는 각 통제가 무엇을 막고 무엇을 막지 못하는지를 한눈에 정리한 것이다.

표 1 — 멀티테넌시 격리 레이어와 책임 범위
레이어 막는 것 막지 못하는 것 기본값 위험
네임스페이스 객체 이름 충돌, 정책 부착 지점 제공 네트워크·자원·커널 격리 경계로 오인하기 쉬움
RBAC API 권한 과다 부여, 교차 테넌트 객체 접근 네트워크·런타임 침해 와일드카드·cluster-admin 남발
NetworkPolicy 테넌트 간 동서(east-west) 트래픽 L7 인증, 애플리케이션 취약점 기본은 전부 허용
ResourceQuota / LimitRange 자원 독점, 노이지 네이버 보안 침해, 권한 상승 미설정 시 무제한 점유
Pod Security Standards 특권 컨테이너, 호스트 접근 권한 상승 커널 0-day, 사이드채널 레이블 누락 시 미적용
노드 격리 커널 공유로 인한 이스케이프 전파 컨트롤 플레인 공유 위험 비용·운영 복잡도 증가

표에서 가장 중요한 메시지는 "기본값 위험" 열이다. 대부분의 격리 통제는 기본적으로 비어 있거나 열려 있다. NetworkPolicy를 하나도 적용하지 않으면 모든 파드가 서로 통신할 수 있고, ResourceQuota를 걸지 않으면 한 테넌트가 클러스터 자원을 독점할 수 있다. 멀티테넌시 설계의 절반은 "기본 거부(default deny)"를 명시적으로 켜는 일이다.

3RBAC — 권한 경계를 좁게 유지한다

네임스페이스 스코프 Role, 최소 권한, 그리고 ClusterRole 남용이라는 함정.

RBAC는 "누가 어떤 API 객체에 무엇을 할 수 있는가"를 정의한다. 멀티테넌시에서 핵심은 테넌트의 권한을 자기 네임스페이스 안으로 가두는 것이다. 테넌트에게는 Role + RoleBinding(네임스페이스 스코프)을 주고, 클러스터 전역 권한을 의미하는 ClusterRole + ClusterRoleBinding은 플랫폼팀이 신중하게 통제한다.

함정
cluster-admin과 와일드카드 권한

편의를 위해 테넌트 서비스 계정에 cluster-admin이나 verbs: ["*"], resources: ["*"]를 부여하면 네임스페이스 경계가 즉시 무의미해진다. 한 테넌트가 다른 테넌트의 시크릿을 읽거나, RBAC 객체를 스스로 수정해 권한을 상승시킬 수 있다. escalate·bind 동사와 시크릿 읽기 권한은 특히 위험하다.

권한 설계는 "필요한 것만 추가"하는 화이트리스트 방식이어야 한다. 처음부터 넓게 주고 나중에 좁히는 방식은 거의 실패한다. 또한 테넌트가 자기 네임스페이스에서 RoleBinding을 만들 수 있게 허용했다면, 그들이 자기 권한을 클러스터 권한으로 끌어올리지 못하도록 부여 가능한 권한의 상한을 함께 통제해야 한다.

권장 패턴
네임스페이스 스코프 최소 권한 + 정기 감사

테넌트별로 사전 정의된 Role 템플릿(읽기 전용 / 배포 / 관리)을 제공하고, ClusterRoleBinding은 플랫폼팀 승인 절차를 거친다. kubectl auth can-i --list와 RBAC 감사 도구로 과다 권한을 주기적으로 점검하고, 사용하지 않는 바인딩은 회수한다. 권한 변경은 GitOps로 코드 리뷰를 거치게 한다.

4NetworkPolicy — 동서 트래픽을 기본 거부로

"기본 전부 허용"을 뒤집고, 테넌트 간 통신을 명시적 화이트리스트로 바꾼다.

Kubernetes의 기본 네트워크 모델에서는 모든 파드가 서로 통신할 수 있다. 멀티테넌시에서 이는 곧 한 테넌트가 다른 테넌트의 서비스에 자유롭게 접속할 수 있다는 뜻이다. NetworkPolicy는 이 흐름을 제어하지만, NetworkPolicy를 지원하는 CNI(예: Calico, Cilium 등)가 설치되어 있어야 실제로 동작한다. 정책 객체를 만들어도 CNI가 이를 시행하지 않으면 아무 효과가 없다는 점을 반드시 확인해야 한다.

권장 출발점은 네임스페이스별 기본 거부(default-deny) 정책이다. 모든 인그레스/이그레스를 막은 뒤, 필요한 통신만 레이블 셀렉터로 열어 준다. 같은 테넌트 내부 통신, 공용 DNS, 그리고 명시적으로 허용한 공유 서비스만 통과하도록 한다.

# 네임스페이스 내 모든 인그레스/이그레스 기본 거부
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: tenant-a
spec:
  podSelector: {}        # 네임스페이스의 모든 파드
  policyTypes:
    - Ingress
    - Egress
함정
DNS를 깜빡한 기본 거부

이그레스를 전부 막으면 파드가 kube-dns/CoreDNS에도 접근하지 못해 모든 이름 해석이 실패한다. 애플리케이션이 "네트워크 연결 안 됨"이 아니라 "호스트를 찾을 수 없음"으로 깨지면서 원인 파악이 어려워진다. 기본 거부와 함께 UDP/TCP 53번 포트로 향하는 DNS 이그레스는 반드시 명시적으로 허용한다.

주의할 점은 NetworkPolicy가 L3/L4(IP·포트) 수준 통제라는 것이다. 누가 연결할 수 있는지는 정하지만, 연결된 뒤 신원 인증이나 요청 권한 검사는 하지 않는다. 강한 테넌트 간 신뢰 경계가 필요하다면 서비스 메시의 mTLS와 L7 인가 정책을 추가 레이어로 검토한다. NetworkPolicy는 1차 방벽이지 만능 자물쇠가 아니다.

5ResourceQuota·LimitRange — 노이지 네이버를 통제한다

자원 독점을 막는 것은 보안만큼이나 중요한 격리 차원이다.

격리는 보안만의 문제가 아니다. 한 테넌트가 CPU·메모리를 무한정 요구해 다른 테넌트의 파드를 굶기는 노이지 네이버(noisy neighbor) 문제는 가용성을 직접 해친다. ResourceQuota는 네임스페이스 단위로 총량 상한(CPU·메모리·파드 수·PVC·오브젝트 개수 등)을 정하고, LimitRange는 개별 컨테이너의 기본값과 최소/최대 한도를 정의한다. 둘은 짝으로 쓸 때 효과가 난다.

표 2 — ResourceQuota와 LimitRange의 역할 구분
구분 ResourceQuota LimitRange
적용 단위 네임스페이스 전체 합계 개별 파드/컨테이너
통제 대상 총 requests/limits, 파드·서비스·PVC 개수 컨테이너별 min/max, default request/limit
미설정 시 네임스페이스가 클러스터 자원 독점 가능 requests 없는 파드가 스케줄링·QoS를 왜곡
함께 쓰는 이유 Quota가 켜지면 requests/limits 미지정 파드는 거부됨 LimitRange가 기본값을 채워 거부를 방지

핵심 메커니즘 하나를 짚는다. ResourceQuota로 CPU/메모리 requests·limits에 상한을 걸면, requests나 limits를 지정하지 않은 파드는 생성이 거부된다. 이때 LimitRange로 합리적인 기본값을 주입하면 테넌트가 매번 값을 적지 않아도 정책이 깨지지 않는다. 이 조합이 빠지면 "갑자기 배포가 거부된다"는 운영 사고가 흔하게 발생한다.

6Pod Security Standards와 노드 격리

런타임 권한을 조이고, 커널 공유 위험을 어디까지 감수할지 결정한다.

Pod Security Standards(PSS)는 파드의 보안 컨텍스트를 세 등급으로 정의한다. privileged(제한 없음), baseline(알려진 권한 상승 차단), restricted(강하게 강화). Pod Security Admission(PSA)은 이 표준을 네임스페이스 레이블로 강제하며, enforce·audit·warn 모드를 둘 수 있다. 멀티테넌트 네임스페이스의 합리적 출발점은 restricted enforce다.

용어
Pod Security Admission (PSA)
Pod Security Standards를 네임스페이스 단위로 시행하는 내장 어드미션 컨트롤러. pod-security.kubernetes.io/enforce: restricted 같은 레이블로 등급을 지정한다. 레이블을 붙이지 않으면 아무 제한도 걸리지 않으므로, 멀티테넌시에서는 "레이블 누락 = 무방비"임을 기억해야 한다.

그런데 PSS·NetworkPolicy·RBAC를 모두 갖춰도 남는 근본 한계가 있다. 모든 테넌트가 같은 노드의 같은 리눅스 커널을 공유한다는 사실이다. 컨테이너 이스케이프나 커널 취약점이 발생하면 한 테넌트의 침해가 같은 노드의 다른 테넌트로 전파될 수 있다. 이것이 단일 클러스터 하드 멀티테넌시의 구조적 약점이다.

완화 방안은 단계적이다. (1) 노드 격리로 테넌트별 전용 노드 풀을 두어 커널 공유 반경을 좁힌다. taint/toleration과 node affinity로 워크로드를 분리하지만, 이는 비용과 운영 복잡도를 키운다. (2) 샌드박스 런타임(예: gVisor, Kata Containers 계열)으로 커널 노출을 줄이는 방법도 있으나, 적용 가능 여부와 성능 영향은 환경별 검증이 필요하다. (3) 진정으로 적대적인 경계라면 클러스터 자체를 분리하는 편이 가장 단순하고 강력하다. 단, 컨트롤 플레인은 여전히 공유될 수 있으므로 격리 목표를 명확히 한다.

비유로 이해하기

네임스페이스·RBAC·NetworkPolicy가 "사무실 문에 단 좋은 자물쇠"라면, 커널 공유는 "모든 사무실이 같은 환기 덕트로 연결돼 있는 것"과 같다. 문을 아무리 잘 잠가도 덕트를 타면 옆방으로 넘어갈 수 있다. 노드 격리는 덕트를 층별로 끊는 일이고, 클러스터 분리는 건물을 통째로 나누는 일이다.

7리스크 매트릭스

발생 가능성과 영향도로 본 멀티테넌시 위험 우선순위.

아래 매트릭스는 단일 클러스터 멀티테넌시에서 자주 관측되는 위험을, 영향도와 흔함을 기준으로 정렬한 것이다. 등급(High/Mid/Low)은 일반적 환경 기준이며, 실제 등급은 각 조직의 위협 모델과 신뢰 경계에 따라 재평가해야 한다(조직별 확인 필요).

매트릭스가 주는 교훈은 단순하다. 가장 흔한 위험은 화려한 0-day가 아니라 "기본값을 안 닫은 설정"이다. RBAC 과다 권한, 네트워크 기본 허용, Quota 부재, 정책 레이블 누락은 모두 발생 가능성이 높고, 코드와 정책으로 막을 수 있는 영역이다. 거버넌스의 첫 투자는 여기에 집중해야 한다.

8의사결정 카드 — 어떤 격리 모델을 택할까

신뢰 경계·규제·비용을 기준으로 세 가지 길 중 하나를 고른다.

아래 세 카드는 가장 흔한 분기점이다. 핵심 질문은 항상 같다. "테넌트가 서로 적대적일 수 있는가?" 이 답이 모델을 결정하고, 비용과 운영 책임 모델이 뒤따른다.

선택지 A

공유 클러스터 · 소프트 격리

적합: 같은 조직의 협력적 내부 팀, dev/staging 환경.

구성: 네임스페이스 + RBAC + NetworkPolicy + Quota + PSA baseline/restricted.

비용/책임: 가장 저렴하고 운영 단순. 플랫폼팀이 정책 일괄 통제, 테넌트는 자기 네임스페이스만 책임.

선택지 B

공유 클러스터 · 노드 격리

적합: 부분적 적대 가능성, 규제 워크로드 분리, 강한 성능 격리 요구.

구성: A의 모든 통제 + 테넌트 전용 노드 풀(taint/affinity) + PSA restricted enforce.

비용/책임: 노드 활용률 저하로 비용 증가. 커널 공유 반경은 좁아지나 완전 제거는 아님.

선택지 C

클러스터 분리

적합: 명백히 적대적인 외부 고객, 강한 규제·격리 보증 요구.

구성: 테넌트별 또는 그룹별 독립 클러스터. 플릿 관리 도구로 다수 클러스터 운영.

비용/책임: 가장 비싸고 운영 부담 큼. 대신 격리 보증이 가장 명확하고 폭발 반경이 최소.

결정 기준

한 줄 규칙: "이 테넌트의 침해가 다른 테넌트에 닿으면 안 되는데, 단일 클러스터 통제만으로 그걸 보증할 수 있다고 감사·규제 앞에서 말할 수 있는가?" 자신 있게 "예"라면 A 또는 B, 망설인다면 C를 진지하게 검토한다. 비용은 격리 보증의 가격표다.

  4. M3 · 지속 · 감사와 재평가예정

    RBAC 권한·NetworkPolicy 커버리지·Quota 사용률·PSS 위반을 정기 리포트로 점검. 신뢰 경계가 적대적으로 바뀌면 노드 격리/클러스터 분리(선택지 B·C)로 재검토.

Validation Checklist

검증 체크리스트 — 실제로 돌려본다

정책이 "선언"되었는지가 아니라 "시행"되는지를 확인한다. 아래 항목은 운영팀이 클러스터에서 직접 검증할 수 있는 형태로 정리했다.

  • RBAC: 테넌트 서비스 계정으로 kubectl auth can-i --list를 실행해 권한이 자기 네임스페이스로 한정되는지 확인한다. 다른 네임스페이스의 시크릿을 읽으려 시도해 거부되는지 본다.
  • NetworkPolicy: 테넌트 A의 파드에서 테넌트 B의 서비스로 연결을 시도해 차단되는지 검증한다. 같은 테넌트 내부 통신과 DNS 해석은 정상 동작해야 한다. CNI가 정책을 실제로 시행하는지 함께 확인한다.
  • ResourceQuota: requests/limits 없는 파드 배포가 거부되는지, LimitRange 기본값이 주입되는지 확인한다. Quota 초과 배포가 막히는지도 본다.
  • Pod Security: privileged: true 또는 hostPath를 사용하는 파드를 restricted 네임스페이스에 배포해 admission 단계에서 거부되는지 확인한다.
  • 정책 누락 방지: 정책 레이블·Quota·기본 거부가 빠진 신규 네임스페이스/파드 생성이 어드미션에서 거부되거나 자동 보정되는지 확인한다.
  • 감사 가시성: RBAC 변경, 정책 위반, Quota 사용률이 로그·대시보드로 추적 가능한지 확인한다. (대시보드를 넘어선 질문 기반 점검은 다음 글의 옵저버빌리티 주제와 이어진다.)
다음 행동

이번 주에 시도해볼 것

  1. 클러스터의 모든 테넌트 네임스페이스에 NetworkPolicy 기본 거부 + DNS 허용이 적용돼 있는지 점검하고, 빠진 곳을 채운다. 가장 흔하고 위험한 구멍이다.
  2. cluster-admin과 와일드카드 RBAC를 전수 조사한다. 테넌트 계정에 붙어 있다면 최소 권한 Role 템플릿으로 교체한다.
  3. requests/limits 없는 파드가 배포되는 네임스페이스에 ResourceQuota + LimitRange를 짝으로 적용해 노이지 네이버를 차단한다.
  4. 주요 테넌트 네임스페이스를 PSA restricted로 올리기 전에 warn/audit로 현재 위반을 먼저 가시화한다.
  5. 현재 테넌트 중 "서로 적대적일 수 있는" 경계가 있다면, 노드 격리 또는 클러스터 분리 비용을 한 페이지로 산정해 의사결정 테이블에 올린다.
출처와 검토 기준

Kubernetes 공식 문서와 CNCF 멀티테넌시 가이드, 보안 표준 문서를 검토해 작성했습니다. 버전별 기본값·기능 가용성(CNI의 NetworkPolicy 시행 여부, 샌드박스 런타임 적용 가능성 등)은 운영 환경에서 직접 확인이 필요합니다. 리스크 등급은 일반적 기준이며 조직별 위협 모델에 따라 재평가해야 합니다.
