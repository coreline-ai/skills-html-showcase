PostgreSQL 인덱스 설계 실습 모듈

인덱스는 "걸면 빨라지는 마법"이 아니라, 읽기 속도를 사기 위해 쓰기 비용과 저장 공간을 지불하는 거래입니다. B-tree·GIN·GiST·BRIN의 쓰임새, 복합 인덱스 열 순서와 선택도, 부분·표현식·커버링 인덱스, 그리고 EXPLAIN (ANALYZE) 읽는 법까지 예제와 퀴즈로 익히는 실습 모듈입니다.

1학습 목표

이 모듈을 마치면 "일단 인덱스를 건다"가 아니라, "이 쿼리에 이 인덱스가 왜 필요한지"를 실행계획으로 증명할 수 있습니다.

인덱스는 자주 묻는 질문에 미리 만들어둔 목차와 같습니다. 목차가 많을수록 찾기는 빨라지지만, 책 내용이 바뀔 때마다 모든 목차를 함께 고쳐야 합니다. 인덱스도 똑같이 읽기를 빠르게 해주는 대신 쓰기(INSERT·UPDATE·DELETE)를 무겁게 만들고 디스크를 더 씁니다. 수강 후 여러분은 다음을 직접 할 수 있어야 합니다.

  • 쿼리의 접근 패턴을 보고 B-tree·GIN·GiST·BRIN 중 무엇이 맞는지 고를 수 있다.
  • 복합 인덱스의 열 순서가 왜 결과를 좌우하는지를 등호·범위·정렬·선택도 관점에서 설명할 수 있다.
  • 부분 인덱스·표현식 인덱스·커버링(INCLUDE) 인덱스를 언제 써야 더 작고 빠른지 판단할 수 있다.
  • EXPLAIN (ANALYZE, BUFFERS) 출력에서 예상 행 수와 실제 행 수의 괴리, Seq Scan vs Index Scan을 읽어낼 수 있다.
  • 인덱스가 쓰기 성능과 블로트에 끼치는 비용을 의식하고, 불필요한 인덱스를 제거할 수 있다.

2시작 전 준비

개념을 외우기 전에, 우리가 다루는 "인덱스"가 데이터베이스 안에서 어떤 물건인지부터 분명히 합니다.

실습을 따라 하려면 PostgreSQL 인스턴스 하나와, 행이 충분히 많은 테이블 하나면 됩니다(수만~수십만 행이면 차이를 보기에 좋습니다). 통계가 최신이어야 실행계획이 의미 있으므로, 데이터를 채운 뒤에는 한 번 ANALYZE를 돌려 두세요. 실습은 운영 DB가 아니라 복제본이나 스테이징에서 하는 것을 권장합니다.

두 가지 개념만 짚고 갑니다. 첫째, 실행계획입니다. EXPLAIN은 플래너가 "이렇게 실행하겠다"는 추정 계획을 보여주고, EXPLAIN (ANALYZE)는 쿼리를 실제로 실행해 추정과 실제(시간·행 수)를 함께 보여줍니다. BUFFERS 옵션을 더하면 읽은 페이지 수까지 나옵니다. ANALYZE는 쿼리를 진짜로 실행하므로, 쓰기 쿼리에는 트랜잭션으로 감싸 롤백하는 등 주의가 필요합니다(자세한 주의점은 예제 섹션에서 다시 다룹니다). 둘째, 데이터가 저장되는 곳과 인덱스가 가리키는 곳을 구분하는 일입니다.

용어
선택도 (selectivity)
어떤 조건이 테이블 전체에서 얼마나 적은 행만 골라내는지를 나타내는 비율입니다. 100만 행 중 10행만 남기는 조건은 선택도가 높고(좁고), 절반을 남기는 조건은 선택도가 낮습니다(넓음). 인덱스는 선택도가 높은 조건에서 가장 효과가 큽니다. 플래너는 통계로 이 비율을 추정해 인덱스 사용 여부를 결정합니다.

인덱스가 "조건을 빨리 찾아주는" 것과 "행의 모든 컬럼을 빨리 돌려주는" 것은 다른 문제입니다. 그 차이는 데이터가 실제로 어디에 저장되는지에서 비롯됩니다.

용어
힙(heap)과 인덱스
PostgreSQL에서 실제 행 데이터는 "힙"이라는 테이블 본체에 저장되고, 인덱스는 그 힙의 위치(tid)를 가리키는 별도 자료구조입니다. 그래서 인덱스로 조건은 빨리 찾아도 행의 다른 컬럼을 읽으려면 보통 힙을 한 번 더 방문해야 합니다. 이 "힙 방문" 비용을 줄이는 것이 커버링 인덱스와 인덱스 온리 스캔의 핵심입니다.
비유로 이해하기

인덱스는 도서관의 색인 카드입니다. 제목 색인이 있으면 제목으로는 빨리 찾지만, 저자로 찾으려면 저자 색인이 따로 있어야 합니다. 색인 카드를 늘릴수록 검색은 빨라지지만, 책 한 권이 들어오고 나갈 때마다 모든 관련 색인 카드를 손으로 고쳐 꽂아야 합니다. 카드함이 가득 차면 공간도 더 듭니다. 인덱스 설계는 "어떤 검색을 자주 하는가"와 "책이 얼마나 자주 드나드는가" 사이의 거래입니다.

3개념 강의 ① — 인덱스 타입과 쓰임새

"무엇으로 검색하는가"가 인덱스 종류를 가릅니다. 같은 컬럼이라도 검색 방식이 다르면 맞는 인덱스가 달라집니다.

PostgreSQL은 여러 인덱스 접근 방식을 제공합니다. 가장 많이 쓰는 넷만 정확히 구분하면 대부분의 결정을 내릴 수 있습니다. 핵심은 "이 컬럼을 등호·범위로 찾는가, 포함 관계로 찾는가, 공간/근접으로 찾는가, 아니면 물리적 순서에 기대는가"입니다.

인덱스 타입별 쓰임새 한눈에
타입잘 맞는 검색대표 사례주의점
B-tree등호(=), 범위(< > BETWEEN), 정렬, 접두 LIKE('abc%')대부분의 일반 컬럼, 기본키, 외래키 조회기본값. 못 정하겠으면 보통 정답
GIN한 행 안의 여러 값에 대한 포함 검색jsonb 키/값, 배열 포함, 전문 검색(tsvector)빌드·쓰기 비용 큼, 인덱스 크기 큼
GiST겹침·근접·범위 등 기하/특수 연산지리좌표(PostGIS), 범위 타입, 최근접 검색연산자 클래스가 타입을 지원해야 함
BRIN물리 저장 순서와 값이 상관된 매우 큰 테이블의 범위append-only 로그·시계열의 시간 컬럼저장 순서가 흐트러지면 효과 급감

표를 외우기보다 결정 흐름으로 기억하세요. 일반 컬럼을 등호·범위로 찾으면 B-tree. jsonb·배열·전문 검색처럼 한 행 안에 든 여러 값을 포함 검색하면 GIN. 좌표·범위처럼 겹침/근접을 따지면 GiST. 시간순으로 계속 쌓이기만 하는 거대한 테이블의 범위 조회면 BRIN입니다.

비유로 이해하기

BRIN은 색인 카드가 아니라 책장에 붙인 "이 칸은 1월, 다음 칸은 2월" 같은 라벨입니다. 책이 시간순으로 꽂혀 있을 때만 "3월 자료는 저 칸만 보면 된다"가 성립합니다. 누군가 책을 마구 섞어 꽂으면(데이터가 시간순으로 쌓이지 않으면) 라벨은 거의 쓸모가 없어집니다.

BRIN이 매력적인 이유는 크기입니다. 같은 시계열 컬럼이라도 BRIN은 B-tree보다 훨씬 작아, 거대 테이블에서 저장 공간을 거의 쓰지 않으면서 넓은 범위 조회를 가속할 수 있습니다. 단, 그 전제는 "물리 순서와 값의 상관"입니다.

개념 강의 ① 심화 · 인덱스 타입 선택

"무엇으로 검색하나"에 따라 인덱스 타입을 고른다

B-tree·GIN·BRIN은 경쟁 관계가 아니라 서로 다른 검색 패턴을 위한 도구입니다. 등호·범위는 B-tree, 한 행 안 다중 값 포함은 GIN, 시간순으로 쌓이는 거대 테이블의 범위는 BRIN이 답입니다.

TL;DR

못 정하겠으면 B-tree. jsonb·배열·전문 검색이면 GIN, append-only 시계열의 시간 범위 조회면 BRIN. BRIN은 같은 컬럼에서 B-tree 대비 수백 분의 1 크기로, 물리 순서와 값이 상관될 때만 효과가 납니다.

01 세 타입은 무엇이 다른가

핵심은 인덱스가 가리키는 단위입니다. B-tree는 정렬된 키→행 포인터, GIN은 "값→그 값을 포함한 행 목록"의 역색인, BRIN은 "이 블록 구간의 최소·최대값" 요약입니다.

  • B-tree: 등호(=)·범위(< > BETWEEN)·정렬·접두 LIKE 'abc%'
  • GIN: jsonb 키/값, 배열 @> 포함, tsvector 전문 검색
  • BRIN: 물리 저장 순서와 값이 상관된 거대 테이블의 범위 스캔
02 BRIN은 왜 작고, 언제 무너지나
  1. 1 테이블을 pages_per_range(기본 128) 블록 단위로 묶어 각 구간의 min/max만 저장
  2. 2 범위 조회 시 겹치지 않는 구간 전체를 건너뜀 → 인덱스가 행 단위가 아니라 블록 단위라 매우 작음
  3. 3 값이 물리 순서와 어긋나면(랜덤 INSERT·잦은 UPDATE) 구간 min/max가 넓어져 가지치기 실패 → 효과 급감

타입별 인덱스 생성 예시

-- 등호·범위·정렬에 두루 쓰이는 기본값
CREATE INDEX idx_orders_created
  ON orders (created_at);

-- 잘 맞는 쿼리: 범위 + 정렬
SELECT * FROM orders
 WHERE created_at >= '2026-05-01'
 ORDER BY created_at
 LIMIT 50;
-- jsonb 포함 검색은 GIN
CREATE INDEX idx_events_payload
  ON events USING gin (payload jsonb_path_ops);

-- 잘 맞는 쿼리: 키/값 포함(@>)
SELECT * FROM events
 WHERE payload @> '{"type":"signup"}';
-- append-only 거대 테이블의 시간 범위는 BRIN
CREATE INDEX idx_logs_ts_brin
  ON logs USING brin (ts)
  WITH (pages_per_range = 64);

-- 효과 전제: ts가 물리 순서와 상관
SELECT count(*) FROM logs
 WHERE ts >= now() - interval '7 days';

자주 묻는 질문

jsonb 컬럼에 B-tree를 걸면 안 되나요

전체 값 등호 비교(payload = '...')라면 B-tree도 되지만, 실무의 @>·? 같은 포함/키 존재 검색은 B-tree가 못 씁니다. 그래서 USING gin이 표준입니다.

BRIN을 걸었는데 느려요

대개 물리 순서가 깨진 경우입니다. 잦은 UPDATE·랜덤 INSERT로 블록 구간 min/max가 넓어졌다면 CLUSTER로 재정렬하거나, 그냥 B-tree로 바꾸는 편이 낫습니다.

하나의 컬럼에 여러 타입을 같이 둬도 되나요

물리적으로 가능하지만 쓰기 비용과 블로트가 두 배가 됩니다. 같은 컬럼이면 보통 하나만 남기고, 검색 패턴이 정말 다를 때만(예: 정렬용 B-tree + 시계열 범위용 BRIN) 신중히 병행하세요.

4개념 강의 ② — 복합 인덱스 열 순서와 선택도

복합 인덱스에서 열 순서는 취향이 아니라 성능입니다. 순서 하나로 인덱스가 쓰이기도, 무시되기도 합니다.

여러 컬럼을 묶은 복합(다중 컬럼) B-tree 인덱스는 왼쪽부터 차례로 정렬된 전화번호부와 같습니다. 성(姓)으로 먼저, 같은 성 안에서 이름으로 정렬되어 있죠. 그래서 (a, b) 인덱스는 a만으로도, a와 b 함께로도 잘 쓰이지만, b만으로 찾을 때는 거의 쓰이지 않습니다. 이를 "leftmost prefix(왼쪽 접두) 규칙"이라고 부릅니다.

권장 패턴
등호 조건을 앞에, 범위·정렬 컬럼을 뒤에

일반적으로 등호(=)로 거르는 컬럼을 앞쪽에 두고, 범위(> < BETWEEN)나 ORDER BY에 쓰는 컬럼을 뒤쪽에 둡니다. 범위 컬럼을 앞에 두면 그 뒤 컬럼은 정렬 이점을 잃기 쉽습니다. 예를 들어 WHERE tenant_id = ? AND created_at > ?를 자주 쓰면 (tenant_id, created_at)이 보통 정답입니다.

그렇다면 등호 컬럼이 여러 개라면 누구를 더 앞에 둘까요? 여기서 선택도가 등장합니다. 더 적은 행만 남기는(선택도 높은) 컬럼을 앞에 두면 인덱스를 타고 내려가는 초반에 후보가 빠르게 줄어듭니다. 단, "자주 함께 쓰이는 쿼리 패턴"이 선택도보다 우선입니다. 아무리 선택도가 높아도 그 컬럼을 조건에 거의 안 쓰면 앞에 둘 이유가 없습니다.

함정
컬럼마다 단일 인덱스를 남발

WHERE a = ? AND b = ?를 위해 (a)와 (b) 두 개의 단일 인덱스를 만드는 경우가 많습니다. 플래너가 비트맵으로 둘을 결합할 수는 있지만, 잘 설계된 복합 인덱스 (a, b) 하나가 보통 더 빠르고 더 작습니다. 인덱스 개수가 늘면 쓰기 비용도 함께 늘어납니다.

반대로 모든 쿼리 조합마다 전용 복합 인덱스를 만드는 것도 과합니다. 가장 자주 실행되고 가장 느린 쿼리부터 인덱스를 맞추고, 나머지는 기존 인덱스의 접두로 흡수되는지 먼저 확인하세요. (a, b, c) 하나가 (a), (a, b) 쿼리까지 함께 커버합니다.

"어떤 컬럼에 인덱스를 걸까"가 아니라 "어떤 쿼리를 빠르게 할까"에서 출발해야 열 순서가 자연스럽게 정해집니다.

5개념 강의 ③ — 부분·표현식·커버링 인덱스

"전부에 거는 인덱스"보다 "꼭 필요한 만큼만 거는 인덱스"가 더 작고 더 빠를 때가 많습니다.

표준 인덱스는 테이블의 모든 행을 담습니다. 하지만 실제로 조회하는 행이 일부뿐이라면, 그 일부만 담는 더 작은 인덱스를 만들 수 있습니다. 이것이 부분 인덱스입니다.

용어
부분 인덱스 (partial index)
CREATE INDEX ... WHERE 조건 형태로, 조건을 만족하는 행만 인덱스에 담습니다. 예를 들어 "처리 대기 중인 주문"처럼 전체의 일부만 자주 조회한다면, WHERE status = 'pending' 부분 인덱스는 전체 인덱스보다 훨씬 작고, 그만큼 빠르고 가볍습니다. 플래너가 이 인덱스를 쓰려면 쿼리의 조건이 인덱스의 WHERE 조건을 포함해야 합니다.

한편 컬럼 값 그대로가 아니라 가공한 결과로 검색할 때가 있습니다. 대소문자 무시 검색이 대표적입니다. WHERE lower(email) = ?를 쓰면 email 컬럼의 일반 인덱스는 쓰이지 않습니다. 이때 표현식 인덱스가 필요합니다. CREATE INDEX ... ON t (lower(email))처럼 컬럼이 아니라 함수/식의 결과를 인덱싱하고, 쿼리도 같은 식(lower(email) = ?)으로 써야 인덱스가 쓰입니다. 사용하는 함수는 IMMUTABLE이어야 하며, 매번 식을 계산하므로 쓰기 시 약간의 추가 비용이 있습니다.

마지막으로, 인덱스로 조건은 찾았는데 결과로 돌려줄 컬럼 때문에 힙을 또 방문해야 할 때가 있습니다. 이 힙 방문을 없애는 것이 커버링 인덱스입니다.

권장 패턴
INCLUDE로 커버링 인덱스 만들기

CREATE INDEX ... ON t (a) INCLUDE (b, c)처럼 검색에 쓰는 컬럼은 키(a)로, 결과로만 필요한 컬럼은 INCLUDE로 함께 담습니다. 쿼리가 필요한 컬럼을 인덱스가 모두 가지고 있으면 힙을 방문하지 않는 Index Only Scan이 가능해 빨라집니다. 단, 가시성 정보 때문에 이 스캔이 잘 작동하려면 테이블의 visibility map이 최신이어야 하고(=정기 VACUUM), INCLUDE 컬럼을 늘리면 인덱스가 커집니다.

세 기법의 공통점은 분명합니다. 전부가 아니라 필요한 부분만, 값 그대로가 아니라 검색하는 형태로, 힙을 다시 안 봐도 되게 인덱스를 좁히고 맞추는 것입니다. 작은 인덱스는 캐시에도 더 잘 올라가 부수 효과로 더 빨라집니다.

6개념 강의 ④ — 인덱스 쓰기 비용과 블로트

인덱스를 거는 결정의 절반은 "이걸 유지하는 비용을 감당할 수 있는가"입니다.

모든 인덱스는 공짜가 아닙니다. 행을 INSERT하면 그 행에 해당하는 모든 인덱스 항목을 함께 추가해야 하고, UPDATE는 변경된 컬럼이 속한 인덱스를 갱신해야 합니다. 인덱스가 여러 개면 INSERT 한 번이 그 인덱스를 모두 건드립니다. 읽기를 위해 만든 인덱스가 쓰기를 느리게 한다는 거래를 항상 의식해야 합니다. 특히 갱신이 잦은 테이블에서는 MVCC 특성상 죽은 공간이 쌓이는 블로트 문제가 함께 따라옵니다.

용어
블로트 (bloat)
PostgreSQL의 MVCC는 UPDATE/DELETE 시 기존 행을 즉시 지우지 않고 "죽은 튜플(dead tuple)"로 남겨둡니다. 이 죽은 공간이 테이블과 인덱스에 쌓여 실제 데이터보다 물리 크기가 커지는 현상이 블로트입니다. 인덱스가 많을수록 죽은 항목도 많아져 블로트가 커지고, 스캔할 페이지가 늘어 오히려 느려질 수 있습니다.
함정
"혹시 몰라서" 만든 채 방치된 인덱스

한 번도 안 쓰이는데 쓰기마다 갱신되는 인덱스는 순수한 손해입니다. 쓰기를 느리게 하고, 디스크를 먹고, 블로트를 키우고, 플래너의 선택지를 늘려 계획 수립까지 더디게 만들 수 있습니다. pg_stat_user_indexes의 idx_scan이 오래도록 0인 인덱스는 제거 후보입니다(운영 패턴·배치 주기를 충분히 관찰한 뒤 판단).

해결의 출발점은 정기적인 정리입니다. autovacuum이 죽은 튜플을 회수하도록 두되, 갱신이 잦은 테이블은 설정을 더 공격적으로 조정합니다. 인덱스 블로트가 심하면 REINDEX로 재생성하며, 운영 중에는 잠금을 줄이는 REINDEX 동시(CONCURRENTLY) 방식이나 CREATE INDEX CONCURRENTLY 후 교체를 검토합니다. 정확한 명령·옵션·잠금 수준은 버전에 따라 다를 수 있어 적용 전 사용 중인 버전의 공식 문서 확인이 필요합니다.

요약하면 인덱스 설계는 더하기만큼 빼기가 중요합니다. 새 인덱스를 추가할 때마다 "이미 있는 인덱스의 접두로 커버되지 않나?", "이 컬럼은 정말 자주 쓰이나?", "쓰기 부하가 큰 테이블인가?"를 함께 물어야 합니다.

7예제 — EXPLAIN (ANALYZE) 읽기

인덱스가 "걸렸는지"가 아니라 "실제로 쓰였고 도움이 됐는지"는 실행계획으로만 확인됩니다.

아래는 orders(tenant_id, status, created_at, ...) 테이블에서 특정 테넌트의 최근 대기 주문을 찾는 흐름입니다. 인덱스 전후의 계획이 어떻게 달라지는지 봅니다. 출력은 형식 설명용이며, 숫자는 환경마다 다릅니다.

-- 자주 쓰는 쿼리
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM orders
WHERE tenant_id = 42
  AND status = 'pending'
ORDER BY created_at DESC
LIMIT 20;

인덱스가 없을 때, 전형적으로 이런 모양이 나옵니다.

Limit  (actual rows=20 ...)
  ->  Sort  (actual rows=20 loops=1)
        Sort Key: created_at DESC
        ->  Seq Scan on orders  (cost=... rows=... ...)
              (actual rows=... loops=1)
              Filter: ((tenant_id = 42) AND (status = 'pending'))
              Rows Removed by Filter: ...  (버린 행이 매우 많음)
              Buffers: shared read=...  (많은 페이지를 읽음)

읽는 순서는 안쪽(가장 깊은 들여쓰기)부터입니다. Seq Scan이 테이블 전체를 훑고, Rows Removed by Filter가 매우 크다는 것은 거의 다 버릴 거면서 대부분의 행을 다 읽었다는 뜻입니다. 게다가 정렬을 위해 Sort가 따로 돌고 있습니다. 이제 복합 인덱스를 추가합니다.

CREATE INDEX idx_orders_tenant_pending_created
  ON orders (tenant_id, created_at DESC)
  WHERE status = 'pending';   -- 부분 인덱스: 대기 주문만 담음
Limit  (actual rows=20 loops=1)
  ->  Index Scan using idx_orders_tenant_pending_created on orders
        (cost=... rows=... ...)  (actual rows=20 loops=1)
        Index Cond: (tenant_id = 42)
        Buffers: shared hit=... read=...  (소수 페이지만 접근)
읽는 법

좋아진 신호는 네 가지입니다. (1) Seq Scan이 Index Scan으로 바뀌었다. (2) 별도 Sort가 사라졌다 — 인덱스가 이미 created_at DESC 순서라 정렬 없이 위에서 20개만 떼면 된다. (3) Rows Removed by Filter가 사라지고 접근한 Buffers가 급감했다. (4) status = 'pending' 조건이 부분 인덱스의 WHERE에 흡수돼 Index Cond에는 tenant_id만 남았다.

가장 먼저 보는 한 가지를 꼽자면, 플래너의 추정 행 수(rows=)와 실제 행 수(actual rows=)의 괴리입니다. 둘이 크게 어긋나면 통계가 낡았거나 컬럼 간 상관을 플래너가 모르는 경우입니다. 이럴 땐 인덱스를 늘리기 전에 ANALYZE로 통계부터 갱신하세요.

주의
EXPLAIN ANALYZE는 실제 실행이다

ANALYZE를 붙이면 쿼리가 진짜 실행됩니다. SELECT는 괜찮지만 UPDATE·DELETE·INSERT는 데이터가 바뀌므로, 트랜잭션으로 감싸 ROLLBACK하는 등 안전장치를 두세요. 또한 비용 단위(cost)는 절대 시간이 아니라 상대 추정치이므로, 실제 빠르기는 actual time으로 판단합니다.

8실습 — 내 테이블 인덱스 점검 5단계

읽기만 하고 끝내지 않습니다. 지금 가장 느린 쿼리 하나를 골라 따라가세요.

  1. 느린 쿼리 포착. 자주 실행되면서 느린 쿼리를 하나 고른다(가능하면 pg_stat_statements로 호출 횟수×평균 시간이 큰 것). 이 쿼리의 WHERE·JOIN·ORDER BY 컬럼을 적어 둔다.
  2. 현재 계획 측정. EXPLAIN (ANALYZE, BUFFERS)로 돌려 Seq Scan 여부, Rows Removed by Filter, 별도 Sort, 추정 vs 실제 행 수의 괴리를 기록한다.
  3. 인덱스 설계. 등호 컬럼을 앞, 범위·정렬 컬럼을 뒤로 두는 복합 인덱스를 가설로 세운다. 조회가 일부 행에 집중되면 부분 인덱스를, 가공값으로 검색하면 표현식 인덱스를, 결과 컬럼이 적으면 INCLUDE 커버링을 검토한다.
  4. 적용과 재측정. (운영이라면 CREATE INDEX CONCURRENTLY) 인덱스를 만든 뒤 같은 EXPLAIN (ANALYZE, BUFFERS)를 다시 돌려 2단계 기록과 비교한다. Index Scan/Index Only Scan으로 바뀌고 buffers가 줄었는지 확인한다.
  5. 비용 점검과 정리. pg_stat_user_indexes로 기존 인덱스의 idx_scan을 보고, 오래도록 안 쓰인 인덱스는 제거 후보로 표시한다. 이번에 추가한 인덱스가 기존 인덱스의 접두와 중복되지 않는지 본다.
점검에 쓸 한 줄

안 쓰이는 인덱스와 통계 상태를 빠르게 보려면 다음 시스템 뷰를 살펴보세요(읽기 전용 조회):

pg_stat_user_indexes(idx_scan=0 후보) · pg_stat_user_tables(seq_scan vs idx_scan, n_dead_tup) · pg_stat_statements(느린 쿼리) · pg_indexes(현재 정의 확인).

9퀴즈

정답을 외우기보다, "이 선택이 어떤 비용·이득을 만드는지" 한 문장으로 설명할 수 있는지 확인하세요.

  1. jsonb 컬럼의 특정 키 포함 여부로 자주 검색한다. B-tree와 GIN 중 무엇이 맞고, 그 이유는?
  2. 시간순으로만 계속 쌓이는 매우 큰 로그 테이블에서 날짜 범위 조회를 한다. BRIN이 매력적인 이유와, BRIN이 무력해지는 조건은?
  3. (tenant_id, created_at) 복합 인덱스가 있다. WHERE created_at > ?만 있는 쿼리(테넌트 조건 없음)에 이 인덱스가 잘 쓰일까? 이유는?
  4. 등호 조건 컬럼이 두 개일 때, 복합 인덱스에서 어느 컬럼을 앞에 둘지 정하는 두 가지 기준은?
  5. 전체의 일부(소수 비율)만 차지하는 status='pending' 행을 자주 조회한다. 어떤 인덱스가 더 작고 빠를까? 그 인덱스가 쓰이기 위한 쿼리 조건은?
  6. WHERE lower(email) = ? 쿼리가 email 일반 인덱스를 안 쓴다. 무엇을 만들어야 하고, 쿼리는 어떻게 써야 하는가?
  7. 커버링(INCLUDE) 인덱스로 Index Only Scan을 노린다. 이 스캔이 실제로 힙을 안 보려면 운영상 무엇이 전제되어야 하는가?
  8. EXPLAIN (ANALYZE)에서 가장 먼저 확인할 한 가지를 꼽고, 그 값이 어긋날 때 인덱스보다 먼저 할 일은?

10정답 해설

아래 해설은 "왜"까지 설명합니다. 답만 맞히고 이유를 못 대면 다시 해당 섹션으로 돌아가세요.

  1. GIN입니다. B-tree는 컬럼 값 전체를 하나의 키로 다루지만, jsonb의 "이 키/값을 포함하는가" 같은 검색은 한 행 안의 여러 요소를 인덱싱해야 합니다. GIN은 이런 포함(containment) 검색에 맞게 설계되어 있습니다. 대신 빌드·쓰기 비용과 인덱스 크기가 큽니다. (→ 섹션 3)
  2. BRIN은 블록 범위마다 최소/최대 같은 요약만 저장해 인덱스가 매우 작습니다. 데이터가 시간순으로 쌓이면 "이 날짜 범위는 저 블록들에만 있다"가 성립해 적은 페이지만 읽고 끝납니다. 그러나 물리 저장 순서가 값과 무관해지면(잦은 갱신·재배치로 섞이면) 거의 모든 블록을 봐야 해 효과가 사라집니다. (→ 섹션 3)
  3. 잘 안 쓰입니다. 복합 인덱스는 왼쪽 접두(leftmost prefix) 규칙을 따르므로 선두 컬럼(tenant_id) 조건이 없으면 인덱스를 효율적으로 타기 어렵습니다. created_at 단독 조회가 잦다면 created_at이 선두인 인덱스가 따로 필요합니다. (→ 섹션 4)
  4. (1) 쿼리 패턴: 더 자주 단독으로도 조건에 쓰이는 컬럼을 앞에. (2) 선택도: 함께 쓰일 때 더 적은 행만 남기는(선택도 높은) 컬럼을 앞에 두어 초반에 후보를 줄인다. 패턴이 선택도보다 우선합니다. (→ 섹션 4)
  5. 부분 인덱스(... WHERE status='pending')가 전체 인덱스보다 훨씬 작고 빠릅니다. 다만 플래너가 이 인덱스를 쓰려면 쿼리의 조건이 인덱스의 WHERE 조건을 포함해야 합니다(즉 쿼리에도 status='pending'가 있어야 함). (→ 섹션 5)
  6. 표현식 인덱스 ON t (lower(email))를 만들고, 쿼리도 동일하게 WHERE lower(email) = ?로 써야 합니다. 인덱스의 식과 쿼리의 식이 일치해야 플래너가 사용합니다. (→ 섹션 5)
  7. 테이블의 visibility map이 최신이어야 합니다. 이는 정기적인 VACUUM(autovacuum)으로 죽은 튜플이 정리되어야 보장됩니다. 갱신이 잦은 테이블은 vacuum이 따라가지 못하면 Index Only Scan이라도 힙을 다시 확인하게 됩니다. (→ 섹션 5·6)
  8. 추정 행 수(rows=)와 실제 행 수(actual rows=)의 괴리입니다. 크게 어긋나면 통계가 낡았거나 상관을 모르는 경우이므로, 인덱스를 추가하기 전에 ANALYZE로 통계를 갱신해 계획을 다시 봅니다. (→ 섹션 7)

11복습 체크리스트

한 항목이라도 "아니오"가 나오면, 그 항목이 가리키는 강의 섹션으로 돌아가 인덱스를 고친 뒤 다시 실행계획으로 확인하세요.

  1. 각 쿼리의 검색 방식(등호·범위·포함·근접·시계열)에 맞는 인덱스 타입을 골랐는가?
  2. 복합 인덱스에서 등호 컬럼을 앞, 범위·정렬 컬럼을 뒤로 배치했는가?
  3. 일부 행에 집중되는 조회는 부분 인덱스로, 가공값 검색은 표현식 인덱스로 줄였는가?
  4. EXPLAIN (ANALYZE, BUFFERS)로 Index Scan 전환·Sort 제거·buffers 감소를 실제로 확인했는가?
  5. 오래 안 쓰인 인덱스와 기존 인덱스 접두와의 중복을 점검해 불필요한 인덱스를 제거했는가?
