1학습 목표

이 모듈을 마치면 "동작하는 파이프라인"이 아니라 "탈취되어도 피해가 갇히는 파이프라인"을 설계할 수 있습니다.

CI/CD는 코드 저장소, 클라우드 자격증명, 패키지 배포 권한을 한 자리에 모아둔 곳입니다. 그래서 공격자에게는 가장 보상이 큰 표적이고, 우리에게는 가장 먼저 최소권한을 적용해야 할 곳입니다. 수강 후 여러분은 다음을 직접 할 수 있어야 합니다.

  • 워크플로우의 GITHUB_TOKEN 권한을 명시적으로 최소화하고, 기본 권한이 무엇인지 설명할 수 있다.
  • 장기 클라우드 키를 시크릿에 저장하는 대신 OIDC로 단기 자격증명을 발급받는 흐름을 설명할 수 있다.
  • 서드파티 액션을 태그(@v4)가 아니라 커밋 SHA로 핀닝하는 이유를 공급망 관점에서 설명할 수 있다.
  • pull_request_target이 왜 위험한지, 어떤 경우에만 써야 하는지 판단할 수 있다.
  • 내 레포의 워크플로우를 점검표에 따라 직접 진단하고 고칠 수 있다.

2시작 전 준비

개념을 외우기 전에, 우리가 다루는 "토큰"이 무엇을 할 수 있는 물건인지부터 분명히 합니다.

실습을 따라 하려면 본인이 관리자 권한을 가진 GitHub 레포지토리 하나와, 그 안의 .github/workflows/ 디렉터리에 있는 워크플로우 파일 하나면 충분합니다. 클라우드 OIDC 실습은 AWS·GCP·Azure 중 하나에 IAM 설정 권한이 있으면 더 좋지만, 권한이 없어도 흐름은 읽기만 해도 됩니다.

용어
GITHUB_TOKEN
워크플로우가 실행될 때 GitHub가 자동으로 발급하는 임시 토큰입니다. 사람이 만든 PAT(개인 액세스 토큰)가 아니라, 해당 잡(run) 동안만 유효하고 끝나면 폐기됩니다. 별도 시크릿 등록 없이 secrets.GITHUB_TOKEN 또는 github.token으로 참조합니다.
용어
permissions
워크플로우나 잡 수준에서 GITHUB_TOKEN이 가질 수 있는 권한 범위(contents, packages, id-token 등)를 선언하는 키입니다. 명시하지 않으면 레포/조직 설정에 따른 기본값이 적용되며, 그 기본값이 넓을 수 있다는 점이 핵심입니다.
용어
OIDC (OpenID Connect)
GitHub가 워크플로우 실행마다 서명된 단기 ID 토큰을 발급하고, 클라우드가 그 토큰을 신뢰해 수 분짜리 임시 자격증명으로 바꿔주는 방식입니다. 영구 클라우드 키를 시크릿에 저장하지 않게 해줍니다.
비유로 이해하기

장기 클라우드 키를 시크릿에 넣는 것은 건물 마스터키를 복사해 외주 업체에 넘기는 것과 같습니다. 편하지만, 그 업체가 털리면 마스터키가 통째로 새어 나갑니다. OIDC는 대신 방문할 때마다 안내데스크에서 발급하는, 오늘 그 층에서만 쓰는 일회용 출입증을 받는 방식입니다. 출입증이 새어도 내일이면 무용지물이고, 출입할 수 있는 층도 제한됩니다.

3개념 강의 ① — GITHUB_TOKEN 최소권한

가장 먼저, 가장 싸게, 가장 큰 피해를 막는 한 줄: permissions 선언.

모든 워크플로우 잡에는 GITHUB_TOKEN이 자동으로 주어집니다. 문제는 이 토큰의 기본 권한이 넓을 수 있다는 점입니다. 권한을 따로 좁히지 않으면, 단순히 테스트만 돌리는 잡이 레포 코드를 푸시하거나, 이슈/PR을 조작하거나, 패키지를 게시할 수 있는 수준의 토큰을 들고 실행될 수 있습니다.

공격 시나리오는 단순합니다. 악성 의존성이나 탈취된 액션이 빌드 중에 실행되면, 그 코드는 같은 잡 안의 GITHUB_TOKEN을 그대로 사용할 수 있습니다. 토큰 권한이 넓을수록 한 번의 침투가 곧 레포 쓰기 권한으로 번집니다.

함정
권한을 선언하지 않고 방치

permissions를 한 번도 쓰지 않은 워크플로우는 "기본값"에 의존합니다. 기본값이 넓게 설정된 레포/조직에서는 읽기만 필요한 잡이 쓰기 토큰을 들고 돌아갑니다. "지금까지 문제 없었다"는 권한이 안전하다는 뜻이 아니라, 아직 악용되지 않았다는 뜻일 뿐입니다.

해결
기본은 read-all, 필요한 권한만 잡 단위로 추가

워크플로우 최상단에 permissions: contents: read처럼 전역을 가장 좁게 두고, 실제로 쓰기가 필요한 잡(배포·릴리스·코멘트 작성)에서만 해당 권한을 켜는 패턴이 안전합니다. 조직 설정에서 기본 토큰 권한을 "읽기 전용"으로 낮추는 것도 강력한 조치입니다(조직 정책 변경은 영향 범위가 넓으니 사전 공지 필요).

핵심 원칙은 하나입니다. 토큰은 그 잡이 실제로 하는 일에 딱 맞는 권한만 가져야 한다. 읽기만 하면 contents: read, PR에 코멘트를 달면 pull-requests: write만 추가합니다.

4개념 강의 ② — 시크릿과 OIDC 단기 자격증명

시크릿은 "줄이는" 대상이고, 클라우드 키는 가능하면 "없애는" 대상입니다.

시크릿(Actions secrets)은 암호화되어 저장되고 로그에 출력될 때 마스킹됩니다. 하지만 마스킹은 실수로 출력된 값을 가려주는 안전망일 뿐, 시크릿이 안전하다는 보장이 아닙니다. 시크릿을 환경 변수로 흘려보내면 빌드 중 실행되는 임의 코드가 env를 읽어갈 수 있습니다.

함정
장기 클라우드 키를 시크릿에 영구 저장

AWS_ACCESS_KEY_ID 같은 영구 키를 시크릿에 넣어두면, 그 값이 한 번 새는 순간 키를 수동으로 회수(rotate)하기 전까지 계속 유효합니다. 유출 시점과 발견 시점 사이의 모든 시간이 공격 가능 시간입니다.

해결
OIDC로 단기 자격증명 발급

잡에 permissions: id-token: write를 주면 GitHub가 실행마다 서명된 OIDC 토큰을 만들고, 클라우드의 신뢰 정책(특정 레포·브랜치·환경에서 온 토큰만 허용)을 통과하면 수 분짜리 임시 자격증명을 내줍니다. 저장된 영구 키가 없으니 "유출되어 두고두고 악용되는" 위험 자체가 사라집니다.

OIDC를 쓸 때도 방심은 금물입니다. 클라우드 쪽 신뢰 조건(subject 클레임)을 충분히 좁게 잡아야 합니다. 예를 들어 "이 조직의 어떤 레포든"처럼 넓게 매칭하면, 조직 내 다른 레포의 워크플로우가 같은 역할을 가져갈 수 있습니다.

용어
subject 클레임 (sub)
OIDC 토큰에 담기는, "어느 레포의 어느 브랜치/환경/태그에서 실행됐는가"를 나타내는 식별자입니다. 클라우드 신뢰 정책에서 이 값을 정확히 매칭하면 "main 브랜치의 배포 잡에서 온 토큰만" 같은 정밀한 제한이 가능합니다. 와일드카드를 넓게 쓰면 제한이 사실상 무력화됩니다.

"시크릿을 잘 지키는 것"보다 "지킬 시크릿을 만들지 않는 것"이 한 단계 위의 보안입니다.

5개념 강의 ③ — 액션 SHA 핀닝과 공급망

당신의 워크플로우는 당신이 신뢰한 적 없는 수십 명의 코드를 실행하고 있습니다.

uses: some-org/some-action@v4처럼 액션을 가져다 쓸 때, @v4는 버전이 아니라 움직이는 라벨(태그)입니다. 액션 작성자(또는 그 계정을 탈취한 공격자)는 같은 v4 태그가 가리키는 커밋을 언제든 바꿀 수 있습니다. 즉 어제까지 안전했던 @v4가 오늘 악성 코드를 가리키게 될 수 있습니다. 이것이 공급망 공격의 전형적인 통로입니다.

비유로 이해하기

태그 참조는 "3번 사물함을 쓰는 사람"에게 열쇠를 맡기는 것과 같습니다. 그 사물함의 주인이 바뀌어도 당신은 모릅니다. 커밋 SHA 핀닝은 "지문이 정확히 이 사람인 경우에만" 열쇠를 맡기는 것입니다. 내용이 한 글자라도 바뀌면 지문(SHA)이 달라져 통과하지 못합니다.

해결
전체 커밋 SHA로 핀닝 + 주석으로 버전 표기

서드파티 액션은 uses: owner/action@<full-40자-SHA> # v4.1.0 형태로, 전체 커밋 해시를 고정하고 사람이 읽을 버전은 주석으로 남깁니다. SHA는 내용에 따라 결정되므로, 핀닝된 액션의 코드가 바뀌면 SHA가 달라져 자동으로 실행되지 않습니다. 업데이트는 Dependabot 같은 도구로 SHA를 의도적으로 갱신하는 방식이 안전합니다.

함정
짧은 SHA·브랜치·태그 핀닝

짧은 SHA는 충돌 가능성이 있고, @main 같은 브랜치 참조는 태그만큼이나 움직입니다. "핀닝했다"고 안심하려면 반드시 40자 전체 커밋 SHA여야 합니다. GitHub 공식 액션(예: actions/checkout)도 신뢰가 높지만, 같은 원칙으로 핀닝하는 조직이 늘고 있습니다.

핀닝은 끝이 아니라 시작입니다. 신뢰할 액션의 수 자체를 줄이고, 핀을 정기적으로 갱신하는 운영이 함께 가야 공급망 위험이 실제로 줄어듭니다.

6개념 강의 ④ — pull_request_target의 함정

가장 흔한 치명적 실수 한 가지를 따로 떼어 다룹니다.

pull_request 이벤트는 외부 기여자의 PR 코드를 권한이 거의 없는 토큰과 시크릿 없이 실행합니다(포크 PR 기준). 그런데 "PR에 라벨을 달거나 코멘트를 남기고 싶다"는 이유로 pull_request_target으로 바꾸는 경우가 많습니다. 이 이벤트는 베이스 레포의 워크플로우를 쓰기 토큰과 시크릿이 있는 컨텍스트에서 실행합니다.

함정
pull_request_target에서 PR 코드를 체크아웃해 실행

pull_request_target 잡에서 PR의 head 브랜치를 체크아웃해 빌드·테스트·스크립트를 돌리면, 외부인이 보낸 코드가 시크릿과 쓰기 토큰이 있는 환경에서 실행됩니다. 공격자는 PR 하나로 시크릿을 탈취하거나 레포에 쓰기를 할 수 있습니다. 이는 잘 알려진 공급망/CI 공격 패턴입니다.

해결
신뢰 경계를 분리하라

외부 PR 코드를 실제로 빌드·테스트해야 한다면 pull_request(시크릿 없는 컨텍스트)에서 하고, 결과 코멘트처럼 쓰기가 필요한 작업은 별도의 안전한 잡(예: workflow_run으로 분리, 또는 신뢰된 코드만 실행하는 잡)에서 처리합니다. pull_request_target을 쓴다면 절대로 PR head 코드를 체크아웃해 실행하지 않습니다.

비유로 이해하기

pull_request_target으로 PR 코드를 돌리는 것은, 면접 보러 온 낯선 사람에게 금고 비밀번호가 적힌 사무실을 잠깐 비워주고 "편하게 둘러보세요"라고 말하는 것과 같습니다. 친절하지만, 금고를 잃을 수 있습니다.

7예제 — 안전한 워크플로우 한 장

위 네 가지 원칙을 한 파일에 모으면 이렇게 보입니다. 핵심 라인에 주석을 달았습니다.

아래는 "테스트는 최소 권한으로, 클라우드 배포는 OIDC로, 액션은 SHA로 핀닝"한 구조를 보여주는 예시입니다. 실제 SHA·역할 ARN·리전 값은 환경에 맞게 채워야 하며, 여기 표기는 형식 설명용입니다.

# .github/workflows/ci.yml
name: ci

on:
  push:
    branches: [ main ]
  pull_request:            # 포크 PR은 시크릿 없는 컨텍스트로 실행됨

# 전역은 가장 좁게: 읽기만 허용
permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    # 이 잡은 추가 권한이 필요 없으므로 전역 read 그대로 사용
    steps:
      # 서드파티/공식 액션 모두 전체 SHA로 핀닝 (주석으로 버전 표기)
      - uses: actions/checkout@<40자-full-commit-SHA>  # v4.x
      - uses: actions/setup-node@<40자-full-commit-SHA> # v4.x
        with:
          node-version: 20
      - run: npm ci
      - run: npm test

  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'   # main 푸시에서만 배포
    runs-on: ubuntu-latest
    environment: production               # 보호 규칙/리뷰어 적용 지점
    permissions:
      contents: read
      id-token: write                     # OIDC 토큰 발급에 필요
    steps:
      - uses: actions/checkout@<40자-full-commit-SHA>  # v4.x
      # OIDC로 단기 자격증명 교환 — 영구 키를 시크릿에 두지 않음
      - uses: aws-actions/configure-aws-credentials@<40자-full-commit-SHA> # v4.x
        with:
          role-to-assume: arn:aws:iam::<account-id>:role/<deploy-role>
          aws-region: ap-northeast-2
      - run: ./scripts/deploy.sh
읽는 법

이 예시에서 보안적으로 의미 있는 결정은 네 군데입니다. (1) 전역 permissions를 contents: read로 좁혔다. (2) 배포 잡에만 id-token: write를 켜고 OIDC를 썼다. (3) 모든 액션을 전체 SHA로 핀닝했다. (4) 배포는 main 조건 + environment: production 보호 아래에서만 일어난다.

주의
버전·도구 세부값은 확인 필요

액션의 최신 메이저 버전, 클라우드 OIDC 제공자 설정 세부 절차, 토큰 유효 기간 등 구체 수치는 시점에 따라 달라질 수 있습니다. 실제 적용 전 각 액션 저장소와 클라우드 공식 문서에서 현재 권장값을 확인하세요.

8실습 — 내 레포 점검 5단계

읽기만 하고 끝내지 않습니다. 지금 본인 레포의 워크플로우 하나를 열고 따라가세요.

  1. 권한 진단. 워크플로우에 permissions: 블록이 있는지 본다. 없다면 전역에 permissions: contents: read를 추가하고, 빨간불이 켜지는 잡(배포·코멘트 등)에만 필요한 권한을 되돌려 추가한다.
  2. 토큰 사용처 추적. secrets.GITHUB_TOKEN 또는 github.token이 어디서 쓰이는지 찾고, 그 잡이 정말 쓰기가 필요한지 자문한다. 읽기로 충분하면 권한을 낮춘다.
  3. 시크릿 인벤토리. 등록된 Actions secrets 목록을 보고, 그중 장기 클라우드 키가 있는지 확인한다. 있다면 OIDC로 전환 가능한지 후보로 표시한다.
  4. 액션 핀닝 점검. 모든 uses: 라인을 훑어 @v숫자·@main으로 된 서드파티 액션을 찾아 전체 SHA로 핀닝하고, 주석에 버전을 남긴다. Dependabot을 켜 갱신을 자동화한다.
  5. 이벤트 트리거 검토. pull_request_target이 있는지 검색한다. 있다면 그 잡이 PR head 코드를 체크아웃해 실행하지 않는지 반드시 확인한다.
검색에 쓸 한 줄

레포에서 위험 신호를 빠르게 찾으려면 다음 패턴을 검색해 보세요(텍스트 검색 예시):

pull_request_target · @v(서드파티 액션 태그 참조) · permissions 누락 워크플로우 · AWS_ACCESS_KEY_ID 같은 장기 키 이름.

9퀴즈와 정답 해설

정답을 외우기보다, "이 설정이 어떤 공격을 막는지" 한 문장으로 설명할 수 있는지 확인하세요.

  1. permissions를 워크플로우에 전혀 쓰지 않으면 어떤 권한이 적용되는가? 왜 위험할 수 있는가?
  2. 장기 클라우드 키를 시크릿에 저장하는 방식과 OIDC 방식의 가장 큰 차이는 무엇인가?
  3. OIDC를 켜는 잡에 추가해야 하는 권한 키는 무엇인가?
  4. 서드파티 액션을 @v4 태그로 참조하면 왜 위험한가? 권장 대안은?
  5. pull_request와 pull_request_target의 핵심 차이는 무엇이며, 후자에서 절대 하면 안 되는 행위는?
  6. OIDC를 쓰더라도 클라우드 신뢰 정책의 subject(sub) 매칭을 넓게 잡으면 어떤 문제가 생기는가?

정답해설

아래 해설은 "왜"까지 설명합니다. 답만 맞히고 이유를 못 대면 다시 해당 섹션으로 돌아가세요.

  1. 레포/조직의 기본 권한이 적용됩니다. 그 기본값이 넓으면 읽기만 하는 잡도 쓰기 토큰을 들고 실행됩니다. 빌드 중 실행된 악성 코드가 그 토큰으로 레포에 쓰기를 할 수 있어 위험합니다. (→ 섹션 3)
  2. 저장된 영구 키는 유출 시 회수 전까지 계속 유효하지만, OIDC는 실행마다 수 분짜리 임시 자격증명을 발급하므로 유출되어도 곧 무효가 됩니다. "두고두고 악용"의 위험을 제거합니다. (→ 섹션 4)
  3. permissions:에 id-token: write를 추가합니다. 이게 있어야 GitHub가 서명된 OIDC 토큰을 발급합니다. 함께 contents: read 등 필요한 권한만 둡니다. (→ 섹션 4)
  4. @v4는 움직이는 태그여서 작성자나 계정 탈취자가 같은 태그가 가리키는 커밋을 바꿀 수 있습니다. 권장 대안은 40자 전체 커밋 SHA로 핀닝하고 버전은 주석으로 남기는 것입니다. (→ 섹션 5)
  5. pull_request는 포크 PR을 시크릿 없는 약한 토큰으로, pull_request_target은 시크릿과 쓰기 토큰이 있는 컨텍스트로 실행합니다. 후자에서 PR head 코드를 체크아웃해 실행하는 것은 절대 금물입니다. 외부 코드에 시크릿을 넘겨주는 셈이기 때문입니다. (→ 섹션 6)
  6. subject를 넓게(예: 조직 내 모든 레포) 매칭하면 의도하지 않은 다른 레포의 워크플로우가 같은 클라우드 역할을 가져갈 수 있습니다. 특정 레포·브랜치·환경으로 좁혀야 OIDC의 이점이 실제로 발휘됩니다. (→ 섹션 4)

복습Review Checklist

한 항목이라도 "아니오"가 나오면, 그 항목이 가리키는 강의 섹션으로 돌아가 워크플로우를 고친 뒤 다시 점검하세요.

  1. 내 워크플로우 최상단에 permissions: contents: read가 선언돼 있는가?
  2. 쓰기 권한은 그것이 꼭 필요한 잡에만 좁게 추가돼 있는가?
  3. 장기 클라우드 키 시크릿을 OIDC + id-token: write로 전환했는가(또는 전환 계획이 있는가)?
  4. 모든 서드파티 액션이 40자 전체 SHA로 핀닝되고 버전 주석이 달려 있는가?
  5. pull_request_target 잡이 PR head 코드를 실행하고 있지는 않은가?
