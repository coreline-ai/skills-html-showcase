로컬 AI 워크스테이션 구축기: GPU보다 먼저 배운 것들

"그래픽카드만 좋으면 되겠지" 하고 시작했다가, 정작 발목을 잡은 건 GPU가 아니라 VRAM 산정과 양자화 설정이었다. 모델은 안 돌아가는데 카드 탓만 하던 몇 주를 정리한, 솔직한 시행착오 기록이다.

로컬 LLM · Ollama / llama.cpp / GGUF · 양자화 · 개인 빌드 경험담 · 읽는 데 약 9분

개인 경험 노트

처음 한 일은 부끄럽게도 "어떤 GPU가 제일 빠른가" 검색이었다. 벤치마크 영상 수십 개를 보고, 장바구니에 카드를 담았다 뺐다를 반복했다. 그런데 막상 작은 카드로 7B 모델을 먼저 돌려보니 깨달았다. 내 병목은 연산 속도가 아니라 모델이 메모리에 올라가느냐 마느냐였다. 카드 스펙표를 외우던 시간에 "내 모델이 몇 GB를 먹는가"를 계산하는 법을 배웠다면, 지출도 며칠도 아꼈을 것이다.

그래서 이 글은 "이 GPU를 사라"는 추천 글이 아니다. GPU를 고르기 전에 먼저 알았어야 했던 것들에 대한 기록이다.

왜 지금 로컬 AI인가

클라우드 API가 멀쩡히 있는데, 굳이 책상 밑에서 모델을 돌린 이유

솔직히 말하면 처음엔 클라우드 API로 충분했다. 빠르고, 최신 모델이 바로 붙고, 전기요금 걱정도 없다. 로컬로 눈을 돌린 건 멋이 아니라 세 가지 불편 때문이었다.

첫째, 반복 실험의 비용이다. 같은 프롬프트를 수백 번 변형하며 돌리는 작업에서는 토큰 과금이 의외로 빠르게 쌓였다. 둘째, 데이터를 밖으로 내보내기 꺼려지는 작업이 있었다. 개인 메모나 사내 초안 같은 것들이다. 셋째, 오프라인에서도 돌아가는 환경이 필요했다. 네트워크가 불안정한 곳에서 작업할 일이 잦았다.

이 세 가지가 겹치자 "그럼 내 기계에서 돌려보자"가 됐다. 다만 분명히 해두자. 로컬 LLM은 클라우드 최상위 모델을 대체하는 게 아니라, 특정 용도에서 더 싸고 더 통제 가능한 선택지를 하나 더 갖는 일이다. 이 전제를 일찍 받아들였다면 카드 욕심도 덜 부렸을 것이다.

비유

로컬 LLM 환경은 "집에 커피 머신을 들이는 것"과 비슷하다. 매번 카페(클라우드)에 가는 게 더 좋은 커피일 수 있다. 하지만 하루 다섯 잔씩 마시고, 레시피를 끝없이 바꿔보고 싶고, 새벽에도 마시고 싶다면 — 집 머신이 답이다. 중요한 건 가장 비싼 머신이 아니라, 내 소비 패턴에 맞는 머신을 고르는 것이다.

관점: GPU는 마지막에 고르는 부품이다

스펙표보다 먼저 답해야 할 질문이 있다

구축을 한 번 겪고 나서 가진 분명한 주장이 하나 있다. GPU는 구매 결정의 출발점이 아니라 도착점이라는 것이다. 순서가 거꾸로 됐을 때 돈과 시간을 가장 많이 버렸다.

"어떤 카드가 빠른가"가 아니라 "내가 돌릴 모델이 얼마나 큰가"가 먼저다. 모델 크기가 카드를 고르지, 카드가 모델을 고르는 게 아니다.

이유는 단순하다. 로컬 LLM에서 체감 성능을 가르는 1순위는 연산력(FLOPS)이 아니라 모델이 VRAM에 통째로 올라가느냐다. 모델이 VRAM에 다 들어가면 빠르게 돌고, 넘치면 일부를 시스템 메모리(RAM)로 떠넘기는데(CPU 오프로딩) 이때 속도가 급격히 떨어진다. 그래서 "조금 느린 카드 + 충분한 VRAM"이 "아주 빠른 카드 + 부족한 VRAM"을 이기는 상황이 자주 생긴다.

그러니 구매 전 던질 질문 순서는 이렇게 뒤집혀야 한다.

  1. 나는 어떤 크기의 모델을 주로 돌릴 것인가? (7B? 13B? 그 이상?)
  2. 그 모델을 어떤 양자화 수준으로 쓸 것인가? (Q4 / Q5 / Q8)
  3. 그러면 VRAM이 대략 몇 GB 필요한가?
  4. 그 VRAM을 만족하는 카드 중 예산 안에서 무엇이 있는가?

카드 모델명은 4번에서야 처음 등장한다. 나는 이걸 1번부터 시작했다가 헤맸다.

먼저 정리한 용어

Ollama · llama.cpp · GGUF · 양자화 — 헷갈리면 빌드 전체가 흔들린다

나는 이 네 단어를 두루뭉술하게 알고 시작했다가 한참을 돌아왔다. 서로 다른 층위의 개념인데 비슷하게 들려서 자꾸 섞였다. 짧게 정리하고 넘어가자.

용어 llama.cpp C/C++로 작성된 추론 엔진. 무거운 프레임워크 없이 CPU와 GPU에서 LLM을 돌리도록 만든 핵심 런타임이다. 우리가 말하는 "로컬에서 모델이 실제로 계산되는 곳"이 대개 여기다.
용어 Ollama 위의 엔진을 감싸 모델 다운로드·실행·관리를 한 줄 명령으로 만든 도구. 비유하면 llama.cpp가 엔진이고 Ollama는 시동 키와 계기판이다. 입문자가 가장 빨리 첫 모델을 돌리는 통로.
용어 GGUF llama.cpp 계열이 쓰는 모델 파일 포맷. 모델 가중치와 메타데이터, 그리고 양자화 정보를 한 파일에 담는다. 모델을 받을 때 보게 되는 ...Q4_K_M.gguf 같은 이름이 이것이다.
용어 양자화(Quantization) 가중치를 더 적은 비트로 표현해 모델 용량과 메모리 사용량을 줄이는 기법. Q4는 약 4비트, Q8은 약 8비트 수준이라고 이해하면 출발점으로 충분하다. 용량을 줄이는 대신 정밀도를 조금 내준다.

관계를 한 문장으로 묶으면 이렇다. Ollama(관리 도구) → 내부적으로 llama.cpp(엔진) → GGUF 포맷의 모델 파일 → 그 파일은 특정 양자화(Q4/Q5/Q8)로 만들어져 있다.

양자화를 사진 파일에 비유하면 이해가 쉬웠다. 원본 RAW 파일(미양자화)은 화질이 완벽하지만 용량이 거대하다. JPEG 고화질(Q8)은 거의 차이가 없으면서 훨씬 가볍다. JPEG 중화질(Q4)은 자세히 보면 약간 뭉개지지만 일상용으로는 충분하고 아주 가볍다. 모델도 똑같다 — "얼마나 압축해도 내 용도에서 티가 안 나는가"의 균형 잡기다.

구체 예시: 같은 카드, 다른 결과

하드웨어를 바꾸지 않고 양자화만 바꿨더니 벌어진 일

가장 인상 깊었던 경험은 카드를 그대로 둔 채 양자화 수준만 바꿨을 때다. 같은 13B급 모델을 세 가지 양자화로 돌려봤더니 결과가 이렇게 갈렸다(수치는 내 환경의 대략적 경향이며, 모델·드라이버·설정에 따라 달라진다 — 확인 필요).

같은 모델, 양자화별 체감 차이(개인 환경 기준 경향)
양자화파일 크기VRAM 적재체감 품질내 결론
Q8가장 큼VRAM 초과 → 일부 CPU 오프로딩가장 좋음품질은 최고였지만 느려서 대화가 답답했다
Q5_K_M중간아슬아슬하게 적재거의 차이 못 느낌이 모델에선 가장 균형이 좋았다
Q4_K_M가장 작음여유 있게 적재긴 추론에서 가끔 약함빠르고 가볍다. 가벼운 작업엔 충분

핵심은 "Q8이 제일 좋으니 무조건 Q8"이 아니었다는 것이다. Q8은 VRAM을 넘겨 오프로딩이 일어나면서 오히려 가장 답답했다. 반대로 Q4는 빠르지만 긴 문맥의 추론에서 결을 놓치는 순간이 있었다. 내 일상 용도에서는 Q5가 "충분히 똑똑하면서 VRAM 안에 들어가는" 단 하나의 지점이었다.

좋은 습관 한 모델로 Q4·Q5·Q8을 모두 받아 같은 프롬프트로 비교해보기

벤치마크 숫자보다 내 실제 작업 프롬프트로 비교한 게 가장 정확했다. 30분이면 끝나고, 카드를 바꾸지 않고도 체감 성능을 크게 끌어올릴 수 있다.

흔한 오해 / 주의 "VRAM에 다 안 들어가도 오프로딩하면 되잖아?"

된다. 다만 느려진다. 모델 일부가 시스템 RAM으로 넘어가면 GPU↔CPU 사이를 데이터가 오가며 속도가 크게 떨어진다. "돌아가긴 한다"와 "쓸 만하다"는 다른 이야기다. 오프로딩은 비상수단이지 기본 전략이 아니다.

VRAM 산정: 카드를 사기 전에 했어야 할 계산

정밀한 공식이 아니라, 장바구니 앞에서 쓸 어림셈

여기서 거창한 공식을 들고 오진 않겠다. 내가 실제로 쓴 건 주머니 계산기 수준의 어림셈이었고, 그것만으로도 카드 선택의 80%가 정리됐다.

아주 거칠게 말하면, 모델 파일 크기(GGUF 용량)에 여유분을 더한 값이 필요 VRAM의 출발점이다. 여유분이 필요한 이유는 두 가지다.

  • KV 캐시: 모델이 대화 맥락을 기억하려고 쓰는 메모리. 컨텍스트 길이를 늘리면 이 부분이 같이 커진다.
  • 오버헤드: 런타임, 활성화 값 등 모델 가중치 외에 항상 얹히는 추가 사용량.

그래서 나는 "모델 파일 크기 + 컨텍스트용 여유 + 오버헤드 ≤ 카드 VRAM"이 대략 성립하는지를 먼저 봤다. 정확한 수치는 모델 구조·양자화·컨텍스트 설정에 따라 달라지므로 실측이 정답이지만, 장바구니 단계의 판단에는 이 어림셈으로 충분했다.

컨텍스트 길이라는 숨은 변수

처음엔 컨텍스트 길이를 "공짜로 크게 잡을 수 있는 옵션"으로 착각했다. 아니었다. 컨텍스트를 크게 늘리면 KV 캐시가 함께 부풀어 VRAM을 잠식한다. 결국 모델 크기 ↔ 컨텍스트 길이 ↔ 양자화 세 가지가 한정된 VRAM을 두고 줄다리기를 한다.

모델을 키우면
품질은 오르지만 VRAM을 더 먹는다. 컨텍스트나 양자화에서 양보해야 한다.
컨텍스트를 늘리면
긴 문서를 다루지만 KV 캐시가 커진다. 정말 긴 입력이 필요할 때만 늘리는 게 이득이었다.
양자화를 낮추면(Q8→Q4)
VRAM 여유가 생겨 더 큰 모델이나 긴 컨텍스트를 쓸 수 있다. 대신 정밀도를 조금 내준다.
내가 빠졌던 함정

"이왕이면 컨텍스트 최대로" 하고 잡아두고는, 모델이 자꾸 오프로딩되며 느려지는 걸 카드 탓으로 돌렸다. 컨텍스트를 내 실제 입력 길이에 맞게 줄이자, 같은 카드에서 같은 모델이 눈에 띄게 빨라졌다. "필요한 만큼만"이 가장 빠른 설정이었다.

How-to: 0부터 첫 모델까지의 실제 순서

카드를 새로 사기 전에, 지금 가진 기계로 먼저 해볼 것

가장 후회되는 건 "환경부터 만들고 카드를 나중에 정했어야 했다"는 점이다. 지금 다시 한다면 이 순서로 한다. 새 하드웨어 없이 1~4단계까지 오늘 바로 할 수 있다.

1단계 — 가장 쉬운 통로로 첫 모델 띄우기

Ollama를 설치하고 작은 모델(7B 안팎)부터 받아 돌려본다. "내 기계에서 LLM이 돈다"는 감각을 먼저 확보하는 게 목적이다. 큰 모델은 그다음이다.

# 설치 후, 작은 모델부터
ollama run llama3:8b
# 또는 더 가벼운 모델로 감 잡기
ollama run phi3:mini

2단계 — 같은 모델의 양자화별 비교

가능하면 같은 모델의 Q4 / Q5 / Q8 변형을 받아, 내 실제 작업 프롬프트로 품질과 속도를 비교한다. 표가 아니라 내 손끝으로 확인하는 단계다.

# 태그로 양자화 수준을 골라 받는다(모델에 따라 제공 태그가 다름 — 확인 필요)
ollama run llama3:8b-instruct-q4_K_M
ollama run llama3:8b-instruct-q8_0

3단계 — 적재 상태와 속도 관찰

모델이 GPU에 다 올라갔는지, CPU로 새는지를 본다. GPU 사용량과 VRAM 점유를 모니터링하면서, 오프로딩이 일어나는 임계점을 직접 찾는다. 이 임계점이 곧 "내가 필요한 VRAM"의 실측값이다.

# 실행 중 GPU/VRAM 관찰(NVIDIA 예시)
nvidia-smi
# Ollama에 적재된 모델/메모리 확인
ollama ps

4단계 — 컨텍스트 길이를 내 용도에 맞게 조정

긴 입력이 정말 필요한 작업인지 따져보고, 필요 이상으로 컨텍스트를 키우지 않는다. 짧게 잡을수록 VRAM 여유와 속도가 좋아진다.

5단계 — 그제서야 GPU(혹은 추가 VRAM) 검토

여기까지 오면 "나는 N B 모델을 Q5로, 컨텍스트 얼마로 쓰고, VRAM 약 몇 GB가 부족하다"가 숫자로 나온다. 이 숫자를 만족하는 카드 중에서 예산을 맞춘다. 구체적 GPU 모델과 가격은 시기·지역에 따라 변동이 크니 구매 직전 시세를 직접 확인하자(가격 확인 필요).

한 줄 요약

1~4단계는 지금 가진 기계로 공짜로 할 수 있고, 그 결과가 5단계의 카드 선택을 자동으로 정해준다. 카드는 사야 할 것을 알게 된 뒤에 사는 게 가장 싸게 사는 길이었다.

정리하며: 다시 시작한다면

GPU 스펙표를 외우기 전에 알았으면 좋았을 것들

로컬 AI 워크스테이션 구축에서 내가 진짜로 배운 건 하드웨어가 아니라 순서였다. 모델 크기 → 양자화 → VRAM → 컨텍스트 → 그리고 마지막에 GPU. 이 순서를 지키면 비싼 카드를 사고도 답답할 일이 줄고, 적당한 카드로도 충분히 만족스러운 환경을 만들 수 있다.

  • GPU는 결론이지 출발점이 아니다 — 모델이 VRAM에 들어가느냐가 1순위.
  • 양자화는 화질 압축처럼 생각하라 — "티 안 나는 가장 가벼운 설정"을 찾는다. 보통 Q4~Q5가 균형점이었다.
  • 컨텍스트는 공짜가 아니다 — 필요한 만큼만. KV 캐시가 VRAM을 먹는다.
  • 오프로딩은 비상수단 — 돌아가는 것과 쓸 만한 것은 다르다.
  • 실측이 벤치마크를 이긴다 — 내 프롬프트로 직접 비교한 값이 가장 믿을 만했다.
