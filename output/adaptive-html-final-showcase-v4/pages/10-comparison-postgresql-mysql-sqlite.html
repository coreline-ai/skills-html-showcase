PostgreSQL vs MySQL vs SQLite 선택 기준

동시성·확장성·데이터 모델·복제·배포·운영을 기준으로 세 관계형 데이터베이스를 비교하고, 상황별로 무엇을 고를지 판단하는 의사결정 문서입니다.

1Decision Context

셋 다 SQL을 말하지만, 풀려고 하는 문제의 크기와 모양이 다릅니다.

"어떤 DB를 써야 하나요?"라는 질문은 보통 잘못 짜여 있습니다. PostgreSQL, MySQL, SQLite는 경쟁 제품이라기보다 서로 다른 운영 시나리오를 위한 도구입니다. 같은 SQL 문법을 공유한다는 사실이 셋을 동급 대체재처럼 보이게 만들 뿐입니다.

핵심 차이를 한 문장으로 정리하면 이렇습니다. SQLite는 애플리케이션에 내장(embedded)되어 별도 서버 프로세스 없이 파일 하나로 동작합니다. MySQL과 PostgreSQL은 독립 서버 프로세스로 떠서 네트워크로 다수 클라이언트를 받습니다. 그리고 그 둘 사이에서도 PostgreSQL은 표준 준수와 데이터 모델의 풍부함을, MySQL은 단순함과 운영 생태계의 익숙함을 강조하는 경향이 있습니다.

비유로 이해하기

SQLite는 개인 수첩입니다. 항상 주머니에 있고 펼치면 바로 쓸 수 있지만, 여러 사람이 동시에 같은 칸에 적기는 어렵습니다. MySQL과 PostgreSQL은 도서관의 대출 데스크입니다. 사서(서버)가 줄을 정리해 동시 요청을 처리합니다. 차이가 있다면, PostgreSQL은 규정집이 두껍고 특수 자료(JSON, 지리정보, 전문 검색)까지 다루는 큰 도서관, MySQL은 회전이 빠르고 운영이 단순한 대중 도서관에 가깝습니다.

그래서 이 문서는 "무엇이 더 좋은가"가 아니라 "내 상황에서 무엇이 덜 위험한가"를 기준으로 봅니다. 의사결정에 실제로 영향을 주는 다섯 축은 다음과 같습니다.

동시성 모델

여러 쓰기가 동시에 들어올 때 어떻게 줄을 세우는가. MVCC인가 잠금인가, 단일 라이터인가.

확장 방식

읽기 부하와 쓰기 부하를 어떻게 나눠 받는가. 복제, 파티셔닝, 샤딩의 성숙도.

데이터 모델

관계형 외에 JSON, 배열, 지리정보, 전문 검색 같은 표현을 얼마나 1급으로 다루는가.

배포·운영

설치·백업·업그레이드·모니터링의 난이도와, 팀이 이미 가진 운영 지식.

적합 사용처

내장형 단말인가, 트랜잭션 OLTP인가, 분석·복합 질의가 섞인 워크로드인가.

용어
MVCC (Multi-Version Concurrency Control)
읽는 쪽이 쓰는 쪽을 막지 않도록, 같은 행의 여러 버전을 동시에 유지하는 동시성 기법입니다. 트랜잭션마다 "그 시점의 스냅샷"을 보게 해, 읽기와 쓰기가 서로 기다리는 일을 줄입니다. PostgreSQL과 MySQL(InnoDB)이 모두 채택하지만 구현 방식이 다릅니다.

2기준별 비교 매트릭스

표는 우열표가 아니라 '내 워크로드에서 어느 칸이 중요한가'를 짚는 도구입니다.

아래 표는 일반적으로 통용되는 아키텍처 특성을 정리한 것입니다. 구체적인 한계값, 최신 버전 동작, 성능 수치는 사용하는 버전과 설정에 따라 달라지므로 반드시 해당 버전 공식 문서로 확인해야 합니다. 표의 목적은 정밀 벤치마크가 아니라 선택의 방향을 잡는 데 있습니다.

표 1 — 핵심 특성 비교(일반화한 경향이며, 세부 한계·수치는 버전별 공식 문서 확인 필요)

표를 빠르게 읽는 법은 이렇습니다. 행이 여러 줄에 걸쳐 SQLite만 '해당 없음'이면, 그 워크로드는 애초에 서버형 DB의 문제 영역입니다. 반대로 PostgreSQL 칸에만 풍부한 기능이 적혀 있고 내 앱이 그걸 안 쓴다면, 그 풍부함은 비용일 뿐 이점이 아닙니다.

동시성과 MVCC를 한 칸 더 깊게

세 DB의 동시성 모델은 의사결정에서 가장 자주 발목을 잡는 항목입니다.

표 2 — 동시성 모델 비교
관점SQLiteMySQL(InnoDB)PostgreSQL

흔한 오해
"SQLite는 동시 접속을 못 한다"

정확하지 않습니다. SQLite는 다수의 동시 읽기를 잘 처리하고, WAL 모드에서는 읽기와 쓰기가 상당히 겹칠 수 있습니다. 한계는 "동시 접속"이 아니라 동시 쓰기를 한 줄로 직렬화한다는 점입니다. 쓰기가 가끔이거나 단일 프로세스라면 충분하고, 쓰기 동시성이 높아질수록 부적합해집니다.

3상황별 승자(Winners)

하나의 절대 승자는 없습니다. 상황을 좁히면 답은 거의 자동으로 나옵니다.

모바일·데스크톱·엣지 앱

SQLite

네트워크 없이 로컬에 데이터를 두고, 단일 사용자 또는 단일 프로세스가 접근합니다. 설치·운영 비용이 사실상 0이고 배포가 파일 하나로 끝나는 점이 결정적입니다.

테스트·프로토타입·캐시

SQLite

CI에서 즉시 띄우고 버리거나, 인메모리로 빠르게 검증합니다. 운영 DB가 PostgreSQL이어도 테스트 보조로는 잘 맞지만, SQL 방언 차이는 주의해야 합니다.

일반 웹 서비스·CMS

MySQL

읽기 위주 트래픽, 풍부한 운영 자료, 관리형 서비스의 보편성이 장점입니다. 팀이 이미 MySQL 운영에 익숙하다면 그 자체가 강한 근거입니다.

복잡 질의·분석 혼합

PostgreSQL

윈도 함수, CTE, 부분/표현식 인덱스, jsonb를 적극 쓰는 워크로드에서 표현력이 빛납니다. OLTP에 분석성 질의가 섞일수록 유리합니다.

지리정보·전문 검색·확장

PostgreSQL

PostGIS, 전문 검색, 사용자 정의 타입 같은 확장 생태계가 강점입니다. "DB가 더 많은 일을 직접 해주길" 원할 때 적합합니다.

데이터 무결성이 핵심인 도메인

PostgreSQL

제약·타입·트랜잭션 의미가 엄격해, 금융·정산처럼 잘못된 데이터를 허용하면 안 되는 곳에서 안정적인 기본값이 됩니다.

좋은 판단
기본값을 정하고 예외만 따로 둔다

많은 팀에게 합리적인 출발점은 "서버형이 필요하면 PostgreSQL을 기본값으로, 로컬·내장이면 SQLite"입니다. MySQL은 이미 팀의 운영 자산이거나 특정 관리형 환경에 강하게 묶여 있을 때 명확한 우위를 갖습니다. 중요한 것은 매번 토론하지 않도록 기본값을 정하고, 예외 상황만 근거와 함께 따로 빼두는 것입니다.

4트레이드오프

각 DB의 강점은 거의 항상 그만큼의 운영 책임을 데려옵니다.

트레이드오프
SQLite의 단순함 ↔ 동시 쓰기 한계

설치·운영이 없다는 최대 장점은, 다수 프로세스가 동시에 쓰는 순간 약점이 됩니다. "지금은 작으니 SQLite로"가 나쁜 선택은 아니지만, 쓰기 동시성이 커지는 시점을 미리 정의해 두지 않으면 마이그레이션이 급해집니다.

완화
전환 신호를 숫자로 박제

"동시 쓰기 프로세스 N개", "쓰기 QPS X" 같은 임계치를 미리 적어두고, 추상화 계층(ORM/리포지토리)을 둬 서버형 DB로의 전환 비용을 낮춥니다.

트레이드오프
PostgreSQL의 풍부함 ↔ 운영 학습 곡선

기능이 많다는 것은 알아야 할 것도 많다는 뜻입니다. autovacuum, 인덱스 전략, 커넥션 관리 등을 모르면 "느린 PostgreSQL"을 만들기 쉽습니다. 풍부함은 그 기능을 실제로 쓸 때만 이점입니다.

완화
관리형 + 모니터링 기본 탑재

관리형 서비스로 운영 표면을 줄이고, 느린 쿼리·정리 상태·커넥션 지표를 처음부터 관측합니다. 안 쓰는 확장 기능에 끌려 과설계하지 않습니다.

트레이드오프
MySQL의 익숙함 ↔ 표현력·표준의 절충

운영 자료와 인력이 풍부하다는 장점 뒤에는, 특정 고급 질의나 데이터 모델에서 PostgreSQL보다 우회가 늘 수 있다는 절충이 있습니다. 또 스토리지 엔진·설정에 따라 동작이 달라질 수 있어 기본 설정을 그대로 신뢰하지 말고 확인해야 합니다.

완화
워크로드를 먼저, 익숙함은 그 다음

복합 분석성 질의가 핵심이 아니라면 익숙함이 큰 자산입니다. 반대로 그런 질의가 핵심이면 익숙함만으로 결정하지 말고 PostgreSQL을 후보에 올립니다.

트레이드오프의 공통 교훈은 분명합니다. 선택을 끝낸 뒤에 늘어나는 운영 책임까지가 그 DB의 진짜 비용입니다. 벤치마크 한 줄보다, "이 DB를 6개월 운영할 우리 팀의 역량"을 같이 평가해야 합니다.

5최종 추천

기본값을 정하고, 갈아탈 신호를 미리 적어 두세요.

다음은 대부분의 팀이 바로 적용할 수 있는 기본 경로입니다. 절대 규칙이 아니라, 토론을 줄이기 위한 출발점으로 쓰세요.

  1. 로컬·내장·엣지·테스트면 SQLite를 먼저 고려한다. 단, "동시 쓰기 프로세스 수"와 "쓰기 QPS" 전환 임계치를 문서에 박제한다.
  2. 서버형이 필요하면 PostgreSQL을 기본값으로 둔다. 데이터 무결성·복합 질의·다양한 데이터 모델에서 안전한 선택이 되기 때문이다.
  3. MySQL은 이미 팀의 운영 자산이거나 특정 관리형 환경에 강하게 묶일 때 명시적 근거와 함께 택한다.
  4. 어떤 선택이든 관리형 서비스 + 백업·복원 리허설 + 느린 쿼리 모니터링을 1순위 운영 항목으로 둔다.
  5. ORM/리포지토리로 DB 접근을 추상화해, 후속 전환 비용을 줄여 둔다. 단 SQL 방언 차이는 테스트로 잡는다.
  6. 최종 결정 전, 한계값·기본 설정·복제 동작은 해당 버전 공식 문서로 반드시 재확인한다.

6자주 나오는 질문

결정 직전에 가장 많이 막히는 지점들입니다.

SQLite로 시작하면 나중에 후회하나요?

워크로드가 로컬·단일 프로세스 성격이면 후회하지 않습니다. 문제는 "성장하면 서버형으로 옮기겠다"는 막연한 계획뿐일 때입니다. 전환 임계치를 숫자로 정해 두면 SQLite는 훌륭한 시작점입니다.

MySQL과 PostgreSQL 중 고민될 때 한 줄 기준은?

"DB가 더 많은 일을 직접 해주길 원하는가, 운영이 단순하고 익숙하길 원하는가"입니다. 전자면 PostgreSQL, 후자이고 팀이 MySQL에 익숙하면 MySQL이 합리적입니다.

JSON을 많이 쓰면 NoSQL로 가야 하나요?

꼭 그렇지 않습니다. PostgreSQL의 jsonb는 인덱싱·질의가 강력해, 관계형 무결성과 유연한 문서 저장을 함께 가져갈 수 있습니다. 먼저 관계형 DB의 JSON 기능을 검토한 뒤 결정하세요.

성능 벤치마크만 보고 정하면 안 되나요?

위험합니다. 벤치마크는 설정·버전·워크로드에 매우 민감합니다. 같은 비용을 들여도 "우리 팀이 6개월 운영할 수 있는가"가 실제 성능보다 결과를 더 크게 좌우하는 경우가 많습니다.
