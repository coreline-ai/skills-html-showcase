gRPC 스트리밍 3주 교육 모듈

gRPC 스트리밍은 "빠른 REST"가 아니다. 하나의 연결을 유지하며 여러 메시지를 주고받는 모델이다. unary → server stream → client stream → bidi 순서로, 가장 단순한 호출부터 양방향까지 실습으로 직접 익힌다.

대상: 신입·주니어 백엔드 엔지니어 기간: 3주(주 4~6시간 추정) 선행: HTTP/2, Protocol Buffers 기초 언어 무관(Go/Java/Python 예시 호환)

이 모듈을 마치면 할 수 있는 것

이 모듈의 목적은 "스트리밍 API를 외워서 쓰는 것"이 아니라 언제 어떤 호출 모델을 골라야 하는지 스스로 판단하는 것이다. 많은 주니어가 server stream과 bidi를 혼동하거나, 모든 것을 unary로 처리하다 N+1 호출 폭주를 만든다. 그 판단 근거를 4개 모델의 차이에서 끌어낸다.

  • 모델 구분 — 요청/응답의 개수(1:1, 1:N, N:1, N:M)로 unary, server stream, client stream, bidi를 정확히 구분하고, 주어진 요구사항에 맞는 모델을 고를 수 있다.
  • 흐름 제어 — 백프레셔(수신 측이 못 따라올 때 송신을 늦추는 메커니즘)와 데드라인(요청 전체에 거는 마감 시각)을 설정하고, 둘이 없을 때 생기는 메모리 폭증·무한 대기를 설명할 수 있다.
  • 오류 진단 — 스트림 중간에 끊긴 연결, half-close 누락, 데드라인 초과(DEADLINE_EXCEEDED)를 로그만 보고 분류할 수 있다.
  • 산출물 — 주차마다 동작하는 .proto와 서버/클라이언트 코드를 직접 만들어, 3주 차에는 채팅형 bidi 데모를 완성한다.

평가 기준: 각 주차 끝의 퀴즈를 정답과 함께 통과하고, 실습 산출물이 컴파일·실행되면 해당 주차를 "이수"로 본다. 아래 핵심 용어가 막힘없이 설명되면 모듈 전체를 통과한 것으로 추정한다.

핵심 용어(칩): unary server stream client stream bidi 백프레셔 데드라인

시작 전에 준비할 것

스트리밍은 "연결이 살아 있는 동안" 일어나는 일이라, REST 핸들러처럼 함수 하나가 끝나면 응답이 나가는 모델과 사고방식이 다르다. 본격 실습 전에 환경과 멘탈 모델을 먼저 맞춘다. 아래 항목 중 하나라도 막히면, 1주 차 unary 실습이 진행되지 않는다.

우선 protoc(Protocol Buffers 컴파일러)와 사용 언어의 gRPC 플러그인이 설치돼 코드 생성이 되는지 확인한다. 그다음, HTTP/2 위에서 동작한다는 점(하나의 TCP 연결에 여러 스트림이 멀티플렉싱됨)을 머릿속에 둔다. 스트리밍의 "여러 메시지"는 새 연결을 매번 여는 게 아니라, 한 연결 위에서 프레임이 계속 흐르는 것이다.

✓
protoc + 언어 플러그인 설치

.proto 한 개를 컴파일해 스텁 코드가 생성되는지 확인. 생성이 안 되면 PATH나 플러그인 누락이 원인일 가능성이 높다.

필수
✓
HTTP/2 멀티플렉싱 개념 확인

한 연결에 여러 스트림이 동시에 흐른다는 점을 그림으로 설명할 수 있어야 한다. 스트리밍의 전제다.

필수
✓
로컬 grpcurl 또는 클라이언트 도구

서버를 띄우고 호출을 직접 던져볼 도구가 있으면 디버깅 속도가 크게 빨라진다(권장).

권장
✓

핵심 개념 — 네 가지 호출 모델과 3주 진행

gRPC의 호출 모델은 요청 메시지 개수 × 응답 메시지 개수의 조합으로 정리하면 한눈에 들어온다. unary는 1:1, server stream은 1:N, client stream은 N:1, bidi는 N:M이다. 이 표 하나가 모듈 전체의 뼈대이며, 실습은 단순한 1:1에서 복잡한 N:M으로 난이도를 올린다.

네 가지 호출 모델 비교 — 요청/응답 개수와 대표 사례
모델 요청 : 응답 한 줄 정의 대표 사례 주차
unary 1 : 1 요청 하나에 응답 하나. REST와 가장 비슷하다. 사용자 단건 조회, 결제 요청 1주
server stream 1 : N 요청 하나에 서버가 응답을 여러 번 흘려보낸다. 실시간 시세 구독, 진행률 푸시 2주
client stream N : 1 클라이언트가 여러 번 보내고 서버가 마지막에 한 번 응답. 대용량 업로드, 로그 일괄 적재 2주
bidi N : M 양쪽이 독립적으로 보내고 받는다. 순서가 묶이지 않는다. 채팅, 양방향 게임 동기화 3주

흔히 하는 오해: "스트리밍이면 무조건 빠르다"는 잘못된 직관이다. 스트리밍의 장점은 속도 자체가 아니라 연결 유지로 매 메시지의 핸드셰이크 비용을 없애고, 데이터가 준비되는 즉시 흘려보낼 수 있다는 데 있다. 단건 요청/응답이면 unary가 더 단순하고 디버깅도 쉽다. 모델 선택은 "메시지가 정말 여러 개인가"라는 질문에서 출발한다.

아래 타임라인은 3주 진행 순서를 단계로 정리한 것이다. 각 단계는 앞 단계의 멘탈 모델 위에 쌓이도록 설계했다. 1주에서 "한 연결 위의 호출"에 익숙해진 뒤에야 2주의 "여러 메시지 흐름"이, 그다음에야 3주의 "동시 양방향"이 자연스럽게 이해된다.

  1. 1주 — unary로 기초 다지기

    1:1 호출로 .proto 정의·스텁 생성·서버/클라이언트 연결을 끝까지 경험한다. 여기서 데드라인 설정을 처음 붙인다.

  2. 2주 — 단방향 스트림 두 종류

    server stream(1:N)으로 서버 푸시를, client stream(N:1)으로 업로드를 구현한다. half-close와 백프레셔를 처음 마주친다.

  3. 3주 — bidi와 운영 관점

    양방향(N:M) 채팅을 만들고, 동시성·순서·연결 종료를 다룬다. 데드라인/취소를 양쪽에서 함께 본다.

  4. 마무리 — 모델 선택 판단 훈련

    주어진 요구사항을 보고 네 모델 중 하나를 고르고 근거를 말하는 연습. 이 판단력이 모듈의 최종 산출물이다.

백프레셔와 데드라인 — 스트리밍에서만 커지는 두 위험

백프레셔는 수신 측이 처리 속도를 못 따라갈 때 송신 측을 늦추는 흐름 제어다. server stream에서 서버가 초당 수천 건을 흘리는데 클라이언트가 천천히 읽으면, 버퍼가 쌓여 메모리가 폭증할 수 있다. gRPC 구현은 보통 흐름 제어 윈도를 통해 이를 자동으로 일부 막아주지만, 애플리케이션 레벨에서 읽기 속도에 맞춰 보내는 설계를 함께 해야 안전하다(세부 동작은 언어/구현마다 달라 약간의 차이가 있다고 본다).

데드라인은 "이 시각까지 끝나지 않으면 포기한다"는 절대 마감이다. 타임아웃(상대 시간)과 비슷하지만, gRPC는 호출 체인을 따라 데드라인을 전파하므로 분산 호출에서 무한 대기를 막는 핵심 장치다. 데드라인을 안 걸면 스트림이 영원히 열린 채 자원을 잡고 있을 수 있다. 다음 행동: 1주 차 unary부터 모든 호출에 데드라인을 습관처럼 붙인다.

예제로 보는 차이 — 같은 데이터, 다른 모델

"최근 주문 100건을 클라이언트에 전달한다"는 한 가지 요구를 네 모델로 풀면 차이가 또렷해진다. 코드를 외우기보다, 각 모델이 데이터를 언제·몇 번 흘리는지에 집중한다.

1) unary — 한 번에 100건을 배열로

서버는 100건을 모아 OrderList 하나로 묶어 한 번에 응답한다. 단순하고 디버깅이 쉽다. 단점: 100건이 다 준비될 때까지 클라이언트는 아무것도 못 받고, 메시지가 커지면 메모리·지연이 함께 커진다.

2) server stream — 준비되는 대로 한 건씩 푸시

서버는 stream Order로 선언하고 주문을 하나씩 흘려보낸다. 클라이언트는 첫 건을 즉시 받기 시작한다. 진행률 표시나 실시간 구독에 적합. 이때 클라이언트가 느리면 백프레셔를 고려해야 한다.

3) client stream — 클라이언트가 여러 건 올리고 끝에 요약 한 번

반대 방향. 클라이언트가 주문을 여러 번 Send한 뒤 half-close(더 보낼 게 없다고 알림)하면, 서버가 집계 결과 하나를 응답한다. 업로드·일괄 적재에 적합. half-close를 빠뜨리면 서버는 영원히 기다린다.

4) bidi — 양쪽이 독립적으로 주고받음

요청 스트림과 응답 스트림이 분리돼, 보낸 순서와 받는 순서가 묶이지 않는다. 채팅처럼 "내가 말하는 동안 상대도 말하는" 상황에 맞다. 가장 강력하지만 동시성·종료 처리가 가장 까다롭다.

판단 정리: 데이터가 정말 흐름(stream)인지, 아니면 한 덩어리인지를 먼저 묻는다. 한 덩어리면 unary가 정답에 가깝다. 한쪽만 여러 개면 server/client stream, 양쪽 다 여러 개이고 순서가 독립적이면 bidi다.

주차별 실습과 산출물

각 주차는 "동작하는 산출물"로 끝난다. 코드가 컴파일되고 호출이 왕복하면 통과다. 아래는 주차별 목표·산출물·흔한 오류를 묶은 것이다.

1주 차 — unary 왕복 완성

  • 목표: .proto에서 스텁을 생성하고, unary RPC 한 개로 서버↔클라이언트 왕복을 성공시킨다. 데드라인을 처음 설정한다.
  • 산출물: GetUser(UserRequest) returns (UserReply) 형태의 동작하는 서비스 + 데드라인이 걸린 클라이언트 호출.
  • 흔한 오류: 스텁 미생성 상태로 import 실패 / 서버·클라이언트의 .proto 버전 불일치 / 데드라인을 안 걸어 장애 시 무한 대기.

2주 차 — 단방향 스트림 두 개

  • 목표: server stream으로 서버 푸시를, client stream으로 업로드를 각각 구현한다. half-close와 스트림 종료를 직접 다룬다.
  • 산출물: Subscribe(Req) returns (stream Event)와 Upload(stream Chunk) returns (Summary) 두 RPC가 모두 왕복.
  • 흔한 오류: client stream에서 half-close 누락으로 서버 무한 대기 / server stream에서 클라이언트가 느려 버퍼가 쌓이는데 백프레셔 미고려 / 스트림 종료 시 에러 코드 미처리.

3주 차 — bidi 채팅 데모

  • 목표: bidi로 다중 메시지를 양방향으로 주고받는 미니 채팅을 완성한다. 동시성·순서 독립성·연결 종료를 다룬다.
  • 산출물: Chat(stream Msg) returns (stream Msg) 기반의, 두 클라이언트가 메시지를 교환하는 데모.
  • 흔한 오류: 보내는 고루틴/스레드와 받는 쪽을 한 흐름에서 처리하려다 교착 / 한쪽 종료 시 상대 스트림 정리 누락 / 데드라인을 너무 짧게 걸어 정상 대화가 DEADLINE_EXCEEDED로 끊김.

다음 행동: 주차 산출물을 제출하기 전, 아래 점검 섹션의 체크리스트로 자가 검수를 돌린다. 특히 "모든 호출에 데드라인"과 "스트림 종료/half-close 처리"는 거의 모든 운영 장애의 원인이라 반드시 확인한다.

이해도 점검 퀴즈

각 주차 학습 직후 풀어본다. 정답은 다음 섹션에 근거와 함께 정리했다. 정답 자체보다 왜 그런지를 말로 설명할 수 있는지가 핵심이다.

  1. Q1. 클라이언트가 100MB 파일을 청크로 쪼개 서버에 올리고, 서버는 업로드가 끝난 뒤 검증 결과 하나만 돌려준다. 적합한 호출 모델은?
  2. Q2. client stream에서 클라이언트가 모든 청크를 보냈는데도 서버 응답이 오지 않고 멈춰 있다. 가장 의심되는 원인은?
  3. Q3. server stream으로 초당 수천 건을 푸시하는데 클라이언트 메모리가 계속 증가한다. 이 현상을 막는 메커니즘의 이름은?
  4. Q4. 분산 호출 체인에서 한 단계가 응답하지 않을 때, 전체가 무한 대기에 빠지지 않도록 거는 절대 마감 장치는?
  5. Q5. (참/거짓) "스트리밍은 항상 unary보다 빠르므로 모든 API를 스트리밍으로 만드는 것이 좋다."

퀴즈 정답과 해설

  • A1 — client stream(N:1). 클라이언트가 여러 청크를 보내고 서버가 마지막에 결과 하나를 응답하므로 N:1 모델이다. unary로 100MB를 한 메시지에 담으면 메시지 크기 한도와 메모리에 부담이 크다.
  • A2 — half-close 누락. 클라이언트가 "더 보낼 것이 없다"는 신호(half-close)를 보내지 않으면 서버는 스트림이 끝났는지 알 수 없어 계속 기다린다. 전송 루프 종료 후 스트림을 닫는 처리를 확인한다.
  • A3 — 백프레셔(흐름 제어). 수신 측 처리 속도에 맞춰 송신을 늦추는 메커니즘이다. gRPC는 HTTP/2 흐름 제어로 일부 자동 대응하지만, 애플리케이션이 읽는 속도에 맞춰 보내도록 설계해야 안전하다.
  • A4 — 데드라인. 호출 체인을 따라 전파되는 절대 마감 시각이다. 초과 시 DEADLINE_EXCEEDED로 호출이 종료돼 자원이 회수된다. 타임아웃(상대 시간)과 의미는 비슷하나 gRPC는 데드라인 전파를 표준으로 쓴다.
  • A5 — 거짓. 스트리밍의 이점은 "여러 메시지·연결 유지"가 필요한 상황에 한정된다. 단건 1:1 요청은 unary가 더 단순하고 디버깅도 쉽다. 모델은 데이터 흐름의 형태로 고르는 것이지 속도만으로 고르지 않는다.

채점 기준(추정): 5문항 중 4개 이상을 근거와 함께 설명하면 해당 구간을 이수한 것으로 본다. 특히 A2(half-close)와 A5(거짓)는 실무에서 가장 많이 틀리는 항목이라 반드시 짚는다.
