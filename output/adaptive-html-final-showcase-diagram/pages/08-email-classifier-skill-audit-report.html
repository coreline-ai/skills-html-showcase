이메일 자동 분류 스킬 감사 리포트

이 스킬은 폴더를 정확히 나누는 능력보다 오분류 안전망·회신 필요 메일 누락 방지·분류 근거 표시가 더 중요하다. 감사는 트리거·입력 처리·분류 기준·실패 모드·사람 확인 루프를 분리해 각각의 위험과 출시 조건을 따진다.

대상 독자: 스킬 제작자·업무 자동화 팀 · 감사 기준일: 2026-05-31 · 판단 목표: 다섯 축(트리거·입력·기준·실패·확인) 분리 감사 · 핵심 결론: 정확도 게이트 1개가 아니라 안전망 게이트 4개로 출시 판정

요약 진단

이메일 자동 분류 스킬을 평가할 때 가장 흔한 실수는 "정확도(폴더를 맞게 나눴는가)" 하나로 합격/불합격을 가르는 것이다. 그러나 업무 메일에서 비용이 큰 사건은 분류가 약간 틀린 경우가 아니라, 회신이 필요한 메일을 자동으로 묻어버리거나, 중요한 메일을 스팸으로 오탐(false positive)하거나, 사용자가 왜 그렇게 분류됐는지 확인할 수 없는 경우다. 따라서 이 감사는 정확도를 한 축으로만 두고, 안전망·누락 방지·근거 표시를 동등한 비중의 출시 조건으로 본다.

현재 스킬을 다섯 축으로 분해해 본 결과, 분류 기준(어떤 신호로 폴더를 정하는가)은 비교적 잘 정의되어 있으나, 실패 모드 정의와 사람 확인 루프가 약하다는 것이 핵심 판단이다. 구체적으로 (1) 규칙 충돌 시 우선순위가 명문화되어 있지 않고, (2) 스팸 오탐을 되돌릴 경로가 없으며, (3) 회신 필요 메일을 "처리됨"으로 표시하는 단일 실패점이 존재한다. 이 셋은 모두 자동화가 조용히 일을 잘못하게 만드는 종류의 결함이라 정확도 수치로는 드러나지 않는다.

다음 행동의 우선순위는 명확하다. 첫째, 스팸/삭제처럼 되돌리기 어려운 동작은 자동 실행에서 제외하고 사람 확인 큐로 보낸다. 둘째, 회신 필요(reply-needed) 신호를 별도 1급 라벨로 분리해 분류 폴더와 독립적으로 추적한다. 셋째, 모든 자동 분류에 한 줄 근거(어떤 규칙·신호가 작동했는지)를 부착해 사람이 5초 안에 검증할 수 있게 한다. 이 세 가지가 들어가기 전에는 "정확도 90%"라는 수치만으로 출시해서는 안 된다는 것이 본 감사의 결론이다.

다섯 축 점수와 출시 게이트

아래 점수는 코드·문서·예시 프롬프트를 함께 검토한 정성 평가이며, 자동화된 회귀 테스트가 아직 없어 수치는 약/추정으로 읽어야 한다. 5점 만점에서 4점 이상을 "출시 가능", 3점을 "조건부", 2점 이하를 "차단"으로 본다.

다섯 축 감사 점수표 (5점 만점, 추정치 · 상태는 색이 아니라 텍스트 라벨로 구분)
감사 축 무엇을 보는가 점수(추정) 판정 핵심 근거
트리거 언제 분류를 실행/보류하는가 4 / 5 통과 수동 실행과 신규 메일 수신 트리거가 분리됨. 다만 대량 유입 시 배치 경계가 모호
입력 처리 본문·헤더·첨부·인코딩을 어떻게 읽는가 3 / 5 조건부 HTML 본문 정제는 되나 첨부 처리 경로가 불명확하고, 발신자 위장 헤더 신뢰 처리가 약함
분류 기준 어떤 신호로 폴더를 정하는가 4 / 5 통과 발신자·키워드·스레드 맥락 신호 정의가 명확. 다만 신호 충돌 시 가중치 규칙 부재
실패 모드 틀렸을 때 무슨 일이 일어나는가 2 / 5 차단 스팸 오탐·회신 필요 누락에 대한 복구 경로 없음. 되돌리기 어려운 동작이 자동 실행됨
사람 확인 루프 불확실한 건을 누가 어떻게 확인하는가 2 / 5 차단 신뢰도 임계값 없이 모든 건을 자동 확정. 확인 큐·근거 표시·되돌리기 모두 부재

표의 핵심은 "잘하는 것"과 "위험한 것"이 갈린다는 점이다. 분류를 하는 능력(트리거·기준)은 4점대로 양호하지만, 분류가 틀렸을 때를 다루는 능력(실패 모드·사람 확인)은 2점대로 출시 차단 수준이다. 정확도 한 축으로만 봤다면 이 스킬은 합격으로 보였을 것이다.

스팸 오탐 안전망 — 차단

중요 메일을 스팸으로 보내면 사용자가 모르게 손실이 난다. 스팸/삭제 같은 비가역 동작은 자동 실행 금지, 확인 큐로만 보낼 것. 현재 미구현이므로 출시 차단.

회신 필요 누락 — 차단

분류 폴더와 별개로 reply-needed 신호를 1급 라벨로 추적. "분류됨=처리됨"으로 묻히는 단일 실패점 제거 전까지 출시 차단.

규칙 충돌 우선순위 — 주의

발신자 규칙과 키워드 규칙이 다른 폴더를 가리킬 때 결정 규칙이 없음. 명시적 우선순위 표를 문서화하면 해소 가능.

분류 근거 표시 — 주의

자동 분류마다 어떤 신호가 작동했는지 한 줄 근거를 부착. 사람이 5초 내 검증 가능해야 신뢰가 쌓임.

첨부 처리 경계 — 통과(조건부)

대용량·실행형 첨부는 본문 분류 신호에서 분리해 다루는 규칙이 있으면 통과. 누락 시 주의로 강등.

되돌리기(undo) — 통과 목표

모든 자동 분류는 최근 N건 일괄 되돌리기가 가능해야 한다. 가역성이 안전망의 마지막 줄.

PRE-FLIGHT 게이트: 정확도 수치보다 먼저 — 비가역 동작 차단 · 회신 필요 분리 · 분류 근거 표시 세 가지가 모두 통과해야 출시 판정에 들어간다.

섹션·라인별 진단

여기서는 스킬 정의 문서와 동작 흐름을 항목별로 짚는다. 각 항목은 "관찰 → 왜 문제인가 → 무엇을 바꾼다"로 읽으면 된다.

1) 트리거 정의 — 실행 시점이 둘로 나뉘는가

현재 스킬은 "신규 메일 수신"과 "사용자 수동 일괄 정리" 두 경로에서 실행된다. 두 경로를 분리한 것은 좋은 설계다. 다만 대량 유입(예: 뉴스레터 동시 도착)에서 배치 경계와 처리 순서가 정의되어 있지 않아, 같은 스레드의 메일이 서로 다른 배치에서 다른 폴더로 갈 위험이 있다. 다음 행동: 트리거에 "스레드 단위로 묶어 처리"를 명시하고, 1회 배치 최대 건수를 둔다.

2) 입력 처리 — 무엇을 신뢰하고 무엇을 의심하는가

본문이 HTML일 때 텍스트만 추출해 분류 신호로 쓰는 정제 단계는 적절하다. 그러나 발신자 표시 이름과 실제 도메인이 다른 위장 메일을 그대로 신뢰해 "거래처" 폴더로 보낼 수 있다. 또한 첨부 처리 경로가 모호해, 첨부 파일명이 본문 분류에 과도하게 영향을 주는 사례가 보인다. 다음 행동: 발신 도메인 검증을 신호 가중치에 반영하고, 첨부는 별도 신호 채널로 분리한다.

3) 분류 기준과 규칙 충돌 — 누가 이기는가

발신자·키워드·스레드 맥락이라는 세 신호의 정의는 명확하다. 문제는 이 신호들이 서로 다른 폴더를 가리킬 때다. 예를 들어 발신자는 "거래처"인데 본문 키워드는 "스팸성 광고"인 경우, 현재는 마지막에 평가된 규칙이 우연히 이긴다. 이것이 전형적인 규칙 충돌이며 재현이 어려운 오분류의 주원인이다. 다음 행동: 신호별 우선순위·가중치를 표로 고정하고, 충돌 시 자동 확정 대신 사람 확인 큐로 보낸다.

4) 실패 모드 — 틀렸을 때 무슨 일이 벌어지는가

가장 심각한 결함이 여기 있다. 스팸 오탐(정상 메일을 스팸으로) 시 복구 경로가 없고, 스팸으로 분류된 메일은 사용자 눈에 띄지 않게 된다. 더 큰 문제는 회신 필요 메일이 일반 폴더로 분류되며 "처리됨"으로 간주돼, 마감이 있는 회신을 놓치는 단일 실패점이다. 다음 행동: 비가역 동작 자동 실행 금지 + reply-needed를 분류와 독립된 1급 라벨로 승격.

5) 사람 확인 루프 — 불확실을 누가 처리하는가

현재 스킬은 신뢰도와 무관하게 모든 메일을 자동 확정한다. 신뢰도 임계값, 확인 큐, 근거 표시, 되돌리기 중 어느 것도 없다. 자동화에서 "확실할 때만 자동, 애매하면 사람"이라는 분기가 없으면 오류가 조용히 누적된다. 다음 행동: 신뢰도 임계값(예: 약 0.8 이상만 자동) 도입, 그 아래는 사람 확인 큐, 모든 자동 건에 한 줄 근거 부착.

rules.ymlfocus

발신자·키워드·스레드 신호와 폴더 매핑을 정의하는 규칙 파일.

개선 우선순위 로드맵

아래는 위험과 구현 비용을 함께 고려한 권장 순서다. 1순위는 출시 차단을 푸는 안전망, 2순위는 신뢰를 쌓는 근거 표시, 3순위는 정확도 자체를 끌어올리는 튜닝이다.

개선 우선순위와 완료 조건 (P1이 가장 시급 · 상태 라벨로 구분)
우선순위 개선 항목 해결하는 축 완료 조건
P1 (차단 해제) 비가역 동작 자동 실행 금지 + 사람 확인 큐 실패 모드 · 사람 확인 스팸/삭제가 자동 확정되지 않고, 최근 N건 일괄 되돌리기가 동작
P1 (차단 해제) 회신 필요 1급 라벨 분리 실패 모드 reply-needed가 폴더 분류와 독립 유지, 마감 메일이 묻히지 않음
P2 (신뢰) 분류 근거 한 줄 표시 사람 확인 모든 자동 분류에 작동 신호가 노출, 5초 내 사람 검증 가능
P2 (신뢰) 규칙 충돌 우선순위 표 분류 기준 충돌 시 결정이 재현 가능, 동률은 사람 확인 큐로 라우팅
P3 (정확도) 발신 도메인 검증·첨부 신호 분리 입력 처리 위장 발신자 오신뢰 감소, 첨부 파일명이 본문 분류를 왜곡하지 않음
P3 (정확도) 신뢰도 임계값·회귀 테스트 셋 트리거 · 분류 기준 임계값 미만 자동 보류, 확인 큐 로그로 회귀 테스트 자동화

순서를 지키는 이유는 명확하다. 정확도 튜닝(P3)을 먼저 하더라도 안전망(P1)이 없으면 "정확하지만 위험한" 자동화가 된다. 반대로 P1·P2를 먼저 깔면 정확도가 다소 낮아도 사람이 안전하게 개입할 수 있어, 운영하면서 정확도를 점진적으로 올릴 수 있다.

개선본 적용 — 트리거·프롬프트 튜닝

마지막으로 스킬 정의에 들어갈 트리거·프롬프트 문구를 손본다. 핵심은 "분류만 잘해라"에서 "확신이 있을 때만 자동 분류하고, 애매하거나 비가역적인 건은 사람에게 넘기고, 근거를 남겨라"로 지시의 무게중심을 옮기는 것이다. 아래는 개선 전후 비교다.

Before — 정확도만 요구

"받은 메일을 폴더로 정확하게 분류해줘. 스팸은 스팸함으로 옮기고 나머지는 적절한 폴더에 넣어줘."

After — 안전망·근거 포함

"신뢰도 약 0.8 이상일 때만 자동 분류하고, 그 미만이거나 규칙이 충돌하면 사람 확인 큐로 보낸다. 스팸·삭제는 자동 실행하지 말고 큐에만 제안한다. 회신 필요 메일은 폴더와 별개로 reply-needed 라벨을 단다. 모든 자동 분류에는 어떤 신호가 작동했는지 한 줄 근거를 남긴다."

After 프롬프트는 다섯 축 중 차단 상태였던 실패 모드·사람 확인 루프를 직접 지시문으로 끌어올린다. 신뢰도 임계값(트리거 보류), 비가역 동작 금지(안전망), reply-needed 분리(누락 방지), 한 줄 근거(검증 가능성)가 모두 한 문단에 들어간다. 이 문구를 스킬 정의의 동작 규칙으로 고정하면, 구현이 바뀌어도 안전 경계가 흔들리지 않는다.

검증 체크리스트(출시 전 필수): (1) 스팸/삭제가 자동 확정되지 않는가 — 확인 큐 경유만 허용. (2) 회신 필요 메일이 일반 폴더로 묻히지 않는가 — reply-needed 라벨 유지. (3) 임계값 미만 건이 사람 확인 큐로 가는가. (4) 자동 분류마다 근거 한 줄이 보이는가. (5) 최근 분류를 일괄 되돌릴 수 있는가. 다섯 항목이 모두 통과해야 정확도 수치를 보기 시작한다.

감사 범위와 한계

이 리포트는 스킬 정의 문서·예시 프롬프트·동작 흐름 검토에 기반한 정성 감사다. 점수와 임계값(예: 신뢰도 약 0.8)은 운영 데이터로 검증되지 않은 추정치이며, 자동 회귀 테스트 셋이 마련되면 재측정해야 한다. 본문의 "차단/주의/통과" 판정은 색이 아니라 텍스트 라벨로 표기했으며, 표에는 모두 캡션을 달았다. 실제 메일 데이터·사용자 폴더 구조가 확인되면 분류 기준과 우선순위 표를 해당 환경에 맞춰 다시 보정할 것을 권한다.
