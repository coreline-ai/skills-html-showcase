게시판에 Coreline Auth 붙이기: 세션·권한·소유권 실습

BoardService와 Coreline Auth를 연결하는 흐름을 실습형 교육 모듈로 정리했습니다.

생성일 2026-05-30검토 기준: 접근성·SEO·보안 정확성courseboard integrationrbac

1학습 목표

  • BoardService가 CorelineAuthService의 세션을 어떻게 소비하는지 설명할 수 있다.
  • own/any 권한을 게시글 소유권과 연결할 수 있다.
  • 동기 데모에서 비동기 production 전환 시 빠진 컴포넌트를 식별할 수 있다.

2사전 개념

Principal

검증된 세션과 사용자 정보를 합친 실행 주체다. 게시판은 raw cookie가 아니라 Principal을 기준으로 권한을 판단한다.

own / any

`post:delete:own`은 내 글만, `post:delete:any`는 타인의 글까지 관리할 수 있음을 뜻한다.

3예제 흐름

1. 브라우저가 coreline_auth_session cookie 전송
2. board route가 auth.verify_session(token) 호출
3. BoardService가 AuthorizationContext(actor, owner)을 구성
4. ResourceAuthorizer가 post:update:own 또는 post:update:any 평가
5. 허용되면 storage update, 실패하면 403

이 흐름의 핵심은 게시판이 별도 인증 체계를 만들지 않는다는 점이다. 인증은 Coreline Auth가 맡고, 게시판은 도메인 소유권과 권한명을 연결한다.

4실습

  1. 작성자 역할로 글을 하나 생성한다.
  2. 다른 사용자의 글 삭제를 시도하고 실패를 확인한다.
  3. moderator 역할로 같은 삭제를 성공시킨다.
  4. 사용자를 viewer로 강등한 뒤 기존 세션으로 삭제 API가 실패하는지 확인한다.

5퀴즈

Q1. `post:*:own`이 `post:delete:any`를 만족하면 왜 위험할까?

Q2. password reset 후 기존 board 세션을 폐기해야 하는 이유는?

정답 해설: Q1은 scope가 확장되어 소유권 경계가 깨지기 때문이다. Q2는 탈취된 cookie가 reset 이후에도 유효하면 복구 절차가 의미를 잃기 때문이다.
