인증 버그를 패치하며 배운 것: 오래된 성공을 지우는 일

Coreline Auth 보안 패치 경험을 개인적 관점과 실행 조언으로 풀어낸 블로그형 HTML입니다.

생성일 2026-05-30검토 기준: 접근성·SEO·보안 정확성blogengineering notessecurity

가장 무서운 인증 버그는 로그인 실패가 아니라, “실패했어야 할 오래된 성공”이다.

이번 패치를 보면서 계속 떠오른 장면은 퇴사한 직원의 출입증이었다. 시스템에서는 퇴사 처리됐는데 문은 여전히 열린다면, 인사 기록은 아무 소용이 없다.

1내가 가장 먼저 본 것은 세션이었다

session touch가 stale revoked_at을 되살릴 수 있는 문제는 작은 race처럼 보이지만, 로그아웃·admin revoke·password reset의 의미를 뒤집는다. 그래서 인증에서는 “상태를 갱신한다”보다 “금지 상태를 덮어쓰지 않는다”가 더 중요하다.

2권한은 이름보다 비교 규칙이 어렵다

`post:*:own`이라는 이름은 분명해 보인다. 하지만 matcher가 action wildcard를 먼저 통과시키면 scope 검증은 사라진다. 이 문제를 보며 권한 문자열은 DSL이고, DSL은 테스트 없이는 쉽게 거짓말을 한다는 걸 다시 느꼈다.

3좋은 보안 패치는 개발자를 덜 믿는다

MFA vault를 기본 fail-closed로 바꾼 것도 같은 이유다. “문서에 production에서는 쓰지 말라고 적혀 있음”은 충분한 장치가 아니다. production에서 위험한 선택은 코드가 직접 멈춰야 한다.

4실행 방법

  • 보안 설정은 default-deny로 둔다.
  • host app이 직접 호출할 public method는 안전한 기본 동작을 가진다.
  • 예외는 `revoke_sessions=False`, `allow_insecure_mfa_vault=True`처럼 이름만 봐도 위험이 드러나게 만든다.
  • 패치마다 “이전 취약 상태가 재발하지 않는 테스트”를 붙인다.

✓부드러운 CTA

오늘 자기 프로젝트의 인증 코드를 하나만 본다면, password change 함수가 기존 세션을 어떻게 처리하는지 찾아보자. 그 한 줄이 사고 대응의 체감 품질을 바꾼다.
