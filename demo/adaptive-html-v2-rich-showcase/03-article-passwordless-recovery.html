비밀번호 없는 로그인 시대에도 account recovery가 더 어려운 이유

Passkey가 로그인 보안을 높여도 계정 복구는 더 정교한 인증 수단 생명주기와 세션 폐기 정책을 요구한다는 점을 설명합니다.

생성일 2026-05-30병렬 에이전트 리서치 기반모드: articlepasskeyaccount recoveryMFA

패스키와 비밀번호 없는 로그인은 인증의 많은 문제를 해결합니다. 하지만 더 어려워지는 지점은 로그인 화면이 아니라 account recovery입니다. 인증 수단을 잃은 사람이 정말 계정 주인인지 판단하는 일은, 패스키를 검증하는 일보다 훨씬 애매하고 위험합니다.

비밀번호 없는 로그인의 약한 고리는 로그인 자체가 아니라, 사용자가 모든 인증 수단을 잃어버렸다고 말하는 순간 시작되는 복구 절차다.

1Passkey는 로그인 위험을 낮추지만 복구 위험을 없애지 않는다

Passkey는 공개키 기반 인증입니다. 서버는 사용자의 비밀키를 알지 못하고, 사용자는 사이트별로 재사용 가능한 비밀번호를 입력하지 않습니다. 이 구조는 피싱과 credential stuffing에 강합니다. 그러나 사용자가 휴대폰을 잃어버리고, 동기화 계정에도 접근하지 못하고, TOTP 앱까지 사라졌다면 이야기가 달라집니다.

로그인은 등록된 인증 수단을 검증하면 끝납니다. 복구는 등록된 인증 수단을 쓸 수 없을 때 시작됩니다. 그래서 복구 절차는 passkey보다 약한 fallback 경로가 될 수 있습니다.

2Account recovery는 인증이 아니라 authenticator lifecycle 관리다

복구가 끝난 뒤 시스템은 새 passkey 등록, 기존 passkey 폐기, 기존 세션 revoke, MFA 재설정, recovery code 재발급, 사용자 알림을 결정해야 합니다. NIST도 account recovery를 사용자가 필요한 authenticator를 잃었을 때 계정을 회복하고 새 authenticator를 바인딩하는 흐름으로 다룹니다.

질문필요한 결정
새 passkey를 등록해도 되는가?검증 수준과 위험 점수 확인
기존 passkey를 폐기할 것인가?분실·탈취 가능성에 따른 revoke
기존 세션을 유지할 것인가?recovery 이후 session revoke
MFA를 초기화할 것인가?공격자가 MFA를 제거하지 못하게 제한
recovery code를 재발급할 것인가?기존 코드는 폐기하고 새 코드 발급

3Synced passkey는 편리하지만 책임 경계가 흐려진다

iCloud Keychain, Google Password Manager, 1Password 같은 synced passkey는 사용자 경험을 크게 개선합니다. 하지만 서비스의 계정 보안 일부가 passkey provider의 계정 복구 보안에 의존하게 됩니다. 고위험 계정일수록 device-bound passkey 추가 등록, 관리자 계정 passkey 2개 이상, 새 기기 등록 시 step-up MFA 같은 정책이 필요합니다.

4MFA는 복구의 답이지만 MFA 분실도 복구 문제다

MFA는 강력하지만, 사용자가 passkey 기기, TOTP 앱, 보안키, 이메일 접근권, recovery code를 동시에 잃을 수 있습니다. 좋은 recovery 설계는 정상 사용자를 영구 잠그지 않으면서 공격자에게 우회로를 주지 않아야 합니다.

좋은 recovery code 정책

충분한 엔트로피, 원문 미저장, hash 저장, 단회성 사용, rate limit, 사용 후 재발급, 고위험 계정 추가 검증을 함께 적용합니다.

5Recovery 이후 session revoke가 마지막 단계다

복구 완료 후 기존 refresh token, remember-me cookie, 관리자 세션이 살아 있다면 공격자는 계속 접근할 수 있습니다. 따라서 password reset, passkey 재등록, MFA 초기화, recovery code 사용 이후에는 기존 세션과 장기 토큰 폐기가 기본값이어야 합니다.

이벤트권장 세션 처리
password reset 완료모든 기존 세션 revoke
passkey 신규 등록고위험이면 기존 세션 revoke
MFA 초기화모든 기존 세션 revoke 권장
관리자 권한 회수해당 사용자 세션 revoke
recovery code 사용모든 기존 세션 revoke + 알림

6사례: 비밀번호 없는 관리자 계정이 복구 링크 하나로 뚫리는 경우

관리자 계정은 passkey만으로 로그인하도록 강하게 보호되어 있습니다. 하지만 계정 복구가 이메일 링크 하나만으로 새 passkey 등록을 허용한다면, 이메일 계정만 탈취한 공격자가 passkey를 새로 등록할 수 있습니다. 더 나쁜 경우 기존 관리자 세션이 남아 있어 추적과 차단이 어려워집니다.

위험한 흐름

이메일 링크 → 새 passkey 등록 → 기존 세션 유지 → 기존 passkey/MFA 상태 유지 → 관리자 권한 계속 사용.

개선 흐름

이메일 링크 + recovery code 또는 기존 MFA → step-up → 새 passkey 등록 → 기존 세션 revoke → 기존 passkey 목록 확인 → audit log와 사용자 알림.

7Takeaway

비밀번호 없는 로그인의 목표는 “비밀번호 입력창 제거”가 아닙니다. 진짜 목표는 계정 통제권을 더 안전하게 증명하고 유지하는 것입니다. 로그인은 passkey로 단순하게, 복구는 MFA·recovery code·session revoke·알림으로 신중하게 설계해야 합니다.
