쿠키 세션·CSRF·SameSite를 카페 출입 팔찌로 이해하기

쿠키 기반 로그인에서 왜 CSRF 토큰과 SameSite가 함께 필요한지 카페 출입 팔찌 비유로 풍성하게 설명합니다.

큰 비유: 세션 쿠키는 회원 전용 카페의 출입 팔찌입니다. 브라우저는 카페 도메인으로 갈 때마다 팔찌를 자동으로 보여줍니다. 편리하지만, 외부 전단지가 몰래 주문서를 보내도 팔찌가 같이 보일 수 있습니다. 그래서 진짜 주문서에는 그날 카페 안에서 받은 도장, 즉 CSRF 토큰이 필요합니다.

1왜 “자동으로 보내는 쿠키”가 위험해질까

로그인 후 브라우저가 세션 쿠키를 자동 첨부하는 것은 사용자 경험을 좋게 만듭니다. 사용자는 매번 비밀번호를 입력하지 않아도 되고, 서버는 쿠키의 세션 토큰 해시를 통해 사용자를 식별합니다. 하지만 CSRF 관점에서는 바로 이 자동 첨부가 공격 표면입니다. 공격자는 쿠키 값을 몰라도 됩니다. 사용자의 브라우저가 이미 알고 있기 때문입니다.

카페 직원이 손목 팔찌만 보고 모든 주문을 처리한다면, 외부 전단지가 손님 모르게 “멤버십 해지” 주문서를 제출해도 직원은 팔찌 때문에 진짜 요청으로 오해할 수 있습니다.

3핵심 용어 5개

세션 쿠키

로그인 상태를 유지하는 브라우저 쿠키입니다. Coreline Auth에서는 coreline_auth_session이 대표적입니다. 원문 토큰은 클라이언트에만 있고, 서버 저장소에는 해시가 저장되어야 합니다.

HttpOnly

자바스크립트가 세션 쿠키를 읽지 못하게 하는 옵션입니다. XSS 피해를 줄이지만, 브라우저가 요청에 쿠키를 자동 첨부하는 CSRF를 직접 막지는 않습니다.

CSRF

사용자가 로그인된 브라우저를 이용해 공격자가 의도한 요청을 보내게 만드는 공격입니다. 사용자의 “신원”이 아니라 “의도”가 위조됩니다.

CSRF 토큰

쿠키와 별도로 제출해야 하는 요청 도장입니다. Coreline Auth에서는 coreline_auth_csrf 쿠키와 x-csrf-token 헤더를 함께 검증합니다.

SameSite

브라우저가 cross-site 요청에 쿠키를 자동으로 보낼지 조절합니다. Strict가 가장 강하고, Lax는 사용성과 방어의 균형이며, None은 Secure와 함께 써야 합니다.

4Coreline Auth의 안전한 쿠키 요청 흐름

1. 로그인

서버가 세션 토큰을 발급하고 브라우저에 HttpOnly 세션 쿠키를 설정합니다. 서버 DB에는 원문이 아니라 해시가 남습니다.

2. CSRF 발급

GET /auth/csrf로 토큰을 발급받고, state-changing 요청에 헤더로 넣습니다.

3. 상태 변경

서버는 세션, 권한, CSRF 쿠키/헤더 일치, 서명, session binding을 모두 검증합니다.

POST /auth/logout
Cookie: coreline_auth_session=...
Cookie: coreline_auth_csrf=...
x-csrf-token: ...

서버 검증: session OK + csrf OK + permission OK

5흔한 오해와 함정 5개

SameSite=Lax면 CSRF 토큰이 없어도 된다?

아닙니다. SameSite는 방어층 중 하나입니다. 상태 변경 GET, 오래된 브라우저, 복잡한 OAuth/redirect 흐름, subdomain 환경을 고려하면 서버 측 CSRF 토큰 검증이 필요합니다.

HttpOnly가 있으면 CSRF도 막는다?

HttpOnly는 쿠키 읽기를 막습니다. CSRF는 쿠키를 읽지 않고 자동 첨부를 악용합니다.

GET으로 삭제해도 내부 링크니까 괜찮다?

상태 변경은 GET으로 만들면 안 됩니다. GET은 조회, POST/PUT/PATCH/DELETE는 변경이라는 원칙을 지켜야 SameSite와 CSRF 정책이 의미를 가집니다.

CSRF 토큰을 쿠키에만 두면 충분하다?

쿠키는 자동 첨부됩니다. 공격자가 자동으로 만들기 어려운 헤더/폼 필드 제출과 서버 서명 검증이 함께 필요합니다.

로그인만 보호하면 된다?

실제로 위험한 것은 로그인 이후의 비밀번호 변경, 권한 변경, 세션 폐기, 관리자 POST 같은 상태 변경 요청입니다.

6따라하기 체크리스트

  • 브라우저 개발자 도구에서 coreline_auth_session에 HttpOnly, Secure, SameSite가 붙었는지 확인합니다.
  • GET /auth/csrf 응답에 csrf token과 CSRF 쿠키가 함께 설정되는지 확인합니다.
  • 정상 POST에 x-csrf-token을 붙이면 성공하는지 확인합니다.
  • 헤더를 제거하고 같은 POST를 보내면 403으로 실패하는지 확인합니다.
  • 쿠키 인증 admin POST가 CSRF protector 없이 fail-closed 되는지 확인합니다.

✓Try: 내 웹앱의 팔찌와 도장을 점검하세요

  1. 로그인 후 세션 쿠키 이름과 속성을 적어봅니다.
  2. 상태 변경 요청 하나를 골라 CSRF 없이 실패하는지 확인합니다.
  3. 관리자 기능 POST가 쿠키 인증일 때 예외 없이 보호되는지 확인합니다.
  4. SameSite에만 의존하는 코드가 있는지 찾습니다.

결론: 세션 쿠키는 “누구인지”를 말하고, CSRF 토큰은 “정말 의도한 요청인지”를 확인하며, SameSite는 브라우저가 팔찌를 아무 데서나 보여주지 않도록 돕습니다.
