독립 인증 모듈을 만든다는 것

앱 코드와 인증 코드를 분리하는 이유를 CoreMCP와 coreline_auth의 단방향 의존성, 세션, 권한, 테스트 관점에서 풀어낸 블로그 에세이입니다.

생성일 2026-05-30병렬 에이전트 리서치 기반모드: blogarchitecturemodule boundaryessay

처음에는 인증 코드를 분리하는 일이 과해 보입니다. 로그인, 로그아웃, 세션, 비밀번호 재설정 정도라면 앱 안에 넣어도 될 것 같습니다. 하지만 그 자연스러움은 시간이 지나면 가장 비싼 복잡도가 됩니다.

인증은 기능이 아니라 신뢰 경계입니다. 게시글 기능이 조금 잘못되면 게시글 하나가 망가지지만, 인증이 조금 잘못되면 계정, 권한, 세션, 감사 로그, 운영자 권한이 함께 흔들립니다.

1인증은 기능이 아니라 경계다

운영 환경의 인증은 단순히 이메일과 비밀번호를 확인하는 일이 아닙니다. 비밀번호 변경 후 기존 세션, role 변경 후 권한 snapshot, 로그아웃된 세션의 touch race, cookie admin POST의 CSRF, TOTP 동시 재사용, magic-link HTML escaping, WebAuthn origin 검증, OIDC production flow까지 모두 정책입니다.

이 질문들은 로그인 기능의 문제가 아니라, 서비스가 사용자를 어떻게 신뢰할지에 대한 경계 문제입니다.

2CoreMCP → coreline_auth 단방향 의존성의 의미

핵심 규칙은 단순합니다.

CoreMCP  ──사용한다──>  coreline_auth
coreline_auth  ──의존하지 않는다──>  CoreMCP

이 구조는 코드 스타일이 아니라 보안 경계 선언입니다. 인증 모듈이 앱 내부 구조를 알기 시작하면, 세션 하나를 검증하는 데도 게시판 도메인 지식이 필요해집니다. 반대로 앱이 인증 모듈을 호출하는 구조라면, 인증 정책은 독립적으로 테스트하고 리뷰할 수 있습니다.

3사례 1: 세션 revoke 정책이 흩어지는 문제

비밀번호 변경 후 기존 세션을 어떻게 할지는 보안 정책입니다. 이 로직이 라우터마다 흩어지면 어떤 경로는 세션을 revoke하고, 어떤 경로는 놓칩니다. 독립 인증 모듈에서는 `set_password()` 같은 핵심 API에 정책 중심을 둡니다.

사용자 self password change는 현재 세션 제외 revoke, 관리자 password reset은 admin layer에서 명시 revoke/audit, reset token 소비는 reset flow에서 revoke/audit처럼 의도를 API 인자로 드러내야 합니다.

4사례 2: 권한 변경 후 기존 세션이 계속 강한 권한을 가진 경우

DB의 role은 viewer로 바뀌었지만 기존 session permissions가 admin이면 demoted admin은 여전히 API를 호출할 수 있습니다. role 변경은 profile update가 아니라 permission boundary change입니다. 따라서 user role update, user session revoke, audit log 기록이 하나의 보안 이벤트로 묶여야 합니다.

5사례 3: 기능이 늘어날수록 인증 코드가 오염되는 경우

magic link, TOTP, recovery code, passkey, OIDC, admin impersonation, organization role, API token, session device list가 붙으면 인증은 금방 서비스 전체에 퍼진 조건문 묶음이 됩니다. 앱은 “이 사용자는 누구인가?”, “이 세션은 유효한가?”, “이 작업 권한이 있는가?”만 묻고, 인증 모듈은 principal, session state, permission decision, MFA challenge, audit event로 답해야 합니다.

6실천 방법

  1. import 방향을 먼저 고정합니다. `src/coreline_auth`가 `coremcp.*`나 `apps.api.coremcp.*`를 import하지 않도록 CI에서 확인합니다.
  2. 앱 전용 코드는 adapter로 밀어냅니다. FastAPI request, cookie, CSRF, response cookie는 adapter가 알고, core 인증 모듈은 정책만 압니다.
  3. 보안 이벤트를 API 부수 효과로 명확히 만듭니다. `update_role()`은 단순 update가 아니라 session invalidation과 audit을 포함하는 command입니다.
  4. 원문 secret을 저장하지 않습니다. password, session token, magic-link token, reset token은 hash-only 저장 원칙을 지킵니다.
  5. 테스트를 보안 회귀 테스트로 씁니다. 취약점 하나를 고치면 “다시는 재발하지 않는 테스트”를 남깁니다.

✓부드러운 CTA

지금 인증 코드가 앱 곳곳에 섞여 있다면, 당장 전부 갈아엎지 않아도 됩니다. 먼저 import 방향을 확인하고, session 검증, password reset, permission check 중 하나만 독립된 서비스 API로 옮겨보세요. 작은 분리 하나가 나중에는 큰 안정감이 됩니다.
