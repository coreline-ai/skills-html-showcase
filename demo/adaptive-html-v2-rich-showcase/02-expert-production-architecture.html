1Executive Conclusion

Coreline Auth는 현재 운영 배포 가능한 보안 기반을 확보했지만, 배포 형태에 따라 필수 운영 어댑터를 선택해야 하는 상태입니다. 최근 패치로 session stale touch, role 변경 후 session 권한 잔존, cookie-auth CSRF, TOTP replay CAS, magic-link escaping, WebAuthn origin/RP 검증, OIDC PKCE/nonce/ID Token 검증, AUTHZ wildcard scope 우회, MFA step-up rate limit, password-change session revoke, email normalization, OAuth URL validation, explicit scope API, MFA vault guardrail이 닫혔습니다.

따라서 판단은 “데모 앱을 그대로 production으로 올려도 된다”가 아니라, core는 production foundation으로 사용 가능하고 production 배포는 Redis/Postgres/encrypted vault/secure cookie/CSRF/OIDC 설정을 갖춘 조합으로만 허용해야 한다는 것입니다.

4Target Architecture

목표 아키텍처는 sync demo를 샘플 UI와 기능 검증용으로 유지하고, production runtime은 외부 의존성을 명시 주입하는 구조입니다. Coreline Auth 자체는 CoreMCP에 의존하지 않고, host app은 adapter 계층에서만 Coreline Auth를 호출해야 합니다.

[Browser/API Client]
  | TLS, Secure Cookie, SameSite, CSRF Header
[Edge / Reverse Proxy / WAF]
  |
[Host App / FastAPI Adapter]
  | require_session / require_admin / require_aal2 / ResourceAuthorizer(scope)
[CorelineAuthService]
  +--> Postgres Auth Storage
  +--> Redis Rate Limiter
  +--> Encrypted MFA Secret Vault
  +--> SMTP / Email Provider
  +--> OIDC Providers with PKCE + nonce
  +--> Audit / Metric / SIEM Sink

5Rollout Roadmap

  1. Phase 0 — Security Baseline Freeze: 전체 테스트, CoreMCP import 금지, token raw 저장 금지, known regression test를 release gate로 고정합니다.
  2. Phase 1 — Secure Single-Node Release: SQLite WAL, encrypted SQLiteMfaSecretVault, SMTP TLS, secure cookie, CSRF protector, demo off, readiness check 통과.
  3. Phase 2 — Shared-State Production: Postgres storage, Redis limiter, external secret manager, structured audit export, backup/rollback runbook.
  4. Phase 3 — Identity Hardening: admin/action별 AAL2, OIDC provider allowlist, passkey UX, suspicious login signal.
  5. Phase 4 — Continuous Assurance: SIEM alert, rate-limit anomaly dashboard, audit retention, key rotation drill, quarterly authorization review.

6Validation Checklist

  • raw token/password가 DB/log/audit에 없는가?
  • revoked session이 touch로 부활하지 않는가?
  • role 변경 후 기존 session이 폐기되는가?
  • cookie POST가 CSRF 없이 실패하는가?
  • TOTP replay CAS가 저장소별로 동작하는가?
  • MFA step-up limiter가 TOTP와 recovery code에 공유되는가?
  • email normalization이 direct/async/SMTP에 적용되는가?
  • OAuth URL이 HTTPS/no-credential/no-fragment인가?
  • OIDC state, nonce, PKCE, ID token signature가 검증되는가?
  • WebAuthn origin/RP가 parsed host 기준인가?
  • ResourceAuthorizer broad action에 scope가 명시되는가?
  • multi-node에서 Redis limiter가 공유 상태인가?
  • audit redaction이 민감 키를 제거하는가?
  • SIEM/JSONL sink와 alert rule이 연결되는가?

✓최종 권고

가장 안전한 production 기본 조합은 Postgres + Redis limiter + encrypted MFA vault + secure cookies + CSRF fail-closed + OIDC exact redirect + SIEM audit export입니다. 이 조합을 release gate로 삼으면 sync demo에서 production까지의 전환 리스크를 통제 가능한 수준으로 낮출 수 있습니다.
