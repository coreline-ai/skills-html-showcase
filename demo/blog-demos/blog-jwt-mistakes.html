Web Security · JWT

개발자가 JWT를 쓸 때 자주 저지르는 실수 7가지

JWT는 "그냥 라이브러리 한 줄 붙이면 끝"처럼 보이지만, 실제로는 토큰을 어떻게 검증하느냐에서 보안이 갈립니다. 그리고 그 검증을 잘못하면 공격자가 직접 토큰을 위조해 관리자로 로그인할 수도 있습니다.

이 글은 막연한 경고가 아니라, IETF의 RFC 8725(JWT Best Current Practices)와 OWASP 권고를 기준으로 가장 자주 터지는 실수 7가지를 정리한 것입니다. 각 실수마다 "왜 위험한지"와 "올바른 방법"을 코드 개념과 함께 짝지어 보여드립니다.

JWT를 한 번이라도 직접 발급하거나 검증해 본 적이 있다면, 이 중 최소 한두 개는 지금 당신의 코드에도 있을 가능성이 높습니다. 10분만 투자해 점검 체크리스트로 활용해 보세요.

1JWT가 뭐길래 실수가 잦을까

자체 검증 가능한 토큰이라는 장점이, 그대로 함정이 된다

JWT(JSON Web Token)는 점(.)으로 구분된 세 부분 — 헤더(header)·페이로드(payload)·서명(signature) — 으로 이루어진 토큰입니다. 앞의 두 부분은 단지 Base64URL로 인코딩되어 있을 뿐, 암호화된 게 아닙니다. 즉 누구나 디코딩해서 내용을 읽을 수 있습니다. 토큰의 진위는 오직 세 번째 조각인 서명으로만 보장됩니다.

용어
서명(Signature)
헤더와 페이로드를 비밀 키(HMAC) 또는 개인 키(RSA/EC)로 계산한 값. 서버는 이 값을 다시 계산해 일치하는지 확인함으로써 "토큰이 변조되지 않았고 우리가 발급한 것"임을 검증합니다.

문제는 여기서 시작됩니다. JWT는 서버에 세션을 저장하지 않고도 토큰 자체로 사용자를 인증할 수 있다는 점이 매력입니다. 하지만 "토큰만 보고 믿는다"는 구조는, 검증 한 줄을 빼먹는 순간 공격자가 마음대로 쓴 토큰을 그대로 신뢰하게 만듭니다. 세션 방식이라면 서버 DB에 없는 세션 ID는 그냥 무효지만, JWT는 검증 로직이 곧 보안 경계 전부입니다.

RFC 8725가 아예 "Best Current Practices" 문서로 따로 나온 이유가 이것입니다. JWT의 위험은 알고리즘이 약해서가 아니라, 라이브러리·애플리케이션의 사용 방식에서 거의 모두 발생한다는 것이죠. 지금부터 그 사용 방식의 실수 7가지를 봅니다.

2실수 1·2 — 서명을 안 믿거나, 알고리즘을 의심하지 않는다

JWT 사고의 대부분은 여기서 난다. 토큰을 위조 가능하게 만드는 가장 직접적인 두 실수

실수 1. 서명을 검증하지 않고 페이로드만 디코딩한다

위험
"디코딩 = 검증"이라는 착각

jwt.decode() 같은 함수는 서명을 확인하지 않고 페이로드만 풀어줍니다. 이 값을 그대로 신뢰하면, 공격자는 페이로드의 "role": "user"를 "role": "admin"으로 바꿔 보낼 수 있습니다. 서명 검증이 없으니 서버는 변조를 전혀 눈치채지 못합니다.

올바른 방법
항상 검증 전용 함수로, 키와 함께 검증

RFC 8725 §3.3은 "JWT의 모든 암호 연산은 검증되어야 하며, 하나라도 실패하면 JWT 전체를 거부해야 한다"고 규정합니다. 디코딩 함수와 검증 함수를 반드시 구분하세요.

# 잘못된 예 — 서명을 검증하지 않음
payload = jwt.decode(token, options={"verify_signature": False})
if payload["role"] == "admin":   # 위조된 값을 그대로 신뢰
    ...

# 올바른 예 — 키와 알고리즘을 명시해 검증
payload = jwt.decode(
    token,
    key=PUBLIC_KEY,
    algorithms=["RS256"],        # 허용 알고리즘 고정
)

실수 2. alg를 토큰이 시키는 대로 따른다 (alg=none / RS256↔HS256 혼동)

JWT 헤더에는 서명에 쓴 알고리즘이 alg 필드로 적혀 있습니다. 문제는 이 값을 토큰 발신자(=잠재적 공격자)가 정한다는 점입니다. 검증 측이 이 값을 그대로 믿으면 두 가지 고전적 공격이 열립니다.

위험 A
alg=none — "서명 없음"을 유효한 토큰으로 받아들임

공격자가 헤더를 {"alg":"none"}으로 바꾸고 서명 부분을 비워 보냅니다. 일부 라이브러리는 이를 "이미 검증된 토큰"으로 취급해 서명 확인 없이 통과시켰습니다. RFC 8725는 라이브러리가 호출자의 명시적 요청 없이는 none 토큰을 소비해서는 안 된다고 권고합니다.

위험 B
RS256 → HS256 알고리즘 혼동(confusion)

서버가 RS256(공개키/개인키)으로 발급했는데 검증 시 알고리즘을 고정하지 않으면, 공격자는 alg를 HS256으로 바꿉니다. 그러면 라이브러리가 공개된 RSA 공개키를 HMAC 비밀 키로 오인해 검증을 시도합니다. 공개키는 누구나 알 수 있으므로 공격자가 유효한 서명을 만들어낼 수 있습니다.

올바른 방법
검증 측에서 허용 알고리즘을 화이트리스트로 고정

RFC 8725 §3.1: "라이브러리는 호출자가 지원 알고리즘 집합을 지정할 수 있게 해야 하며(MUST), 그 외 알고리즘을 사용해서는 안 된다." 토큰의 alg를 신뢰하지 말고, 서버가 기대하는 알고리즘만 명시적으로 허용하세요.

# 잘못된 예 — 토큰의 alg를 그대로 신뢰
jwt.decode(token, key)                     # 알고리즘 미지정 → none/HS256 혼동 위험

# 올바른 예 — 허용 알고리즘을 명시적으로 고정
jwt.decode(token, PUBLIC_KEY, algorithms=["RS256"])  # RS256만 허용
# none은 절대 허용 목록에 넣지 않는다

3실수 3·4 — 만료가 없거나, 무효화가 안 된다

서명이 완벽해도, 토큰의 '수명'을 통제하지 못하면 탈취 한 번에 무한히 당한다

실수 3. exp(만료)가 없거나, 만료 시간이 과도하게 길다

위험
한 번 발급된 토큰이 사실상 영원히 유효

서명된 JWT는 키를 바꾸거나 만료를 명시하지 않는 한 기술적으로 영원히 유효합니다. exp 없이 발급하면, 토큰이 한 번 유출됐을 때 공격자가 무기한 사용할 수 있습니다. 만료를 며칠·몇 달로 길게 잡는 것도 같은 위험의 약한 버전입니다.

올바른 방법
짧은 액세스 토큰 + 회전하는 리프레시 토큰

액세스 토큰은 짧게(업계에서 흔히 권장하는 범위는 5~15분) 두고, 수명이 긴 리프레시 토큰으로 갱신하는 구조를 씁니다. 리프레시 토큰은 사용할 때마다 새로 발급(rotation)하면 탈취 시 노출 창을 크게 줄일 수 있습니다.

# 발급 시 만료를 반드시 포함 (예: 15분)
now = int(time.time())
payload = {
    "sub": user_id,
    "iat": now,
    "exp": now + 15 * 60,   # 만료 명시
}
# 검증 시 라이브러리가 exp를 자동 확인하도록 둔다 (verify_exp=True)

실수 4. 로그아웃·탈취 대응 — 즉시 무효화가 불가능한 설계

JWT의 자체 검증이라는 장점은 곧 단점이 됩니다. 서버가 토큰을 저장하지 않으니, 아직 만료되지 않은 토큰을 "지금 당장 무효화"하기가 어렵습니다. 사용자가 로그아웃하거나 비밀번호를 바꿔도, 이미 발급된 액세스 토큰은 exp 전까지 계속 유효할 수 있습니다.

위험
로그아웃했는데도 토큰이 계속 통한다

"로그아웃 = 클라이언트에서 토큰 삭제"로만 구현하면, 이미 탈취된 토큰은 만료 시각까지 그대로 살아 있습니다. 탈취·계정 침해 상황에서 즉시 차단할 수단이 없습니다.

올바른 방법
리프레시 토큰 폐기 + (필요 시) 거부 목록

리프레시 토큰은 보통 서버 측에 저장·추적되므로 로그아웃·비밀번호 변경·침해 시 즉시 폐기할 수 있습니다. 액세스 토큰의 즉시 무효화가 꼭 필요하면 짧은 수명과 함께 서버 측 거부 목록(denylist) 또는 토큰 버전(token version) 검사를 병행합니다.

4실수 5·6·7 — 저장 위치·페이로드·검증 클레임

서명과 수명을 통제했어도, 토큰을 어디 두고 무엇을 담고 어떤 클레임을 검증하느냐가 남는다

실수 5. 토큰을 localStorage에 저장한다 (XSS 노출)

위험
JS가 읽을 수 있는 곳에 두면 XSS 한 방에 털린다

OWASP는 토큰을 localStorage나 sessionStorage에 두지 말라고 권고합니다. 페이지의 모든 자바스크립트 — XSS로 주입된 악성 스크립트 포함 — 가 이 저장소를 읽을 수 있기 때문입니다. 실제로 페이지에 삽입된 마케팅 위젯의 XSS 버그로 localStorage의 토큰이 탈취돼 API 호출에 악용된 사례가 보고됩니다.

올바른 방법
HttpOnly · Secure · SameSite 쿠키

브라우저 앱이라면 HttpOnly(JS 접근 차단), Secure(HTTPS 전용), SameSite 속성을 가진 쿠키에 저장합니다. HttpOnly는 XSS로부터, SameSite는 CSRF로부터 완화 효과를 줍니다. 단, 쿠키 방식에서도 CSRF 대응은 별도로 점검해야 합니다.

실수 6. 페이로드에 민감 정보를 평문으로 담는다

위험
JWT 페이로드는 암호화가 아니라 인코딩일 뿐

앞서 말했듯 페이로드는 Base64URL 인코딩일 뿐, 누구나 디코딩해 읽을 수 있습니다. 여기에 주민번호·비밀번호·내부 시스템 식별자 같은 민감 정보를 넣으면 그대로 노출됩니다. 서명은 변조를 막을 뿐 내용을 가리지 못합니다.

올바른 방법
최소한의 비민감 클레임만, 필요하면 JWE

페이로드에는 식별자·권한·만료처럼 노출돼도 되는 최소 정보만 담으세요. 정말 기밀이 필요한 데이터라면 서명만 하는 JWS 대신 암호화하는 JWE를 사용하거나, 토큰에 담지 말고 서버에서 조회하는 편이 안전합니다.

# 잘못된 예 — 민감 정보를 평문으로 노출
{ "sub": "1234", "ssn": "900101-1234567", "password": "..." }

# 올바른 예 — 노출돼도 되는 최소 클레임만
{ "sub": "1234", "role": "user", "exp": 1716950000 }

실수 7. aud(대상)·iss(발급자)를 검증하지 않는다

서명이 유효해도 "이 토큰이 우리 서비스를 위해, 우리가 믿는 발급자가 만든 것"인지는 별개 문제입니다. 이를 확인하지 않으면 다른 서비스용 토큰이 우리 쪽에서 통하는 치환 공격(substitution)·교차 사용이 가능해집니다.

위험
다른 수신자용 토큰이 우리 API에서 통한다

같은 발급자가 여러 대상에게 토큰을 발급하는 환경에서 aud를 검증하지 않으면, A 서비스용으로 발급된 유효한 토큰을 B 서비스가 그대로 받아들일 수 있습니다.

올바른 방법
iss·aud를 명시적으로 검증

RFC 8725 §3.8~§3.9: 검증 측은 키가 기대한 발급자(iss)의 것인지 확인하고, 토큰의 aud가 자신을 가리키지 않거나 없으면 거부해야 합니다(MUST). 라이브러리에 기대값을 넘겨 자동 검증하도록 설정하세요.

# 올바른 예 — iss·aud까지 검증
jwt.decode(
    token, PUBLIC_KEY, algorithms=["RS256"],
    issuer="https://auth.example.com",   # iss 검증
    audience="https://api.example.com",  # aud 검증
)

5한눈 요약 — 7가지 체크리스트

배포 전 이 표를 그대로 코드와 대조해 보세요

FAQ

Q. JWT는 암호화되니까 페이로드에 뭘 넣어도 안전하지 않나요?

아닙니다. 일반적인 서명형 JWT(JWS)의 페이로드는 Base64URL 인코딩일 뿐 암호화가 아닙니다. 누구나 디코딩해 내용을 읽을 수 있으므로 민감 정보를 평문으로 넣으면 안 됩니다. 기밀이 필요하면 암호화 토큰인 JWE를 써야 합니다.

Q. HS256과 RS256 중 뭘 써야 하나요?

둘 다 표준 알고리즘이지만, 핵심은 검증 측에서 알고리즘을 고정하는 것입니다. HS256(대칭키)은 비밀 키가 충분히 강해야 하며(RFC 8725는 사람이 외우는 비밀번호를 HMAC 키로 직접 쓰지 말라고 명시), 여러 서비스가 검증해야 하는 환경이라면 공개키로 검증하는 RS256/ES256이 키 분리 면에서 유리합니다.

Q. 액세스 토큰을 짧게 두면 사용자가 자주 로그아웃되지 않나요?

그래서 리프레시 토큰을 함께 씁니다. 짧은 액세스 토큰이 만료되면 클라이언트가 리프레시 토큰으로 조용히 새 액세스 토큰을 받습니다. 사용자 경험은 유지하면서 탈취된 토큰의 유효 창은 짧게 유지하는 구조입니다.

Q. 서명만 잘 검증하면 끝 아닌가요?

서명 검증은 "변조되지 않았다"만 보장합니다. 그 토큰이 만료되지 않았는지(exp), 우리 서비스를 위한 것인지(aud), 믿는 발급자가 만든 것인지(iss)는 별도로 확인해야 합니다. 서명 + 클레임 검증이 한 세트입니다.
