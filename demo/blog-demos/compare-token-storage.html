토큰을 어디에 저장할까: localStorage vs sessionStorage vs 쿠키(HttpOnly) vs 메모리

인증 토큰의 저장 위치는 단순한 편의 문제가 아니라 XSS와 CSRF 위협에 직접 노출되는 결정입니다. 네 가지 보관 방식을 위협 모델 기준으로 비교하고, OWASP·MDN 근거로 상황별 권장안을 정리했습니다.

1왜 저장 위치가 중요한가

두 개의 다른 위협이 서로 다른 저장 위치를 노린다 — 한쪽을 막으면 다른 쪽이 열린다.

Threat model

브라우저에 토큰을 두는 순간 두 가지 공격 표면이 생깁니다. 첫째는 XSS(Cross-Site Scripting)입니다. 같은 출처(origin)에서 실행되는 자바스크립트는 localStorage·sessionStorage와 HttpOnly가 아닌 쿠키를 모두 읽을 수 있으므로, 단 하나의 XSS 취약점만으로 저장된 토큰 전체가 탈취될 수 있습니다. 둘째는 CSRF(Cross-Site Request Forgery)입니다. 쿠키는 브라우저가 요청에 자동으로 첨부하기 때문에, 공격자가 사용자를 속여 요청을 보내게 만들면 쿠키도 함께 실려 갑니다. 반면 Web Storage나 메모리에 든 토큰은 자동 전송되지 않으므로 CSRF에는 본질적으로 노출되지 않습니다. 즉 XSS를 막으려 쿠키로 옮기면 CSRF가, CSRF를 피하려 Storage로 옮기면 XSS가 문제로 돌아옵니다. 그래서 "어디에 둘까"는 "어떤 위협을 어떤 방어와 짝지을까"의 문제입니다.

2저장 위치 비교 매트릭스

동일 출처 자바스크립트 접근성, 자동 전송 여부, 지속성을 기준으로 네 방식을 나란히 본다.

저장 위치 XSS 노출 CSRF 노출 지속성(새로고침·탭) 서버 자동전송 적합한 경우
localStorage 높음 — JS로 항상 읽힘. XSS 한 번이면 전량 탈취 없음 — 자동 전송 안 됨 강함 — 새로고침·탭·브라우저 재시작 후에도 유지(만료 없음) 아니오 — 코드가 직접 헤더에 실어야 함 토큰 외 비민감 UI 상태. 토큰 보관은 OWASP가 권장하지 않음
sessionStorage 높음 — localStorage와 동일하게 JS 접근. 다만 수명이 짧음 없음 — 자동 전송 안 됨 중간 — 같은 탭의 새로고침은 유지, 탭/창을 닫으면 소멸. 탭마다 분리 아니오 — 코드가 직접 실어야 함 단일 탭 한정·단기 세션. 비민감 임시 데이터
쿠키(HttpOnly+Secure+SameSite) 낮음 — HttpOnly면 JS가 읽지 못해 직접 탈취 어려움 있음 — 자동 첨부되어 노출. SameSite/토큰 병행 필요 강함 — 만료(Expires/Max-Age)까지 유지, 출처 단위 공유 예 — 같은 사이트 요청에 브라우저가 자동 첨부 민감 토큰·refresh token. 서버 세션 식별자
메모리(JS 변수/클로저) 중간 — 저장소를 훑는 공격엔 안 잡히나, 실행 중 JS면 접근 가능 없음 — 자동 전송 안 됨 없음 — 새로고침·탭 전환 시 소멸(다시 받아야 함) 아니오 — 코드가 직접 실어야 함 SPA의 단기 access token. 노출 창을 최소화하고 싶을 때

표의 핵심은 두 열입니다. "서버 자동전송"이 예인 쿠키만 CSRF에 노출되고, 나머지 셋은 CSRF가 없는 대신 자바스크립트 접근성 때문에 XSS에 노출됩니다. HttpOnly 쿠키만 유일하게 자바스크립트 직접 접근을 차단합니다.

3상황별 권장 조합

단일 정답은 없다 — 토큰의 종류와 수명에 따라 위치와 방어를 짝짓는다.

민감 토큰 / 세션

HttpOnly 쿠키 + CSRF 방어

장기·민감 토큰(refresh token, 세션 식별자)은 HttpOnly·Secure·SameSite 쿠키에 둡니다. JS 접근이 막혀 XSS 직접 탈취가 어렵습니다. 대신 자동 전송으로 CSRF에 노출되므로 동기화 토큰/이중 제출 같은 토큰 방어를 반드시 병행합니다.

SPA access token

메모리 + refresh는 HttpOnly 쿠키

짧은 수명의 access token은 메모리(JS 변수/클로저)에 두어 노출 창을 줄이고, 갱신용 refresh token은 HttpOnly 쿠키에 둡니다. 새로고침 시 메모리는 비지만 쿠키로 조용히 재발급할 수 있습니다.

Defense in depth
어디에 두든 공통 방어

OWASP는 어떤 위치든 짧은 만료(예: 15~30분)와 토큰 회전, 강력한 Content Security Policy를 권합니다. 저장 위치는 XSS 자체를 막아주지 않으므로, 입력 이스케이프·CSP로 XSS 발생 자체를 줄이는 것이 1차 방어입니다.

4흔한 오해와 함정

"편하니까"와 "HttpOnly면 끝"이라는 두 극단 모두 위험하다.

Anti-pattern
"localStorage가 편하니 토큰을 거기 둔다"

localStorage는 동일 출처 JS에 항상 노출됩니다. OWASP는 "단 한 번의 XSS로 이 객체의 모든 데이터를 탈취할 수 있다"고 명시하며, 세션 식별자를 local storage에 두지 말라고 권고합니다. 게다가 만료가 없어 노출 창이 무기한입니다. 편의가 곧 무기한 탈취 가능성으로 이어집니다.

Anti-pattern
"HttpOnly 쿠키면 안전하다"

HttpOnly는 JS의 직접 읽기를 막아 XSS 탈취를 어렵게 할 뿐, 자동 전송으로 인한 CSRF는 막지 못합니다. OWASP는 "SameSite는 심층 방어용일 뿐 대부분의 배포에서 제대로 된 CSRF 방어를 대체하지 못한다"고 못박습니다. Lax는 안전하지 않은 메서드만 막고, 하위 도메인 공유나 일부 브라우저 미준수 같은 한계가 있습니다.

Correct framing
위치는 위협을 옮길 뿐, 없애지 않는다

핵심은 트레이드오프를 인지하는 것입니다. Storage·메모리는 CSRF가 없는 대신 XSS에 노출되고, 쿠키는 HttpOnly로 XSS 직접 탈취를 줄이는 대신 CSRF 방어를 추가로 져야 합니다. 위치 선택은 어떤 방어와 묶을지를 함께 정하는 일입니다.

Decision guide

5최종 권고: 결정 가이드

  1. 민감·장기 토큰(refresh, 세션)은 HttpOnly + Secure + SameSite 쿠키. JS 직접 접근을 차단해 XSS 탈취를 어렵게 한다.
  2. 쿠키를 쓰면 CSRF 방어를 반드시 병행한다. 동기화 토큰(상태 보존) 또는 이중 제출 쿠키(무상태)를 1차로 두고, SameSite는 심층 방어로만 본다.
  3. SPA의 단기 access token은 메모리에 둔다. 노출 창을 최소화하고, 새로고침 시 HttpOnly 쿠키의 refresh token으로 재발급한다.
  4. localStorage·sessionStorage에는 인증 토큰을 두지 않는다. 부득이하면 짧은 만료와 토큰 회전을 적용하되, sessionStorage(탭 한정·탭 닫으면 소멸)가 localStorage보다 노출 창이 짧다.
  5. 저장 위치와 무관하게 XSS 자체를 줄인다. 출력 이스케이프, 엄격한 Content Security Policy, 입력 검증을 1차 방어로 둔다.
  6. 토큰 무효화·회전 경로를 설계한다. 짧은 만료(예: 15~30분)와 서버 측 폐기로, 탈취되더라도 피해 창을 줄인다.
