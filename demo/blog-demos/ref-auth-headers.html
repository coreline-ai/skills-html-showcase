★가장 먼저 챙길 것

세션을 쿠키로 다룬다면 아래 조합이 출발점입니다. 토큰/캐시/전송 보안은 그다음 줄에서 잡습니다.

  • 세션 쿠키: Set-Cookie: __Host-sid=...; Secure; HttpOnly; SameSite=Lax; Path=/ — OWASP는 가장 엄격한 형태로 SameSite=Strict까지 권장합니다.
  • 전송 강제: Strict-Transport-Security: max-age=63072000; includeSubDomains; preload (HTTPS 응답에서만 의미 있음)
  • 클릭재킹 차단: Content-Security-Policy: frame-ancestors 'none' + 구형 호환용 X-Frame-Options: DENY
  • 토큰 전달: Authorization: Bearer <token> — 항상 HTTPS에서만
  • 인증/민감 응답: Cache-Control: no-store (뒤로가기·공유 캐시 노출 방지)
  • 쿠키 접두사: 도메인 고정이 필요하면 __Host-, 서브도메인 공유가 필요하면 __Secure-

Set-Cookie 핵심 보안 속성

용도 · 세션/인증 쿠키가 탈취·전송·노출되지 않도록 제어하는 1차 방어선.

권장값 · HttpOnly; Secure; SameSite=Lax 를 기본으로, 교차 사이트 전송이 필요 없으면 SameSite=Strict.

주의 · HttpOnly가 빠지면 XSS로 쿠키가 통째로 읽힙니다. Path는 보안 경계가 아니므로 격리 수단으로 쓰지 마세요.

HttpOnly · Secure · SameSite

HttpOnly · JS의 document.cookie 접근 차단. XSS 시 세션 탈취를 막지만, JS가 보낸 fetch/XHR 요청에는 여전히 쿠키가 실립니다.

Secure · HTTPS(및 localhost) 요청에만 쿠키 전송. http: 사이트는 Secure 쿠키를 설정하지 못합니다.

SameSite · Strict(동일 사이트만), Lax(동일 사이트 + 안전한 메서드의 최상위 내비게이션), None(교차 사이트 허용, 반드시 Secure 동반). 일부 브라우저는 미지정 시 Lax를 기본으로 적용합니다(브라우저 의존, 확인 필요).

Domain · Path · Max-Age · Expires

Domain · 생략하면 host-only(서브도메인 미공유)로 더 안전. 지정하면 서브도메인까지 전송됩니다.

Path · 전송 경로 매칭용일 뿐 보안 경계가 아님. 사이트 전역은 Path=/.

Max-Age / Expires · 둘 다 있으면 Max-Age가 우선. 둘 다 없으면 세션 쿠키(브라우저 종료 시 삭제, 단 세션 복원 시 되살아날 수 있음).

__Host- · __Secure- 접두사

용도 · 쿠키가 안전한 조건으로만 설정되도록 브라우저가 강제하게 만드는 이름 접두사.

__Host- · HTTPS에서 Secure + Path=/ 필수, Domain 금지 → 설정 호스트에만 고정. 세션 쿠키에 가장 강력.

__Secure- · HTTPS에서 Secure 필수(Domain 허용). 서브도메인 공유가 필요할 때.

주의 · 미지원 브라우저는 접두사를 일반 이름처럼 받아 제약을 강제하지 않을 수 있습니다.

Authorization · WWW-Authenticate

Authorization · 자격 증명 전달. Bearer <token>(OAuth 2.0·JWT), Basic <base64(user:pass)>. 교차 출처 리다이렉트 시 헤더가 제거됩니다.

WWW-Authenticate · 서버가 401 Unauthorized에 실어 지원 스킴을 알림(예: Bearer realm="api").

주의 · Basic은 암호화가 아니라 Base64 인코딩이라 손쉽게 복호됩니다. 인증 헤더는 항상 HTTPS에서만.

Strict-Transport-Security (HSTS)

용도 · 이후 일정 기간 해당 호스트를 HTTPS로만 접속하도록 브라우저에 강제 → SSL 스트립·다운그레이드 방지.

권장값 · max-age=63072000; includeSubDomains; preload (2년). preload 등록은 max-age 1년 이상 + includeSubDomains 필수.

주의 · HTTPS 응답에서만 적용(HTTP에선 무시). 첫 접속 전엔 보호 공백이 있어 preload로 보완. 인증서 만료 전 기간 설정에 유의.

Content-Security-Policy: frame-ancestors

용도 · 이 페이지를 어떤 출처가 프레임에 임베드할 수 있는지 제어 → 클릭재킹 방지.

권장값 · 임베드 불필요 시 frame-ancestors 'none', 동일 출처만 허용 시 'self'.

주의 · default-src로 폴백되지 않으므로 직접 명시해야 합니다. <meta> 태그에서는 동작하지 않고 HTTP 헤더로만 적용됩니다.

X-Frame-Options

용도 · 구형 브라우저용 클릭재킹 방어. frame-ancestors 'none'이 이를 대체합니다.

권장값 · X-Frame-Options: DENY (또는 동일 출처 허용 시 SAMEORIGIN).

주의 · 다중 출처 허용 같은 세밀한 제어는 불가. 신형 브라우저용 CSP frame-ancestors와 함께 보내 호환성을 확보하세요.

Cache-Control: no-store (인증 응답)

용도 · 인증·민감 응답이 어떤 캐시(브라우저·프록시)에도 저장되지 않게 함 → 로그아웃 후 뒤로가기 노출 방지.

권장값 · Cache-Control: no-store. 폭넓은 호환이 필요하면 no-store, max-age=0 + Pragma: no-cache.

주의 · no-cache는 "캐시 금지"가 아니라 "재검증 후 사용"입니다. 개인화 콘텐츠 캐싱은 private로, 진짜 민감 데이터는 no-store로.

1권장 조합 패턴

개별 헤더보다 "어떻게 묶느냐"가 실제 사고를 가릅니다. 자주 보이는 올바른 조합과 함정을 짝으로 정리합니다.

GOOD · 세션 쿠키 표준 조합
서버가 쿠키로 세션을 관리하는 일반 웹앱

세션 식별자는 JS가 읽을 일이 없으므로 HttpOnly로 잠그고, Secure로 평문 전송을 막고, SameSite=Lax로 CSRF 표면을 줄입니다. 호스트 고정이 필요하면 __Host- 접두사를 더해 Domain 오설정과 서브도메인 누수를 원천 차단합니다.

DANGER · HttpOnly를 빼는 함정
"프런트에서 토큰을 읽어야 하니 HttpOnly를 끄자"

JS에서 읽으려고 HttpOnly를 제거하면, XSS 한 줄로 세션·토큰이 통째로 유출됩니다. 토큰을 JS가 다뤄야 한다면 쿠키 대신 메모리 보관을 검토하고, 쿠키를 쓴다면 HttpOnly를 유지하세요. 편의를 위해 보안 속성을 끄는 것이 가장 흔한 사고 원인입니다.

GOOD · 교차 사이트 쿠키가 꼭 필요할 때
서드파티 임베드/위젯에서 인증 쿠키가 필요

이때만 SameSite=None을 쓰되, 명세상 반드시 Secure를 함께 보내야 브라우저가 무시하지 않습니다. 범위를 최소화하고, 가능하면 토큰 기반 인증으로 우회하는 편이 안전합니다.

DANGER · None인데 Secure 누락
SameSite=None 만 적고 Secure를 빠뜨림

모던 브라우저는 Secure 없는 SameSite=None 쿠키를 거부하거나 무시합니다. 결과적으로 쿠키가 설정되지 않아 로그인 루프 같은 장애로 이어지고, 의도한 보안 모델도 깨집니다.

2실제 헤더 예시

복붙 전에 도메인·경로·만료를 환경에 맞게 바꾸세요. 아래는 형식을 보여주기 위한 예시입니다.

세션 쿠키 (가장 엄격)

Set-Cookie: __Host-sid=S3SS10N-T0KEN; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=3600
# 교차 사이트 전송이 전혀 없다면 SameSite=Strict 로 강화
# __Host- 접두사는 Domain 금지 + Path=/ + Secure 를 강제합니다

전송·클릭재킹·캐시 (인증 페이지 공통)

Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Content-Security-Policy: frame-ancestors 'none'
X-Frame-Options: DENY
Cache-Control: no-store
Pragma: no-cache

토큰 인증 흐름

# 1) 자격 없이 보호 자원 요청 → 서버 응답
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api.example.com"

# 2) 클라이언트가 토큰을 실어 재요청 (항상 HTTPS)
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

3배포 전 점검 6가지

  1. 세션 쿠키 3종 세트 — HttpOnly; Secure; SameSite가 모두 붙어 있는가? 교차 사이트 전송이 없으면 Strict까지 올렸는가?
  2. 쿠키 접두사 — 호스트 고정이면 __Host-(Domain 없음, Path=/), 서브도메인 공유면 __Secure-를 쓰고 조건을 충족했는가?
  3. HSTS — HTTPS 응답에 max-age(권장 1~2년) + includeSubDomains가 있고, preload 등록 전 서브도메인 영향을 확인했는가?
  4. 클릭재킹 — frame-ancestors 'none'(또는 필요한 출처만)과 구형 호환용 X-Frame-Options를 HTTP 헤더로 함께 보냈는가?
  5. 캐시 — 로그인·계정·결제 등 민감 응답에 Cache-Control: no-store를 적용해 뒤로가기·공유 캐시 노출을 막았는가?
  6. 토큰 전송 — Authorization/Basic을 평문(HTTP)으로 보내지 않으며, 교차 출처 리다이렉트에서 헤더가 의도대로 제거되는지 확인했는가?
