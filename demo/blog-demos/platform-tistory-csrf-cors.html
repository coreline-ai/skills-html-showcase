CSRF와 CORS, 헷갈리는 둘의 차이 한 번에 정리

"CSRF? CORS? 이름도 비슷하고 둘 다 출처(origin)랑 쿠키 얘기가 나오니까 매번 헷갈려요." 개발 공부하다 보면 한 번쯤 막히는 지점입니다. 결론부터 말하면 둘은 아예 다른 층위의 개념이에요. 하나는 브라우저가 지키는 규칙, 하나는 그 틈을 노리는 공격입니다. 이 글에서 비유와 예시로 깔끔하게 갈라드릴게요.

1CSRF란? — 내 인증 상태를 빌려쓰는 공격

핵심: CSRF는 보안 기능이 아니라 '공격'입니다.

CSRF부터 봅시다. 이건 기술이나 설정이 아니라 공격 기법의 이름이에요. 사용자가 이미 로그인해 둔 상태를 몰래 빌려쓰는 게 핵심입니다.

용어
CSRF (Cross-Site Request Forgery, 사이트 간 요청 위조)
사용자가 현재 인증되어 있는 웹 애플리케이션에서, 사용자가 의도하지 않은 동작을 강제로 실행시키는 공격. 브라우저가 요청에 세션 쿠키를 자동으로 실어 보내는 점을 악용한다. (출처: OWASP)
비유

은행 자동이체를 떠올려 보세요. 당신이 은행에 "이체 요청서"를 내면, 은행은 도장(=로그인 세션)이 찍혀 있으니 그대로 처리합니다. 그런데 누군가 당신 책상에 미리 채워진 가짜 이체 요청서를 슬쩍 끼워 넣고, 당신이 모르고 서명란에 도장을 찍게 만들었다면? 은행 입장에선 진짜 당신의 요청과 구별할 방법이 없습니다. CSRF가 바로 이 구조예요.

실제로는 공격자가 만든 페이지에 숨겨둔 폼이나 이미지 태그가, 당신이 로그인해 둔 사이트로 요청을 대신 쏘는 식입니다. 브라우저는 그 사이트의 쿠키를 자동으로 함께 보내기 때문에, 서버는 정상 요청으로 착각하고 비밀번호 변경이나 송금 같은 상태 변경 작업을 실행해 버립니다.

아래는 공격자 페이지에 심긴 악성 요청의 단순화된 예시입니다.

사용자가 victim-bank.com 에 로그인된 상태에서 공격자 페이지를 열면, 숨겨진 폼이 자동 제출됩니다 → <form action="https://victim-bank.com/transfer" method="POST"> <input name="to" value="attacker"> <input name="amount" value="1000000"> </form> (JS로 자동 submit). 쿠키는 브라우저가 알아서 첨부합니다.

2CORS란? — 브라우저의 교차 출처 접근 제어

핵심: CORS는 공격이 아니라 '브라우저의 규칙'입니다.

이번엔 CORS. 이건 공격이 아니라 브라우저가 지키는 규칙이자, 서버가 그 규칙을 조정하는 메커니즘입니다. 출발점은 동일 출처 정책(SOP)이에요.

용어
CORS (Cross-Origin Resource Sharing, 교차 출처 리소스 공유)
동일 출처 정책(Same-Origin Policy) 때문에 기본 차단되는 교차 출처 요청에 대해, 서버가 HTTP 헤더로 "어떤 출처의 접근을 허용할지"를 브라우저에 알려 SOP를 안전하게 완화/제어하는 메커니즘. (출처: MDN)
비유

다른 가게에 들어갈 때 필요한 출입 허가증이라고 보면 됩니다. 기본적으로 가게(서버)는 "우리 단골(같은 출처)만 받습니다"라는 규칙(SOP)을 갖고 있어요. 그런데 옆 가게 손님(다른 출처)도 받고 싶다면, 가게가 직접 "이 가게 손님은 들여보내 주세요"라고 적힌 허가증(CORS 헤더)을 발급합니다. 경비원(브라우저)은 그 허가증을 보고 통과시킬지 말지를 결정하죠.

요청 방식이 단순하지 않으면(예: 커스텀 헤더, PUT/DELETE 등), 브라우저는 본 요청 전에 사전 요청(preflight)을 먼저 보냅니다. OPTIONS 메서드로 "이런 메서드/헤더로 요청해도 되나요?"를 물어보고, 서버가 허락해야만 실제 요청을 보내는 방식이에요.

서버가 돌려주는 CORS 응답 헤더는 대략 이렇게 생겼습니다.

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://my-frontend.example
Access-Control-Allow-Methods: POST, GET, OPTIONS
Access-Control-Allow-Headers: Content-Type, X-Custom-Header
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 86400
Vary: Origin

주의할 점 하나. Access-Control-Allow-Credentials: true로 쿠키 같은 자격 증명을 허용할 때는 Access-Control-Allow-Origin에 *(와일드카드)를 쓸 수 없고 정확한 출처를 명시해야 합니다. (출처: MDN)

3왜 헷갈리나 / 핵심 차이

이름·키워드는 겹치지만 작동하는 층위가 다릅니다.

둘 다 "출처(origin)"와 "쿠키"라는 단어가 등장하니 헷갈릴 만합니다. 하지만 정체가 완전히 달라요. CORS는 브라우저가 따르는 '접근 제어 규칙'이고, CSRF는 그 규칙과 무관하게 인증 상태를 노리는 '공격'입니다.

항목CSRFCORS
정체공격 기법브라우저 규칙 / 제어 메커니즘
목적(공격자) 사용자의 인증 상태 악용(서버) 교차 출처 접근을 안전하게 허용·통제
다루는 대상사용자의 세션 쿠키 자동 전송JS의 교차 출처 리소스 읽기 권한
주체공격자가 일으킴서버가 헤더로 정책 선언, 브라우저가 집행
방어/설정 위치SameSite 쿠키, CSRF 토큰, 재인증서버의 Access-Control-* 응답 헤더

핵심만 다시 말하면 이렇습니다. CORS는 "누가 내 리소스를 JS로 읽을 수 있는가"를 정하는 규칙이고, CSRF는 "누가 내 이름으로 요청을 보냈는가"의 문제입니다. 질문 자체가 다른 거죠.

4흔한 오해 — "CORS 설정하면 CSRF 막힌다?"

가장 많이 나오는 착각. 결론은 '아니오'입니다.

"우리 서버 CORS 빡빡하게 잠갔으니까 CSRF는 걱정 없죠?" 면접에서도, 실무에서도 자주 나오는 말인데 틀린 생각입니다.

오해
"CORS = CSRF 방어"는 틀림

CSRF 공격의 상당수는 <form> 제출이나 <img> 태그처럼 JS로 응답을 읽지 않는 단순 요청으로 이뤄집니다. CORS는 "JS가 교차 출처 응답을 읽을 수 있는지"를 통제할 뿐, 이런 요청이 서버에 도달해 상태를 바꾸는 것 자체는 막지 못합니다. 공격자는 응답을 읽을 필요도 없어요. 송금이 실행되기만 하면 되니까요.

오히려 CORS를 잘못(너무 넓게) 설정하면 새로운 위험이 생길 수 있습니다. CORS는 CSRF 방어 수단이 아니라 별개의 접근 제어 기능입니다. (출처: OWASP)

바로잡기
CSRF는 이렇게 방어합니다 (CORS와 별개)

· SameSite 쿠키: 쿠키에 SameSite=Lax 또는 Strict를 지정해, 교차 사이트 요청에 쿠키가 따라가지 않게 합니다. 다만 만능은 아니라 심층 방어 한 겹으로 봅니다.
· CSRF 토큰: 서버가 발급한 예측 불가 토큰을 상태 변경 요청마다 함께 보내고 서버가 검증합니다(동기화 토큰/이중 제출 패턴).
· 재인증·민감 작업 확인: 결제·비밀번호 변경 등은 비밀번호 재입력이나 추가 인증을 요구합니다.

그리고 CORS는 그것대로 "어떤 출처가 내 API를 JS로 호출·열람할 수 있는지"를 서버에서 명시적으로 통제하는 용도로 따로 설정합니다. 둘은 같이 쓰되 역할이 겹치지 않습니다. (출처: OWASP CSRF Prevention Cheat Sheet)

한 줄 정리

CSRF와 CORS, 이것만 기억하세요

  1. CORS는 규칙, CSRF는 공격. 하나는 브라우저가 지키는 접근 제어 메커니즘이고, 하나는 그 틈이 아니라 인증 상태를 노리는 공격이다.
  2. CORS의 질문은 "누가 내 리소스를 JS로 읽어도 되는가"이고, CSRF의 질문은 "이 요청이 정말 사용자 본인의 의도인가"이다.
  3. "CORS 잠그면 CSRF 막힘"은 틀렸다. 폼·이미지 같은 단순 요청은 CORS와 무관하게 서버에 도달해 상태를 바꿀 수 있다.
  4. CSRF 방어는 SameSite 쿠키 + CSRF 토큰 + 민감 작업 재인증으로 한다.
  5. CORS 설정은 그것대로, 허용할 출처·메서드·헤더를 서버 응답 헤더로 명시해 통제한다.
