비밀번호 저장 전략 전문가 리포트: bcrypt vs scrypt vs Argon2id

"무엇이 가장 안전한가"라는 질문은 단일 정답이 없습니다. 알고리즘 선택은 메모리-하드니스, 운영 환경의 자원 제약, 마이그레이션 비용이라는 세 축의 트레이드오프 위에서 결정됩니다. 이 리포트는 OWASP·RFC 9106·NIST 권고를 근거로 판단 기준과 리스크를 정리합니다.

Executive Summary

신규 시스템은 Argon2id를 기본값으로 채택하는 것이 OWASP·RFC 9106의 일치된 권고입니다. Argon2id는 메모리-하드 KDF로서 GPU·ASIC 기반 대량 크래킹에 대한 비용을 시간(iteration)과 메모리(KiB) 양축으로 동시에 끌어올릴 수 있습니다. Argon2 라이브러리를 신뢰성 있게 쓸 수 없는 제약 환경(레거시 런타임, 메모리가 극히 제한된 임베디드 등)에서는 bcrypt(work factor ≥ 10)가 합리적 차선책이며, scrypt는 둘 사이의 중간 선택지입니다. 다만 권장 파라미터 수치는 모두 출판 시점·검증 서버 하드웨어에 종속되므로, 도입 전 자체 벤치마크로 "해시 1회 ≤ 1초" 목표에 맞춰 재보정해야 합니다. 가장 큰 리스크는 알고리즘 선택 자체가 아니라, 평문·MD5·SHA 단독 해시·salt 부재 같은 기초 결함과 마이그레이션 부재입니다.

1핵심 판단 — 무엇을 왜 권하는가

알고리즘 등급이 아니라, "공격자가 1개 해시를 깨는 비용"을 어떻게 끌어올리느냐로 판단한다.

비밀번호 해시의 목적은 단 하나입니다. 데이터베이스가 유출되었을 때, 공격자가 원본 비밀번호를 복원하는 비용을 경제적으로 비현실적인 수준으로 만드는 것. 일반 해시(SHA-256 등)는 빠르게 설계되어 있어 GPU 한 대로 초당 수십억 회를 시도할 수 있습니다. 비밀번호 저장에는 반대로 느리고 자원을 많이 먹도록 설계된 함수, 즉 KDF가 필요합니다.

TERM
KDF (Key Derivation Function)
비밀번호·salt·비용 파라미터를 입력받아 의도적으로 느리게 해시를 도출하는 함수. 비밀번호 저장용 KDF는 "비용 조절 축"을 노브처럼 올려, 하드웨어가 빨라져도 방어 강도를 유지한다. bcrypt·scrypt·Argon2id·PBKDF2가 대표적이다.

현대 권고의 핵심 분기점은 메모리-하드(memory-hard) 여부입니다. bcrypt는 CPU 시간만 늘릴 수 있는 반면, scrypt와 Argon2id는 대량의 메모리를 강제로 점유하게 만들어, 메모리 대역폭이 병목인 GPU·ASIC 병렬 공격의 비용 효율을 무너뜨립니다. 이것이 신규 시스템에서 Argon2id가 기본으로 권고되는 이유입니다.

TERM
memory-hard
함수 계산에 큰 메모리를 반드시 사용하도록 설계되어, 메모리를 줄이면 계산 시간이 급격히 늘어나는 성질. 공격자가 칩에 코어를 많이 박아도 코어당 메모리를 함께 늘려야 하므로 병렬화의 경제성이 떨어진다.

다만 "Argon2id가 항상 정답"은 과잉 단순화입니다. 실무 판단은 세 가지를 함께 봅니다. (1) 신뢰할 수 있는 Argon2 구현을 쓸 수 있는가 — 검증된 라이브러리 바인딩이 없는 런타임에서는 직접 구현보다 bcrypt가 안전합니다. (2) 서버 자원 여유 — 메모리-하드 함수는 동시 인증 요청마다 수십 MiB를 점유하므로, 트래픽 폭증 시 메모리가 DoS 벡터가 될 수 있습니다. (3) 마이그레이션 비용 — 이미 bcrypt로 운영 중이라면, 무리한 전면 교체보다 점진적 재해싱이 현실적입니다.

RECOMMENDATION
기본 권고

신규 시스템: Argon2id를 기본값으로. Argon2를 신뢰성 있게 쓸 수 없으면 scrypt, 그조차 어려운 레거시·제약 환경이면 bcrypt(work factor ≥ 10). 어떤 경우든 salt 자동 처리·비용 파라미터 재보정·재해싱 경로를 함께 설계한다.

2구조 분석 — bcrypt / scrypt / Argon2id

각 함수의 원리, 메모리-하드니스, 비용을 조절하는 노브를 분해한다.

ALGORITHM A

bcrypt — 검증된 CPU-하드 베테랑

원리: Blowfish 암호의 키 스케줄을 반복적으로 비싸게 만든 함수. 1999년 발표 이후 가장 오래 검증된 비밀번호 해시 중 하나로, 거의 모든 언어에 성숙한 구현이 존재한다.

메모리-하드: 아니오. 약 4 KiB의 작은 상태만 사용해 CPU 시간만 늘린다. 따라서 메모리 대역폭으로 공격자를 압박하지 못하며, GPU·FPGA 병렬화에 상대적으로 취약하다.

비용 조절 축: 단일 work factor(cost) 하나. 값을 1 올릴 때마다 반복 횟수가 2배가 된다(지수적). OWASP는 최소 10 이상, 검증 서버 성능이 허용하는 한 크게 권고한다.

주의: 입력이 72바이트에서 잘리는 구조적 한계가 있다. 긴 비밀번호나 사전 해싱(pre-hashing) 조합 시 null 바이트 절단·"password shucking" 같은 함정이 있어, 사전 해시는 base64 인코딩과 함께 다뤄야 한다(아래 4장 참조).

ALGORITHM B

scrypt — 최초의 실용적 메모리-하드 KDF

원리: 2009년 Colin Percival이 제안. 대량의 의사난수 데이터를 메모리에 채운 뒤 무작위 순서로 접근하게 만들어, 메모리를 절약하려면 계산을 다시 해야 하는 시간-메모리 트레이드오프를 강제한다.

메모리-하드: 예. CPU와 메모리를 동시에 압박한다. bcrypt보다 GPU·ASIC 공격 비용을 높이는 데 유리하다.

비용 조절 축: 세 파라미터 — N(CPU/메모리 비용, 2의 거듭제곱), r(블록 크기), p(병렬화). 메모리 사용량은 대략 128 · N · r 바이트.

주의: 파라미터 3개가 서로 얽혀 직관적 튜닝이 어렵고, 잘못 조합하면 메모리-하드니스가 약해질 수 있다. Argon2id를 쓸 수 없을 때의 차선책으로 위치한다.

ALGORITHM C

Argon2id — 2015 PHC 우승, 현행 권고 기본값

원리: Password Hashing Competition(2015) 우승작. Argon2d(데이터 의존 접근, 트레이드오프 방어 강함)와 Argon2i(데이터 독립 접근, 사이드채널 방어 강함)의 장점을 결합한 하이브리드가 Argon2id다. RFC 9106은 첫 패스의 전반부는 Argon2i처럼, 이후는 Argon2d처럼 동작해 양쪽 보호를 모두 제공한다고 설명한다.

메모리-하드: 예. 메모리와 시간을 독립적으로 조절할 수 있어 가장 유연하게 비용을 설계할 수 있다.

비용 조절 축: 세 파라미터 — m(메모리, KiB), t(iteration/passes), p(parallelism/lanes). RFC 9106은 사이드채널 위협 환경에서 Argon2id를 권한다.

주의: 메모리 점유량이 크므로(권고 구성에서 수십 MiB~수 GiB), 동시성 높은 인증 엔드포인트에서는 메모리 사용량을 부하 테스트로 검증해야 한다.

TERM
salt
비밀번호마다 고유하게 부여하는 무작위 값. 해시 입력에 섞어, 동일 비밀번호라도 서로 다른 해시가 나오게 하여 사전 계산된 레인보우 테이블 공격을 무력화한다. NIST SP 800-63B는 최소 32비트 이상을 요구하며, 현대 라이브러리는 salt 생성·저장을 자동 처리한다.
TERM
pepper (peppering)
DB와 분리된 곳(예: 앱 설정·HSM)에 보관하는 공유 비밀값. 해시와 함께 저장하지 않는 것이 핵심으로, DB만 유출되어도 추가 방어선이 된다. 보통 해시 후 HMAC의 키로 사용하거나(post-hashing), 사전 해싱에 무작위 pepper를 결합한다.

3비교표 — 한눈에 보는 선택 기준

아래 수치는 OWASP·RFC 9106 출판 기준 권고이며, 시점·하드웨어에 따라 반드시 재보정해야 한다.

다음 표의 모든 파라미터는 "확인 필요(버전·하드웨어 의존)"임을 전제로 읽으십시오. OWASP와 RFC 9106의 권고 숫자가 다른 것은 오류가 아니라, 대상 위협 모델과 메모리 예산 가정이 다르기 때문입니다 — RFC 9106은 더 공격적인 메모리 예산(최대 2 GiB)을, OWASP는 범용 서버에서 현실적으로 적용 가능한 하한선을 제시합니다.

알고리즘 메모리-하드 권장 파라미터 (출처·주의) 권장 상황
Argon2id 예 (m·t 양축) OWASP: m=19456(19 MiB), t=2, p=1 (대안 m=47104·t=1·p=1 등). RFC 9106: 1순위 m=2²¹(2 GiB)·t=1·p=4, 2순위 m=2¹⁶(64 MiB)·t=3·p=4. 출판 시점 기준·재보정 필수 신규 시스템 기본값. 자원 여유가 있고 신뢰 가능한 Argon2 구현 사용 가능 시
scrypt 예 (N·r) OWASP: N=2¹⁷(128 MiB), r=8, p=1 (대안 N=2¹⁶·r=8·p=2 등). 시점 의존·재보정 필요 Argon2id를 못 쓰지만 메모리-하드니스가 필요할 때의 차선책
bcrypt 아니오 (CPU만) OWASP: work factor ≥ 10(서버 성능 허용 한도까지 크게). 입력 72바이트 제한. 하드웨어 의존 레거시·제약 환경, 또는 Argon2/scrypt 사용이 어려운 경우
PBKDF2 (참고) 아니오 (CPU만) OWASP: HMAC-SHA256 600,000회, SHA512 220,000회. NIST SP 800-63B: 최소 10,000회 이상. FIPS 준수 필요 시 한정 FIPS-140 등 규제로 승인 알고리즘만 써야 할 때

표에서 가장 중요한 메시지는 숫자 자체가 아닙니다. "해시 1회 계산이 검증 서버에서 1초 미만이 되도록 자체 측정해 파라미터를 정한다"는 원칙입니다. OWASP는 작업 비용 계산이 1초 미만이어야 하며, 하드웨어가 빨라지면 파라미터를 주기적으로 상향(work factor upgrading)하라고 명시합니다.

4위험 요소 — 흔한 실패 패턴

알고리즘 선택보다 더 자주, 더 치명적으로 시스템을 무너뜨리는 기초 결함들.

CRITICAL
평문 저장 / MD5·SHA 단독 해시

비밀번호를 평문 또는 빠른 일반 해시(MD5, SHA-1, SHA-256 "단독")로 저장하는 것은 사실상 무방비다. GPU로 초당 수십억 회 시도가 가능해, 유출 즉시 대량 복원된다. 비밀번호에는 의도적으로 느린 KDF만 사용해야 한다.

CRITICAL
salt 부재 또는 고정 salt

salt가 없거나 전 사용자 공통이면, 레인보우 테이블과 일괄 사전 공격에 무너진다. salt는 사용자마다 고유한 무작위 값이어야 하며(NIST 최소 32비트), 해시와 함께 저장해도 무방하다. 현대 라이브러리는 이를 자동 처리한다.

HIGH
너무 낮은 cost / 파라미터 미보정

work factor를 기본값 그대로 두거나(예: bcrypt cost 4~6), Argon2 메모리를 수 KiB로 둔 경우 메모리-하드니스 이점이 사라진다. 도입 시점에 자체 벤치마크로 ≤ 1초 목표에 맞추고, 하드웨어 발전에 따라 주기적으로 상향해야 한다.

HIGH
bcrypt 72바이트 절단 · password shucking

bcrypt는 입력을 72바이트에서 자른다. 긴 입력을 먼저 다른 해시로 줄여 넣는 "pre-hashing"을 쓸 때 null 바이트가 끼면 추가 절단이 발생할 수 있고, 약한 사전 해시는 shucking 공격에 악용된다. OWASP는 bcrypt(base64(hmac-sha384(password, pepper)), salt, cost)처럼 base64 인코딩과 pepper-HMAC를 함께 쓰도록 권고한다.

MEDIUM
마이그레이션 경로 부재

알고리즘·파라미터를 정해 놓고 "한 번 저장하면 끝"으로 두면, 수년 뒤 약해진 해시가 그대로 남는다. 로그인 성공 시점에 옛 해시를 새 파라미터로 재해싱하는 경로가 없으면 보안 부채가 누적된다.

MEDIUM
메모리-하드 KDF의 자원 DoS

Argon2id/scrypt는 요청마다 수십 MiB를 점유한다. 동시 인증 요청이 폭증하면 메모리 고갈로 서비스 자체가 흔들릴 수 있다. 파라미터를 정할 때 보안 강도뿐 아니라 최대 동시성 하의 메모리 예산을 함께 부하 테스트해야 한다.

5개선 우선순위

자원이 한정될 때, 어떤 순서로 손대면 위험을 가장 빨리 줄이는가.

  1. 기초 결함 제거(최우선). 평문·MD5·SHA 단독·고정 salt를 사용 중이라면 다른 무엇보다 먼저 차단한다. 즉시 전환이 어렵다면, 기존 해시를 KDF로 한 번 더 감싸는(wrap) 과도기 방식을 검토한다.
  2. 검증된 KDF + 자동 salt 도입. 신규는 Argon2id, 제약 환경은 bcrypt(≥10). 직접 구현 대신 성숙한 라이브러리를 쓰고 salt 자동 처리를 신뢰한다.
  3. 파라미터 자체 보정. 검증 서버에서 해시 1회 ≤ 1초가 되도록 측정해 cost/메모리/iteration을 정한다. 출처의 숫자는 출발점일 뿐 최종값이 아니다.
  4. 로그인 시 재해싱 경로 구축. 인증 성공 시 저장된 파라미터가 현재 기준보다 낮으면 새 파라미터로 다시 해싱해 저장한다(work factor upgrading).
  5. pepper·심층 방어 추가(여유 시). DB와 분리된 비밀(pepper)을 HMAC 키로 결합하면 DB 단독 유출 시 추가 방어선이 된다. 단, 기초가 끝난 뒤의 보강 항목이다.
  6. 파라미터 상향 운영 절차화. 하드웨어 발전 주기에 맞춘 파라미터 재검토를 정기 점검 항목으로 등록한다.

6검증 체크리스트

배포 전·정기 점검 시 그대로 확인할 수 있는 항목.

  • 비밀번호가 평문·MD5·SHA 단독으로 저장되는 코드 경로가 전무한가
  • 저장 함수가 Argon2id / scrypt / bcrypt(≥10) / 승인된 PBKDF2 중 하나인가
  • salt가 사용자별 고유 무작위값이며(최소 32비트), 라이브러리가 자동 생성·저장하는가
  • 파라미터가 검증 서버에서 해시 1회 ≤ 1초 기준으로 측정·설정되었는가
  • bcrypt 사용 시 72바이트 제한·사전 해시 시 base64 인코딩이 반영되었는가
  • 로그인 성공 시 약한 파라미터 해시를 재해싱하는 경로가 존재하는가
  • 메모리-하드 KDF 사용 시 최대 동시성 하의 메모리 사용량을 부하 테스트했는가
  • pepper를 쓴다면 DB와 물리적·논리적으로 분리 저장되는가
  • 파라미터 재검토(상향)가 정기 점검 항목으로 문서화되어 있는가
  • 의존 라이브러리가 직접 구현이 아닌, 검증된 성숙한 구현인가

FINAL RECOMMENDATION

실무 액션 — 지금 바로 적용할 5가지

  1. 기본값은 Argon2id. 신규 시스템은 Argon2id로 시작하고, 신뢰 가능한 구현이 없으면 scrypt, 제약 환경은 bcrypt(work factor ≥ 10)로 단계적으로 선택한다.
  2. 숫자는 베끼지 말고 측정하라. OWASP·RFC의 권고값은 출발점이다. 검증 서버에서 해시 1회 ≤ 1초가 되도록 cost·메모리·iteration을 자체 벤치마크로 확정한다.
  3. 로그인 시 재해싱 경로를 반드시 넣어라. 인증 성공 시 옛 파라미터 해시를 현재 기준으로 다시 해싱해, 시간이 지나도 방어 강도가 유지되게 한다.
  4. 기초 결함을 알고리즘 고민보다 먼저 없애라. 평문·SHA 단독·salt 부재·너무 낮은 cost가 진짜 사고 원인이다. 메모리-하드 KDF의 자원 DoS도 부하 테스트로 점검한다.
  5. 심층 방어로 마감하라. 기초가 끝나면 DB와 분리된 pepper(HMAC 키)를 추가하고, 파라미터 상향 검토를 정기 운영 절차로 등록한다.
