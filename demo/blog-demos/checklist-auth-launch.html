로그인·인증 보안 출시 전 점검 플레이북

프로덕션 로그인 기능을 처음 켜기 직전, 비밀번호 해싱부터 무차별 대입 방어·MFA·세션·토큰·전송 보안·계정 복구·로깅까지 영역별로 빠짐없이 확인하는 OWASP·NIST 표준 기반 출시 게이트 체크리스트입니다.

OWASP ASVS V2 기준NIST SP 800-63B 반영8개 점검 영역업데이트 2026-05
USE CASE · 언제 누가 쓰나

프로덕션 로그인을 출시(또는 대규모 인증 변경 배포)하기 직전의 백엔드·보안·SRE 담당자를 위한 체크리스트입니다. 신규 서비스의 로그인/회원가입 오픈, 자체 인증을 외부 IdP나 패스키로 전환, MFA 도입, 비밀번호 정책 변경 같은 "인증 경로가 바뀌는 릴리스"의 출시 승인(go/no-go) 게이트로 사용하세요. 각 영역의 항목을 모두 통과한 뒤에야 출시 결정을 내리는 것이 목적이며, 항목은 추측이 아니라 OWASP Authentication Cheat Sheet, OWASP ASVS V2, NIST SP 800-63B의 명시 요구사항에 근거합니다.

1영역별 점검 카드

8개 영역을 각각 독립적으로 검증합니다. 한 영역이라도 미충족 항목이 남으면 출시 보류가 기본입니다. 항목 옆 괄호는 근거 표준 조항입니다.

① 비밀번호·자격증명

  • 비밀번호를 평문·가역 암호화가 아닌 전용 단방향 해시로 저장 — 1순위 Argon2id, 레거시는 bcrypt(work factor ≥ 10) 또는 PBKDF2(≥ 100,000회) 사용 (ASVS 2.4.1–2.4.4)
  • 자격증명마다 고유 salt(최소 32비트) 적용 (ASVS 2.4.2)
  • 단일 인증 시 최소 길이를 충분히 길게(권장 15자 이상, 최소 12자), 최대 64자 이상 허용·128자 초과만 거부 (ASVS 2.1.1–2.1.2, NIST 800-63B)
  • 유니코드·공백 포함 모든 문자 허용, 문자 종류 강제 규칙(대문자/특수문자) 금지, 주기적 강제 변경 금지 (ASVS 2.1.4·2.1.9·2.1.10)
  • 설정·변경 시 유출 비밀번호 목록(Pwned Passwords 등)과 대조해 차단 (ASVS 2.1.7)

② 무차별 대입 방어

  • 계정 단위 실패 횟수 제한 — IP가 아닌 계정 기준 카운터, 최대 시간당 100회 실패 상한 (ASVS 2.2.1)
  • 임계치·관찰 윈도·잠금 시간을 정의하고, 지수적 백오프(throttle)로 1초→2초→4초 식 점증 지연 적용
  • 유출 자격증명 대입(credential stuffing) 테스트를 막는 안티오토메이션 컨트롤 적용 (ASVS 2.2.1)
  • 자동화 의심 트래픽에 CAPTCHA 등 추가 검증 단계 추가 (잠금만으로 인한 DoS 방지)
  • 잠금 중에도 안전한 복구 경로를 열어 잠금이 서비스 거부 무기로 악용되지 않게 함

③ 다중 인증(MFA)

  • 가능한 곳에 MFA 제공 — TOTP·패스키(FIDO/WebAuthn) 등 강한 방식을 먼저 제시 (ASVS 2.2.2)
  • SMS·이메일 OTP는 기본값이 아닌 보조 수단으로만 한정 (ASVS 2.2.2·2.7.1)
  • 피싱 저항성 확보 — 암호학적 인증기(WebAuthn)로 가짜 사이트 입력 우회 방지 (ASVS 2.2.4)
  • TOTP는 유효시간 정의·재사용 거부, 코드 검증에 승인된 알고리즘 사용 (ASVS 2.8.1·2.8.3·2.8.4)
  • 비밀번호 변경·이메일 변경 등 민감 작업 전 재인증 요구

④ 세션·쿠키

  • 세션 쿠키에 HttpOnly·Secure·SameSite 속성 모두 설정
  • 로그인 성공 직후 세션 식별자 회전(고정 공격 방지), 권한 상승 시에도 재발급
  • 유휴·절대 만료 시간을 명확히 설정하고 서버 측에서 강제
  • 로그아웃 시 서버 세션을 즉시 무효화 — 클라이언트 쿠키 삭제에만 의존하지 않음
  • 인증 요소 변경·OTP 폐기 시 모든 세션에 즉시 반영(revocation) (ASVS 2.8.6)

⑤ 토큰(JWT 등)

  • 서명 알고리즘을 서버에서 고정 검증 — alg:none·알고리즘 혼동 공격 차단
  • 발급 토큰에 짧은 만료(exp)·발급자(iss)·대상(aud) 클레임을 넣고 매 요청 검증
  • 서명·검증 키를 코드·저장소에 하드코딩하지 않고 별도 비밀 관리로 보관 (ASVS 2.4.5)
  • 접근 토큰을 localStorage 대신 안전한 위치(HttpOnly 쿠키 등)에 저장해 XSS 탈취 표면 축소
  • 리프레시 토큰 회전·폐기 목록(revocation list)으로 탈취 시 무효화 경로 확보

⑥ 전송·보안 헤더

  • 로그인·인증된 모든 페이지를 HTTPS 전용으로 제공, 비밀번호는 TLS로만 전송 (OWASP Auth Cheat Sheet)
  • HSTS(includeSubDomains, preload) 적용으로 다운그레이드 차단
  • 보안 헤더 적용 — Content-Security-Policy, X-Content-Type-Options, Referrer-Policy 등
  • 분리된 인증 서버·검증기 사이 통신은 상호 인증 TLS로 보호 (ASVS 2.2.5)
  • 쿠키 Secure 플래그와 HTTPS 정합성 확인(혼합 콘텐츠 없음)

⑦ 계정 복구·이메일 검증

  • 복구는 시간 제한 1회용 토큰(만료 후 무효)으로만, 현재 비밀번호를 노출하지 않음 (ASVS 2.5.1·2.5.3)
  • 비밀번호 힌트·지식기반 질문(KBA) 사용 금지 (ASVS 2.5.2)
  • 인증 요소 변경·복구 시 사용자에게 알림 발송 (ASVS 2.5.5)
  • 가입·복구·로그인 응답을 동일하게 처리해 사용자 열거(enumeration) 차단 — "해당 주소가 등록돼 있으면 메일을 보냅니다" 식 일반 메시지 (OWASP Auth Cheat Sheet)
  • 아웃오브밴드 복구 요청은 10분 내 만료, 코드는 1회용 (ASVS 2.7.2·2.7.3)

⑧ 로깅·모니터링

  • 로그인 성공·실패, MFA 사용, 비밀번호/요소 변경 등 인증 이벤트를 감사 로그로 기록
  • 실패 급증·계정당 다지역 로그인 등 이상 징후 탐지·알림 구성
  • 로그에 비밀번호·토큰·OTP·세션ID 등 민감정보를 절대 기록하지 않음
  • 다요소 OTP 재사용은 거부하고 기록 후 기기 보유자에게 알림 (ASVS 2.8.5)
  • 인증 변경 시 안전한 채널로 알림 발송 — SMS·이메일보다 푸시 선호 (ASVS 2.2.3)

2자주 빠지는 함정표준 위반으로 가장 흔히 출시를 막는 패턴들입니다.

FAILURE MODE 1
평문 저장 또는 약한 해시

비밀번호를 평문·가역 암호화로 저장하거나 솔트 없는 MD5/SHA-1처럼 빠른 일반 해시를 쓰는 경우입니다. DB 유출 한 번으로 전체 계정이 즉시 노출됩니다. Argon2id 등 전용 단방향 KDF에 고유 솔트를 적용해야 합니다 (ASVS 2.4.1).

FAILURE MODE 2
사용자 열거가 가능한 에러·응답

"존재하지 않는 아이디" vs "비밀번호 오류"처럼 메시지·상태코드·응답시간이 갈리면 공격자가 유효 계정을 수집합니다. 로그인·가입·복구 모두 동일 메시지·동일 처리 경로·일정한 응답시간으로 통일해야 합니다.

FAILURE MODE 3
OTP를 가짜 사이트에 입력 (피싱)

SMS·TOTP 코드를 기본 MFA로만 두면, 피싱 사이트가 실시간으로 코드를 중계해 우회합니다. 피싱 저항성이 있는 패스키/WebAuthn을 먼저 제시하고 SMS는 보조로만 한정해야 합니다 (ASVS 2.2.2·2.2.4).

VERIFY · DONE 기준 (출시 가능 판단)

아래 7개를 모두 충족하면 go, 하나라도 미충족이면 no-go

  1. 저장 검증 — 스테이징 DB 덤프를 떠서 비밀번호 컬럼이 Argon2id/bcrypt/PBKDF2 해시이며 솔트가 계정마다 다른지 직접 확인했다.
  2. 대입 방어 검증 — 한 계정에 반복 실패를 자동화로 시도해 시간당 100회 이내에서 throttle/잠금이 작동하고, 잠금 중에도 복구 경로가 열려 있음을 확인했다.
  3. MFA 검증 — TOTP 또는 패스키 등록·로그인이 동작하고, 강한 방식이 SMS보다 먼저 제시되며 코드가 1회용·시간제한임을 확인했다.
  4. 세션 검증 — 쿠키에 HttpOnly·Secure·SameSite가 모두 붙고, 로그인 시 세션ID가 회전하며 로그아웃 후 기존 세션이 서버에서 무효화됨을 확인했다.
  5. 토큰·전송 검증 — JWT 서명·exp·aud가 매 요청 검증되고 alg:none이 거부되며, 모든 인증 경로가 HTTPS·HSTS로만 제공됨을 확인했다.
  6. 복구·열거 검증 — 복구 토큰이 1회용·시간제한이고, 존재/미존재 계정에 대한 로그인·복구 응답이 메시지·시간·상태코드까지 동일함을 확인했다.
  7. 로깅 검증 — 인증 이벤트가 감사 로그에 남고 이상 탐지 알림이 동작하며, 로그 샘플에 비밀번호·토큰·OTP가 없음을 확인했다.
