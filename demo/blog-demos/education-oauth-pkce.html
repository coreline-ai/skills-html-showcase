OAuth 2.0 Authorization Code + PKCE 흐름 강의

"구글로 로그인" 버튼 뒤에서 무슨 일이 벌어지는지 궁금했던 분을 위한 강의입니다. 인가 코드(Authorization Code) 흐름의 다섯 단계를 실제 요청·응답 예시로 따라가 보고, 왜 요즘은 PKCE가 사실상 필수가 되었는지를 공격 시나리오와 함께 한 번에 정리합니다. 표준(RFC 6749 · RFC 7636)에 정의된 동작만 다루므로, 강의가 끝나면 스펙 문서를 직접 읽을 자신감이 생길 거예요.

학습 목표

이 강의를 끝까지 따라오면 다음을 할 수 있습니다.

  • OAuth 2.0의 네 가지 역할(client / resource owner / authorization server / resource server)을 구분해 설명할 수 있다.
  • Authorization Code 흐름을 다섯 단계로 그려내고, 각 단계에서 오가는 파라미터(code, state, access_token 등)를 말할 수 있다.
  • 인가 코드 가로채기 공격이 왜 가능한지, 그리고 PKCE의 code_verifier·code_challenge(S256)가 그것을 어떻게 막는지 설명할 수 있다.
  • 안전한 구현(좋은 예)과 위험한 구현(나쁜 예)을 구별하고, 왜 OAuth 2.1에서 PKCE가 모든 클라이언트의 기본이 되었는지 근거를 댈 수 있다.

1사전 개념: OAuth의 등장인물과 용어

흐름을 따라가기 전에, 무대에 오를 배우들과 핵심 단어를 먼저 익혀 둡니다.

OAuth 2.0은 "내 비밀번호를 넘겨주지 않고도, 다른 앱이 내 데이터의 일부에 접근하도록 허락하는" 위임(delegation) 프로토콜입니다. 여기서 가장 자주 헷갈리는 지점부터 짚고 갑니다.

용어
인가(Authorization) ≠ 인증(Authentication)
인증은 "당신이 누구인지" 확인하는 일이고, 인가는 "무엇을 할 수 있는지" 권한을 주는 일입니다. OAuth 2.0은 본질적으로 인가 프로토콜입니다. 로그인(신원 확인)까지 표준화하려면 그 위에 얹는 OpenID Connect가 필요하다는 점만 기억하세요.
용어
Resource Owner (자원 소유자)
보호된 자원에 대한 접근을 허락할 수 있는 주체. 사람일 때는 end-user(최종 사용자), 즉 보통 "당신"을 가리킵니다.
용어
Client (클라이언트)
자원 소유자를 대신해 자원에 접근을 요청하는 애플리케이션입니다. 웹 서버 앱, 모바일 앱, SPA(브라우저 단일 페이지 앱) 등이 모두 클라이언트입니다.
용어
Authorization Server (인가 서버)
자원 소유자를 인증하고 동의를 받은 뒤 토큰을 발급하는 서버. 구글 로그인 화면, 카카오 동의 화면이 바로 이 서버가 보여 주는 것입니다.
용어
Resource Server (자원 서버)
실제 보호된 데이터를 가지고 있고, access token을 받아 요청을 처리하는 서버. 예: 사용자의 프로필이나 캘린더를 내주는 API 서버.
용어
Redirect URI (리다이렉트 URI)
인가 서버가 사용자를 다시 돌려보낼 클라이언트의 주소입니다. 표준상 이 주소는 클라이언트 등록 시 미리 약속해 두며, 인가 서버는 등록된 값과 일치하는지 검증합니다. 흐름에서 "결과를 받는 우편함" 역할을 합니다.
용어
Access Token (액세스 토큰)
자원 서버에 "이 요청은 허가된 것"임을 증명하는 자격 증명. 흐름의 최종 목표물이며, 보통 만료 시간(expires_in)이 있고 필요하면 refresh_token으로 갱신합니다.

2핵심: Authorization Code 흐름 5단계

RFC 6749의 Authorization Code Grant를 한 단계씩 따라갑니다. 예시 도메인은 모두 가상입니다.

아래 예시에서 클라이언트는 app.example-client.com(우리 앱), 인가/자원 서버는 auth.example-idp.com(가상의 신원 제공자)이라고 하겠습니다. 흐름의 큰 그림은 "먼저 단기 코드(code)를 받고, 그 코드를 뒷단에서 토큰으로 교환한다"는 것입니다. 토큰이 브라우저 URL에 직접 노출되지 않는다는 점이 이 흐름의 핵심 장점입니다.

단계 1 · 인가 요청

클라이언트가 사용자를 인가 서버로 보낸다

사용자가 "로그인" 버튼을 누르면, 클라이언트는 브라우저를 인가 엔드포인트로 리다이렉트합니다. response_type=code로 "코드 흐름을 쓰겠다"고 선언하고, state에 추측 불가능한 임의 값을 담아 보냅니다(나중에 CSRF 방지에 씁니다).

브라우저가 이동하는 주소(인가 요청):
GET https://auth.example-idp.com/authorize?
    response_type=code
  & client_id=s6BhdRkqt3
  & redirect_uri=https://app.example-client.com/callback
  & scope=profile%20email
  & state=af0ifjsldkj
단계 2 · 사용자 인증 & 동의

인가 서버가 사용자를 인증하고 동의를 받는다

인가 서버는 로그인 화면을 띄워 resource owner를 인증하고, "이 앱에 프로필·이메일 접근을 허용할까요?"라고 동의를 구합니다. 이 단계는 전적으로 인가 서버와 사용자 사이에서 일어나며, 클라이언트는 사용자의 비밀번호를 절대 보지 못합니다. 이것이 OAuth의 존재 이유입니다.

단계 3 · 인가 응답(코드 전달)

인가 서버가 코드를 들고 사용자를 돌려보낸다

사용자가 동의하면, 인가 서버는 미리 등록된 redirect_uri로 브라우저를 되돌리며 code를 붙여 보냅니다. 이때 단계 1에서 보낸 state를 그대로 다시 돌려줍니다. 클라이언트는 이 값이 자기가 보낸 것과 같은지 검증해야 합니다.

콜백으로 돌아오는 주소(인가 응답):
GET https://app.example-client.com/callback?
    code=SplxlOBeZQQYbYS6WxSbIA
  & state=af0ifjsldkj
단계 4 · 토큰 요청(코드 교환)

클라이언트가 백채널에서 코드를 토큰으로 바꾼다

이제 클라이언트는 브라우저가 아니라 서버 간 직접 통신(back channel)으로 토큰 엔드포인트에 코드를 보냅니다. grant_type=authorization_code와 함께 방금 받은 code, 그리고 단계 1과 동일한 redirect_uri를 포함합니다.

서버 간 POST 요청(토큰 요청):
POST https://auth.example-idp.com/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
& code=SplxlOBeZQQYbYS6WxSbIA
& redirect_uri=https://app.example-client.com/callback
& client_id=s6BhdRkqt3
단계 5 · 토큰 응답

인가 서버가 액세스 토큰을 발급한다

코드가 유효하면 인가 서버는 access_token을 발급합니다. token_type(보통 Bearer), 만료 시간 expires_in, 그리고 선택적으로 갱신용 refresh_token이 함께 옵니다. 클라이언트는 이제 이 토큰을 resource server의 API 호출에 사용합니다.

토큰 엔드포인트의 JSON 응답:
HTTP/1.1 200 OK
Content-Type: application/json

{
  "access_token": "2YotnFZFEjr1zCsicMWpAA",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA"
}

3PKCE는 왜 필요한가 — 가로채기 공격과 방어

코드 흐름은 좋아 보이는데, 도대체 어디가 뚫린다는 걸까요? 한 가지 약점을 봅시다.

단계 3을 다시 보세요. code는 브라우저/OS를 거쳐 전달됩니다. 특히 모바일·데스크톱 앱은 com.myapp://callback 같은 커스텀 URI 스킴으로 코드를 돌려받는데, 같은 기기에 악성 앱이 동일한 스킴을 등록해 두면 그 코드를 가로챌 수 있습니다. 이것이 RFC 7636이 정의한 authorization code interception attack(인가 코드 가로채기 공격)입니다.

위험
인가 코드 가로채기 공격

악성 앱이 정상 앱과 같은 리다이렉트 스킴을 등록합니다. 사용자가 정상적으로 동의를 마치면, OS가 콜백을 악성 앱에도 전달할 수 있습니다.

공격자는 가로챈 code를 토큰 엔드포인트로 보내 access token으로 교환합니다. 공개 클라이언트(public client)는 client secret을 안전히 숨길 수 없으므로, 코드만 손에 넣으면 이 교환을 막을 방법이 없습니다.

여기서 등장하는 것이 PKCE(Proof Key for Code Exchange, "픽시"로 읽습니다) 입니다. 아이디어는 단순합니다. "코드를 처음 요청한 그 클라이언트만이 알고 있는 한 번 쓰는 비밀을 마지막 교환 단계에서 증명하게 하자."

방어
PKCE: code_verifier & code_challenge(S256)

1) 시작 전: 클라이언트가 매 요청마다 임의의 비밀 문자열 code_verifier를 만듭니다. 이를 SHA-256으로 해시하고 Base64-URL로 인코딩한 값이 code_challenge입니다.

2) 단계 1(인가 요청)에서: 해시 값인 code_challenge와 code_challenge_method=S256만 함께 보냅니다. 원본 비밀은 보내지 않습니다.

3) 단계 4(토큰 교환)에서: 이번엔 원본 code_verifier를 보냅니다. 인가 서버는 받은 verifier를 같은 방식으로 해시해 처음 저장해 둔 challenge와 비교하고, 일치할 때만 토큰을 내줍니다.

핵심은 단방향 해시입니다. 공격자가 단계 1의 요청을 엿보거나 단계 3의 코드를 가로채더라도, 거기에는 해시 값(code_challenge)만 들어 있습니다. 원본 code_verifier 없이는 해시를 거꾸로 풀 수 없으므로, 가로챈 코드를 토큰으로 바꾸는 단계 4에서 막힙니다. RFC 7636은 S256을 지원할 수 있는 클라이언트는 반드시 S256을 쓰라고 못 박았고(plain은 challenge=verifier라 도청에 취약), S256은 서버 구현 필수(MTI) 항목입니다.

code_challenge 생성 개념 (의사 표기 — 실제 값은 라이브러리가 계산):
# 1) 43~128자 길이의 임의 비밀 (unreserved 문자: A-Z a-z 0-9 - . _ ~)
code_verifier  = base64url( random_bytes(32) )
#    예) "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"

# 2) S256 변환: SHA-256 해시 후 Base64-URL 인코딩
code_challenge = base64url( SHA256( ASCII(code_verifier) ) )
#    예) "E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM"

# 인가 요청에는 challenge만, 토큰 요청에는 verifier를 보낸다.

그래서 OAuth 2.1 초안은 PKCE를 공개 클라이언트뿐 아니라 모든 클라이언트의 필수 사항으로 끌어올렸고, 토큰이 URL 조각에 그대로 노출되어 PKCE를 적용할 수 없는 implicit grant는 아예 제거했습니다. "코드 흐름 + PKCE 하나로 SPA를 포함한 모든 앱 유형을 안전하게 처리할 수 있다"는 것이 현대 권고의 결론입니다.

4좋은 예 / 나쁜 예

스펙을 외우는 것보다, 안전한 습관과 위험한 습관을 구별하는 눈이 더 오래갑니다.

좋은 예
state로 CSRF를 방지한다

인가 요청에 추측 불가능한 state를 담고, 콜백에서 돌아온 값이 정확히 일치하는지 검증합니다. 일치하지 않으면 흐름을 중단합니다. 표준이 CSRF 방지를 위해 권고하는 동작입니다.

좋은 예
모든 클라이언트에 PKCE(S256)를 적용한다

SPA·모바일은 물론, client secret을 가진 서버 앱도 PKCE를 켭니다. 코드 가로채기·치환 공격 표면을 전 영역에서 닫는 방향이며, OAuth 2.1이 권장하는 기본값입니다.

좋은 예
redirect URI를 정확히 일치(exact match) 검증한다

리다이렉트 URI는 사전 등록된 값과 문자 단위로 정확히 비교합니다. 와일드카드나 부분 일치는 열린 리다이렉트로 코드를 탈취당하는 통로가 됩니다.

나쁜 예
implicit grant로 토큰을 URL에 직접 받는다

access token이 URL 조각에 실려 브라우저 히스토리·리퍼러·악성 스크립트로 새기 쉽습니다. 토큰 엔드포인트를 거치지 않아 PKCE도 적용할 수 없어, OAuth 2.1에서 제거되었습니다.

나쁜 예
client secret을 SPA에 박아 넣는다

브라우저로 내려가는 코드 안의 비밀은 비밀이 아닙니다. 누구나 개발자 도구로 꺼내 볼 수 있습니다. 공개 클라이언트는 secret 대신 PKCE로 자신을 증명해야 합니다.

나쁜 예
state를 보내기만 하고 검증하지 않는다

콜백으로 돌아온 state를 확인하지 않으면, 공격자가 자기 코드를 피해자 세션에 끼워 넣는 CSRF/코드 주입을 막지 못합니다. "보냈으니 됐다"가 아니라 "돌아온 값을 비교한다"가 핵심입니다.

5실습 과제

읽기만 하면 금세 잊습니다. 손으로 한 번 짚어 보면 흐름이 몸에 붙습니다.

아래 미션을 순서대로 수행해 보세요. 코드 작성 없이 종이와 펜, 또는 메모장만으로도 충분합니다.

  1. 역할 매핑: 평소 자주 쓰는 "OO으로 로그인" 서비스 하나를 골라, 네 가지 역할(client / resource owner / authorization server / resource server)에 각각 무엇이 해당하는지 적어 봅니다.
  2. 흐름 그리기: 단계 1~5를 화살표 다이어그램으로 그리고, 각 화살표 위에 그때 오가는 핵심 파라미터(response_type, state, code, access_token 등)를 표시합니다.
  3. PKCE 끼워 넣기: 방금 그린 다이어그램에 code_challenge(단계 1)와 code_verifier(단계 4)가 들어갈 위치를 빨간 펜으로 추가합니다.
  4. verifier·challenge 만들어 보기: 임의의 32바이트를 Base64-URL로 인코딩해 code_verifier 모양(43자 이상)을 흉내 내고, 온라인 SHA-256 도구로 해시해 code_challenge가 어떻게 달라지는지 눈으로 확인합니다.
  5. 공격 시뮬레이션: "공격자가 단계 3에서 code를 가로챘다"고 가정하고, PKCE가 있을 때와 없을 때 단계 4에서 무슨 일이 벌어지는지 두 시나리오로 서술합니다.

먼저 스스로 답해 본 뒤 펼쳐서 확인하세요. 막히는 항목이 복습 지점입니다.

Q1. OAuth 2.0은 인증(Authentication) 프로토콜인가요, 인가(Authorization) 프로토콜인가요?

인가 프로토콜입니다. OAuth 2.0은 "이 앱이 무엇에 접근할 수 있는가"라는 권한 위임을 다룹니다. 사용자의 신원 확인(로그인)까지 표준화하려면 그 위에 얹는 OpenID Connect가 필요합니다. 둘을 섞어 쓰지만 개념은 별개입니다.

Q2. Authorization Code 흐름에서 access token이 브라우저 URL에 직접 노출되지 않는 이유는?

브라우저로는 단기 코드(code)만 돌아오고, 토큰은 클라이언트가 서버 간 백채널 통신(단계 4)으로 토큰 엔드포인트에서 교환해 받기 때문입니다. 토큰이 히스토리·리퍼러에 남지 않는 것이 implicit grant 대비 큰 장점입니다.

Q3. 공격자가 단계 3에서 code를 가로채도 PKCE가 있으면 왜 토큰을 못 받나요?

토큰 교환(단계 4)에는 원본 code_verifier가 필요합니다. 공격자가 본 것은 단방향 해시인 code_challenge뿐이라, 이를 거꾸로 풀어 verifier를 알아낼 수 없습니다. verifier를 모르면 인가 서버의 검증을 통과하지 못해 코드가 토큰으로 바뀌지 않습니다.

Q4. PKCE에서 plain 대신 S256을 써야 하는 이유는?

plain은 code_challenge가 code_verifier와 동일해서, 단계 1의 요청을 도청하면 비밀이 그대로 노출됩니다. S256은 SHA-256 해시 값만 전송하므로 도청·가로채기로부터 verifier를 보호합니다. RFC 7636은 S256이 가능하면 반드시 S256을 쓰도록 규정합니다.

복습 & 다음 단계

한 시간을 한 문장으로: "코드를 먼저 받고, PKCE로 증명하며 토큰으로 바꾼다."

  1. 복습: OAuth는 인가 프로토콜이고, 네 역할(client·resource owner·authorization server·resource server)이 단계 1~5에 걸쳐 코드와 토큰을 주고받는다.
  2. 복습: 코드는 브라우저를 거치므로 가로채기 위험이 있고, PKCE의 code_verifier/code_challenge(S256)가 토큰 교환 단계에서 그것을 차단한다.
  3. 다음: OpenID Connect를 학습해 "인가" 위에 "인증(로그인)"을 어떻게 표준으로 얹는지 본다(id_token, nonce).
  4. 다음: refresh token rotation과 토큰 만료·재발급 전략을 익혀 장기 세션을 안전하게 다룬다.
  5. 다음: 실제 라이브러리(예: 표준 준수 OAuth 클라이언트)로 단계 1~5 + PKCE를 한 번 구현해 보고, 인가 서버 로그로 challenge·verifier 검증을 직접 확인한다.
