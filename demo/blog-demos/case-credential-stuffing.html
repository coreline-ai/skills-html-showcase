Credential Stuffing 대응 회고: 탐지부터 패스키 전환까지 (가상 사례)

어느 가상의 SaaS 서비스가 크리덴셜 스터핑 공격의 징후를 포착하고, 즉시 완화에서 근본 대응(MFA 강제·패스키 전환)까지 끌고 간 과정을 시간순으로 정리했습니다. 등장하는 회사·사건·수치는 모두 설명을 위해 만든 가상 시나리오입니다. 다만 공격이 작동하는 방식과 방어 기법의 근거는 OWASP·NIST 등 공개 표준에 맞췄습니다.

주제 · 인증 보안 유형 · 사후 회고(가상) 근거 · OWASP / NIST 800-63B / FIDO 읽는 시간 · 약 9분
상황 요약 (가상 시나리오)

가상의 B2C SaaS "보드(Board)" 서비스(웹·모바일, 로그인은 이메일+비밀번호)가 어느 평일 밤, 로그인 실패율이 평소 대비 비정상적으로 치솟는 징후를 모니터링 대시보드에서 발견했습니다. 특정 한두 계정에 집중된 무차별 대입(brute force)과 달리, 수많은 서로 다른 계정에 대해 계정당 1~2회씩만 시도되고, 그 중 일부는 곧바로 성공하는 패턴이었습니다. 시도에 쓰인 이메일·비밀번호 조합은 자사에서 유출된 적이 없는데도 "맞는" 경우가 있었습니다. 이것이 다른 서비스에서 유출된 자격증명을 재사용해 대입하는 크리덴셜 스터핑(credential stuffing)의 전형적인 모습입니다. 아래 내용은 이 가상 상황을 가정해, 일반적으로 권고되는 대응을 어떻게 단계적으로 적용했는지를 회고 형식으로 풀어낸 것입니다. 구체적 수치는 모두 "(가상)"으로 표기합니다.

1무슨 일이 벌어졌나

공격의 정체와 탐지 순간 — 시간순 타임라인.

크리덴셜 스터핑은 무차별 대입과 다릅니다. 공격자는 다른 사이트에서 유출된 실제 (이메일, 비밀번호) 조합 목록을 그대로 들고 와, "사용자가 같은 비밀번호를 여러 곳에 재사용했을 것"이라는 가정에 베팅합니다. 그래서 한 계정을 수천 번 두드리는 대신, 수많은 계정을 가볍게 한 번씩 두드립니다. 계정 단위 잠금이나 단순 임계치 알람으로는 잘 안 잡히는 이유가 여기 있습니다.

T0 · 징후 포착

로그인 실패율 급등 알람. 실패가 소수 계정이 아니라 광범위한 계정에 얕게 분산돼 있었고, 트래픽은 다수의 서로 다른 IP(주거용 프록시로 추정되는 대역 포함)에서 왔습니다. User-Agent는 단조롭게 반복되는 경향을 보였습니다. (예시 수치: 평소 대비 실패 시도 수십 배 — 가상)

T1 · 분석 — "재사용 비밀번호 대입"임을 확인

로그를 보니 (a) 계정당 시도 횟수가 1~2회로 낮고, (b) 성공한 로그인 중 일부가 평소와 다른 지역·기기에서 발생했으며, (c) 시도된 자격증명이 최근 외부 유출 데이터셋과 겹친다는 정황이 확인됐습니다. 무차별 대입이 아니라 크리덴셜 스터핑으로 결론지었습니다.

T2 · 즉시 완화 — 자동화 비용을 올린다

몇 시간 내 배포: IP·세션 단위 속도 제한(rate limit)과 점진적 지연(progressive delay), 의심 트래픽에 대한 CAPTCHA, 비정상 패턴(헤드리스 브라우저·자바스크립트 미실행 등) 차단. 성공했지만 위험 신호가 있는 로그인은 추가 인증을 요구하도록 이상 탐지 규칙을 강화했습니다.

T3 · 피해 봉쇄 — 위험 계정 보호

성공한 의심 로그인에 묶인 계정은 위험 계정으로 분류해 세션 무효화 + 재인증 요구, 해당 사용자에게 "낯선 로그인" 알림을 발송했습니다. 전체 강제 비밀번호 리셋 대신 위험 계정에 한정하는 쪽을 택했습니다(2번 섹션의 의사결정 참고).

T4 · 근본 대응 — 비밀번호 의존을 줄인다

로그인 시 유출 비밀번호 검사(예: Pwned Passwords류 정책)를 도입해 재사용·유출 비밀번호 설정을 막고, MFA를 강하게 권장 후 단계적 강제로 전환. 동시에 패스키(FIDO2/WebAuthn) 등록 흐름을 출시해 "비밀번호 없는, 피싱 저항 로그인"을 기본 경로로 밀기 시작했습니다.

T5 · 안정화 — 측정과 정착

공격 트래픽이 잦아든 뒤에도 완화 규칙을 유지하며 false positive(정상 사용자 차단)를 모니터링하고, 패스키·MFA 채택률을 KPI로 추적했습니다. 사후 회고에서 탐지 지표와 대응 플레이북을 문서화했습니다.

2핵심 의사결정과 트레이드오프

정답이 하나가 아니었던 분기점들 — 무엇을 고르고 무엇을 버렸나.

대응 과정의 가치는 "기법 목록"이 아니라 제약 속에서 무엇을 우선했는가에 있습니다. 가상 사례지만, 아래 분기점들은 실제 인증 운영에서 거의 항상 마주칩니다.

결정 A · 2차 인증 수단: SMS OTP vs TOTP·패스키

빠르게 깔 수 있다는 이유로 SMS OTP가 매력적으로 보였습니다. 하지만 SMS는 SIM 스와핑·중간자 피싱에 취약하고, NIST는 SMS 같은 공중망(PSTN) 기반 인증을 제약(restricted) 수단으로 취급합니다.

버린 선택
SMS OTP를 주력 2차 인증으로

도입은 빠르지만 피싱·SIM 스와핑에 약하고, 사용자가 "충분히 안전해졌다"고 오인하게 만들 위험.

택한 선택
TOTP(인증 앱)를 기본, 패스키를 목표

TOTP는 공유 비밀이지만 PSTN 의존이 없고, 패스키(FIDO2)는 오리진 바인딩으로 피싱에 저항하며 서버에 재사용 가능한 비밀을 남기지 않습니다. SMS는 최후 폴백으로만.

결정 B · 비밀번호 리셋: 전체 강제 vs 위험 계정 한정

"전부 리셋"은 단순하고 안심되지만, 공격과 무관한 절대다수 사용자에게 마찰을 강요해 대규모 이탈·CS 부하·도리어 피싱 사칭의 빌미를 줍니다. NIST는 침해 정황 없는 주기적 강제 변경을 권장하지 않습니다.

택한 선택
위험 계정만 표적 대응

의심 로그인이 성공한 계정에 한해 세션 무효화 + 재인증 + 알림. 나머지 사용자에게는 강제 리셋 대신 유출 비밀번호 검사와 MFA 권장으로 점진 유도. "전체 마찰"보다 "표적 마찰"이 보안과 사용성의 균형점이었습니다.

결정 C · IP 차단: 단독 방어 vs 다층 방어

IP 차단은 정교하지 않은 공격은 막지만, 주거용 프록시·봇넷으로 손쉽게 우회됩니다. OWASP는 IP 차단을 유일하거나 주된 방어로 쓰지 말 것을 권고합니다.

버린 선택
IP 차단만으로 끝내기

고정 임계치 한 줄에 의존하면 우회당하고, 정상 사용자(공유 IP·기업 NAT)를 오차단할 위험도 큼.

택한 선택
속도 제한·CAPTCHA·이상 탐지의 단계적 대응

공격 신호의 강도에 따라 지연 → CAPTCHA → 추가 인증 → 차단으로 점진적으로 강도를 올리는 다층 구성. IP는 신호 중 하나일 뿐.

Lessons · 일반화할 수 있는 교훈

이 가상 사례에서 끌어낼 수 있는 6가지

  1. 크리덴셜 스터핑은 "분산·저빈도"로 위장한다. 계정 단위 임계치만 보지 말고, 다수 계정에 얕게 퍼진 실패 패턴과 성공 후 이상 신호를 함께 봐야 탐지된다.
  2. 단일 방어는 우회된다. IP 차단·CAPTCHA·속도 제한 어느 것도 단독으로는 부족하다. 신호 강도에 따라 강도를 올리는 다층·점진 대응을 설계하라.
  3. 즉시 완화와 근본 대응을 분리하라. 속도 제한·CAPTCHA로 출혈을 멈춘 뒤, MFA·패스키로 구조를 바꾼다. 둘을 섞으면 둘 다 늦어진다.
  4. 마찰은 표적화하라. 전체 강제 리셋·전체 차단은 정상 사용자를 적으로 돌린다. 위험 기반으로 마찰을 위험 계정에 집중시켜라.
  5. 2차 인증은 수단의 질이 중요하다. SMS OTP는 폴백일 뿐, 피싱 저항이 필요하면 TOTP를 넘어 패스키(FIDO2)로 간다.
  6. 비밀번호를 줄이는 것이 최종 해법이다. 재사용 비밀번호가 공격의 연료다. 유출 비밀번호 검사 + 패스키 전환으로 연료 자체를 없애라.
근거 및 고지

본 사례의 회사·사건·수치·타임라인은 전부 설명을 위해 구성한 가상 시나리오이며 실제 침해 사례가 아닙니다. 반면 공격 메커니즘과 방어 기법(속도 제한·CAPTCHA·위험 기반 인증·MFA·패스키)의 설명은 아래 공개 표준·문서에 근거합니다.

  1. OWASP, Credential Stuffing Prevention Cheat Sheet — MFA를 1차 방어로, 다층 방어(다단계 로그인·기기 핑거프린팅·IP 분류·CAPTCHA·헤드리스 차단·유출 비밀번호 검사·사용자 알림)를 권고. IP 차단을 단독·주력 방어로 쓰지 말 것.
  2. NIST, SP 800-63B Digital Identity Guidelines (Authenticators) — 실패 인증 시도에 대한 속도 제한(throttling) 의무, 침해 정황 없는 주기적 강제 변경 비권장, SMS 등 PSTN 기반 인증의 제약적 취급.
  3. FIDO Alliance, Passkeys (FIDO2/WebAuthn) — 공개키 기반·오리진 바인딩으로 피싱에 저항하고 서버에 재사용 가능한 비밀을 남기지 않아 크리덴셜 스터핑에 본질적으로 강한 구조.
  4. OWASP, Multifactor Authentication Cheat Sheet — 인증 수단별 강도·트레이드오프(SMS의 한계, FIDO의 피싱 저항)에 대한 보조 근거.
