보안 패치는 기능 추가가 아니라 신뢰 부채를 갚는 일

인증 모듈 운영 관점에서 보안 패치를 “새 기능”이 아니라 사용자 신뢰 부채를 상환하는 작업으로 보는 실무 블로그입니다.

1Hook: 잘 끝난 보안 패치는 아무 일도 일어나지 않습니다

그래서 보안 패치는 쉽게 밀리지만, 인증 영역에서는 가장 중요한 신뢰 작업입니다.

새 기능은 보입니다. 새 대시보드, 새 결제 플로우, 새 버튼은 바로 박수를 받습니다. 반면 보안 패치는 조용합니다. 잘 끝나면 침해도 없고, 장애도 없고, 고객 문의도 없습니다. 그래서 스프린트에서 자주 밀립니다.

하지만 인증 시스템을 운영해 보면 생각이 바뀝니다. 보안 패치는 기능 추가가 아닙니다. 이미 사용자에게 빌려 쓴 신뢰를 갚는 일입니다.

2개인 메모: 가장 무서운 코드는 “나중에”입니다

복잡한 코드보다 오래된 예외와 임시 우회가 더 위험합니다.

인증 모듈에서 가장 무서운 코드는 암호학적으로 어려운 코드가 아니었습니다. “for now”, “later”, “temporary”, “TODO security”가 붙은 코드였습니다.

  • magic link URL이 access log에 그대로 남는 코드
  • session revoke는 있지만 일부 background token은 회수하지 않는 코드
  • OAuth redirect URI 검증을 “일단 startswith”로 처리한 코드
  • role 변경 후 기존 session permission snapshot을 그대로 믿는 코드
  • TOTP replay는 막았지만 동시 요청 CAS를 빼먹은 코드

3관점 전환: 보안 패치는 신뢰 부채 상환이다

기능 경쟁에서 이기려면 보안 패치를 “보이지 않는 기능”으로 설명해야 합니다.

보안 패치는 사용자가 맡긴 비밀을 계속 맡길 수 있는 상태, 사고가 나도 피해 범위를 줄일 수 있는 구조, 운영자가 문제를 발견했을 때 빠르게 회수할 수 있는 통제권을 만듭니다.

TRUST LEDGER
좋은 패치는 영수증을 남깁니다

reset token 원문 저장 제거, session token redaction, logout revoke 검증, OAuth nonce negative test처럼 “이전에는 실패했을 테스트”를 추가해야 합니다. 테스트는 신뢰 부채 상환 영수증입니다.

4실행법: 티켓을 구체화하고 secret inventory부터 만든다

막연한 “보안 개선”은 계속 밀립니다. 구체적인 공격 표면 이름을 붙여야 합니다.

1. 티켓 제목

“인증 보안 개선”이 아니라 “password reset token 원문 저장 제거”처럼 씁니다.

2. Secret inventory

password, session id, magic token, reset token, OAuth code, MFA seed, recovery code를 모두 적습니다.

3. 직접 암호 금지

password hashing, AEAD, signature, random generation은 검증된 라이브러리와 표준을 씁니다.

4. 실패 테스트

CSRF 누락, stale session revive, TOTP replay, origin spoofing 같은 negative test를 남깁니다.

5. 운영 증거

readiness CLI, SIEM redaction, backup drill, release version alignment를 evidence로 저장합니다.

6. 회수 통제

사고 후 토큰과 세션을 얼마나 빠르게 무효화할 수 있는지가 실제 피해 범위를 결정합니다.

오래된 TODO 하나를 신뢰 부채 상환 티켓으로 바꿔보세요.
