BIG PICTURE

로그인은 문 하나가 아니라 도시 전체의 출입 정책입니다.

정문 암호가 비밀번호라면, 세션은 임시 출입증, MFA는 추가 검문소, 패스키는 도시 이름에 묶인 개인 스마트키입니다. 계정 복구는 분실물 센터입니다. 보안 사고는 대개 가장 화려한 정문이 아니라 가장 약한 분실물 센터나 낡은 출입증 관리에서 시작됩니다.

1도시 출입 시스템으로 보는 로그인 보안

처음 보는 개념도 같은 도시 지도 위에 올리면 역할이 분명해집니다.

웹 서비스에는 공개 광장, 내 계정, 결제 정보, 관리자 콘솔, 비밀번호 변경, API 토큰 발급 같은 서로 다른 구역이 있습니다. 인증은 “이 사람이 누구인지” 확인하는 절차이고, 인가는 “그 사람이 어느 구역까지 들어갈 수 있는지” 결정하는 절차입니다.

ANALOGY

정문에서 암호를 말해도 곧바로 전력 제어실에 들어가면 안 됩니다. 정문 통과, 임시 출입증, 제한 구역 권한표, 고위험 구역 재검문이 함께 있어야 도시가 안전합니다.

요소도시 비유실제 역할초보자 기억법
비밀번호정문 암호사용자가 아는 장기 비밀원문 저장 금지
해시·salt검사용 일방향 표원문 없이 일치 확인되돌릴 수 없어야 안전
세션 쿠키임시 출입증로그인 상태 유지훔치면 가장 가능
MFA추가 검문소서로 다른 증거 요구암호 하나만 믿지 않기
패스키개인 스마트키공개키 기반 로그인사이트별 키, 피싱 저항
계정 복구분실물 센터접근권 회복정문보다 약하면 뒷문

2핵심 용어를 한 번에 잡기

용어를 외우기보다 언제 위험해지는지까지 함께 이해합니다.

TERM
Authentication 인증

“너 누구야?”를 확인합니다. 이메일+비밀번호, 패스키, OTP 입력이 여기에 해당합니다.

TERM
Authorization 인가

“너는 무엇을 할 수 있어?”를 결정합니다. 일반 사용자가 관리자 페이지에 들어가면 안 되는 이유입니다.

TERM
Session 세션

로그인 후 매 요청마다 다시 암호를 묻지 않도록 서버가 발급하는 임시 상태입니다. 세션 토큰은 원문을 DB나 로그에 남기지 않는 쪽이 안전합니다.

TERM
CSRF

브라우저가 쿠키를 자동으로 보내는 성질을 이용해 사용자의 의도와 다른 상태 변경 요청을 만들게 하는 공격입니다.

TERM
Passkey 패스키

사용자가 비밀번호를 서버에 보내지 않고, 기기 안 개인키로 서비스 도메인에 바인딩된 서명을 만드는 인증 방식입니다.

3회원가입부터 로그아웃까지 안전한 인증 흐름

각 단계에서 “무엇을 저장하고 무엇을 절대 저장하지 않을지”가 핵심입니다.

1. 가입

비밀번호는 Argon2id/bcrypt/PBKDF2 같은 검증된 password hashing으로 저장합니다. 원문은 저장·로그·감사 기록에 남기지 않습니다.

2. 로그인

계정을 찾고 비밀번호를 검증한 뒤, 실패 횟수와 rate limit를 적용합니다. 사용자 존재 여부를 지나치게 드러내지 않습니다.

3. MFA

OTP, recovery code, passkey, 보안키 같은 추가 요소로 계정 탈취 난도를 높입니다. 같은 TOTP code 재사용은 막아야 합니다.

4. 세션

세션 토큰은 충분한 난수로 만들고, 서버 저장소에는 해시를 둡니다. 로그아웃·비밀번호 변경·role 변경 후 세션 회수가 중요합니다.

5. 권한

요청마다 권한을 다시 확인합니다. role이 바뀌면 기존 session permission snapshot이 계속 살아 있지 않게 해야 합니다.

6. 복구

magic link·reset token도 원문 저장 금지, 만료, 1회 사용, HTML/URL escaping, open redirect 방어가 필요합니다.

4위험한 설계와 좋은 설계

안전한 인증은 보안 기능 하나가 아니라 여러 통제의 조합입니다.

DANGER
위험한 로그인 도시

비밀번호 원문 저장, URL에 세션 토큰 포함, 로그아웃 후 서버 세션 유지, CSRF optional default, role 변경 후 기존 세션 유지, magic-link return_to 미검증, origin prefix check 같은 설계는 정문보다 뒷문을 약하게 만듭니다.

GOOD
좋은 로그인 도시

hash-only token 저장, session revoke 즉시 반영, cookie state-changing route CSRF fail-closed, TOTP replay atomic CAS, exact origin/RP 검증, OAuth PKCE·nonce·ID token 검증을 함께 적용합니다.

공격무슨 일이 생기나방어 우선순위
Credential stuffing다른 서비스 유출 암호를 대량 시도유출 암호 차단, rate limit, MFA
Session hijacking세션 토큰으로 사용자 가장HttpOnly/Secure/SameSite, token redaction, revoke
CSRF사용자 의도 없는 상태 변경Signed double-submit, SameSite, unsafe method 보호
TOTP replay같은 OTP를 동시 재사용counter/window CAS, rate limit
Open redirect복구 링크가 공격자 URL로 이동same-origin allowlist, escaping

5실무 체크리스트

처음에는 이 목록만 따라도 큰 사고 가능성을 낮출 수 있습니다.

  • password/session/magic-link/reset/recovery token 원문을 DB·로그·audit에 저장하지 않는다.
  • 로그인 성공, 권한 상승, 민감 작업 후 세션 재발급 또는 재검증 정책을 둔다.
  • 쿠키 기반 state-changing route는 CSRF protector 누락 시 실패하도록 한다.
  • 관리자 role 변경, password reset, admin revoke 후 대상 세션을 회수한다.
  • WebAuthn origin은 prefix가 아니라 정확한 host/RP 기준으로 검증한다.
  • OAuth/OIDC는 PKCE S256, state, nonce, ID token claim 검증을 함께 쓴다.
TRY

✓내 프로젝트에 바로 적용해 보기

  1. 현재 로그인 후 발급되는 토큰 목록을 적습니다.
  2. 각 토큰이 원문으로 저장·로그되는 경로가 있는지 확인합니다.
  3. 로그아웃, role 변경, 비밀번호 재설정 후 기존 세션이 실제로 막히는지 테스트합니다.
  4. 쿠키 인증 POST에서 CSRF 헤더를 제거했을 때 실패하는지 확인합니다.
