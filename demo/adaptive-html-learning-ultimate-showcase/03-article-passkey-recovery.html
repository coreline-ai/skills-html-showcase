패스키는 로그인의 끝이 아니라 계정 복구 설계의 시작이다

패스키가 비밀번호 피싱을 줄이는 동안 계정 복구, 새 기기 등록, 고객지원 우회로가 더 중요한 제품 보안 표면이 되는 이유를 다룹니다.

PULL QUOTE

패스키의 성공은 “비밀번호 없이 로그인했는가”가 아니라 “비밀번호 없이도 안전하게 잃고, 되찾고, 폐기할 수 있는가”로 판단해야 합니다.

1Lead: 패스키가 해결한 문제와 새로 드러낸 문제

로그인 버튼은 안전해졌지만 계정 생명주기는 더 복잡해졌습니다.

패스키는 사용자가 비밀번호를 서버에 보내는 모델을 공개키 기반 서명 모델로 바꿉니다. 서비스에는 공개키가 남고, 개인키는 사용자 기기나 credential manager 안에 머뭅니다. 도메인에 바인딩되기 때문에 피싱에 강하고, 비밀번호 재사용·유출 문제를 크게 줄입니다.

하지만 제품 전략 관점에서 패스키는 “로그인의 종결”이 아닙니다. 오히려 인증자 목록, 기기 교체, 동기화 제공자, recovery code, 고객지원 복구, 기존 세션 회수, 새 패스키 등록 정책이 모두 제품 보안 표면이 됩니다.

2핵심 주장: 전략의 중심은 인증보다 복구다

공격자는 강한 정문을 만나면 약한 분실물 센터를 찾습니다.

FIDO와 NIST 가이드의 공통 메시지는 계정 복구가 독립된 보안 설계 대상이라는 점입니다. 사용자가 기기를 잃어버렸을 때 쉽게 되찾는 UX와 공격자가 이메일·SMS·고객센터를 통해 계정을 빼앗지 못하게 하는 통제는 서로 긴장합니다.

패스키가 강할수록, 복구 절차가 제품 보안의 가장 약한 고리가 될 가능성은 더 커집니다.

3가상 사례: 로그인은 완벽했지만 복구가 뚫린 SaaS

이 사례는 특정 회사 사고가 아니라 패턴 설명을 위한 가상 시나리오입니다.

B2C 핀테크 앱이 패스키 로그인을 기본값으로 도입했습니다. 피싱 신고는 줄고 로그인 성공률은 높아졌습니다. 그러나 사용자가 휴대폰을 잃어버린 뒤 고객센터 복구가 시작됩니다. 고객센터는 이메일 링크와 개인정보 몇 가지를 확인하고 새 기기 등록 링크를 발급합니다. 공격자는 이미 이메일 계정을 장악했고, 유출 개인정보로 질문에 답합니다.

패스키 인증 자체는 실패하지 않았습니다. 실패한 것은 복구 설계입니다. 복구 링크는 새 패스키 등록, 기존 세션 검토, 출금 한도 제한, 의심 기기 폐기를 강제하지 않았고 공격자는 새 기기에서 계정을 장악했습니다.

LESSON
복구는 예외가 아니라 대체 로그인입니다.

정문보다 약한 복구는 공격자에게 공식 우회로를 제공합니다. 고가치 계정일수록 복구에는 다중 증거, 대기 시간, 수동 검토, 제한 세션이 필요합니다.

4복구 설계의 네 가지 원칙

사용자 경험과 보안 통제가 충돌하지 않도록 흐름 자체를 설계합니다.

1. 복구를 로그인보다 약하게 만들지 않는다

이메일/SMS 하나만으로 완전한 계정 장악이 가능하면 패스키의 장점이 사라집니다.

2. 여분의 패스키는 온보딩 기능이다

첫 등록 직후 다른 기기, 보안키, recovery code 등록을 자연스럽게 유도합니다.

3. 동기화형과 기기 고정형을 구분한다

동기화형은 복원성이 높고, 기기 고정형은 분실 리스크가 큽니다. UX와 위험 정책이 달라야 합니다.

4. 복구 후 계정 청소를 자동화한다

기존 세션, 패스키 목록, OAuth 연결, API 토큰, 결제 정보를 검토하게 해야 합니다.

5제품팀 체크리스트

패스키 프로젝트의 완료 기준을 로그인 구현이 아니라 lifecycle 완성으로 바꿉니다.

  • 패스키 등록·삭제·이름 변경·마지막 사용일을 사용자에게 보여준다.
  • 새 패스키 등록은 기존 강한 인증 또는 AAL2 step-up을 요구한다.
  • 복구 코드는 충분한 엔트로피, hash-only 저장, 1회 사용, 동시성 방어를 갖춘다.
  • 복구 성공 후 제한 세션에서 보안 점검 wizard를 거치게 한다.
  • 고객지원 복구는 별도 권한, 이중 승인, 감사 로그, 사용자 알림을 요구한다.
  • 지표는 passkey adoption만이 아니라 다중 인증자 보유율, 복구 후 탈취율, 의심 인증자 폐기율을 본다.
