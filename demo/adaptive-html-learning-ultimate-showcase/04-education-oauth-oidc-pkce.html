1학습 목표

수강 후에는 소셜 로그인 데모가 아니라 production-grade OIDC callback을 설명할 수 있어야 합니다.

  • Authorization Code Flow에서 PKCE가 막는 공격 지점을 설명한다.
  • state, nonce, code_verifier의 역할 차이를 구분한다.
  • Authorization Request와 Token Request를 직접 조립한다.
  • ID Token의 서명, iss, aud, azp, exp, iat, nonce를 검증한다.
  • wrong issuer, wrong audience, expired token, unknown kid, nonce mismatch를 실패 테스트로 만든다.

3핵심 개념

세 값은 서로 대체재가 아니라 서로 다른 공격을 막는 보완재입니다.

PKCE
code_verifier / code_challenge

authorization code를 훔쳐도 code_verifier 없이는 token endpoint에서 교환하지 못하게 합니다. 최신 보안 권고에서는 public client에 필수이며 confidential client에도 권장됩니다.

STATE
callback CSRF 방어

내 앱이 시작한 로그인 요청의 응답인지 확인합니다. callback에서 저장된 state와 요청 state가 다르면 실패해야 합니다.

NONCE
ID Token replay 방어

인증 요청과 ID Token을 연결합니다. 요청에 보낸 nonce가 ID Token claim과 일치해야 합니다.

code_verifier = base64url(random(32 bytes))
code_challenge = base64url(sha256(ascii(code_verifier)))

GET /authorize?response_type=code
  &scope=openid%20profile%20email
  &state=csrf_...
  &nonce=n_...
  &code_challenge=...
  &code_challenge_method=S256

4실습: Callback 처리와 검증 순서

ID Token payload만 디코딩해서 로그인 처리하면 안 됩니다. 검증 전 payload는 신뢰할 수 없습니다.

실습 A · Discovery 확인

issuer, authorization_endpoint, token_endpoint, jwks_uri, code_challenge_methods_supported를 확인합니다.

실습 B · Callback 처리

  1. 저장된 state와 callback state를 constant-time compare로 확인합니다.
  2. authorization code와 code_verifier를 token endpoint에 보냅니다.
  3. JWKS에서 kid를 찾아 서명을 검증합니다.
  4. issuer, audience, authorized party, exp, iat, nonce를 검증합니다.
  5. 성공 후 사용자 식별자는 provider user id가 아니라 iss + sub 조합으로 저장합니다.
실패 케이스조작기대 결과
Wrong nonce저장 nonce와 ID Token nonce 불일치로그인 거부
Wrong audienceaud가 다른 client_id로그인 거부
Expired tokenexp가 과거로그인 거부
Unknown kidJWKS에 없는 kid갱신 후에도 없으면 거부
PKCE mismatch다른 code_verifier 제출token request 실패

5퀴즈와 정답

정답을 외우기보다 어떤 공격을 막는지 연결해 설명합니다.

  1. Authorization Request에 보내는 것은 code_verifier인가 code_challenge인가?
  2. S256 code_challenge 계산식은?
  3. state와 nonce의 가장 큰 차이는?
  4. ID Token aud는 무엇과 비교해야 하는가?
  5. unknown kid가 나오면 어떻게 해야 하는가?
  6. payload만 디코딩하고 로그인 처리해도 되는가?
  1. code_challenge.
  2. BASE64URL(SHA256(ASCII(code_verifier))).
  3. state는 callback CSRF 방어, nonce는 ID Token replay 방어.
  4. 내 client_id.
  5. 안전한 JWKS refresh 후에도 없으면 거부.
  6. 안 됩니다. 서명과 claim 검증 전에는 신뢰할 수 없습니다.
