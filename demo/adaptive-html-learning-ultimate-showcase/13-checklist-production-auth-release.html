Production Auth Release Security Playbook

Executive Release Verdict

이 문서는 “production 배포 가능 여부”를 기능 완성도가 아니라 보안 불변식과 운영 증거 기준으로 판정합니다.

Release posture

Conditional GO — 모든 P0/P1 gate와 evidence pack이 충족될 때만 production 후보로 승격

Coreline Auth는 독립 인증 모듈로서 password/session/magic-link token 원문 비저장, 세션 revoke, CSRF, MFA, OAuth/OIDC, readiness check를 갖춘 구조입니다. 다만 production 후보 배포는 테스트 통과만으로는 부족합니다. 세션 폐기, 권한 회수, CSRF fail-closed, MFA replay 방지, OIDC 검증, WebAuthn origin/RP 검증, secret-safe 운영 증거가 모두 남아야 합니다.

Release blocker

아래 중 하나라도 실패하면 production 후보 배포 금지

  • src/coreline_auth가 coremcp.* 또는 apps.api.coremcp.*를 import합니다.
  • password/session/magic-link/reset/recovery token 원문이 DB, log, audit, analytics에 저장됩니다.
  • cookie-backed state-changing route가 CSRF 없이 성공합니다.
  • logout/admin revoke/password reset 이후 기존 session token이 계속 유효합니다.
  • role demotion 이후 기존 session permission snapshot으로 admin 기능이 가능합니다.
  • multi-worker/multi-node production에서 process-local rate limit만 사용합니다.
  • OIDC ID Token을 signature/issuer/audience/nonce 검증 없이 decode만 합니다.
  • WebAuthn origin/RP 검증이 문자열 prefix check 수준입니다.
  • readiness output, audit event, email queue, error log에 secret value가 노출됩니다.

1릴리스 철학

인증 모듈 릴리스는 “코드가 돌아간다”가 아니라 “이전 신뢰 상태를 안전하게 끝낼 수 있다”를 증명해야 합니다.

운영 비유

로그인은 입장 허가, 세션은 출입증, revoke는 비상 폐쇄입니다.

인증 시스템은 건물 출입 통제실입니다. MFA는 제한 구역 추가 검문, OAuth/OIDC는 외부 신원기관 확인서, WebAuthn은 위조가 어려운 스마트키입니다. production 릴리스는 “문이 열린다”가 아니라 분실 신고, 권한 회수, 비상 폐쇄, 감사 기록까지 동작한다는 증명입니다.

릴리스 원칙의미Coreline Auth 적용 기준
Fail closed설정이 빠지면 안전하지 않게 통과하지 않습니다.cookie-auth POST는 CSRF protector 없으면 실패해야 합니다.
Hash-only secret handlingDB/log/audit 유출 시 bearer secret 원문이 없어야 합니다.session/magic/reset/recovery token 원문 저장 금지.

Assurance-aware release민감 작업은 더 높은 인증 보증이 필요합니다.admin role/password/ban/revoke에는 AAL2 step-up을 release blocker로 둡니다.

2Use Cases

배포 형태별로 release gate 강도를 다르게 적용합니다. production 후보는 최소 UC-03 기준을 통과해야 합니다.

UC-01. Local demo / self-test

로컬 개발자 검증, HTTP localhost, SQLite, process-local limiter 사용 가능. 단, demo mode가 꺼진 상태에서 debug token 또는 약한 secret이 노출되면 안 됩니다.

판정: 개발 전용. production claim 금지.

UC-02. Single-node internal beta

내부 사용자 제한, 단일 프로세스 또는 단일 노드, SQLite 가능. Secure cookie, CSRF, session revoke, audit redaction, SMTP readiness는 확인해야 합니다.

판정: Conditional GO.

UC-03. Public SaaS production candidate

외부 사용자 대상. Postgres, Redis shared limiter, SMTP, encrypted MFA vault, readiness evidence, incident rollback plan이 필요합니다.

판정: 본 플레이북의 기본 기준.

UC-04. B2B SSO / OIDC

기업 IdP, Google/OIDC provider 연동. Authorization Code + PKCE, state, nonce, ID Token 검증, provider negative test가 필요합니다.

판정: OIDC evidence 없으면 NO-GO.

UC-05. Admin / high-risk account

관리자, 감사자, 운영자 계정. MFA/AAL2 step-up, session inventory, admin action audit, self-ban/last-owner lockout 방지가 필수입니다.

판정: AAL2 gate 없으면 NO-GO.

UC-06. Passkey/WebAuthn preview

WebAuthn primitive 또는 passkey-ready 기능 검증. full ceremony, credential lifecycle, recovery UX가 없으면 primary auth로 광고하지 않습니다.

판정: Preview/primitive claim만 허용.

5Failure Modes

아래 실패 모드는 인증 production 배포에서 실제 사고로 이어질 가능성이 높은 항목입니다.

FM-01

독립 모듈 경계 붕괴

src/coreline_auth가 CoreMCP runtime을 import하면 인증 모듈이 host app 상태와 결합되어 독립 감사와 재사용성이 깨집니다.

Detection: import grep, dependency graph.

Mitigation: CoreMCP 전용 코드는 host adapter로 이동.

FM-02

raw token leakage

session/magic/reset token 원문이 DB나 audit log에 남으면 저장소 또는 로그 유출이 곧 계정 탈취로 이어집니다.

Detection: secret scan, storage schema review, audit sample review.

Mitigation: hash-only storage, redaction, token fingerprint만 표시.

FM-03

revoked session stale revive

revoke된 세션이 touch 과정에서 오래된 객체 저장으로 revoked_at=None으로 되살아나는 문제.

Detection: revoke와 concurrent verify/touch race test.

Mitigation: revoke-aware partial touch, 조건부 update, row 없음이면 invalid session.

FM-04

role demotion 이후 stale permission

admin에서 user로 demote 되었는데 기존 세션의 permission snapshot이 계속 admin 권한을 가질 수 있습니다.

Detection: role update 후 기존 token으로 admin API negative test.

Mitigation: role 변경 시 대상 사용자 세션 revoke 또는 session_version 정책.

FM-05

CSRF optional default

cookie-auth POST가 CSRF protector 미설정 상태에서도 성공하면 외부 사이트가 사용자의 ambient cookie를 악용할 수 있습니다.

Detection: no-CSRF cookie POST negative test.

Mitigation: production cookie flow는 fail-closed.

FM-06

TOTP replay race

두 요청이 동시에 같은 TOTP code를 검증하고 counter update를 나중에 수행하면 둘 다 성공할 수 있습니다.

Detection: concurrent TOTP verify test.

Mitigation: storage-level CAS consume.

FM-07

OIDC decode-only authentication

ID Token을 decode만 하고 signature, issuer, audience, nonce, expiry를 검증하지 않으면 인증이 아닙니다.

Detection: forged token, wrong issuer/audience/nonce/kid negative tests.

Mitigation: JWKS 기반 검증, issuer allowlist, nonce/state one-time consume.

FM-08

WebAuthn origin prefix bypass

localhost prefix check는 localhost.evil.example 같은 host boundary 우회를 만들 수 있습니다.

Detection: malicious origin negative tests.

Mitigation: URL parser, exact origin, RP ID hash, host boundary 검증.

FM-09

readiness overclaim

readiness CLI는 환경 변수가 있는지 확인할 수 있지만 SMTP 전송, Redis 연결, Postgres migration 성공을 자동 증명하지 않습니다.

Detection: readiness와 smoke evidence 분리.

Mitigation: 실제 provider smoke와 migration rollback test를 별도 evidence로 요구.

7Release Runbook

릴리스 당일 운영 순서입니다. 각 단계에서 실패하면 즉시 stop-the-line으로 전환합니다.

  1. T-72h · Scope freeze

    릴리스 범위, 버전, migration, OAuth provider, WebAuthn RP ID/origin, SMTP/Redis/Postgres 환경 변수를 고정합니다. 이 시점 이후 auth core 변경은 release manager 승인 없이는 금지합니다.

  2. T-48h · Security regression

    session revoke, role demotion, CSRF, TOTP replay, magic-link escaping, OIDC negative, WebAuthn origin negative test를 실행합니다. P0 실패가 있으면 릴리스 후보를 폐기합니다.

  3. T-24h · Readiness evidence

    make readiness-check와 실제 provider smoke를 분리해 저장합니다. readiness는 secret 값을 출력하지 않아야 하며, 실제 연결 smoke는 별도 로그로 남깁니다.

  4. T-4h · Deployment preflight

    cookie header, CSRF cookie/header, TLS, reverse proxy header, secure origin, redirect URI exact match, session cookie domain/path를 확인합니다.

  5. T-0 · Deploy canary

    제한된 traffic 또는 내부 admin 계정으로 canary 배포합니다. 로그인, 로그아웃, password reset, admin revoke, MFA step-up, OIDC callback, readiness page를 확인합니다.

  6. T+30m · Abuse watch

    login failure spike, reset request spike, CSRF mismatch spike, OAuth callback error, Redis limiter error, SMTP bounce, audit sink error를 모니터링합니다.

  7. T+24h · Post-release review

    security events, metrics, support ticket, failed auth rates, suspicious session revokes를 검토하고 release evidence pack을 보관합니다.

8Done Criteria

모든 완료 기준이 충족될 때만 “production candidate release complete”로 표시합니다.

Hard Done

  • src/coreline_auth에 CoreMCP import가 없다.
  • password/session/magic-link/reset/recovery token 원문이 DB/log/audit에 없다.
  • make test가 통과했다.
  • make smoke-demo-secure가 통과했다.
  • cookie-auth state-changing route는 CSRF 없이 실패한다.
  • logout/admin revoke/password reset 후 기존 session token은 실패한다.
  • role 변경 후 기존 session permission으로 admin action이 불가능하다.
  • TOTP same-window replay negative test가 통과한다.
  • OIDC 사용 시 PKCE, state, nonce, ID Token negative tests가 통과한다.
  • WebAuthn claim 시 bad origin/RP/counter negative tests가 통과한다.
  • production readiness output에 secret value가 없다.
  • public multi-node 배포는 Redis shared limiter와 Postgres readiness evidence를 가진다.
  • encrypted MFA vault 또는 host-managed vault가 production profile에 연결되어 있다.
  • rollback plan, incident contact, evidence pack이 release ticket에 첨부되어 있다.

Not Done

  • 테스트는 통과했지만 readiness JSON이 secret을 출력합니다.
  • CSRF는 구현되어 있지만 adapter mount에 연결되어 있지 않습니다.
  • OIDC callback은 동작하지만 ID Token negative test가 없습니다.
  • WebAuthn helper는 있지만 full passkey primary auth로 마케팅합니다.
  • SQLite/process-local limiter 상태로 public multi-node production 배포를 시도합니다.
  • 버전, README, CHANGELOG가 서로 다른 릴리스 번호를 가리킵니다.

최종 릴리스 선언문

“Coreline Auth production candidate는 인증 성공 경로뿐 아니라 인증 상태의 종료, 권한 회수, 토큰 비저장, CSRF fail-closed, MFA replay 방지, OIDC/WebAuthn 검증, secret-safe 운영 증거를 통과했다.”
