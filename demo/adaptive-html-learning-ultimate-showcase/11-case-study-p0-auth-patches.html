이 페이지의 “사건”, “영향”, “타임라인”, “수치”는 가상입니다. 실제 사고 규모나 실제 운영 결과처럼 인용하면 안 됩니다.

1Situation: 가상 사건 정문보다 세션 생명주기가 더 위험했다

가상 Findings는 단일 취약점이 아니라 인증 생명주기 전반의 일관성 문제로 설정했습니다.

가상 시나리오: 보안 리뷰 팀은 session touch가 stale revoked_at=None을 다시 저장해 revoke된 세션을 되살릴 수 있다는 가상의 P0 흐름과, role 변경 후 기존 session permissions가 유지되어 demoted admin이 기존 token으로 관리자 기능을 계속 사용할 수 있다는 가상의 P0 흐름을 발견했다고 가정합니다.

표준 기반 해석: 이 대응의 핵심은 “로그인 성공”이 아니라 “인증 상태의 만료, 폐기, 재인증, 권한 변경이 일관되게 적용되는가”입니다. NIST는 세션 관리와 step-up authentication을 인증 보증 흐름의 일부로 다루고, OWASP는 인증·세션·CSRF 통제를 애플리케이션 보안 검증 대상으로 봅니다.

2Timeline: 전부 가상 타임라인

아래 T0~T5는 실제 일정이 아니라 보안 회고 학습을 위한 가상 순서입니다.

가상 T0 · Findings triage

가상 P0 session revive와 가상 role permission snapshot을 최우선으로 분리했습니다.

가상 T1 · Session lifecycle

verify/touch 경로는 revoked session을 되살리지 않도록 조건부 업데이트와 실패 처리를 적용하는 방향으로 설계했습니다.

가상 T2 · Authorization/session permission

role 변경은 단순 사용자 속성 변경이 아니라 session invalidation 이벤트로 취급했습니다.

가상 T3 · CSRF fail-closed

cookie-auth state-changing route는 CSRF protector가 없으면 실패하는 정책으로 설정했습니다.

가상 T4 · MFA/WebAuthn/OIDC

TOTP replay, WebAuthn origin/RP, OIDC nonce/ID token 검증을 각각 표준 기반 negative test로 묶었습니다.

가상 T5 · Secondary review

가상 후속 리뷰에서 scope 평가, MFA step-up rate limit, vault guardrail, email normalization 같은 hardening을 점검했습니다.

5Lessons

가상 사고 회고의 목적은 실제 침해를 주장하는 것이 아니라, 회귀가 다시 열리지 않도록 통제 언어를 정리하는 것입니다.

  • 세션 object를 통째로 저장하는 touch는 stale write 위험을 만들 수 있으므로 revoke-aware partial update가 안전합니다.
  • role/permission 변경은 기존 session snapshot을 회수하는 lifecycle event로 취급해야 합니다.
  • CSRF는 “선택 기능”이 아니라 cookie-auth state-changing route의 기본 방어선입니다.
  • TOTP replay 방어는 Python 로직뿐 아니라 저장소 CAS가 있어야 동시 요청에서 의미가 있습니다.
  • URL escaping과 HTML escaping은 다르며 magic-link에서는 return URL 정책과 template escaping이 모두 필요합니다.
  • WebAuthn origin 검증은 prefix가 아니라 URL 파서와 RP ID 경계 규칙으로 해야 합니다.
  • demo social login도 production path로 오해될 수 있으므로 PKCE/nonce/ID Token 검증이 연결되어야 합니다.
