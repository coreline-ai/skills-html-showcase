1Decision context

인증 방식은 유행이 아니라 제품 표면, threat model, 운영 역량에 따라 선택해야 합니다.

세션 쿠키, JWT, OAuth/OIDC, Magic Link, Passkey는 서로 대체재처럼 보이지만 실제로는 목적이 다릅니다. 세션은 앱 로그인 상태 유지, JWT는 stateless/API 연동, OAuth/OIDC는 외부 identity federation, Magic Link는 이메일 기반 passwordless, Passkey는 피싱 저항 인증에 강합니다.

3상황별 winner

하나를 고르기보다 기본 경로와 보조 경로를 조합합니다.

관리자 콘솔

세션 쿠키 + CSRF + AAL2. 회수 가능성과 재인증이 중요합니다.

모바일 API

짧은 JWT + refresh rotation. 토큰 저장소와 회수 전략이 핵심입니다.

B2B SSO

OIDC Authorization Code + PKCE. provider metadata와 claim 검증을 자동화합니다.

Passwordless Consumer

Passkey first + email fallback. fallback이 정문보다 약하지 않아야 합니다.

초기 SaaS MVP

세션 쿠키 + 이메일/비밀번호. 복잡도보다 revoke·CSRF·password storage 기본기가 중요합니다.

계정 복구

Magic link 단독 금지. recovery code, step-up, 제한 세션과 결합합니다.

4Tradeoffs

보안 방식의 장점은 보통 운영 책임을 함께 늘립니다.

COMMON MISTAKE

JWT를 쓰면 세션 저장소가 필요 없다고 생각하지만, logout/revoke, device inventory, compromised token 대응이 어려워집니다.

COMMON MISTAKE

Magic Link를 passwordless라고 부르지만 이메일 계정이 약하면 전체 계정이 이메일 보안 수준으로 내려갑니다.

GOOD DECISION

관리자 기능은 cookie session을 쓰되 CSRF와 AAL2를 강제하고, API는 audience가 좁은 짧은 token으로 분리합니다.

GOOD DECISION

Passkey는 로그인만 구현하지 말고 credential lifecycle, recovery, device list, suspicious session revoke까지 함께 설계합니다.

5Recommendation

Coreline Auth 기준의 기본 조합입니다.

  • 웹 UI: server-side session cookie + CSRF + SameSite=Lax.
  • 관리자 기능: AAL2 step-up + session revoke on role/password/security changes.
  • API: bearer token/JWT는 짧은 TTL, audience 제한, 회수 전략을 명시.
  • Social/SSO: OIDC Authorization Code + PKCE S256 + nonce + ID token validation.
  • Passwordless: magic link는 hash-only one-time token으로 제한하고, passkey를 장기 목표로 둔다.
  • 복구: 제한 세션, 다중 증거, 기존 세션/credential 검토 wizard를 도입한다.
