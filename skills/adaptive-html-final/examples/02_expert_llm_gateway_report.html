LENS단일 통제점비용 가시성데이터 경계점진 전환
Executive Summary

도입을 권고한다. 단, 빅뱅 전환이 아니라 비차단 프록시 → 강제 경유 순의 단계적 도입이 조건이다. 현재처럼 팀마다 직접 외부 LLM을 호출하면 API 키가 분산되고, 누가 얼마를 쓰는지 집계되지 않으며, 어떤 데이터가 외부로 나가는지 통제 지점이 없다. 단일 게이트웨이는 이 세 가지(인증·비용·데이터 경계)를 한 통제점으로 모은다. 다만 게이트웨이는 모든 LLM 트래픽이 지나는 단일 장애점이 되므로, 가용성·지연·우회 방지 설계가 도입 성패를 가른다.

왜 지금인가

월 LLM 지출이 팀별로 흩어져 집계 불가, 키 회수 절차 부재, 데이터 반출 감사 불가. 사용량이 더 커지기 전 통제점을 세우는 비용이 가장 싸다.

핵심 리스크

게이트웨이가 단일 장애점·지연 추가 지점이 된다. 가용성, p99 지연, 그리고 "몰래 직접 호출"하는 우회를 막지 못하면 도입 효과가 무너진다.

도입한다 (권고)

LLM 호출 팀이 3개 이상이거나 월 지출이 집계 불가능하고, 데이터 반출 감사 요구가 있을 때. 단계적 전환을 전제로 권고한다.

조건부 보류

실시간·초저지연 추론이 핵심 제품 경로이고 게이트웨이 지연 예산을 못 맞추면, 해당 경로만 예외로 두고 나머지부터 경유시킨다.

도입 안 함

LLM 호출 주체가 1개 팀·단일 서비스이고 지출·데이터 경계가 이미 그 팀 안에서 통제된다면, 게이트웨이는 과한 운영 부담이다.

1문제 정의와 진단 기준

"게이트웨이가 멋있는가"가 아니라 "지금 통제되지 않는 위험이 무엇이고, 게이트웨이가 그것을 줄이는가"로 본다.

사내 LLM 게이트웨이는 모든 LLM/임베딩 호출이 통과하는 단일 진입점이다. 애플리케이션은 외부 모델 제공자를 직접 부르지 않고, 사내 게이트웨이에 사내 토큰으로 요청한다. 게이트웨이가 인증·라우팅·키 관리·비용 집계·로깅·정책 적용을 대신 수행하고 실제 제공자로 중계한다.

진단의 핵심 질문은 단순하다. 현재 직접 호출 구조에서 통제되지 않는 위험이 실재하는가, 그리고 단일 통제점으로 모았을 때 새로 생기는 위험(단일 장애점·지연)이 그 이득보다 작은가. 이 두 질문에 모두 "그렇다"가 나와야 도입이 정당화된다.

게이트웨이의 가치는 기능이 아니라 통제점을 하나로 모았다는 사실 그 자체에 있다.

인증·비용·데이터 경계가 한 곳을 지나기 때문에 키 회수, 지출 집계, 반출 감사가 비로소 "한 번에" 가능해진다. 동시에 그 한 곳이 막히면 전부 막힌다는 점이 가장 큰 비용이다.

Analogy

게이트웨이는 회사 정문의 단일 출입 통제소와 같다. 직원이 각자 옆문·창문으로 드나들면(팀별 직접 호출) 누가 언제 무엇을 들고 나갔는지 알 수 없다. 출입을 정문 하나로 모으면 출입증 발급·회수, 반출물 점검, 통행 기록이 한 번에 된다. 대신 정문이 막히면 아무도 못 들어온다 — 그래서 정문은 이중화하고 빠르게 통과시켜야 한다.

2현재 구조 대 게이트웨이 구조

두 구조의 차이는 "통제 지점이 분산되어 있는가, 한 곳에 모이는가"로 압축된다.

직접 호출 구조 대 단일 게이트웨이 구조 비교

표의 위쪽 다섯 줄(키·비용·데이터·관측·교체)은 모두 게이트웨이가 명확히 이긴다. 아래 두 줄(가용성·지연)이 게이트웨이가 새로 떠안는 비용이며, 이 두 줄을 설계로 막는 것이 도입의 전제 조건이다.

단일 통제점
Single Control Point

인증·비용·데이터 정책·관측을 분산된 여러 호출 지점이 아니라 하나의 경유 지점에 모으는 설계. 통제·감사가 쉬워지는 대신, 그 지점의 가용성과 지연이 전체 시스템 품질을 좌우하게 된다.

3위험 매트릭스와 완화책

매트릭스의 목적은 위험을 나열하는 것이 아니라, 각 위험에 막는 설계와 책임자를 붙이는 것이다.

Anti-pattern
우회를 막지 않은 "권고" 게이트웨이

게이트웨이를 세우되 제공자 키를 앱이 여전히 들고 있고 외부 직결도 막지 않으면, 바쁜 팀은 지연·장애를 피해 직접 호출로 돌아간다. 그 순간 비용·데이터 통제는 다시 0이 된다. 강제 경유는 정책 문구가 아니라 키 독점 + 송신 차단이라는 기술적 통제로 보장해야 한다.

4도입 우선순위와 단계별 로드맵

초기에는 강제하지 않는다. 먼저 투명한 프록시로 신뢰를 얻고, 키를 회수한 뒤에야 경유를 강제한다.

P0 · 비차단 프록시

옵트인으로 게이트웨이를 세우고, 통과시키되 막지 않는다. 비용·지연 기준선을 모으고 이중화·지연 예산을 검증한다.

P1 · 키 회수와 강제 경유

제공자 키를 게이트웨이로 회수하고 외부 직결을 차단한다. 팀별 쿼터·반출 정책을 켜고 우회를 기술적으로 막는다.

P2 · 운영 표준화

멀티 프로바이더 fallback, 비용 대시보드, 감사 리포트, 모델 교체 절차를 운영 캘린더에 정착시킨다.

Roadmap rule
강제 경유는 신뢰를 산 다음에

P0에서 지연·가용성이 직접 호출과 견줄 만하다는 데이터를 확보하기 전에는 절대 강제하지 않는다. 강제는 게이트웨이가 "더 느리고 더 잘 죽는 길"이 아님을 증명한 뒤에만 정당하다. 미달 시 즉시 비차단 모드로 강등한다.

5검증 기준 — 무엇을 보면 성공/실패인가

도입의 성패는 "트래픽이 게이트웨이를 지나는가"가 아니라 "지나면서도 빠르고, 죽지 않고, 데이터가 새지 않는가"로 본다.

Go 기준
게이트웨이가 통제 이득을 실제로 낸다

가용성이 직접 호출 대비 동등 이상(예: 99.9%+), p99 추가 지연이 예산(예: +50ms) 이내, LLM 트래픽 경유율 100%·우회 0, 비용이 팀·모델 단위로 100% 귀속, 외부 전송 전 비밀값 마스킹이 동작하고 평문 본문이 로그에 남지 않는다.

No-Go 기준
통제점이 병목이나 사각이 된다

게이트웨이 장애로 전체 LLM 기능이 동반 중단되거나, 추가 지연이 사용자 체감 수준으로 커지거나, 키 회수 후에도 외부 직결 우회가 계속되거나, 프롬프트 평문이 의도치 않게 로그·감사 저장소에 평문으로 쌓인다.

비용 가시성

팀·모델 단위 귀속 0% → 100%. 청구서 한 장이 요청 단위 태깅으로 분해된다.

키 노출 면적

제공자 키 보유 지점 팀 수만큼 → 1곳. 회수·회전이 한 번의 작업이 된다.

추가 지연

목표 p99 +50ms 이내. 스트리밍 패스스루로 체감 지연을 억제한다.

모델 교체 비용

앱 코드 변경 전 앱 수정 → 0. 라우팅 정책 한 줄로 별칭을 다시 매핑한다.

6자주 나오는 반론과 답

도입 검토에서 반복되는 우려를 미리 정리한다.

한 곳이 막히면 전부 막히는 것 아닌가?
맞다. 그래서 이중화와 제공자 직결 비상 fallback을 P0의 진입 게이트로 둔다. 가용성이 직접 호출과 동등하다는 데이터 없이는 강제하지 않는다.
지연이 늘어 사용자 경험이 나빠지지 않나?
토큰 스트리밍을 버퍼링 없이 흘려보내면 추가 지연은 게이트웨이 처리 시간(수십 ms)에 그친다. p99 지연 예산을 정하고 상시 모니터링해 초과 시 강등한다.
팀들이 그냥 직접 호출로 우회하지 않을까?
정책 문구로는 못 막는다. 제공자 키를 게이트웨이만 보유하고 외부 LLM 도메인 직결을 송신 방화벽으로 차단해 기술적으로 봉쇄한다.
구축·운영 비용이 절감액보다 크지 않나?
LLM 호출 팀이 1개뿐이면 그럴 수 있어 "도입 안 함"을 권한다. 3개 이상·집계 불가·반출 감사 요구가 있으면 통제 이득이 운영 비용을 넘어선다.
NEXT ACTION

비차단 프록시 4주를 먼저 잠근다

강제하지 말고 옵트인 프록시부터 세워 가용성·지연·비용 기준선을 모은다. 키 회수와 강제 경유는 그 데이터가 직접 호출과 동등함을 증명한 뒤에만 진행한다.

  1. 이중화·헬스체크·비상 fallback 경로를 먼저 구성한다.
  2. 옵트인 팀 1~2곳을 게이트웨이로 통과시켜 p99 추가 지연과 가용성을 측정한다.
  3. 요청 단위 비용 태깅과 메타데이터 로깅(평문 본문 무보존)을 켠다.
  4. 제공자 키 회수와 외부 직결 차단 계획을 Security와 합의한다.
  5. Go/No-Go 임계값을 조직 값으로 확정하고 롤백 트리거를 문서화한다.
