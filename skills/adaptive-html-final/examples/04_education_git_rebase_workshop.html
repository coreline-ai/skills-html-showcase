Learning Goal

rebase는 커밋을 옮기는 게 아니라 다시 만든다. 수료자는 rebase가 어떤 커밋을 어떤 base 위에 다시 적용하는지 그림으로 설명하고, 충돌을 절차대로 해결하며, 사고가 나도 reflog로 복구하고 공유 브랜치는 --force-with-lease로만 갱신할 수 있어야 한다.

3일 후 할 수 있는 일
  • 설명한다 — merge와 rebase의 결과 히스토리가 왜 다른지, rebase가 새 커밋 해시를 만든다는 점을 그림으로 설명한다.
  • 해결한다 — interactive rebase 중 충돌을 만나도 멈추지 않고 add → --continue 절차로 끝까지 진행한다.
  • 복구한다 — 잘못 rebase해도 git reflog로 이전 상태를 찾아 reset으로 되돌린다.
  • 판단한다 — “지금 이 브랜치를 rebase해도 되는가”를 공유 여부 기준으로 스스로 판단한다.

3일 학습 로드맵: 무엇이 언제 가능해지는가

각 날이 끝날 때 학습자가 실제로 할 수 있게 되는 일을 기준으로 진도를 잡는다.

1Day 1 — rebase가 실제로 하는 일

목표는 rebase를 무서워하지 않는 것이 아니라, 그것이 무엇을 다시 만드는지 정확히 그리는 것이다.

이 워크숍의 최종 산출물은 “rebase를 했다”가 아니라 “이 브랜치를 왜 rebase했고, 어떤 커밋이 어떤 base 위에 다시 적용됐으며, 사고가 났다면 어떻게 복구할지”를 설명하는 한 장짜리 판단 메모다.

git rebase main은 현재 브랜치의 커밋을 main의 최신 커밋 위로 옮기는 것처럼 보이지만, 실제로는 각 커밋의 변경 내용을 새 base 위에 다시 적용(replay)해 새로운 커밋을 만든다. 따라서 커밋 해시가 바뀐다. 이것이 rebase의 위력이자 위험의 출발점이다.

핵심 용어
base / upstream / replay

base는 내 커밋들이 분기해 나온 기준점이다. rebase는 그 base를 새 upstream(예: 최신 main)으로 바꾸고, 그 사이 내가 쌓은 커밋들을 하나씩 replay한다. replay된 커밋은 내용은 같아도 부모가 달라지므로 새 해시를 갖는다.

merge와 rebase의 결과 비교
관점mergerebase
히스토리 모양분기와 병합 커밋이 그대로 남는다한 줄(선형)로 정리된다
커밋 해시기존 커밋 유지replay된 커밋은 새 해시
병합 커밋생성됨없음
추적성“언제 합쳤나”가 보존됨“무엇을 했나”가 깔끔히 보임
공유 브랜치 적합성안전위험(히스토리 재작성)
판단 기준
언제 rebase가 합리적인가

아직 나만 가진 로컬 브랜치를 main 최신 상태 위로 깔끔히 올릴 때 rebase가 잘 맞는다. 반대로 이미 push해 동료가 받아간 브랜치는 rebase로 해시를 바꾸면 동료 히스토리와 어긋난다. 한 줄 규칙: 공유했으면 rebase 금지, 안 했으면 자유.

2Day 1 예제 — merge와 rebase를 직접 비교

같은 분기 상황을 두 방법으로 정리하고 그래프 차이를 눈으로 확인한다.

아래는 feature 브랜치가 두 커밋을 쌓은 사이 main이 한 커밋 더 진행된 상황이다. 먼저 rebase를 적용한다.

# 현재 상태: feature가 main에서 갈라져 나옴
#   main:    A---B---C
#   feature:      \---D---E   (D,E는 내 작업)

git switch feature
git rebase main

# 결과: D,E가 C 위로 다시 적용됨 (D',E'는 새 해시)
#   main:    A---B---C
#   feature:          \---D'---E'

같은 상황을 merge로 정리하면 분기 흔적과 병합 커밋 M이 남는다. 어느 쪽이 “옳다”가 아니라, 무엇을 보존하고 무엇을 정리할지의 선택임을 확인한다.

git switch feature
git merge main

#   main:    A---B---C
#   feature:      \---D---E---M   (M = 병합 커밋, D·E 해시 유지)
Day 1 실습

그래프로 차이 확인하기

샘플 저장소에서 같은 분기를 한 번은 rebase로, 한 번은 merge로 정리하고 결과를 캡처한다.

  1. 실습용 브랜치를 두 개 만든다: feat-rebase, feat-merge.
  2. 각 브랜치에 동일한 커밋 2개를 쌓는다.
  3. 한쪽은 git rebase main, 다른 쪽은 git merge main으로 정리한다.
  4. git log --oneline --graph --all로 두 그래프를 캡처한다.
  5. 커밋 해시가 바뀐 쪽이 어디인지 표시한다.

3Day 2 — interactive rebase로 히스토리 정리

목표는 커밋을 “예쁘게” 만드는 게 아니라 리뷰어가 읽기 좋은 단위로 묶는 것이다.

git rebase -i는 replay할 커밋 목록을 편집기로 열어 각 커밋에 동작을 지정하게 한다. pick은 그대로 두기, reword는 메시지만 수정, squash/fixup은 앞 커밋에 합치기, drop은 버리기, edit은 그 커밋에서 멈춰 내용을 수정한다. 목록은 위에서 아래로(오래된 것부터) 적용된다는 점이 직관과 반대라 자주 헷갈린다.

# 최근 3개 커밋을 정리
git rebase -i HEAD~3

# 편집기에 열리는 todo 목록 (위 = 오래된 커밋)
pick   a1b2c3d  feat: 로그인 폼 추가
squash e4f5g6h  fix: 오타
reword i7j8k9l  feat: 검증 로직

# squash 결과 a1b2c3d + e4f5g6h가 한 커밋으로 합쳐지고
# reword로 i7j8k9l의 메시지를 다시 작성하게 된다
interactive rebase 주요 명령
명령하는 일대표 용도
pick커밋을 그대로 적용유지할 커밋
reword내용은 두고 메시지만 수정오타·불명확한 메시지
squash앞 커밋에 합치고 메시지 병합관련 작업 묶기
fixup앞 커밋에 합치고 메시지 버림“오타 수정” 같은 잔커밋
drop커밋 제거실수로 들어간 변경
edit해당 커밋에서 멈춤커밋 쪼개기·내용 수정

4Day 2 — 충돌을 절차대로 해결하기

충돌은 실패가 아니라 rebase가 정상 작동 중이라는 신호다. 멈추지 말고 절차를 따른다.

커밋을 replay하다 같은 줄을 다르게 고친 경우 rebase가 멈추고 충돌을 알린다. 핵심은 한 커밋씩 멈춘다는 점이다. 충돌난 파일을 고치고 git add로 “해결했음”을 표시한 뒤 git rebase --continue로 다음 커밋을 이어간다. git commit을 새로 하지 않는다 — 지금은 기존 커밋을 다시 적용하는 중이기 때문이다.

git rebase main
# CONFLICT (content): Merge conflict in src/auth.js
# 1) 충돌 파일을 열어 <<<<<<< ======= >>>>>>> 구간을 정리
# 2) 해결한 파일을 스테이징
git add src/auth.js
# 3) 다음 커밋으로 진행 (commit 아님!)
git rebase --continue

# 손쓸 수 없으면 언제든 시작 전으로 되돌리기
git rebase --abort
자주 하는 실수
충돌 해결 후 git commit을 또 한다

rebase 도중에는 “해결 → git add → git rebase --continue”가 한 세트다. 여기서 git commit을 하면 의도치 않은 빈 커밋·중복 커밋이 끼어 히스토리가 더 꼬인다. 막히면 깨끗하게 git rebase --abort로 원위치하고 다시 시작하는 편이 빠르다.

읽기 요령
충돌 메시지가 알려주는 것

Merge conflict in <파일> 줄과 “현재 적용 중인 커밋”을 함께 본다. git status는 항상 다음 한 걸음(add할 파일, --continue 여부)을 알려준다. 충돌을 한꺼번에 풀려 하지 말고 멈춘 그 커밋만 해결한다.

Day 2 실습

충돌 1건을 끝까지 해결

의도적으로 충돌이 나는 브랜치에서 interactive rebase를 돌리고, abort 없이 끝까지 진행한다.

  1. 같은 파일의 같은 줄을 main과 브랜치에서 다르게 수정해 둔다.
  2. git rebase -i main으로 squash·reword를 섞어 실행한다.
  3. 충돌이 나면 파일을 정리하고 git add한다.
  4. git rebase --continue로 끝까지 진행한다.
  5. 중간에 한 번은 일부러 --abort로 되돌린 뒤 다시 시도해 본다.

5Day 3 — reflog: 사고가 나도 복구한다

rebase로 무엇을 “날렸다”고 느껴도, 그 커밋은 보통 아직 reflog에 남아 있다.

git reflog는 HEAD가 거쳐 간 모든 위치를 시간순으로 기록한다. rebase·reset·checkout으로 브랜치 끝이 옮겨가도 이전 위치가 HEAD@{n} 형태로 남는다. 따라서 잘못 rebase했더라도 rebase 직전 위치를 찾아 reset하면 그대로 되돌릴 수 있다. 이 안전망이 있다는 사실이 rebase를 연습할 용기를 준다.

git reflog
# e4f5g6h HEAD@{0}: rebase (finish): returning to refs/heads/feature
# a1b2c3d HEAD@{1}: rebase (start): checkout main
# 9z8y7x6 HEAD@{2}: commit: feat: 검증 로직   <- rebase 직전 상태

# rebase 직전으로 되돌리기
git reset --hard HEAD@{2}
핵심 용어
HEAD@{n} / reset --hard

HEAD@{n}은 “n번 전의 HEAD 위치”다. reset --hard는 브랜치 끝과 작업 트리를 그 위치로 강제 이동시킨다. 강력한 만큼 커밋되지 않은 변경은 사라지므로, 실행 전 git status로 잃을 것이 없는지 확인한다.

복구 절차
“rebase 망했다” 3단계

① 당황하지 말고 git reflog로 rebase 직전 줄(보통 rebase (start) 바로 위)을 찾는다. ② 그 해시나 HEAD@{n}을 git reset --hard 대상으로 쓴다. ③ 되돌아왔는지 git log --oneline으로 확인한다. reflog 기록은 기본 90일간 유지되므로 대부분의 사고는 복구 가능하다.

6Day 3 — 원격 갱신은 force-with-lease로

rebase 후 push가 거부되는 건 정상이다. 그러나 그냥 --force는 동료 커밋을 덮을 수 있다.

rebase로 해시가 바뀌면 원격과 히스토리가 어긋나 일반 push가 거부된다. 여기서 --force를 쓰면 원격을 무조건 덮어쓰므로, 내가 마지막으로 본 이후 동료가 올린 커밋까지 날려버릴 수 있다. --force-with-lease는 “내가 기억하는 원격 상태와 지금 원격이 같을 때만 덮어쓴다”는 조건을 걸어, 동료가 그사이 push했다면 거부한다.

# 위험: 원격을 조건 없이 덮어씀 (동료 커밋 유실 가능)
git push --force

# 안전: 원격이 내가 본 그대로일 때만 덮어씀
git push --force-with-lease

# 더 안전: 비교할 ref를 명시
git push --force-with-lease=feature:9z8y7x6
--force와 --force-with-lease 비교
항목--force--force-with-lease
덮어쓰기 조건무조건원격이 내가 본 상태와 같을 때만
동료 새 커밋조용히 유실될 수 있음감지하고 push 거부
공유 브랜치 권장금지에 가깝다그나마 안전한 선택
실패 시 행동해당 없음(항상 성공)git fetch 후 다시 검토
안전 주의
공유 브랜치를 rebase한 뒤 --force는 사고의 지름길

여러 명이 쓰는 브랜치를 rebase하고 --force로 밀면, 동료는 다음 pull에서 충돌·중복 커밋을 떠안는다. 공유 브랜치는 가급적 rebase하지 말고, 불가피하면 팀에 알린 뒤 --force-with-lease로만 갱신한다. main 같은 보호 브랜치는 애초에 강제 push를 막아 둔다.

7퀴즈와 평가 루브릭

퀴즈는 명령 암기가 아니라 “왜 그렇게 하는가”의 판단 근거를 확인한다.

  1. rebase 후 커밋 해시가 바뀌는 이유는 무엇인가?
  2. 이미 push해 동료가 받아간 브랜치를 rebase하면 왜 위험한가?
  3. 충돌 해결 후 git commit 대신 무엇을 해야 하는가?
  4. 막혔을 때 rebase를 깨끗이 되돌리는 명령은?
  5. 잘못 rebase해서 커밋이 사라진 것 같을 때 가장 먼저 볼 곳은?
  6. --force 대신 --force-with-lease를 쓰는 이유는?

정답 요약: rebase는 커밋을 새 base 위에 다시 적용하므로 부모가 바뀌어 해시가 새로 생긴다. 공유 브랜치는 해시가 바뀌면 동료 히스토리와 어긋나 충돌·중복을 만든다. 충돌 해결 후에는 git add 뒤 git rebase --continue를 한다. 막히면 git rebase --abort. 사라진 듯한 커밋은 git reflog에서 찾아 reset --hard HEAD@{n}으로 복구한다. --force-with-lease는 원격이 내가 본 상태일 때만 덮어써 동료 커밋 유실을 막는다.

평가 루브릭
축기준우수 답안의 모습
동작 모델rebase가 커밋을 replay해 새 해시를 만든다고 설명한다.merge·rebase 그래프 차이를 직접 그린다.
충돌 절차add → continue / abort 흐름을 따른다.중간에 commit하지 않고 끝까지 해결한다.
복구 능력reflog로 직전 상태를 찾아 되돌린다.reset 전 잃을 변경이 없는지 확인한다.
안전 판단공유 여부로 rebase 가부를 결정한다.원격 갱신에 force-with-lease만 쓴다.
재현성명령·그래프·복구 기록을 남긴다.동료가 같은 절차로 재현할 수 있다.
NEXT ACTION

바로 실행할 일

  1. 실습용 저장소에서 로컬 브랜치 하나를 골라 git rebase main으로 정리한다.
  2. git rebase -i HEAD~3으로 squash·reword를 한 번씩 적용한다.
  3. 충돌을 일부러 만들고 add → --continue 절차로 끝까지 해결한다.
  4. git reflog로 rebase 직전 상태를 찾아 한 번 복구해 본다.
  5. 원격 갱신은 --force-with-lease로만 하고, 결과를 안전 체크리스트 한 장으로 남긴다.
